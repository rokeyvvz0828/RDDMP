# RDDMP 当前确认需求集正式规格

Status: ready-for-agent
Label: ready-for-agent
Scope status: 产品需求基线已就绪；仅允许进入现状差距盘点和系统建模，尚未取得仓库编码准入
Baseline date: 2026-08-22

## Problem Statement

RDDMP 当前需求来自多份原始材料和持续访谈。原始材料混合了已确认需求、未确认设想、平台已有能力、重复模块、已废弃模块以及不合理的多租户设计，且在“架构定义、申请需求、实际资源、计划任务、工单过程、运行事实”之间存在概念混用。若直接按原文档实施，会导致重复台账、状态可随意覆盖、模板更新污染执行历史、计划与环境绑定过紧、资源与网络事实缺少可追溯来源，以及把外部运维动作误当成本平台自动化能力。

本规格把已确认结论收敛为当前产品需求基线。它必须使后续团队能够明确回答：管理什么业务对象、谁可以执行什么业务动作、哪些状态由计算产生、哪些记录必须保留、哪些平台能力必须复用、哪些模块明确不做，以及用什么测试接缝证明实现满足需求。

本规格不直接授权编码。当前需求集跨越多个业务域，必须先完成现状差距盘点、模块边界、数据所有权、权限审计矩阵和关键用户旅程设计，再按可独立验收的实施批次建立仓库内的正式需求记录、控制前缀和可写范围。

## Solution

RDDMP 将围绕五个当前业务域形成相互关联但数据所有权清晰的能力：架构资产、环境搭建与资源、网络访问、加密机入池、架构规范与架构决策。

架构资产提供逻辑子系统、物理子系统和部署单元等稳定定义；环境搭建用“具体环境 → 搭建计划 → 环节 → 任务 → 检查项”组织工作，并以模板版本和执行快照保护历史；资源申请的办理结果按每台机器和 IP 形成环境部署实例及实际资源分配；网络访问申请在受管实例或外部地址之间形成可追溯的有效访问关系；加密机入池与 CLB、DNS、证书等能力只管理申请内容、办理过程和办理结果，不执行外部平台动作；架构规范统一发布文档，架构决策围绕一事一议形成不可原地篡改的正式结论。

平台已有的认证、RBAC、数据范围、实体授权、工作流、字典、附件预览、通知和审计能力应被复用。业务域只维护自身业务数据、规则和办理结果，不复制平台通用能力，也不得跨模块直接改写其他模块的数据。

## User Stories

1. 作为技术人员，我可以查询逻辑子系统清单及其基本信息，以便理解物理子系统的归类结构。

2. 作为应用架构师，我可以直接新增、修改、停用和排序逻辑子系统，而无需发起物理子系统变更申请。

3. 作为技术人员，我可以按编号、名称、所属逻辑子系统、事业群和状态等已定义维度查询物理子系统，以便定位架构主记录。

4. 作为申请人，我可以为物理子系统的新增、修改、作废或下线创建并保存变更申请草稿。

5. 作为系统，我会阻止同一物理子系统同时存在超过一张已提交但未结束的变更申请，以避免并发办理结果互相覆盖。

6. 作为系统，我会通过确定性规则生成物理子系统编号，并在提交和发布时检查编号、中文名、英文名及受控唯一字段的冲突。

7. 作为申请人，我可以根据权威主数据、确定性规则、AI 建议和人工补充的顺序获得智能补全建议，以减少重复录入。

8. 作为申请人，我可以选择是否采用新的智能补全建议；我已经人工修改的当前值不会被后台重新计算自动覆盖。

9. 作为应用架构师，我可以在办理物理子系统变更申请时调整最终发布值，并在批准前看到申请提交值与最终发布值的差异。

10. 作为审计人员，我可以追溯物理子系统变更申请的提交内容、最终发布内容、办理人、办理时间、办理意见和完整操作历史。

11. 作为系统，我只会在物理子系统变更申请获批后更新物理子系统主记录，智能建议和未批准申请不能直接改写主记录。

12. 作为应用架构师，我可以通过变更申请调整物理子系统所属逻辑子系统，并保留调整前后的归属历史。

13. 作为应用架构师，我只能作废没有业务引用的错误物理子系统；作废不会物理删除记录，其编号也不会复用。

14. 作为应用架构师，我只能在不存在活动环境部署实例、部署记录或网络访问关系时完成物理子系统下线；下线后其下属部署单元保留原状态和历史，但不能再用于新增资源申请、搭建任务或部署。

15. 作为技术架构师，我可以在一个物理子系统下创建多个部署单元，以表达可独立部署、升级、启停和运行的环境无关架构定义。

16. 作为技术架构师，我可以把满足独立生命周期边界的数据库或 MQ 服务定义为部署单元，而不是另建不一致的对象体系。

17. 作为技术架构师，我可以直接维护部署单元并发布新版本；已发布版本不可原地改写，变更形成新版本并保留审计记录。

18. 作为系统，我会为部署单元保留稳定身份和永久唯一编号；发布后编号不可修改、不可复用，显示名称变化不改变稳定身份。

19. 作为系统，我不会允许已发布部署单元直接改挂到其他物理子系统；迁移用途必须停用原部署单元并在目标物理子系统下新建部署单元。

20. 作为技术架构师，我可以停用不再使用的部署单元；停用阻止其用于新的资源申请、搭建任务或部署，但不自动下线既有实例或删除历史。

21. 作为技术架构师，我只能作废从未被引用的错误部署单元，且作废后编号仍不可复用。

22. 作为技术架构师，我可以长期使用部署单元初始化导入，通过预览和关系校验后确认写入，而不是让文件直接无校验入库。

23. 作为技术架构师，我可以查看每次部署单元导入批次的来源、预览结果、成功记录、失败记录和错误报告，以便修正后重新导入。

24. 作为环境管理人员，我可以新增、修改、停用和排序环境类型；环境类型不与某个默认搭建模板强绑定，也不会自动生成计划。

25. 作为环境管理人员，我可以创建和维护具体环境，使具体环境即使暂时没有搭建计划也可作为独立业务对象存在。

26. 作为系统，我不会允许删除已经产生业务引用的具体环境；停用只阻止新建计划和新增实例，不会自动取消计划、下线实例或关闭网络关系。

27. 作为技术人员，我可以在具体环境视图中查看从环境部署实例和实际资源分配聚合出的规划需求、实际计算资源、存储资源、数据库资源和网络信息，而无需维护重复环境资源台账。

28. 作为资源办理人员，我可以针对一个物理子系统和一个具体环境创建资源申请工单，并在该工单中连续添加该物理子系统下多个部署单元的资源需求规格。

29. 作为申请人，我在填写资源需求时通过“物理子系统 → 部署单元”级联选择目标，并为整张工单选择一个具体环境，避免跨物理子系统或跨环境混填。

30. 作为申请人，我可以在一条资源需求规格中填写 CPU、内存、存储、计划节点数及其他已批准资源项，以表达申请目标而非实际资源事实。

31. 作为申请人，当同一部署单元需要多套不同规格时，我可以复制已有需求明细并修改规格，而无需引入新的分组概念。

32. 作为申请人，我可以从搭建任务发起资源工单并建立关联，也可以为后续扩容、缩容或规格调整独立创建工单。

33. 作为资源办理人员，我会按实际下发的每台机器分别登记机器标识、IP、CPU、内存、存储和其他实际资源，而不是只登记申请汇总值。

34. 作为系统，我会把资源工单的实际下发结果直接形成对应部署单元在目标环境中的环境部署实例及实际资源分配。

35. 作为系统，我会展示资源申请值与实际分配值的差异，并要求记录差异原因，不能为了匹配申请而改写实际事实。

36. 作为资源办理人员，我可以通过资源工单办理扩容、缩容、CPU 调整、内存调整和存储调整；这些变化不得通过直接编辑实例来绕过来源工单。

37. 作为审计人员，我可以从环境部署实例和实际资源分配追溯其来源工单及每次变更前后值。

38. 作为技术人员，我可以分别查看申请态资源总量和实际态资源总量；前者由单节点需求、计划节点数和单节点附加资源计算，后者由未下线实例的实际分配汇总。

39. 作为系统，我以未下线环境部署实例数量计算当前实际节点数，已下线实例只进入历史视图，不允许人工维护一个可能失真的实际节点数。

40. 作为系统，我把环境部署实例定义为部署单元在具体环境中落到单台机器及其 IP 的最小单元，并确保一个实例只归属一个部署单元。

41. 作为系统，我会保证同一具体环境中的同一机器和 IP 只形成一个在用实例，不允许多个部署单元共享或直接改挂该实例。

42. 作为普通用户，我不能手工创建环境部署实例；日常新增只能来自资源工单办理结果，历史存量只能通过受控导入初始化。

43. 作为资源办理人员，当机器用途或 IP 变化时，我会下线原实例并创建新实例，从而保留前后两段归属历史，而不是直接覆盖原记录。

44. 作为技术人员，我可以看到环境部署实例当前采用的部署单元设计版本以及与部署单元最新版本的差异；发布新设计版本不会自动升级实例。

45. 作为环境管理人员，我只在环境部署实例上维护部署平台和服务器类型，不在部署单元上维护会被误当成事实的默认值。

46. 作为环境管理人员，我可以在同一部署单元的实例之间建立主备、双活等灾备关系，并允许关系跨具体环境；不同部署单元之间的依赖不作为灾备关系。

47. 作为资源办理人员，我可以把环境部署实例标记为在用或已下线；运行健康和搭建进度不会混入实例业务状态。

48. 作为系统，我允许实例在机器或 IP 回收后下线并保留记录；下线不自动删除部署记录或关闭有效网络关系，而是对未处理关联显示风险。

49. 作为系统，我不会允许已下线实例被新的部署或网络访问申请引用，但历史记录仍可查询和追溯。

50. 作为模板管理员，我可以创建包含多个环节的搭建计划模板，并通过发布新版本调整模板结构；已发布版本不可原地改写。

51. 作为模板管理员，我可以为特定环节创建任务模板，在模板中维护标准检查项和任务生成维度，并通过新版本发布变更。

52. 作为模板管理员，我可以把任务生成维度设置为“不展开”“按物理子系统”或“按部署单元”，不引入未确认的动态维度体系。

53. 作为计划责任人，我只能从已发布计划模板创建搭建计划，不能直接新建没有结构基线的空白计划。

54. 作为计划责任人，我可以为同一具体环境分别创建初次搭建、后续扩展和局部重建计划；多个未结束计划可以覆盖相同部署单元，系统不强制互斥。

55. 作为计划责任人，我在创建计划时选择目标物理子系统或部署单元，系统只为选中目标按任务模板生成任务，未选目标不属于计划范围。

56. 作为计划责任人，我在系统部署环节选择 A、B、C 等目标后，可以使用同一系统部署任务模板分别生成 A、B、C 的独立任务，并为每个任务复制一套独立检查项。

57. 作为系统，我会保存计划模板版本、任务模板版本、选定目标及关联信息的快照；全局模板或架构资产后续变化不会自动改写既有计划和任务。

58. 作为技术人员，我可以看到计划快照与当前架构资产之间的差异提示，但历史执行内容保持可解释。

59. 作为计划责任人，我可以为计划指定一名责任人，为每个环节指定一名环节责任人，为每个任务指定一名任务责任人和多名参与人。

60. 作为计划责任人，我可以从模板或上级继承默认责任人，也可以在生成后人工调整具体人员并保留变更记录。

61. 作为计划责任人，我可以在计划开始后新增环节、任务或检查项，以适应实际搭建过程，并让新增内容进入当前有效范围。

62. 作为计划责任人，我只能删除尚未执行的错误内容，且必须记录操作人、时间和原因；已经开始或完成的内容不得物理删除。

63. 作为计划责任人，我可以填写原因后增加计划目标；系统使用该计划自身的模板快照生成新增任务，而不是使用后来发布的全局模板版本。

64. 作为计划责任人，我可以填写原因后移出计划目标；关联的未完成任务自动取消，已完成记录继续保留，历史不会被删除。

65. 作为任务责任人或参与人，我可以查看计划、环节、任务和检查项的自顶向下关联，以及任务对应的具体目标。

66. 作为任务责任人，我可以开始满足前置条件的任务，并完成其检查项；任务不能通过通用状态下拉框任意改写状态。

67. 作为任务执行者，我可以为检查项记录完成、重新打开、备注和可选附件，系统保留操作人、操作时间及每次状态变化历史。

68. 作为系统，我会把任务状态计算为未开始、等待前置、进行中、阻塞、已完成或已取消；逾期作为独立标识，不覆盖任务执行状态。

69. 作为计划责任人，我可以在任务之间建立显式前置依赖；前置未完成时后续任务不能开始，并显示等待前置而不自动产生阻塞记录。

70. 作为系统，我不会把已取消的前置任务视为已完成；后续任务继续等待并提示依赖已取消，直到计划责任人移除、改绑依赖或取消后续任务。

71. 作为任务责任人，我可以登记一条或多条阻塞记录，并在障碍消除后解除；存在未解除记录时任务计算为阻塞，解除后恢复由实际进度决定的状态。

72. 作为计划参与者，我可以在环节和计划层看到“存在阻塞”的聚合提示，并下钻查看具体阻塞任务和记录。

73. 作为任务责任人，我可以从任务发起或事后关联资源、网络、CLB、DNS、证书和加密机入池等工单。

74. 作为系统，我会在任务存在未结束关联工单时阻止任务完成；工单结束只解除约束，不会自动完成任务，检查项仍必须满足完成条件。

75. 作为系统，我会按当前有效范围内“已完成检查项数 ÷ 未取消检查项总数”计算任务、环节和计划进度，不允许人工填写或加权调整进度。

76. 作为系统，我只在任务的全部未取消检查项完成后将任务标记为完成，只在环节的全部未取消任务完成后将环节标记为完成。

77. 作为系统，我只在计划的全部未取消环节完成后将计划标记为完成；全部环节都被取消时，计划不会自动成为已完成。

78. 作为计划责任人，我可以取消未完成检查项以实施豁免，并必须记录原因；任务责任人和参与人只能提出附原因的取消建议，不能直接取消。

79. 作为计划责任人，我可以取消整个未完成任务或不再适用的环节，并保留其检查项、已完成内容和全部历史；已完成任务必须先重新打开才能取消。

80. 作为计划责任人，我可以填写原因后恢复已取消检查项、任务或环节；恢复后它们重新进入有效范围并触发任务、环节和计划状态与进度重算。

81. 作为系统，当任务全部检查项都被取消时，我会显示进度 100% 和“全部豁免”，并将任务视为满足完成条件，但不会把它展示成普通完成。

82. 作为系统，当环节全部任务都被取消时，我可以显示“已完成（全部豁免）”；该规则不会继续把全部环节都取消的计划计算为完成。

83. 作为计划参与者，我可以在任务、环节和计划层看到“存在豁免”聚合标识，并下钻查看取消对象、操作人、时间和原因。

84. 作为计划责任人，我可以填写原因取消整个未完成计划；取消后停止新增和执行任务，计划进入与已完成不同的终态，所有历史继续保留。

85. 作为计划责任人，我可以填写原因恢复已取消计划；恢复后继续使用取消前的快照、任务状态和依赖，不重新套用模板或重建任务。

86. 作为任务责任人，我可以重新打开已完成任务或检查项；当前有效子项重新打开后，上级任务、环节和计划立即退出已完成并重新计算。

87. 作为计划责任人、环节责任人或任务责任人，我可以维护本层级计划开始和计划结束时间，并在计划开始后填写原因进行调整。

88. 作为系统，我会由执行事件计算实际开始和实际完成时间，不允许直接编辑汇总实际时间；有权限的管理人员只能通过附原因的事件更正来修正结果。

89. 作为系统，我以首个有效子项的实际开始时间聚合计划和环节的实际开始时间，以最近一次完成事件作为重新打开后再次完成的当前实际完成时间，并保留历次事件。

90. 作为系统，我允许子项计划时间超出上级计划时间，但会提示风险；计划时间调整后按新时间重新计算当前逾期并保留曾经逾期历史。

91. 作为计划参与者，我可以同时看到任务原有执行状态和独立逾期标识；当前时间超过计划结束且对象未完成时产生逾期，取消后不再计算当前逾期，恢复后重新判断。

92. 作为计划管理人员，我可以按具体环境、计划、环节、责任人、目标、状态、阻塞、逾期和豁免等维度查询搭建工作，并从汇总视图下钻到检查项和操作历史。

93. 作为计划管理人员，我可以查看适合计划层级的进度看板、时间视图和搭建结果报告；所有汇总数字必须能追溯到当前有效检查项，不能形成第二套状态事实。

94. 作为相关责任人，我可以收到平台通知能力发送的任务分派、工单状态变化、阻塞、临期、逾期和关键状态变更通知；通知失败不改变业务事实。

95. 作为网络架构师，我可以维护具有父子层级的网络分区和隔离规则，使子分区能够增加限制但不能直接放宽父分区规则。

96. 作为网络管理人员，我可以把环境部署实例的单个 IP 归入一个最具体的叶子网络分区，并让它继承上级策略。

97. 作为网络管理人员，我可以维护不属于受管环境部署实例、但需要参与申请的外部 IP、网段或域名，并在申请中明确引用，而不是混入自由文本资源。

98. 作为技术人员，我可以输入源网络地址、目标网络地址、目标端口、协议和申请时间范围，获得“需要申请”或“不需要申请”的二值结论。

99. 作为系统，我只有在全部适用隔离规则都明确无需申请，或已有有效访问关系完整覆盖地址、端口、协议和时间范围时，才返回“不需要申请”；规则未知、覆盖不完整或无法确定时严格返回“需要申请”。

100. 作为申请人，我在网络访问申请的源端和目标端分别且各自只能选择一组“物理子系统 → 具体环境 → 部署单元”，再从级联结果中选择多个环境部署实例并带入输入框。

101. 作为申请人，我首次打开实例选择时默认全选当前级联结果，也可以取消选择；后来新增的实例不会自动加入已经提交的申请或已经形成的关系。

102. 作为申请人，当同一端需要跨部署单元时，我必须拆分申请，不能在一张申请中混合多个部署单元来源。

103. 作为申请人，我可以在受管实例集合与受管实例集合之间、受管实例集合与外部网络地址之间申请访问，并填写明确端口或端口范围、协议、用途和有效期类型。

104. 作为系统，我把一张成功办理的网络访问申请形成一条网络访问关系，使选定的全部源实例可按申请协议和端口访问全部目标实例；需要限制特定实例对时必须拆分申请。

105. 作为申请人，我可以为同一协议填写多个明确端口或端口范围，不必为每个端口重复创建完全相同的申请。

106. 作为申请人，我可以把关系设置为限时或长期；限时关系必须有覆盖申请范围的开始和结束时间，长期关系不使用遥远日期占位。

107. 作为网络办理人员，我可以通过平台工作流办理申请、登记实施结果和凭证；只有成功办理才形成访问关系。

108. 作为申请人，我只能通过新的修改、续期或关闭申请改变既有网络访问关系，不能直接编辑已开通事实。

109. 作为网络管理人员，我可以看到已下线关联实例的风险；实例下线不会自动关闭历史关系，但已下线实例不能用于新申请。

110. 作为申请人，我可以提交 CLB 开通或调整工单并查询办理结果；平台不承担 CLB 实例、监听器、后端池和健康检查的完整生命周期管理。

111. 作为申请人，我可以提交 DNS 域名新增、变更或注销工单并查询办理结果；实际 DNS 操作在线下或外部系统完成。

112. 作为申请人，我可以提交 SSL 证书或外联证书的申请、续期或吊销工单并查询办理结果；平台不生成证书、不保存私钥、不自动部署，附件只包含申请材料或公开证书。

113. 作为申请人，我可以为一个物理子系统下的一个部署单元创建加密机入池工单，并让安全节点号从物理子系统主记录带出并保存提交快照。

114. 作为系统，我不允许在加密机入池工单中另行改写安全节点号，以避免工单内容偏离架构主记录。

115. 作为申请人，我可以在一张加密机入池工单中添加多条接口项，为每项填写预计峰值交易量和计量单位。

116. 作为申请人，我优先从权威接口目录选择接口并保存提交快照；目录不存在的接口可以明确标记为临时接口，而不是伪装成权威主数据。

117. 作为系统，我会从全部接口项汇总工单总交易量，不允许另行填写一个可能与明细不一致的总数。

118. 作为办理人员，我可以通过平台工作流核验、要求补充、退回、受理并登记最终处理结果和凭证；完成仅表示外部实际配置已完成并已登记。

119. 作为系统，我不会自动分配加密机资源、创建外部协同任务或执行加密机配置。

120. 作为架构规范维护人员，我可以按部署规范、网络规划、编码规范、数据库规范等平台字典类别发布和维护架构规范文档。

121. 作为技术人员，我可以在线查阅有权限的架构规范及附件；PDF 只是文件格式，不形成独立部署公告或网络文档模块。

122. 作为网络管理人员，我仍以结构化数据维护网络分区、IP 段等网络事实，架构规范文档不能替代结构化网络数据。

123. 作为事项提出人，我可以围绕一个明确问题或困难提交一件架构决策事项，并在提交时暂不具备完整方案、影响分析或争议点。

124. 作为事项提出人和架构组成员，我可以在后续协作中补齐方案、影响和争议信息；系统不因首次材料不够完整而强制拒绝进入事项记录。

125. 作为管理员，我可以使用平台字典维护架构事项类型；事项提出时允许待分类，但正式决策发布前必须确定类型。

126. 作为架构组成员，我需要在收到事项后的 7 个自然日内完成首次处理，即确认受理、要求补充信息或确定评审方式，而不是被要求在 7 日内完成最终决策。

127. 作为架构组成员，我可以选择异步评审或会议评审，并记录参与人、过程材料和关键意见；系统不强制所有事项都必须开会。

128. 作为架构组成员，我在完成评审时必须记录正式结论、理由和行动项，不能只用口头结论结束事项。

129. 作为系统，我在正式决策结论发布后将架构决策事项标记为完成；行动项可以继续跟踪，但不阻止已发布结论成为可查询决策。

130. 作为架构管理人员，我不能直接修改已经发布的正式结论，只能通过明确标注“替代”或“部分修订”的后续决策改变其有效范围。

131. 作为技术人员，我可以查询当前有效决策及其历史链路，识别哪些旧结论已被全部替代、部分修订或仍然有效。

132. 作为已认证用户，我只能看到并操作与角色、数据范围和具体实体授权一致的业务对象；前端隐藏按钮不能替代服务端校验。

133. 作为审计人员，我可以查询所有关键写操作、状态事件、办理意见、取消与恢复、事件更正、导入、发布以及关系变更的操作人、时间、原因和前后值。

134. 作为业务用户，我可以在适用页面使用统一的查询、筛选、分页、排序、导出和详情查看能力；导出必须遵守与页面查询一致的权限和数据范围。

135. 作为业务用户，我可以使用平台附件上传和在线预览能力提交业务材料；附件访问必须继承所属业务对象的实体授权。

136. 作为业务用户，我在桌面端和移动端都能完成已定义的核心查看与办理旅程，并能看到加载、空数据、失败、无权限和提交中等明确状态。

137. 作为系统，我按单租户领域模型处理当前需求，不创建租户实体、租户配置或租户级业务隔离，也不向业务接口暴露新的租户概念。

## Implementation Decisions

1. 当前产品基线由本规格、已确认领域词汇、范围决策和待确认问题共同组成。若内容冲突，以日期更晚且明确标记“已确认”的决定为准；未确认原文不得自动进入实施。

2. 当前范围采用单租户领域模型。现有平台内部可能仍含兼容性租户字段，但本需求不得扩展多租户业务概念；是否清理既有兼容字段只能由单独迁移决策处理。

3. 逻辑子系统、物理子系统、部署单元、具体环境和环境部署实例是不同对象。架构定义、申请需求、实际资源、计划执行和工单过程不得合并成一张宽表或相互覆盖。

4. 物理子系统编号和部署单元编号是稳定、不可复用的受控身份。作废、停用和下线均保留历史，不以物理删除代替业务状态。

5. 模板采用发布版本，计划和任务采用创建时快照。全局模板、架构资产和部署单元新版本只产生差异提示，不自动改写既有执行数据。

6. 计划、环节、任务和检查项组成自顶向下结构；“环节”是计划与任务之间的节点，任务和检查项必须具体归属于某一环节。

7. 完成、等待前置、阻塞、逾期、进度、全部豁免和存在豁免均依照本规格计算，不提供通用状态覆盖入口。所有能够改变计算结果的业务动作必须留痕。

8. 取消是当前豁免机制，不等于删除或伪完成。检查项、任务、环节和计划的取消及恢复权限、传播规则和历史保留遵循用户故事中的明确约束。

9. 资源需求规格属于资源工单，实际资源分配属于环境部署实例。环境资源视图通过聚合得到，不另建人工维护的资源总账。

10. 环境部署实例的日常新增和资源调整以资源工单办理结果为来源。受控存量导入是唯一初始化例外，普通用户不能直接新建或任意改挂实例。

11. 网络访问申请的一端只允许一组物理子系统、具体环境和部署单元级联选择；一张成功申请形成一条源集合到目标集合的访问关系，快照外实例不自动加入。

12. 网络访问判定采用严格策略：只有明确不需要或已有关系完整覆盖时返回不需要申请，其余均返回需要申请，并校验时间范围覆盖。

13. 资源、网络、CLB、DNS、证书、加密机入池和物理子系统变更的流程编排复用平台工作流引擎。业务模块维护业务表单、业务规则和办理结果，不重复建设通用流程状态机。

14. 环境类型、架构事项类型和架构规范类别等受控分类优先复用平台字典，不在业务代码中写死可管理分类。

15. 附件、在线预览、站内通知、认证、RBAC、数据范围、实体授权和审计优先复用平台能力。业务权限矩阵和跨模块公开契约必须在编码前的后续决策票据中固定。

16. 业务模块不得直接写入其他模块负责的数据表。跨域动作通过公开服务契约或事件完成；确切模块归属和契约所有权由后续系统建模票据决定，本规格不提前冻结包结构。

17. 当前不恢复已下线的动态业务表单元数据能力。每个业务模块维护自己的字段契约、校验、数据库结构和页面。

18. 本规格的 `ready-for-agent` 表示产品需求足以由 Agent 开展差距盘点和系统建模，不表示可以直接编码。每个实施批次都必须建立独立的仓库需求记录和控制前缀；该批次的 `codex-task-scope` 是唯一可写范围来源。

19. 当前不指定一个覆盖全部需求的巨型仓库控制前缀。后续路线应按可独立验收、回退和观测的业务纵向切片分配前缀，避免一次授权跨越所有模块。

20. 正式编码载体必须包含该批次的需求说明、任务范围、依赖、测试、迁移、权限、审计、上线验证和回退方式，并在 `.ai-control` 中保留对应阶段记录；缺少任一准入要素时不得编码。

## Testing Decisions

1. 主自动化验收接缝放在已认证的公开 HTTP API：使用真实 MySQL、完整 Flyway 迁移和真实平台工作流集成，按用户故事组织业务场景，覆盖成功、拒绝、越权、并发、历史保留和失败回滚。测试应观察公开结果、持久化事实、审计与跨模块契约，不依赖控制器或服务内部实现细节。

2. 只有难以通过主接缝经济、稳定覆盖的确定性规则才补充领域级单元测试，重点包括状态与进度传播、取消与恢复、全部豁免、前置依赖、阻塞与逾期、资源汇总、网络申请判定以及有效期覆盖。领域测试不替代公开 API 场景。

3. 数据库迁移使用 Testcontainers 与项目实际 MySQL 版本验证，至少覆盖空库完整迁移、受支持基线升级、约束与索引、历史数据兼容和失败可诊断性；不得用内存数据库代替生产方言证明迁移正确。

4. 权限、数据范围、实体授权、附件授权、审计记录和导出数据范围包含在公开 HTTP 验收场景中，不另建与业务流程脱节的重复测试体系。

5. 最终验收必须运行真实后端、真实前端和真实 MySQL，使用代表性角色完成关键用户旅程，并在项目规定的桌面与移动视口检查布局、滚动边界、弹层、操作层级、加载、空、失败、无权限和提交中状态。

6. 当前仓库没有既定的前端自动化测试框架，因此本基线不预先引入新框架。第一阶段以可重复的真实浏览器 UAT 和截图、控制台、网络请求证据验收；是否增加自动化浏览器接缝由后续系统设计根据回归成本单独决定。

7. 每个实施批次完成时必须明确区分：代码已实现、自动化检查通过、服务运行可达、真实浏览器已验收、未验证项和待确认项。任何未执行验证不得描述为通过。

## Out of Scope

1. 多租户实体、租户隔离、租户级数据范围和租户配置。

2. 已废弃的批量作业管理、日常需求研发流程管理和只有名称没有业务内容的配置管理。

3. 暂缓的环境变更模块，包括跑批、清数、翻数、系统日期调整、紧急变更和补审批。

4. 暂缓的交付与制品模块，包括交付单元、交付版本、交付制品、交付映射和部署记录的当前实现；其领域词汇仅作为后续候选记录。

5. ITM 应用资产关联查看和联机接口、EDA、交换接口、集成请求等外部主数据集成。

6. 微隔离策略管理和实施。

7. CLB 完整资源管理、DNS 解析管理平台、证书私钥管理及证书自动生成或部署。

8. 自动执行资源下发、网络开通、加密机配置、DNS 操作、证书生成、证书部署或其他外部运维动作。

9. 独立的部署单元公告模块和网络规划 PDF 模块；相关文档统一纳入架构规范发布。

10. 环境运行健康监控、部署单元之间的一般运行依赖、以及用独立人工资源台账重复记录环境实际资源。

11. 在当前需求基线中确定未经后续建模验证的具体模块包结构、数据库表结构、API 路径、页面路由或工作流定义。

## Further Notes

1. 当前仍有四个登记问题，但均不阻断本规格范围：交付制品类型与命名规则、实例实际制品版本来源、交付映射是否构成部署硬约束随交付模块暂缓；环境变更的紧急补审批随环境变更模块暂缓。
