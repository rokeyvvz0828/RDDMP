# 架构与环境能力按项目隔离

## 业务目标

项目成员在顶部选择当前项目后，只能查看和操作该项目的物理子系统、部署单元、环境、资源申请、环境部署实例和搭建计划。不同项目的数据、候选项、审批实例和执行结果必须相互隔离，同时允许不同项目使用相同的业务编号或名称。

原“具体环境”菜单和页面统一改名为“环境管理”。搭建计划模板及模板版本继续作为租户级共享能力，不绑定具体项目。

## 范围

### 本次实施

- 六类业务主数据绑定唯一 `project_id`：物理子系统、部署单元、环境、资源申请、环境部署实例、搭建计划。
- 可独立查询、关联、审计或回调的版本、关系、申请明细、工作流轮次、实例明细、计划目标、环节、任务、事件等关键子数据同步保存项目归属。
- 架构管理页面保留现有菜单位置，自动使用顶部当前项目，不增加第二个项目选择器。
- 业务接口显式接收必填 `projectRef`，通过 `ProjectAccessService` 解析可信项目主键并校验访问权；业务 DTO 不接收 `projectId` 或 `tenantId`。
- 项目有效成员还必须具备原有 `architecture:*` 权限；超级管理员可访问当前租户全部项目。
- 编号和名称唯一性由租户内唯一调整为项目内永久唯一；父子、部署、申请、实例和计划关联禁止跨项目。
- 资源申请、物理子系统变更等相关业务流程启动时传递当前项目上下文，复用工作流模块已有的项目定义、项目成员、项目角色、实例和待办隔离能力。
- 将存量架构数据及可可靠关联的下游数据归入项目编码 `RDDMP-PLATFORM`；存在待迁移数据但该项目不存在时迁移失败。
- 增加项目删除引用保护：项目存在未删除架构数据时返回冲突，不允许删除。
- 修正数据迁移、测试管理等现有物理子系统消费者的项目匹配条件，避免项目内编号重复后产生错误关联。
- 更新虚构 Mock 数据，至少使用两个项目和重复业务编号验证隔离。

### 本次不实施

- 不把架构管理页面移入项目详情，不提供双入口。
- 不允许一个物理子系统、部署单元或环境归属多个项目，不提供跨项目共享或转移。
- 不新增项目级架构角色，继续使用项目成员资格与现有系统动作权限组合授权。
- 不给搭建计划模板及模板版本增加 `project_id`。
- 不重复实现工作流项目权限，不修改 Flowable `ACT_*` 表或新增工作流范围类型。
- 不重命名 Java 包、数据库表和 `/api/architecture/environments` 路径。
- 不访问生产系统，不迁移无法可靠识别业务归属的历史工作流实例。

## 现状与规则

- 当前六类架构数据主要按 `tenant_id` 隔离，相关模型和接口没有统一项目上下文。
- 当前前端已有顶部项目上下文和切换确认，项目标识使用稳定项目编码 `projectRef`。
- 当前 `ProjectAccessService` 可按 `projectRef` 校验项目存在、超级管理员或有效项目成员资格，并返回可信项目 ID。
- 工作流模块已经支持项目流程、项目成员、项目角色、实例 `project_id`、项目待办和审批权限；部分架构业务当前构造 `WorkflowBusinessContext` 时仍将项目字段传为 `null`。
- 所有查询、详情、写入、删除、选项和唯一性检查必须同时限定认证租户与可信项目。
- 客户端直接提交其他项目的实体 ID 时，服务端不得返回或修改目标数据。
- 切换项目继续沿用确认后整页刷新；直接访问其他项目实体链接时不自动切换项目。

## 接口与数据

- API 契约：六类接口及关联选项接口增加必填查询参数 `projectRef`；创建、编辑请求不包含项目主键。
- 项目解析：`projectRef -> ProjectAccessService -> ProjectAccess(id, projectRef, projectName)`。
- 工作流：业务启动上下文填写 `projectRef/projectName`，业务项目、流程实例项目和生命周期回调项目必须一致。
- 数据 Owner：架构数据继续由 `business/architecture` 拥有；项目及成员由 `platform/system` 拥有；工作流数据由 `platform/workflow` 拥有。
- 公共能力：在 `platform/system` 增加通用项目删除检查扩展点，architecture 提供实现，system 不反向依赖业务模块。
- 数据库迁移：追加 MySQL 8.4 Flyway 迁移，不修改历史迁移；采用新增可空列、回填、校验、改为非空和重建索引/约束的顺序。
- 存量兼容：存量业务数据归入 `RDDMP-PLATFORM`；无法可靠关联的历史工作流事实保持原状，不伪造项目关系。
- 脱敏示例：项目 A 和项目 B 均可存在编号 `PAYMENT_AP`，但项目 A 的资源申请不能选择项目 B 的 `PAYMENT_AP`。

## 权限、审计与异常

- 读取和写入同时校验认证、租户、项目成员资格、原有 RBAC、实体项目归属和业务状态。
- 写操作继续保留现有审计，并记录项目编号作为业务上下文，不记录敏感表单正文。
- 未选择项目返回 `400`；项目不存在或已删除返回 `400`；无项目访问权返回 `403`。
- 实体不存在或不属于当前项目时列表不返回，详情返回 `404`。
- 跨项目关联、资源下发或计划目标返回 `400`；并发项目归属冲突返回 `409`。
- 工作流项目与业务项目不一致时拒绝启动或消费，并保留受限失败证据。
- 项目存在架构数据时删除项目返回 `409`。

## 验收标准

1. 顶部切换项目并刷新后，六个页面的列表、详情、选项和操作只显示当前项目数据。
2. 普通用户只能访问其有效成员项目；同时缺少对应 `architecture:*` 权限时接口仍返回 `403`；超级管理员可访问全部项目。
3. 不同项目可创建相同物理子系统、部署单元和环境编号或名称，同一项目内重复及软删除后复用仍被拒绝。
4. 任意详情、更新、删除和审批接口都不能通过直接提交其他项目实体 ID 绕过隔离。
5. 部署单元关联、资源申请、实例生成和搭建计划目标只能引用当前项目对象，数据库中不存在跨项目活动关系。
6. 搭建计划模板及版本保持租户级共享，由模板生成的计划绑定当前项目。
7. 资源申请和物理子系统变更等相关流程实例写入正确 `project_id`，审批人及待办沿用当前项目工作流规则，跨项目用户不能查看或处理。
8. 工作流生命周期事件只能更新同项目业务记录，项目不一致事件不会改变业务状态。
9. 存量架构数据迁入 `RDDMP-PLATFORM`；存在待迁移数据而默认项目缺失时迁移明确失败。
10. 项目存在未删除架构数据时不能删除；无架构引用的项目保持现有删除行为。
11. 数据迁移、测试管理等消费者按项目匹配物理子系统，相同编号不会串联其他项目数据。
12. 原“具体环境”菜单、页面标题和用户提示改为“环境管理”，内部稳定包名、表名和 API 路径保持兼容。
13. 页面覆盖无项目、无权限、加载、项目级空数据、失败、提交中、重复提交、脏表单和项目切换状态。
14. `1280x800`、`375x812`、`390x844`、`430x932` 及明暗主题下无页面级横向溢出，项目上下文持续可见。
15. 聚焦测试、受影响模块回归、真实 MySQL/Flyway、前端构建、治理、范围检查和浏览器验收均有真实证据。

## 测试与发布

- 必须执行：architecture、system、workflow 及受影响数据迁移/测试管理模块聚焦测试；MySQL 空库和既有库迁移；前端生产构建；治理、Flyway、scope 和 `git diff --check`。
- 权限验证：至少使用两个项目、仅属于其中一个项目的普通用户、同时属于两个项目的用户和超级管理员。
- 工作流验证：项目流程启动、项目成员/角色审批、跨项目待办拒绝、生命周期回调一致性和通知项目上下文。
- 浏览器验证：六个页面执行项目切换、列表、详情、新建/编辑及关键业务操作，覆盖四个视口和明暗主题。
- 上线验证：迁移前确认每个有架构存量数据的租户均存在唯一活动项目 `RDDMP-PLATFORM`。
- 回退：应用代码按前端、业务模块和平台扩展点逆序回退；已执行迁移保留新增字段，通过后续补偿迁移恢复兼容索引或关闭入口。
- 风险与人工复核：数据库多表迁移、公共项目删除扩展点、跨模块消费者、权限边界和工作流项目一致性由对应 Owner 专项复核。
