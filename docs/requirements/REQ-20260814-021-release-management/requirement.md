# 配置管理与版本发布控制正式实现

## 业务目标

把现有配置管理前端原型升级为正式业务模块。除当前项目、物理子系统和交付单元的选择来源暂由前端 Mock 提供外，投产窗口、版本申请、附件绑定、业务校验、审批状态、投产基线、生产版本、审计和统计分析全部使用真实数据库及后端接口。

## 必须范围

1. 新增独立 Maven 模块 `ccb-release`，拥有配置管理业务表、状态机、规则、服务和 API；平台模块不拥有配置管理业务状态。
2. “配置管理”保留投产窗口、版本申请、投产基线、生产版本、统计分析五个视图，全部读取正式后端接口。
3. 当前项目、物理子系统和交付单元仍由前端 Mock 提供选择项；提交后后端保存 ID、编码、名称和制品类型快照，历史数据不随未来主数据变化。
4. 投产窗口实现真实 CRUD、四个精确到分钟的时间、项目不可修改、窗口编码系统生成、同项目周期不重叠、修改原因与前后值审计、常规申请开关。
5. 版本申请实现草稿、编辑、提交、撤回、取消、退回后修改、重新提交和详情查询；并发更新使用乐观锁，所有状态变化保留事件日志。
6. 版本申请先选择是否应急。非应急申请选择可用窗口并自动判定常规版本或紧急版本；应急申请不选择窗口、不展示需求编号，必须填写应急情况说明并关联测试报告附件。
7. 一张申请只包含一个物理子系统和至少一个交付单元。每个交付单元保存唯一制品类型（镜像或二进制）和不含空格的版本号。
8. 非应急申请至少保存一个需求编号；需求编号本期手工录入并保存为明细，不接入需求管理模块。
9. 同一窗口、同一交付单元存在历史申请时返回完整冲突信息（附件除外），支持按历史状态取消旧申请、修改旧申请或继续创建新申请；制品准出后的新版本自动标记为追加申请。
10. 申请场景固定映射流程编码 `release.regular`、`release.regular.additional`、`release.regular.overdue`、`release.regular.overdue-additional`、`release.emergency`，申请人不能选择流程。
11. 提交申请必须由 `ccb-release` 调用平台 `WorkflowBusinessGateway.startByCode()` 启动真实流程，保存流程实例、定义版本、轮次和业务摘要；未发布流程不得进入审批中。
12. 工作流生命周期事件驱动申请进入制品准出、已退回或流程终止状态。当前节点、处理人、意见、签名、任务状态和流程日志以平台工作流为唯一事实源，前端不得模拟。
13. 审批操作继续在完整版本申请详情中执行；任务中心只导航。审批权限、允许动作和电子签名由平台工作流服务端校验。
14. 申请附件使用平台持久附件能力完成上传、绑定、预览、下载和删除控制；镜像和二进制制品本身只登记类型与版本，不上传平台。
15. 投产基线按窗口列出每个物理子系统、交付单元最新制品准出版本。投产管理人员维护制品准出、投产成功、投产失败或未投产，结果变更必须记录原因、操作人、时间和前后值。
16. 应急申请制品准出后按完成时间归入当时投产中的窗口；没有投产中窗口时归入最近未来窗口。没有可承接窗口时允许保存草稿但阻止提交。
17. 生产版本跨窗口展示每个物理子系统和交付单元最近一次投产成功的版本、版本类型、投产时间和来源申请；成功结果被改为其他状态后按历史成功记录自动回算。
18. 统计分析由数据库实时聚合窗口、物理子系统、交付单元、需求、申请、版本类型、制品准出和投产结果，并支持筛选和下钻。
19. 菜单、权限、模块治理、Maven 装配和 Flyway 迁移随正式模块一并交付；不得依赖已下线的输入项配置或 `biz_form_*` 表。
20. 正式验收数据必须通过“创建窗口 -> 创建申请 -> 提交 -> 审批 -> 维护投产结果”接口链路生成，不直接向业务表插入演示申请，不保留前端业务状态 Mock。
21. Web 与 `375x812`、`390x844`、`430x932` 视口均能完成申请查看和审批；密集维护表格在手机端使用卡片或受控局部滚动，不产生页面级横向溢出。

## 关键业务规则

### 投产窗口

- 四个时间满足：申报开始 < 申报截止 < 计划投产开始 < 计划投产结束。
- 申报开始默认当月 1 日 00:00，前端显示到分钟。
- 已关闭、未到申报开始或已进入投产期的窗口不可用于非应急新申请，并明确展示不可选原因。
- 常规申请开关关闭时阻止常规和紧急版本提交，不影响应急申请及已进入审批的申请。
- 窗口不允许删除或停用，项目创建后不可修改。

### 版本类型与窗口

- 申报周期内为常规版本。
- 申报截止后、计划投产开始前为紧急版本，紧急原因必填。
- 应急版本由申请人显式选择，不受前序申请影响；只要存在已进入投产开始日期的窗口即可提交，并在制品准出后自动归入承接窗口。
- 追加是系统识别的申请特征，不是用户可选版本类型。

### 申请与冲突

- 后端重新校验项目快照、物理子系统快照、交付单元唯一性、制品类型、版本、需求和场景字段，不能只依赖前端校验。
- 同一交付单元的历史申请提示必须包含原申请单号、状态、窗口、物理子系统、全部交付单元、需求、申请人、说明和版本变化，附件除外。
- 创建新申请不覆盖旧申请；取消、撤回和修改旧申请均执行各自状态规则并保留原因。
- 申请审批为整单通过或整单退回，不支持交付单元部分审批。

### 审批与投产

- 审批完成表示制品准出，不代表已经投产。
- 真实工作流数据是当前节点、审批轮次、处理人、意见、签名和日志的唯一事实源。
- 投产结果以交付单元为粒度维护，只有投产成功影响生产版本。
- 投产失败和未投产原因必填；制品准出改为投产成功时投产时间必填。
- 投产结果可以修改，但必须记录前后值、操作人和原因。

## 数据与权限

- 所有业务表包含 `tenant_id`、创建/更新审计、逻辑删除标志（仅适用于允许删除的数据）和乐观锁版本。
- 当前项目模块未完成前，服务端执行租户、登录身份、RBAC 和实体归属校验，并保存客户端当前项目快照；正式项目权限接入列为后续适配，不伪装为已完成。
- 物理子系统和交付单元主数据未完成前，后端验证快照结构和业务一致性，但不能宣称已验证上游实体有效性。
- 研发人员维护本人允许状态的申请；审批人按工作流任务处理；配置管理员维护窗口和投产结果。
- 前端显隐不能代替服务端权限。

## 非目标

- 本期不开发项目管理、物理子系统或交付单元主数据模块。
- 不接入需求管理、测试缺陷、代码仓库、制品仓库、外部系统或 AI。
- 不上传镜像和二进制制品文件，不做语义版本比较、制品哈希或自动识别实际投产结果。
- 不建设第二套待办、已办、流程配置、电子签名或通知平台。
- 不依赖输入项配置和动态表单元数据。
- 不直接写平台工作流、附件、通知或安全模块私有表。

## 验收标准

1. 清空配置管理业务表后，页面无业务数据；通过正式接口创建的数据可查询、编辑并持久化回显。
2. 五个视图不再读取 `createReleasePrototypeState()` 或前端内存业务仓库；刷新页面后数据保持一致。
3. 通过业务提交接口启动真实流程，申请详情左右两侧当前节点、轮次和状态一致。
4. 审批后申请状态由真实生命周期事件更新，重复事件和重复审批不产生重复状态变化。
5. 投产基线候选、投产结果、生产版本和统计分析使用同一数据库事实，跨页面数量与明细一致。
6. 正常、边界、权限、并发、重复提交、流程不可用、附件失败和长文本场景有自动化或浏览器证据。
7. `ccb-release` 聚焦测试、全量 Maven 测试、前端构建、治理、Flyway、范围检查和规定视口验收通过；用户指定 `rokey` 分支造成的命名告警单独披露。

## 回退

关闭配置管理菜单并回退应用代码；新增 Flyway 表保留为只读证据，不回滚迁移、不删除申请、审批关联、投产结果或审计记录。平台工作流和附件公共能力保持兼容。
