# 配置管理与版本发布控制

## 业务目标

面向项目研发人员、测试人员、流程审批人和配置管理员，在当前项目上下文内完成投产窗口维护、版本申请、审批、基线登记和统计分析。模块应形成可追溯的“窗口 -> 申请 -> 审批轮次 -> 基线批次 -> 交付单元版本”链路，并与平台统一工作流、通知、附件及项目主数据能力通过公开端口协作。

## 范围

### 本次设计

- 新增独立业务模块 `ccb-release`，后端目录规划为 `server/src/modules/release/`，前端目录规划为 `web/src/modules/release/`。
- 投产窗口维护、日期规则、项目绑定和常规申请开关。
- 常规、超期常规、追加常规、超期追加常规和应急版本申请。
- 物理子系统、交付单元、制品类型、制品版本、需求编号、说明和附件登记。
- 历史申请提示、重复申请阻断、追加版本识别和审批轮次留痕。
- 通过固定流程编码接入平台工作流，并消费统一审批状态和生命周期事件。
- 常规版本按投产窗口一次性纳入基线；应急版本审批通过后自动纳入基线。
- 按物理子系统和交付单元维护基线明细、最新基线和版本替代链。
- 项目级和单窗口实时统计、下钻和 Excel 导出。
- 桌面端列表、表单、详情、流程进度、基线和报表页面。
- 表单元数据、菜单权限和本地 Mock/初始化数据由实现 Agent 自动维护。

### 本次不设计

- 顶级项目上下文、工作流公共接口、统一待办/已办、工作流电子签名、站内通知和持久附件的平台内部实现。
- 外部系统对接和 AI 识别能力。
- 需求管理、测试缺陷的正式数据关联；本期需求编号手工录入，缺陷只保留应急情况说明。
- 制品文件上传、制品仓库、文件哈希、版本语义、大小和连续性校验。
- CA 数字签名、组会工作台、投产过程、部分投产、回退和确认未投产。
- 审批完成率、一次通过率、退回率和平均审批轮次等效率指标。
- 移动端业务页面适配和验收。

## 核心规则

### 投产窗口

- 一个窗口只关联一个项目，项目和窗口编码创建后不可修改。
- 申报开始、申报截止、计划投产开始、计划投产结束均使用自然日期，满足严格递增关系。
- 计划投产开始和结束必须位于同一自然年度，完整申报周期允许跨年。
- 同一项目窗口在“申报开始至计划投产结束”范围内不得重叠。
- 窗口不允许删除或停用；名称、日期、说明和常规申请开关可修改，原因必填并记录前后值；常规纳基成功后开关永久锁定为关闭。
- 常规申请开关同时控制普通和超期常规申请，不影响已进入审批的申请和应急申请。

### 申请场景

- 申报开始日前只能准备关联最近未来窗口的草稿。
- 申报开始日至申报截止日为常规版本。
- 申报截止日次日至计划投产开始日前为超期常规版本，超期原因必填。
- 计划投产开始日及以后只能提交应急版本。
- 常规窗口由当前项目和日期自动确定，申请人不可修改；应急版本可以选择当前项目下已到计划投产开始日的历史窗口。
- 业务场景自动映射到固定流程编码：
  - `release.regular`
  - `release.regular.additional`
  - `release.regular.overdue`
  - `release.regular.overdue-additional`
  - `release.emergency`

### 申请内容

- 一张申请单只包含一个物理子系统，可以包含多个交付单元。
- 保存草稿时至少选择一个交付单元，并填写不含空格的制品版本。
- 一个交付单元只有一种制品类型，由研发管理维护并在申请中保存快照；本期仅支持镜像和二进制。
- 常规版本提交时至少关联一个需求编号，应急版本需求编号选填。
- 应急版本必须填写“测试缺陷及应急情况说明”。
- 超期、追加场景分别要求超期原因、追加原因及风险说明。
- 说明附件对所有场景均为选填；单文件初始上限 20MB，每张申请最多 10 个。
- 已保存申请使用项目、窗口、物理子系统、交付单元和制品类型快照，不受上游主数据后续变化影响。

### 冲突与状态

- 同一窗口、同一交付单元、同一制品版本不能存在多张有效申请。
- 草稿、审批中、退回、撤回状态存在不同版本申请时，必须先取消原申请。
- 已审批通过或已纳入基线的常规申请存在新版本时，整单进入追加场景。
- 应急申请的历史记录只提示，不阻断，不转为追加场景；相同版本的有效应急申请仍禁止重复。
- 其他窗口历史记录只提示，不影响当前申请。
- 状态使用：草稿、审批中、已退回、已撤回、审批通过、已纳入基线、已取消。
- 审批完成前可撤回；审批中的申请不能直接取消，必须先撤回，再选择修改重提或填写原因取消。
- 所有取消操作均要求填写取消原因；审批通过后不能撤回、取消或编辑。
- 重新提交生成新审批轮次，并重新判定场景和当前已发布流程版本。

### 审批与基线

- 所有流程必须包含测试审核和配置管理审核，测试审核位于配置管理审核之前。
- 测试和配置管理意见无论通过或不通过均必填；其他节点通过意见选填，不通过原因必填。
- 审批结论只作用于整张申请单，仅允许整单通过或整单不通过，不允许按交付单元部分通过。
- 流程只向业务模块返回通过或不通过结果；节点电子签名要求由工作流配置。
- 常规窗口只能从计划投产结束日期次日起执行一次纳基；所有未取消常规申请必须审批通过。
- 应急申请审批通过后先记录“审批通过”，再自动纳入基线；失败时保留审批通过并幂等重试。
- 常规基线批次按窗口生成，应急基线批次按申请生成。
- 基线明细由“批次号 + 物理子系统编码 + 交付单元编码”唯一定位。
- 新应急版本按交付单元替换最新基线指针，历史版本不可删除。
- 同一常规窗口多个追加版本只把版本链末端写入常规基线明细；前序版本保留替代关系。
- 窗口常规纳基或应急自动纳基成功后不可撤销。

## 角色、权限与审计

- 研发人员创建、编辑、提交、撤回和取消本人申请，并查看本人或当前项目组申请。
- 测试、配置管理和其他审批人按当前工作流任务查看与处理申请。
- 配置管理员维护当前项目窗口、查看全部申请、执行窗口纳基和处理自动纳基异常。
- 平台管理员维护权限和平台能力，但不能代替流程审批人。
- 申请人不可转交；离岗、账号停用等接管场景本期不处理。
- 所有接口执行认证、租户、当前项目、RBAC、数据范围和实体权限校验。
- 窗口修改、申请操作、审批轮次、附件、导出和基线变化均保留审计记录。

## 报表

- 项目级总览比较多个投产窗口；单窗口报表展示窗口内部构成和明细。
- 实时统计窗口、申请、物理子系统、交付单元、去重需求、需求关联次数、版本场景、制品类型、状态和基线替代。
- 申请总数及状态分布包含草稿和已取消；业务规模默认排除草稿和已取消，保留退回和撤回。
- 物理子系统按编码去重，交付单元按“物理子系统编码 + 交付单元编码”去重，需求按编号去重。
- 项目级总量跨窗口去重，窗口对比在各窗口内独立去重。
- 投产年度按计划投产开始日期归属。
- 支持筛选下钻、上下文返回和 Excel 多工作表导出；不导出附件文件。

## 外部端口

当前模块只声明并消费以下端口，不设计其平台内部实现：

- `ReleaseProjectContextPort`
- `ReleaseMasterDataPort`
- `ReleaseWorkflowPort`
- `ReleaseNotificationPort`
- `ReleaseAttachmentPort`

正式环境端口不可用时不得静默使用 Mock；本地 profile 可以使用虚构数据适配器。

## 验收标准

1. 五种申请场景按当前项目、窗口日期、开关和历史版本稳定计算，并匹配固定流程编码。
2. 保存、提交、撤回、退回、取消、转应急和重提符合状态机，重复或并发操作返回明确结果。
3. 冲突弹框准确展示交付单元、前后版本、申请单号和阻断或追加结论。
4. 申请详情展示流程进度、当前节点、处理人、审批轮次、意见和平台返回的签名数据。
5. 常规窗口纳基一次性、不可撤销且存在阻塞申请时不产生批次。
6. 应急自动纳基幂等，失败可重试，旧版本不能覆盖后续应急最新基线。
7. 基线批次、明细、当前指针和替代链可相互追溯。
8. 项目级与单窗口报表统计口径与 Excel 导出一致。
9. 权限、项目范围、附件、导出和写操作均由服务端校验并留痕。
10. 全新本地数据库通过 Mock 自动呈现窗口、申请、流程关联、基线、报表和通知示例，重复加载不产生重复数据。
11. 模块测试、治理检查、全量 Maven 测试、前端生产构建和桌面浏览器用户路径验收通过，或如实记录环境阻塞。

## 风险与回退

- 平台端口实现是集成前置依赖，另行设计和审批。
- 当前申请单号和基线批次号格式为暂定规则，业务主键不得依赖展示编号。
- 数据库迁移必须追加 Flyway 脚本；回退应用版本时保留业务表和审计数据，不在生产物理删除。
- 基线和签名属于不可逆业务证据，实施计划必须包含并发、幂等和补偿测试。
