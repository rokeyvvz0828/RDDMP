# 配置管理交互式前端原型

## 目标

在现有 RDDMP 前端中修订配置管理 Mock 原型，验证“申请审批完成仅代表制品准出，投产结果再决定生产版本”的业务模型，以及版本申请、投产基线、生产版本、响应式审批和统计分析的完整交互。原型不得冒充正式后端能力。

## 必须范围

1. “配置管理”包含投产窗口、版本申请、投产基线、生产版本、统计分析五个视图；移除页面内重复的当前项目、Mock 和状态工具条，调试状态只允许从开发环境专用入口访问。
2. 版本申请先选择是否为应急版本。非应急申请展示投产窗口和只读“版本类型”，由窗口日期自动判定为常规版本或紧急版本；应急申请隐藏投产窗口、版本类型和需求编号。
3. 非应急窗口选项必须展示编码、名称、申报周期、投产周期、窗口状态和不可选原因；关闭、未到申报时间或已进入投产期的窗口禁用。四个窗口时间精确到分钟，申报开始默认当月 1 日 00:00。
4. 每张申请只包含一个物理子系统和至少一个交付单元。交付单元登记唯一制品类型（镜像或二进制）和禁止空格的版本号，并展示该单元最近一次投产成功版本、版本类型和投产时间。
5. 非应急申请至少关联一个需求编号；应急申请不展示需求编号，必须填写应急情况说明并至少上传一份测试报告附件。普通或紧急申请附件选填，单文件不超过 20MB，单申请不超过 10 个附件。
6. 同一窗口、同一交付单元出现历史申请时弹出冲突框，展示原申请除附件外的全部业务信息。草稿、已退回、已撤回支持取消旧申请、修改旧申请或新建；审批中允许新建，旧单须先撤回才能取消或编辑；制品准出申请不可取消或编辑，只能新建并标记为追加申请。
7. 追加申请是系统识别的申请特征，不作为用户可选版本类型；沿用常规追加、紧急追加对应的流程编码。审批流程按稳定流程编码启动，审批完成只把申请置为“制品准出”。
8. 投产基线按投产窗口展示每个物理子系统、交付单元最新准出的候选版本，候选以审批完成时间排序。投产管理人员可维护制品准出、投产成功、投产失败、未投产，修改结果必须填写原因并记录前后值、操作人和时间。
9. 只有投产成功更新生产版本。生产版本跨窗口展示每个物理子系统、交付单元最近一次投产成功版本、版本类型、投产日和来源窗口；撤销成功结果时必须根据有效历史重新计算。
10. 应急申请提交时不选择窗口；审批完成后按完成时间归入当时投产中的窗口，否则归入最近未来窗口并固定。没有当前或未来可承接窗口时允许保存草稿，但阻止提交并提示先维护窗口。
11. 提供统一审批链接 `/workflow/review/:taskId?businessType=release&businessId=...`。当前待办人可查看完整详情并执行同意、拒绝、退回和当前登录身份确认签署；同一路由在 Web 使用完整审批页，在 H5 使用卡片详情和底部操作栏。
12. 统计分析覆盖窗口数量、物理子系统数量、交付单元数量、需求数量、申请及版本类型分布、准出和投产结果，并支持窗口、系统、交付单元、版本类型和需求维度下钻。
13. 页面使用统一虚构会话数据，覆盖正常、加载、空、失败、无权限、提交中、只读、冲突、并发失效、长文本和恢复初始数据状态。
14. 复用交付示范中心、公共 UI、Element Plus、ECharts、语义主题变量和现有路由模式；原型接口形状须能平滑替换为正式业务 API。

## 关键状态与规则

- 版本类型：常规版本、紧急版本、应急版本。
- 申请特征：普通申请、追加申请。
- 申请主要状态：草稿、审批中、已退回、已撤回、已取消、制品准出。
- 投产状态：制品准出、投产成功、投产失败、未投产。
- 流程编码：`release.regular`、`release.regular.additional`、`release.regular.overdue`、`release.regular.overdue-additional`、`release.emergency`；其中 overdue 编码继续承载界面名称“紧急版本”。
- 版本号首期只校验必填且不允许空格，不比较语义版本大小。
- 窗口内候选版本以审批完成时间决定最新，不以版本号字符串决定。
- 原型项目上下文、物理子系统和交付单元均为 Mock；正式实现后由项目管理和研发管理提供，服务端必须重新执行项目与实体权限校验。

## 非目标

- 不新增或修改 Java 后端、数据库表、Flyway 迁移、真实权限、真实工作流、真实附件存储、通知和导出服务。
- 不接入需求管理、测试缺陷或外部系统；需求编号暂允许手工登记，应急缺陷以文字说明和测试报告附件替代。
- 不上传镜像或二进制制品，只登记制品类型和版本。
- 不实现独立 H5 路由、外部电子签章、语义版本比较或自动识别实际投产结果。
- 不宣称完成 `REQ-20260814-021` 的正式业务模块验收。

## 验收标准

1. 登录后可进入 `/release` 并切换五个视图，页面不再显示重复项目/Mock/状态工具条；开发调试入口不影响正常用户界面。
2. 常规、紧急、应急及追加申请均能按规则展示字段、窗口、流程编码、冲突信息和校验结果，失败不会丢失已录入内容。
3. 审批完成只产生制品准出候选；维护投产成功后生产版本才变化，改为失败或未投产后可回算到上一有效成功版本。
4. 交付单元录入时可看到最近生产版本；冲突框展示历史申请完整业务信息但不展示附件。
5. 审批链接在 `1280x800` 及 `375x812`、`390x844`、`430x932` 可查看详情和完成当前用户允许的审批动作，不产生页面级横向溢出。
6. 统计指标、图表、下钻、申请详情、投产基线和生产版本均由同一 Mock 数据派生，数量和状态一致。
7. 浅色与深色主题无文字遮挡、按钮不可达或非预期溢出，浏览器控制台无错误。
8. `npm --prefix web run build`、`git diff --check`、治理检查和规定视口浏览器验收通过。

## 回退

回退修订 2 的前端组件、类型、Mock、路由和样式变更即可恢复修订 1 原型；不涉及数据库或业务数据清理。修订 1 的历史实施与收敛证据保留，不作为修订 2 的验收证据。
