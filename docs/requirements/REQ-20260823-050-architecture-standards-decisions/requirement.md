# 架构规范与架构决策

## 1. 背景与目标

现有 `business/architecture` 已覆盖逻辑/物理子系统主数据、变更工单全生命周期（REQ-20260822-048）与部署单元版本/导入（REQ-20260823-049）。本需求补齐架构域的最后两块能力：

1. **架构规范**：按受控类别统一发布和维护架构规范文档，技术人员按权限在线查阅及预览附件；PDF 只作为附件格式，不形成独立部署公告或网络文档模块，结构化网络数据不被文档替代。
2. **架构决策**：围绕一事一议的架构决策事项，从提交（允许材料不完整）、后续协作补齐、首次处理（7 个自然日）、异步或会议评审，推进到正式结论发布；已发布结论不可原地修改，只能由后续决策「替代」或「部分修订」，并提供当前有效决策与完整替代链查询。

本需求以仓库治理和本文件为编码准入基准。外部 Wayfinder 票据（`temp/implementation/issues/13-architecture-standards-and-decisions.md`）与 `temp/spec.md`（User Stories 120-131）作为需求来源；用户于 2026-08-23 直接下达「实施 13 架构规范与架构决策」任务并指定使用 worktree，作为本批次开工授权。

## 2. 角色、权限与数据范围

| 权限 | 能力 |
| --- | --- |
| `architecture:standard:view` | 查阅已发布（含已下线历史）架构规范文档、正文与附件预览 |
| `architecture:standard:manage` | 创建/修改草稿、发布、下线、维护版本历史与附件 |
| `architecture:decision:view` | 查看全部已提交决策事项、评审记录、结论与替代链 |
| `architecture:decision:propose` | 包含查看；创建、编辑、补充材料、重新提交本人发起的决策事项 |
| `architecture:decision:review` | 包含查看；执行首次处理、记录异步/会议评审、记录正式结论/理由/行动项、确定事项类型 |
| `architecture:decision:manage` | 包含查看；准备并发布正式结论（经工作流门禁）、维护替代/部分修订关系 |

- 角色种子：`ARCHITECTURE_MANAGER`（110，架构管理人员）授予全部新权限；`ARCHITECTURE_GROUP`（112，架构组成员）授予 view/propose/review；tenant 1 管理员（用户 1）保留全部权限。
- 服务端必须同时校验认证、RBAC、当前租户、实体授权和当前状态；前端按钮显隐不能代替服务端校验。
- 已发布正式结论任何接口都不得提供修改或删除路径；结论数据行只在发布事件中一次性写入。

## 3. 稳定需求

### R1：架构规范类别与查阅

- 类别为受控分类，复用平台 `sys_dict_type` + `sys_config`（参数管理）维护，字典编码 `ARCH_STANDARD_CATEGORY`，种子值：部署规范、网络规划、编码规范、数据库规范；业务代码不写死可管理分类。
- 规范列表按标题、类别、状态筛选，服务端分页与排序；已下线文档保留可查但明确标记；详情返回正文与附件清单。
- 在线查阅不需要额外页面权限以外的条件；附件访问继承文档实体授权（`architecture-standard` 附件业务策略）。

验收：view 用户可查当前租户全部文档且不能看到其他租户；无 view 返回 403；类别选项来自平台参数且可被管理员调整。

### R2：发布与维护

- 文档状态固定为 `DRAFT`、`PUBLISHED`、`OFFLINE`；新建为草稿，发布后进入 `PUBLISHED`，下线进入 `OFFLINE` 并可重新发布。
- 每次发布记录版本快照（标题、类别、摘要、正文、发布时间、发布人），版本号自增且历史不可改写。
- 修改已发布文档只影响后续发布，历史快照保持可追溯；删除仅允许从未发布的草稿。

验收：发布/下线/重发/快照与审计均通过；历史版本内容不被后续修改污染。

### R3：决策事项提交与协作补齐

- 提出人围绕一个问题提交事项：标题、问题或困难描述必填；方案、影响分析、争议点允许为空，后续由提出方与架构组成员按 `SOLUTION`/`IMPACT`/`DISPUTE` 类别追加补齐，每次追加留痕（操作人、时间）。
- 事项类型来自平台参数 `ARCH_MATTER_TYPE`；提交时允许待分类，但正式结论发布前必须确定类型。
- 事项编号按确定性规则生成 `AD-<年份>-<四位序号>`，租户内永久唯一、不可复用。
- 提交后进入 `SUBMITTED`；要求补充信息时进入 `RETURNED_FOR_INFO`，提出人补充后重新提交回到 `SUBMITTED`。

验收：材料不完整可提交；追加补齐可追溯；待分类事项在发布前被强制要求分类；编号无重复且不复用。

### R4：首次处理与评审

- 事项受理时间即首次进入 `SUBMITTED` 的时间；首次处理期限 = 受理时间 + 7 个自然日，服务端计算并持久化，逾期作为独立计算标识展示，不覆盖办理状态。
- 架构组成员（review 权限）执行首次处理，三选一：确认受理（同时确定异步/会议评审方式）、要求补充信息、确定评审方式；记录操作人、时间与意见。
- 评审以记录形式落地：异步或会议、评审时间、参与人、过程材料摘要、关键意见；一次事项可有多条评审记录。
- 完成评审时必须在评审记录中填写正式结论、理由，并登记行动项（内容、责任人、状态）；行动项在结论发布后继续跟踪，不阻止结论生效。

验收：期限计算与逾期标识正确；三选一办理留痕；多评审记录与参与人可查；结论发布时行动项与理由完整可审计。

### R5：正式结论发布与不可变

- 发布准备由 manage 权限用户执行：必须已确定类型、已有含正式结论的评审记录；可选择被本结论「替代」或「部分修订」的既有已发布结论，形成后续决策关系。
- 发布动作启动平台工作流 `architecture.decision.review`（节点：架构管理人员审批，动作 APPROVE/RETURN/REJECT）；业务详情页执行任务办理，工作流任务中心只导航。
- 只有 `APPROVED` 生命周期事件在同一事务中发布结论：写入不可变的结论行（内容、理由、发布人、时间）、写入替代/部分修订关系、事项进入 `PUBLISHED`（完成）。
- `RETURNED`/`REJECTED` 将发布退回：事项保持评审中，发布准备保留可调整；事件按实例、轮次和摘要幂等，允许平台重试。

验收：未批准不产生结论；批准事件原子发布且结论不可改；退回重提可再次发布；重复/乱序事件不改变业务事实。

### R6：有效决策与替代链

- 结论有效状态由替代关系推导：被任一后续结论「替代」→ `SUPERSEDED`；仅被「部分修订」→ `PARTIALLY_SUPERSEDED`；否则 `EFFECTIVE`。
- 提供当前有效结论列表（可按状态筛选）与单个结论的完整历史链路：该结论替代了谁、被谁替代/部分修订、原文与发布信息可追溯。
- 有效结论查询与页面查询遵守与列表一致的权限与数据范围。

验收：替代/部分修订链推导正确；有效列表与链路可查；已发布结论无修改入口。

### R7：桌面与移动端业务页面

- 新增「架构规范」列表/详情（正文、附件、版本历史、发布/下线操作）与「架构决策」列表、全页提交/编辑表单、业务详情页（协作补齐、首次处理、评审、行动项、结论发布、替代链）。
- 覆盖加载、空、失败、403、409、只读、提交中、长文本、重复点击和脏表单离开确认。
- 验收视口为 `1280x800`、`375x812`、`390x844`、`430x932`，明暗主题均不得出现页面级横向滚动。

### R8：可验证交付

- 后端覆盖单元、MockMvc、真实 MySQL 迁移、工作流公共契约和 Boot 装配；验收必须使用真实 MySQL/Flyway 和真实工作流实例。
- 前端必须构建通过，并在真实浏览器按 R7 视口完成权限、交互、网络、控制台和几何验收。
- 工程控制账本记录执行、独立观测、偏差闭合与收敛；未执行项目明确标为未验证。

## 4. 关键不变量

1. 已发布结论不可修改、不可删除；任何接口不得提供该路径。
2. 结论只能由 APPROVED 工作流事件发布；未批准不产生结论。
3. 事项编号租户内永久唯一、不可复用。
4. 首次处理期限 = 受理时间 + 7 自然日，服务端计算。
5. 类型未确定的事项不能发布结论。
6. 附件访问继承所属业务对象实体授权；租户只能来自认证上下文。
7. 类别与类型等受控分类只由平台参数维护，业务不写死。

## 5. 非目标

- 不实现网络分区/IP 段等结构化网络数据的文档化替代，也不新建部署公告或网络规划 PDF 模块。
- 不实现真实 AI、批量导入导出、外部系统同步或历史物理删除。
- 不修改平台工作流内部代码、既有公共接口或工作流表；不修改附件模块内部实现。
- 不引入租户概念扩展或动态表单元数据。
- 首次处理不要求必须开会；系统自动提醒（通知）不纳入本批次。
