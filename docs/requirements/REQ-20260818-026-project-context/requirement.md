# 正式项目上下文与项目成员权限

## 业务目标

为项目资产库及后续需求、测试、发布等业务模块提供正式、可授权的项目主数据和成员数据范围。业务模块只引用稳定的 `projectId` 和公开项目上下文契约，不复制项目主数据，也不把前端 Mock 项目作为服务端授权依据。

## 范围

### 本次实施

- 新建独立 `ccb-project` 业务模块并登记 Maven、模块所有权、公开包和依赖边界。
- 提供最小项目目录：项目编号、名称、状态、负责人、项目管理员、成员、只读成员和审计字段。
- 提供项目分页查询、详情、创建、更新、归档、恢复、成员查询和成员维护接口。
- 提供稳定的项目摘要、成员关系和数据范围判断 Java 契约。
- 建立统一 Project Context Store/Provider，替换业务页面直接使用 Mock 项目数组的方式。
- 实施“平台 RBAC 操作权限、项目角色范围、实体状态”三层交集授权。

### 本次不实施

- 不建设计划、阶段、里程碑、预算、风险、工时或项目组合管理。
- 不实现项目物理删除、跨租户项目共享或外部项目同步。
- 不实现资产、附件、工作流审核或文件分享功能。

## 现状与规则

- 当前正式后端没有项目管理模块；`delivery-showcase` 和现有 Project Context Store 中的项目均为演示数据，不能作为安全边界。
- 项目编号在租户内唯一；项目不物理删除，只允许 `ACTIVE` 与 `ARCHIVED` 状态切换。
- 项目角色固定为负责人、项目管理员、成员和只读成员。负责人唯一，转移负责人必须审计。
- 项目归档后所有消费模块必须把项目数据视为只读；是否允许查看由消费模块权限决定。
- 平台 RBAC 决定用户是否具备操作类型权限，项目成员关系决定可以操作哪些项目，两者缺一不可。
- 项目与成员写操作记录操作人、对象、前后状态、结果和 trace ID。

## 接口与数据

- 内部 API 使用 `/api/projects`、统一 `ApiResponse`、服务端分页和乐观锁。
- 公开 Java 契约至少提供项目摘要、项目状态、当前用户项目范围、成员角色和指定操作范围判断。
- 数据 Owner 为 `business/project`；其他模块不得读取项目表或接受前端传入的项目权限结论。
- 新增 MySQL 8.4 Flyway 迁移，至少包含项目表和项目成员表；迁移只追加。
- 不接触生产数据；测试使用虚构项目、用户和成员关系。

## 验收标准

1. 授权用户可创建、更新、查询、归档和恢复项目，并维护负责人、管理员、成员和只读成员。
2. 项目编号租户内唯一，负责人唯一，重复成员、非法角色和并发覆盖被服务端拒绝。
3. 项目公开契约能返回稳定项目摘要，并正确判断非成员、成员、只读成员、管理员和负责人范围。
4. 没有平台操作权限、不是项目成员、跨租户或访问不存在项目时，服务端不泄露项目数据。
5. 项目归档后写操作被拒绝，恢复后按原成员关系重新生效。
6. 现有 Mock 项目仍仅用于交付示范，不被后端授权逻辑引用。
7. 聚焦测试、全量 Maven 测试、前端构建、治理检查和桌面/移动项目选择路径通过。

## 测试与发布

- 必须执行项目模块单元与集成测试、项目 API/权限测试、Flyway 校验、`mvn test`、`npm --prefix web run build`、治理和任务范围检查。
- 上线验证项目创建、成员维护、角色切换、归档只读、跨项目拒绝和 Project Context Provider 替换路径。
- 回退应用时关闭正式项目入口并恢复 Mock Provider，仅保留新增项目和成员表，不执行生产 `DROP`。
- 风险包括新业务模块边界、公开项目契约、正式数据范围和前端上下文切换；需模块 Owner、security Owner 和 frontend Owner 复核。
