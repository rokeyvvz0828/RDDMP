# 通知业务板块展示与筛选

## 业务目标

随着配置管理及后续业务模块接入统一通知中心，用户需要在通知中直接识别所属业务板块，并按板块筛选全部或未读消息。平台必须区分“业务板块”“消息来源”和“业务对象”，避免所有审批消息只显示“审批中心”而无法判断来自哪个业务模块。

## 本次实施

- 为平台通知增加稳定的业务板块编码和展示名称，保留现有消息来源、业务类型和业务主键。
- 工作流业务上下文显式携带业务板块，审批通知由工作流桥原样传递，不根据前端路由推断。
- 通知抽屉展示“业务板块 · 消息来源”，并增加可搜索的业务板块筛选。
- 通知分页接口支持按业务板块服务端筛选，新增当前用户可见板块及数量查询接口。
- 通过追加 Flyway 迁移补齐存量通知；兼容存量运行中工作流产生的后续通知。
- 更新系统通知与工作流公开接入契约，并补齐服务、接口、前端和浏览器回归测试。

## 本次不实施

- 不增加短信、邮件、企业微信、WebSocket 或浏览器推送。
- 不增加通知模板、订阅偏好、运营群发、附件或消息删除。
- 不建设业务板块后台维护页面；板块编码和名称由业务接入契约提供。
- 不按项目筛选通知，不改变现有通知跳转、已读和全部已读语义。

## 业务规则

1. 业务板块编码使用稳定机器编码，例如 `release`；板块名称使用用户可识别名称，例如“配置管理”。
2. 消息来源继续表示触发渠道，例如“审批中心”；业务类型继续表示业务对象，例如 `release_application`。
3. 通知顶部显示“配置管理 · 审批中心”，底部继续显示消息级别和业务主键。
4. 业务板块筛选默认“全部业务”，选项只包含当前用户实际收到过通知的板块。
5. 筛选由后端执行；切换板块或全部/未读状态时回到第一页。
6. 铃铛角标始终显示当前用户全平台未读总数，不受板块筛选影响；未读标签显示当前所选板块的未读数。
7. 不存在的板块编码返回空列表，不报错，也不暴露其他用户或租户的板块数据。
8. 新业务流程必须显式提供板块信息；存量通知和运行中流程使用受控兼容映射，不阻塞审批。

## 数据、权限与审计

- `platform/system` 继续拥有通知数据和用户已读状态；业务模块不得直接写通知表。
- `platform/workflow` 负责保存和传递工作流业务上下文中的板块信息。
- 所有通知、板块选项和计数查询从认证主体获取租户和用户，不接受客户端用户身份。
- 通知发布审计保持现有规则，不在日志中记录正文或敏感信息。
- Flyway 只追加新迁移，不修改 `V26__system_notifications.sql`、`V35__workflow_business_integration.sql` 或其他已发布脚本。

## 验收标准

1. 配置管理审批通知显示“配置管理 · 审批中心”，业务单号、标题、内容和跳转保持正确。
2. 选择业务板块后，全部和未读列表只返回该板块的当前用户消息，分页总数与实际数据一致。
3. 板块选项返回当前用户可见板块的总数和未读数，不包含其他用户或租户仅有的板块。
4. 全局铃铛角标不随筛选变化；当前板块未读数在标记单条或全部已读后同步更新。
5. 发布通知时缺少或非法板块编码、名称会被服务端拒绝；站外路由、接收人和幂等规则无回归。
6. 存量版本申请、交付示范和系统通知完成板块补齐，未知类型按约定兜底且仍可读取和跳转。
7. 存量运行中工作流可继续审批并生成可识别板块的结果通知；新流程从业务上下文显式传递板块。
8. 通知抽屉在桌面及 `375x812`、`390x844`、`430x932` 视口中无横向溢出，筛选、加载、空、失败和长文本状态可用。
9. 平台系统、工作流、配置管理和组合桥聚焦测试、后端全量测试、前端构建、治理检查及浏览器验收通过。

## 回退

回退应用和前端代码后保留追加的板块字段及已补齐数据，不执行破坏性数据库回滚。旧版本应用继续忽略新增列；恢复新版后可继续使用已有板块数据。
