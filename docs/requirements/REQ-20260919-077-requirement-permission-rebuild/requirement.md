# 需求管理权限重建（三角色 + 数据范围 + 流转收回）

> 跨模块说明：本需求涉及 `business/requirement`（主）、`platform/infrastructure`（权限与角色种子迁移）、`frontend/application`（需求页菜单/按钮）。不改 `platform/security` 的权限计算实现。

## 业务目标

需求管理当前有 29 个权限码、七套互相叠加的数据范围判据（PMO、管理员、业务组成员、系统行负责人、系统成员、当前流转人、显式成员），导致"列表能看、按钮点不动""权限和业务角色对不上"等问题。本需求把权限与数据范围重建为三个业务角色，并补齐提出人收回、分析员只能往下流转的规则。

可观察的成功结果：

- 需求管理只有三个角色：需求提出人、需求分析员、需求统筹管理员；缺角色就看不到菜单、调接口返回 403。
- 提出人把需求流转给 A 后（A 再转给 B 也一样），随时能把当前处理人收回成自己并重新流转；分析员没有收回入口，直接调接口返回 403。
- 分析员能看到"当前在本人名下"以及"流转日志里曾与本人发生流转关系（转入或转出）"的需求，但只有当前在名下时才可编辑/流转/提交评审。
- 统筹管理员可查看该项目下全部需求的全量信息并执行全部操作。
- 权限目录里不再存在旧的 29 个 `requirement:*` 权限码。

## 范围

### 本次实施

- 权限码重建：旧 29 个 `requirement:*` 码删除并解绑（系统角色、菜单、项目角色三处），新建 9 个码。
- 角色重建：需求提出人 `REQUIREMENT_PROPOSER`、需求分析员 `REQUIREMENT_ANALYST`、需求统筹管理员 `REQUIREMENT_COORDINATOR`，作为项目角色模板写入每个存量项目并在新建项目时自动初始化。
- 数据范围重建：`RequirementSecurityService` 的七条 OR 判定替换为三档范围（本人提交 / 本人名下或曾流转过 / 项目全量）。
- 流转与收回：新增收回接口与 `WITHDRAW` 流转日志；提出人无条件可收回，分析员不可收回。
- 后端 58 处 `@PreAuthorize('requirement:*')` 全部替换为新码。
- 前端：菜单与路由按新码过滤；列表按数据范围；按角色与 `can_edit` 显示"编辑/流转/收回/提交评审"。
- 不迁移存量用户与角色绑定；需要权限的人在项目管理里被分配三个角色之一。

### 本次不实施

- 需求数据 `project_id` 改为 `pm_project.id`（第二批）。
- 主责/协同系统改读架构物理子系统（第二批，走 boot 适配器）。
- 差异序号自动生成、存量抽屉页签重组、需求对接阶段系统硬校验（第二批）。
- 需求模块过期业务表清理（第二批随数据重建一起）。
- 工作流与消息通知逻辑变更（已由 REQ-20260919-076 落地，本次只换权限码）。

## 业务规则

1. 权限唯一来源是项目管理里的三个项目角色；项目负责人与 `PM` 角色按平台既有规则自动拥有本项目全部业务权限。
2. 提出人 = 记录的 `created_by`；分析员的可操作前提 = 当前处理人是本人；统筹 = 项目内全量可操作。
3. 收回只改当前处理人，不改业务状态；差异处于"评审中/已评审"时不允许收回（用现有撤销评审）。
4. 收回与"受理"无关，不新增受理状态。
5. 分析员可见范围含历史参与（流转日志 `to_user_id` 或 `from_user_id` 命中本人），但不可操作非本人在名下的记录。

## 接口与数据

- 权限目录：删除 `requirement:*` 旧码与绑定，新增 9 个码并挂到需求菜单。
- 项目角色：为每个存量项目插入三个固定编码角色并绑定权限；项目创建逻辑补初始化。
- 新增收回接口：差异 `POST /api/requirements/differences/{id}/withdraw`、存量 `POST /api/requirements/legacy/{id}/flow/withdraw`。
- 流转日志：复用 `req_difference_flow_log` / `req_flow_log`，新增 `action='WITHDRAW'`，并补 `(tenant_id, to_user_id, deleted)`、`(tenant_id, from_user_id, deleted)` 索引。

## 权限、审计与数据边界

- 所有接口保留服务端 RBAC + 数据范围 + 实体授权三层校验，前端显隐不作为权限依据。
- 收回、流转、提交评审写 `req_change_log` 与流转日志，均可审计。
- 始终带 `tenant_id`；跨项目一律不可见。

## 验收标准

1. 无角色的项目成员：需求菜单不可见、需求接口 403。
2. 提出人：提交并流转给 A → A 转给 B → 提出人一步收回给自己 → 再流转，全流程可用；操作留 `WITHDRAW` 日志。
3. 分析员：无收回入口；调收回接口 403；能看到曾流转给自己的需求（只读），当前在名下时可编辑并继续流转。
4. 统筹：可见本项目全部需求并执行全部操作，不可见其他项目。
5. 旧 29 个权限码在权限目录与所有角色绑定中都不存在。
6. `mvn -pl :ccb-requirement -am test`、`mvn test`、`npm --prefix web run build`、治理检查通过。

## 回退

回退本次代码与迁移。由于按用户确认不做数据迁移与兼容，回退需同时恢复旧权限码种子与旧注解（建议在测试库回退后重新执行重建迁移）。
