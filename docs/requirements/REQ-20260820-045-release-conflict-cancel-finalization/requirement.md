# 追加申请冲突取消终态

## 业务目标

申请人在追加申请冲突弹框中处理本人审批中的旧申请时，能够终止旧审批并将旧申请直接形成永久只读的“已取消”，避免普通撤回产生的可编辑、可重新提交状态与“放弃旧申请”的业务意图不一致。

## 本次实施

- 冲突弹框仅对本人创建、状态为审批中且具备申请撤回权限的阻塞申请显示“取消申请”。
- 新增独立冲突取消命令，将审批轮次标记为 `CANCEL_REQUESTED` 并终止工作流。
- 工作流终止事件确认后，将旧申请从 `IN_REVIEW` 转为 `CANCELLED`，审批轮次转为 `TERMINATED`。
- 取消处理中保持当前申请的保存草稿和提交门禁；全部阻塞申请退出审批中后才允许继续原操作。
- 已取消申请仅可查看，后端拒绝更新、保存、提交、重新提交和附件变更。
- 申请列表普通撤回继续形成 `WITHDRAWN`，并保持可编辑、可重新提交。

## 本次不实施

- 不修改工作流平台模块、流程引擎终止协议或数据库结构。
- 不新增角色权限项，不允许取消其他用户创建的申请。
- 不改变冲突匹配、追加申请判定、普通取消或普通撤回行为。
- 不处理或转换存量已撤回申请。

## 权限与审计

- 新命令要求 `release:application:withdraw` 或 `system:admin`，服务端继续校验租户、所有者、状态、行版本和有效审批轮次。
- 取消原因必填并写入申请事件；轮次保留 `CANCEL_REQUESTED` 中间状态，终止完成写入生命周期事件。
- 前端按钮显隐不能替代服务端权限和实体授权。

## 桌面与移动端

- 复用现有冲突弹框、卡片操作区、固定底部操作区和响应式布局，不引入新的弹层或横向滚动。
- 桌面与移动端均显示“取消申请/取消处理中”；处理中和仍有审批中阻塞项时，“继续申请”不可用且原因可见。

## 验收标准

1. 仅本人审批中的阻塞申请显示“取消申请”，其他用户或其他状态不显示。
2. 冲突取消请求写入 `CANCEL_REQUESTED` 并终止工作流，但在终止事件前申请保持 `IN_REVIEW`。
3. `CANCEL_REQUESTED` 轮次收到终止事件后，申请变为 `CANCELLED`、轮次变为 `TERMINATED`，不再存在可审批任务。
4. 普通撤回收到终止事件后仍变为 `WITHDRAWN`，并可编辑、重新提交。
5. 取消处理中继续申请保持禁用；轮询确认阻塞解除后恢复原保存草稿或提交动作。
6. 已取消申请的更新、提交、重新提交和附件增删均被后端拒绝，详情保持只读。
7. 终止调用失败时事务回滚，不提前形成 `CANCELLED`，界面保持阻塞并可重试。
8. Release 模块测试、前端生产构建、治理检查、范围检查及桌面/移动真实浏览器验收通过。

## 回退

同时移除冲突取消端点、`CANCEL_REQUESTED` 存储与生命周期映射、前端 API 和弹框接入，恢复弹框调用普通撤回。不得只回退生命周期映射，以免留下无法收敛的取消请求轮次；不涉及数据库补偿。
