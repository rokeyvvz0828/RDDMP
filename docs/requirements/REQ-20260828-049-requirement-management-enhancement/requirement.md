# 需求管理平台增强（存量系统子表/流转/评审/版本 + 新建评审补充）

## 业务目标

在既有需求管理平台（REQ-20260816-001）基础上增强存量需求管理与新建差异评审：

1. **存量需求**：一条用户需求对应一个需求头，下面挂多行系统子表（主责/协同），页面只显示一条需求，库里存多行；仅主责/协同系统归属人员可见，PMO/管理员全量可见；协同通过"整条需求流转"完成（单次流转一人、可继续流转或回传、全程留痕、历史参与人只读）；每个系统独立维护工作量表、软需文档记录并走评审；需求变更涉及工作量/软需时采用替换并保留历史版本（1.0/2.0 Tab）；新增协同事项（改造/测试）、评审记录独立表；需求头新增"工作量需求变更"栏位与版本管理。
2. **新建差异评审**：提交评审对话框增加评审报告信息文档与评审记录字段（本期仅文本元数据 + 上传按钮占位，上传能力后续开放）。
3. **前端交互**：存量点击预览/编辑/阶段推进合并为以编辑为主，点击预览进入加宽编辑抽屉，阶段推进并入编辑页，按分步表单逻辑组织，合并重复预览入口。

## 范围

### 本次实施

- PMO 角色（`requirement:pmo`）：全量查看、阶段推进、发起流转、标记完成、可修改；普通业务人员仅可查看/编辑自己当前负责部分。
- `req_legacy_system_item` 系统子表：主责/协同多行；页面按需求头展示一条，库内多行；可见性 = PMO/管理员 ∪ 系统行负责人/成员 ∪ 业务组成员。
- `req_flow_log` 整条需求流转：SEND（流转给一人）/ RETURN（回传）/ COMPLETE（标记完成）；发起人可见全部历史，历史参与人只读。
- `req_workload` / `req_soft_doc`：按系统独立记录，版本替换保留历史；评审状态（待评审/评审中/已评审/已退回）。
- `req_review_record`：评审记录（评审人/时间/结论/意见/评审报告文档名称预留）。
- `req_coordination_item`：协同事项（改造/测试）单独表。
- `req_requirement_version`：需求版本历史；需求头新增 `version_no`、`workload_change`、当前流转人字段。
- 差异评审：提交评审带评审报告文档名称（上传按钮占位）；评审完成回写评审记录。
- 前端：存量统一编辑抽屉（宽 1100px）、分步 Tab（当前阶段/系统清单/流转记录/工作量表/软需文档/协同事项/版本历史）、保存与"完成（进入下一阶段）"按钮；上传按钮全部保留但本期不实现上传。

### 本次不实施

- 在线签字（另行需求）。
- 文件实际上传与预览（本期仅按钮占位与文本元数据，表结构预留引用字段）。
- 统一项目库接入；`req_project` 先空置，不迁数据、不接 `pm_project`。
- 系统级独立流转（流转按整条需求）。
- 存量需求评审接入平台工作流审批流（本期为 PMO/评审人直接确认并写评审记录）。

## 现状与规则

- 沿用 `req_legacy_requirement` 需求头结构与 6 阶段；阶段推进仍直接状态流转并写 `req_stage_log`。
- 上传能力后续开放：按钮存在并可见，点击提示"本期未开放上传，后续版本支持"。
- 权限在服务端校验：PMO 判定使用 `requirement:pmo` 权限；非 PMO 按业务组与系统行负责人数据范围过滤。

## 验收标准

1. PMO 可见全部存量需求并可阶段推进/流转/标记完成；业务人员仅见自己负责的需求且不能推进整体阶段。
2. 一个主责 + 两个协同 = 需求头 1 条 + 系统子表 3 行；列表只显示 1 条。
3. 流转单次一人，留痕完整；历史参与人只读。
4. 工作量表/软需文档按系统记录，评审后锁定；变更替换时保留历史版本。
5. 版本 Tab 1.0/2.0 可切换，默认最新版。
6. 差异提交评审可填评审报告文档名称并展示评审记录。
7. 前端存量统一编辑抽屉可完成保存与阶段推进，无独立预览/阶段推进页。
