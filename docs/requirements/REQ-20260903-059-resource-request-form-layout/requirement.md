# 资源申请表单主从布局优化

## 业务目标

资源申请人在新建或编辑草稿时，需要在同一弹窗中高效维护基础信息和多条部署单元资源规格。现有表单将所有明细纵向展开，申请项较多时扫描、切换和定位错误的成本较高。

本需求将表单改为两级主从布局：外层左侧维护基础信息，右侧维护部署单元登记表；登记表内部左侧为申请项列表，右侧为当前申请项表单。部署单元仍在申请项表单中选择，并保留同一部署单元多套规格能力。

## 范围

### 本次实施

- 外层分为基础信息和部署单元登记表两栏。
- 左侧纵向维护物理子系统、联系人、具体环境、申请类型、申请原因和物理子系统只读摘要。
- 右侧登记表分为申请项列表和当前申请项表单两列。
- 支持新增、删除、切换申请项；新建默认生成一个空申请项，至少保留一项。
- 部署单元在当前申请项表单内选择；多个申请项允许选择同一部署单元。
- 申请项显示“未选择、待完善、已填写”状态；校验失败自动定位首个错误项。
- 切换物理子系统时，有申请项内容则二次确认；确认后清空、创建一个空项并刷新候选，取消则恢复原选择。
- 中等宽度和手机端按 `design-h5.md` 重排，保证滚动边界和底部操作可达。

### 本次不实施

- 不改变资源申请 API、DTO、数据库、后端校验、权限、审计或工作流。
- 不改变 DB 与应用/Web 字段分流、计算规则和提交载荷。
- 不增加自动保存、复制、拖拽排序或部署单元去重限制。
- 不修改公共 UI、应用壳、路由或其他业务页面。

## 现状与规则

- 当前入口为架构管理“资源申请”页面，表单位于 `ResourceRequestPage.vue`。
- 现有 `items[]` 允许重复部署单元，本需求只改变前端编辑方式。
- 每个申请项使用仅存在于前端的稳定临时标识；提交时剥离该标识并保持原有顺序。
- 编辑草稿按服务端顺序恢复申请项，默认选中第一项；切换不得丢失输入。
- 保存期间禁用新增、删除、切换和重复提交；候选或保存失败时保留输入。
- 前端权限只改善体验，服务端申请人、RBAC、租户和实体校验保持。

## 接口与数据

- 继续使用现有 options、create 和 update API，提交结构不变。
- 数据 Owner 仍为 `business/architecture`，不新增或迁移数据。
- 临时标识和当前选中状态不进入 HTTP 请求。
- 示例：两个申请项均选择 `PORTAL_AP`，分别填写不同 CPU、内存和节点数。

## 验收标准

1. 桌面端清晰呈现外层两栏和登记表内部主从两列。
2. 新建默认一个空项；可新增、删除和切换，删除当前项后选中相邻项且至少保留一项。
3. 同一部署单元可在多个申请项中保存不同规格。
4. 切换不丢输入，编辑按原顺序回显并默认选中第一项。
5. 物理子系统变更正确执行确认、清空、刷新和取消恢复。
6. 申请项状态准确；保存校验失败自动定位首个错误项。
7. DB/非 DB 字段分流、计算、校验和 `items[]` 请求保持兼容。
8. 候选失败、保存失败、无权限和提交中状态可恢复，不重复提交。
9. `1280x800`、`375x812`、`390x844`、`430x932` 无页面级横向溢出，明暗主题可读。
10. 非数据库容量字段按填写逻辑重排：部署条件、核心容量、边车配置各自成组并充分利用整行；计算摘要与容量标题同行；技术栈三项在宽桌面同行展示。

## 测试与发布

- 执行 `npm --prefix web run build`、治理检查、scope 检查和 `git diff --check`。
- 浏览器验收新建、编辑、多申请项、重复部署单元、删除切换、错误定位、物理子系统切换、失败恢复和四视口明暗主题。
- 上线验证使用虚构草稿核对请求 `items[]` 数量、顺序和字段值。
- 回退本需求前端提交即可恢复原纵向表单，无数据补偿。
