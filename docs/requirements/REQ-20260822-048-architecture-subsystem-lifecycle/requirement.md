# 架构子系统全生命周期

## 1. 背景与目标

现有 `business/architecture` 已提供逻辑子系统和物理子系统的固定表单、主数据查询与直接 CRUD，但缺少申请、审批、发布、状态约束、确定性编号及完整历史。本需求在现有模块内建立“草稿申请—提交审批—批准后原子发布—可追溯变更”的完整闭环。

本需求以仓库治理和本文件为编码准入基准。外部 Wayfinder 票据与交接材料仅作为需求来源；其中“只读、不得编码、审批人可调整发布值、仅物理子系统走工单”等限制，已被用户在 2026-08-22 的明确决定覆盖。

## 2. 角色、权限与数据范围

权限按包含关系分为三级：

| 权限 | 能力 |
| --- | --- |
| `architecture:view` | 查看当前租户全部已发布逻辑/物理子系统；查看本人申请及其历史 |
| `architecture:apply` | 包含查看；创建、编辑、提交、取消本人的申请 |
| `architecture:manage` | 包含申请；查看全部申请并批准、退回或拒绝，包括处理本人发起的申请 |

- 管理权限不得绕过流程直接写主记录，但管理人员可独自发起并批准自己的工单，不设置职责分离限制。
- 业务详情页负责展示和执行审批；工作流任务中心只导航到业务详情。
- 服务端必须同时校验认证、RBAC、当前租户、申请归属或管理权限、目标实体和当前状态。前端按钮显隐不能代替服务端校验。

## 3. 稳定需求

### R1：发布主数据查询

- 逻辑和物理主数据保留独立分页列表、筛选和详情。
- 已发布记录具有 `ACTIVE`、`OFFLINE`、`VOIDED` 状态；列表可按状态筛选并清楚标记。
- 逻辑详情可查看所属物理子系统；物理详情可查看所属逻辑子系统。
- 既有字段和受控选项继续有效；物理子系统可选英文名称在租户内永久唯一，逻辑子系统支持稳定排序值。

验收：具有 view 的用户可查看当前租户全部发布数据且不能看到其他租户；无 view 返回 403；列表、详情和双向关联刷新后与数据库一致。

### R2：所有主记录写入必须经过工单

- 逻辑和物理子系统的新增、修改、下线、重新启用、作废都必须先创建变更申请。
- 申请状态固定为 `DRAFT`、`IN_REVIEW`、`RETURNED`、`APPROVED`、`REJECTED`、`CANCELLED`。
- 只有 `APPROVED` 才能改变发布主记录；审批人只能批准、退回或拒绝，不得在审批时修改已提交业务字段。
- 申请保留草稿、每次提交快照、字段差异、状态事件、操作者、时间、工作流实例和审批轮次。

验收：任何未批准申请都不改变主数据；直接写主记录的兼容接口不能产生数据库写入；审批历史可从业务详情复核。

### R3：逻辑新增可选级联物理新增

- 新建逻辑子系统申请包含一个逻辑草稿和可选的 `0..N` 个物理子系统草稿。
- 物理草稿以表单中的稳定行顺序保存和编号，可随草稿增删、排序；不要求至少一条。
- 批准时逻辑和全部物理子系统在同一事务内发布，全成或全不成。
- 已发布逻辑子系统可通过独立物理新增申请追加一个物理子系统。
- 除上述新增场景外，更新、下线、重新启用、作废均为单目标工单，不做级联修改。

验收：逻辑单独创建、逻辑加一条物理、逻辑加多条物理和独立物理创建均通过；任一子记录校验失败时主记录零新增。

### R4：确定性编号策略

- 编号能力采用策略接口；首期提供“固定前缀 + 全局或父级递增序号”实现。
- 逻辑编号为 `A` 加四位全局序号，例如 `A0001`，有效范围 `0001..9999`。
- 物理编号为 `W` 加所属逻辑的四位序号，再加一位槽位，例如逻辑 `A0001` 的首个物理编号为 `W00011`。
- 物理槽位按 `1..9,A..Z` 排列，每个逻辑最多 35 个永久占用槽位。
- 草稿阶段显示“待生成”；首次提交时分配。逻辑级联创建时先分配逻辑序号，再按物理草稿行顺序分配槽位。
- `RETURNED` 保留编号；未批准的 `REJECTED` 或 `CANCELLED` 新增申请释放编号。新分配优先取同命名空间最小已释放值，再取递增值。
- 一经批准发布，编号永久占用；后续下线或作废均不得复用。
- 既有编号不改写；迁移为既有逻辑/物理记录补充内部序号和槽位，以便新编号继续按规则生成。

验收：并发提交不重号；释放后按最小值复用；退回重提编号不变；越过 9999 或 35 槽位时返回明确容量冲突且不产生部分保留。

### R5：变更锁和物理归属迁移

- 同一已发布目标最多有一张已提交且未结束的申请；`IN_REVIEW` 和 `RETURNED` 持有排他变更锁。
- 多张草稿可以存在，首次成功提交者取得锁，其余提交返回 409 并指明冲突申请。
- 物理子系统的普通修改不得改变所属逻辑子系统，因为编号包含父逻辑序号。
- 归属迁移使用专用替换申请：在目标逻辑下创建新物理子系统，同时下线旧物理子系统，并保存不可变的替换关系；批准时原子完成。
- `APPROVED`、`REJECTED`、`CANCELLED` 释放变更锁。

验收：并发提交只有一个成功；退回仍阻止其他申请；替换后新旧编号和历史关系均可查，旧记录不被覆盖或删除。

### R6：状态和引用约束

- `OFFLINE` 可逆：停止接收新引用但保留历史引用和查询；重新启用必须另走工单。
- `VOIDED` 不可逆：只有不存在有效外部引用时才允许，检查器不可用或报错时必须 fail-closed。
- 逻辑下线要求没有 `ACTIVE` 物理子系统；逻辑作废要求从未发布过任何物理子系统且不存在其他有效引用。只要存在物理历史，就只能下线，不能作废。
- 被 `OFFLINE` 或 `VOIDED` 的逻辑子系统不能承接新的物理子系统或物理替换目标。
- 业务引用通过 `com.ccb.architecture.integration` 的公开检查 SPI 汇总；当前没有未来业务模块实现时视为“无外部引用”，但模块内逻辑—物理检查始终执行。

验收：活动子项、历史子项、有效引用、检查器异常、下线后新引用和不可逆作废均有服务端失败路径测试。

### R7：建议与 AI 边界

- 建议与申请草稿、发布主记录相互分离；建议只返回候选值、来源和解释。
- 用户必须显式采用建议；建议不得覆盖已编辑字段，不得直接写申请或主数据。
- 可实现基于受控参数和确定性规则的本地建议。
- 只预留 AI 建议提供者接口；首期 AI 提供者返回空结果，不调用真实 AI、不依赖 `business/ai`、不发送任何业务数据到外部系统。

验收：无网络/AI 配置时建议 API 正常；AI 来源为空；用户未点击采用时表单值不变化。

### R8：申请和审批权限

- view 用户只能查看自己的申请；apply 用户可维护自己的 `DRAFT` 或 `RETURNED` 申请；manage 用户可查看全部申请和审批。
- 审批必须同时满足 `architecture:manage`、工作流当前任务处理人和当前轮次一致性。
- 管理人员可以审批本人申请；普通申请人不能审批，即使能打开详情。
- 旧八项逻辑/物理 CRUD 权限按最小授权迁移：旧查看映射到 view，旧创建/更新/删除映射到 apply；超级管理员和架构管理员具有 manage。
- 既有发布主数据和选项 GET 端点同时接受旧读取权限与新三级权限；旧写端点仍只返回稳定工单 409，不恢复直接 CRUD。
- 固定 `ARCHITECTURE_MANAGER` 角色复用平台既有工作流根/收件箱访问以调用当前任务 API；工作流仍校验当前处理人、轮次和节点动作。平台 `workflow:access` 的既有粗粒度范围作为 T5 权限验收项，不在本需求内改造 workflow 模块。

验收：本人/他人、view/apply/manage、无权限和跨租户矩阵由 API 自动化覆盖。

### R9：工作流轮次和原子发布

- 固定流程编码为 `architecture.subsystem.change`，审批节点只允许 `APPROVE`、`RETURN`、`REJECT`。
- V95 只预置固定流程草稿；由平台既有发布入口生成 Flowable deployment 后方可提交工单。未发布或未部署时提交必须失败并回滚全部业务准备，不得伪造已发布状态。
- 首次提交和每次退回后重提均启动新的工作流实例，并递增 `businessRound`；旧轮次和乱序/重复事件不得改变当前申请。
- 平台 `RETURN` 为当前流程实例终态；业务申请进入 `RETURNED` 后可编辑并重新提交。
- 生命周期事件按 `subscriberKey + eventId` 幂等消费，并校验租户、业务键、实例、轮次和数据摘要。
- `APPROVED` 事件在同一业务事务中重新校验编号、唯一性、引用、状态和行版本，然后原子发布并写历史；失败时申请保持未批准并交由工作流事件重试。
- 取消审批中的申请调用公开工作流终止接口；仅在对应 `TERMINATED` 事件确认后进入 `CANCELLED` 并释放锁和未发布编号。

验收：批准、退回重提、拒绝、取消、重复事件、过期事件和发布失败重试均有自动化证据。

### R10：桌面与移动端业务页面

- 新增独立“架构子系统变更工单”列表、全页表单和业务详情页。
- 主数据页只读展示发布记录，并提供按权限可见的“发起变更”。
- 新建逻辑表单上方为逻辑区域，下方为可选动态物理卡片；桌面端为可展开详情卡片，移动端为纵向卡片。
- 业务详情展示提交快照、发布差异、编号状态、工作流时间线、业务历史和当前审批操作。
- 覆盖加载、空、失败、403、409、只读、提交中、长文本、重复点击和脏表单离开确认。
- 验收视口为 `1280x800`、`375x812`、`390x844`、`430x932`，明暗主题均不得出现页面级横向滚动。

验收：真实浏览器完成逻辑单独创建、逻辑级联物理、独立物理创建、退回重提和自审批旅程，控制台无新增错误。

### R11：兼容和迁移

- 既有发布记录的编号、名称、关联和审计不改写；只补充内部编号元数据、状态和行版本。
- 既有 GET 列表/详情接口保留并返回新增状态字段。
- 既有 POST/PUT/DELETE 接口保留路径但不再写库，统一返回 409 `ARCHITECTURE_WORK_ORDER_REQUIRED` 和工单入口提示。
- Flyway 只追加 V93—V95；不得修改 V1—V92。
- 架构模块新增对 workflow 公开包的依赖，并只公开 `com.ccb.architecture.integration`；不得直接访问 workflow 内部实现或表。

验收：旧 GET 回归通过；旧写接口数据库前后无变化；旧编号保持；模块边界、迁移和公共契约检查通过。

### R12：可验证交付

- 后端必须覆盖单元、MockMvc、真实 MySQL 迁移、并发分配/锁、工作流公共契约和 Boot 装配。
- 验收必须使用真实 MySQL/Flyway 和真实工作流实例，不以纯 Mock 替代完整链路。
- 前端必须构建通过，并在真实浏览器按 R10 视口完成权限、交互、网络、控制台和几何验收。
- 工程控制账本必须记录执行、独立观测、偏差闭合和最终收敛；未执行项目必须明确标为未验证。

验收：全部 R1—R12 均有可重复证据，未关闭反馈为 0，才能声明完成。

## 4. 关键不变量

1. 未批准申请绝不修改发布主记录。
2. 一个已发布目标最多有一张处于 `IN_REVIEW` 或 `RETURNED` 的申请。
3. 逻辑编号全局唯一；物理编号在完整编号维度唯一；已发布编号永久不可复用。
4. 物理编号中的逻辑序号与其发布归属一致，普通修改不能改父级。
5. 逻辑级联创建与物理替换均为原子发布。
6. 作废不可逆；引用检查异常一律拒绝作废。
7. 审批人不能编辑提交业务值；建议不能自动覆盖人工值。
8. 租户只能来自认证上下文，客户端不能提交或覆盖。
9. AI 提供者首期不调用真实 AI 或外部网络。

## 5. 非目标

- 不实现真实 AI 推理、训练、提示词管理或 AI 模块集成。
- 不实现跨租户共享、事业群/团队级二次数据隔离。
- 不实现批量导入导出、外部 CMDB 同步、生产发布或历史记录物理删除。
- 不修改平台工作流内部代码、既有公共接口或工作流表。
- 不恢复业务表单元数据或动态 schema 能力。

## 6. 数据与迁移约束

- V93 建立生命周期、申请、编号、锁、历史和替换关系数据结构，并为既有记录补充内部序号/槽位。
- 迁移前必须验证全系统逻辑历史记录总数不超过 9999、每个逻辑的永久物理历史不超过 35；超限则停止迁移，不静默截断或重号。业务数据仍按租户隔离，但逻辑编号分配域为全系统唯一。
- V94 初始化菜单、三级权限、兼容授权和架构管理员角色；V95 初始化固定工作流定义。
- 应用回退保留 V93—V95、发布数据、申请、编号和审计；关闭入口使用后续补偿迁移，不手工 DROP 或删除生产历史。
