# 部署单元名称、类型与关联模型调整

## 业务目标

架构信息维护者在部署单元页面通过一个醒目的名称输入框维护完整部署单元名称，并通过类型与标准后缀联动减少重复字段和录入冲突。部署单元之间改为可搜索、可多选、双向一致的真实关联，替代自由文本名称。

成功结果是部署单元模型不再维护简称和重复登记类型，名称统一为 `SMSLJ_AP`、`YGQL1_AP` 一类完整标识；应用、数据库、Web 三种类型与 `_AP`、`_DB`、`_WB` 标准后缀双向联动，同时允许自定义后缀后手工选择类型；关联关系可跨物理子系统搜索和多选，并在双方详情中一致显示。

## 范围

### 本次实施

- 部署单元删除 `shortName`、`relatedDeploymentUnitName`、`deploymentUnitType` 三个冗余字段，只保留完整 `name` 和 `kind` 表达名称及业务类型。
- `kind` 收敛为应用、数据库、Web，对应服务端枚举 `APPLICATION`、`DATABASE`、`WEB`。
- 前端使用一个部署单元名称输入框，以最后一个 `_` 识别主名称和后缀；标准后缀与类型双向联动，自定义后缀保留并要求用户选择类型。
- 名称统一转大写；主名称只允许大写字母和数字，后缀只允许 1—8 位大写字母或数字；完整名称在当前租户内永久唯一。
- 关联部署单元改为当前租户内 ACTIVE 部署单元的远程搜索、多选，支持按名称、编号和所属物理子系统检索，排除自身并允许跨物理子系统。
- 关联关系为双向无向关系，数据库按较小 ID、较大 ID 规范化保存一条记录，并保留独立关系历史和操作审计。
- 同步部署单元版本、初始化导入、资源申请、环境实例、网络和搭建计划等模块内下游契约与测试。
- 追加 MySQL 8.4 Flyway 迁移，删除冗余列、调整类型约束并创建关系与关系历史结构；不修改既有迁移。
- 更新虚构 Mock 数据、架构模块集成契约和桌面/移动端页面。

### 本次不实施

- 不保留 `MQ`、`PL` 或旧 `deploymentUnitType` 的新建兼容入口。
- 不提供生产数据迁移、旧客户端兼容层或跨版本灰度双写；当前仍为早期开发阶段，现有开发数据允许清理重建。
- 不新增部署单元类型字典维护页面；三种业务类型为部署单元领域固定枚举。
- 不改变部署单元自动编号 `code`、生命周期、权限码、所属物理子系统、默认网络分区、描述和备注等既有职责。
- 不修改平台公共组件、平台权限实现、工作流内部实现或其他业务模块私有数据。

## 现状与规则

- 当前入口为架构管理的部署单元列表及新建/编辑弹窗；现有模型同时保存 `shortName`、`name`、自由文本 `relatedDeploymentUnitName`、`deploymentUnitType` 和 `kind`，存在重复事实源。
- 新名称是完整业务标识。输入 `SMSLJ` 后选择应用，前端形成 `SMSLJ_AP`；输入 `_AP`、`_DB`、`_WB` 时自动选择对应类型；在标准后缀间切换类型时替换最后一个标准后缀。
- 输入 `_MQ`、`_JOB1` 等合法自定义后缀时不得被类型控件覆盖，用户必须显式选择应用、数据库或 Web 类型。
- 服务端必须重复执行名称规范化、格式校验、标准后缀与类型一致性校验，不能信任前端联动结果。
- 关联候选限定当前租户 ACTIVE 部署单元；已有关联的一端停用后关系继续可读，但停用目标不能被新增选择；作废前必须解除全部关联。
- 写操作继续使用 `architecture:deployment-unit:manage`，查看继续使用现有 view/manage 兼容权限；服务端执行认证、RBAC、租户隔离、实体校验、乐观锁和操作审计。
- 不接触生产系统、真实个人信息、真实附件、密钥或外部网络。

## 接口与数据

- 创建/更新命令固定为 `physicalSubsystemId,name,kind,relatedDeploymentUnitIds,defaultNetworkZoneId,description,remark,rowVersion`；更新时所属物理子系统继续不可变。
- 部署单元响应删除 `shortName`、`relatedDeploymentUnitName`、`deploymentUnitType`，新增结构化 `relatedDeploymentUnits[]`，每项至少包含 `id,code,name,kind,physicalSubsystemId,physicalSubsystemName,status`。
- 新增分页搜索选项接口，接受 `keyword,page,size,excludeId`，只返回当前租户 ACTIVE 记录；关键字匹配名称、编号和物理子系统名称/编号。
- 数据 Owner 为 `business/architecture`。关系表和关系历史表只由架构模块服务写入，其他能力通过公开部署单元投影读取。
- 资源申请的 AP/DB/WB 分流由 `kind` 映射，不再读取 `deploymentUnitType`；自定义后缀不改变业务类型语义。
- 合并 `main` 后迁移版本顺延为 `V148__refine_deployment_unit_model.sql`；实施和再次合并前必须重新扫描全仓迁移版本占用，发生冲突时先更新需求和 scope，不覆盖他人迁移。
- 脱敏示例：`SMSLJ_AP`（应用）、`YGQL1_DB`（数据库）、`PORTAL_WB`（Web）、`BATCH_JOB1`（自定义后缀、应用类型）。

## 验收标准

1. 新建和编辑部署单元只出现一个醒目的完整名称输入框，不再出现部署单元简称、登记类型或自由文本关联名称。
2. 输入名称和切换类型时 `_AP/_DB/_WB` 与应用/数据库/Web 双向联动；自定义合法后缀保持不变并可手工选择任一业务类型。
3. 服务端拒绝缺少分隔符、主名称为空、非法字符、后缀超长、标准后缀与类型不一致和租户内重复完整名称；失败时前端保留输入并就地提示。
4. 部署单元类型只允许 `APPLICATION`、`DATABASE`、`WEB`，资源申请按类型正确进入 AP、DB、WB 资源字段分支。
5. 关联选择器可按名称、编号和物理子系统搜索当前租户 ACTIVE 部署单元，支持跨物理子系统多选，不能选择自身、跨租户、停用、作废或不存在记录。
6. A 关联 B 后双方详情均显示对方；重复提交不产生重复关系；任一端解除后双方同时不可见；并发更新不产生半边或重复关系。
7. 停用部署单元保留并显示既有关联；存在关联的部署单元作废返回 409，解除后方可作废。
8. 部署单元当前版本、版本历史、初始化导入、列表、详情和模块内下游页面均使用完整名称和新类型契约，不再读取已删除字段。
9. 写接口继续执行服务端权限、租户、实体、乐观锁和审计校验；HTTP DTO 不接收或返回 `tenantId`。
10. 前端覆盖加载、搜索中、无结果、失败重试、无权限、提交中、重复提交、409 保留输入和脏表单关闭保护。
11. 桌面 `1280x800` 与手机 `375x812`、`390x844`、`430x932` 的弹窗、选择标签、列表和详情无页面级横向滚动，明暗主题可读，底部操作始终可达。
12. 架构模块聚焦测试、MySQL/Flyway、前端构建、模块内下游回归、治理、scope、迁移版本和真实浏览器验收按任务范围通过。

## 测试与发布

- 必须执行：部署单元 service/store/controller 测试；名称解析、后缀联动、唯一性、双向关系、租户、状态、并发和作废限制测试；初始化导入与资源申请等下游回归；MySQL 空库/既有开发库迁移；`npm --prefix web run build`；治理、scope、Flyway 和 `git diff --check`。
- 上线验证：使用虚构数据完成应用、数据库、Web、自定义后缀、远程搜索、多选、解除、停用和作废限制全旅程；检查 Network、Console 和四个视口的布局。
- 回退或补偿：应用代码按前端、服务、持久化逆序回退；已执行迁移不原地修改，通过后续补偿迁移恢复兼容结构。早期开发环境可重建数据库和 Mock 数据，不将该方式用于生产。
- 风险与人工复核：公开架构契约删除字段、资源申请类型分流、关系并发、破坏性删列和候选迁移版本由 `business/architecture` Owner 复核。
