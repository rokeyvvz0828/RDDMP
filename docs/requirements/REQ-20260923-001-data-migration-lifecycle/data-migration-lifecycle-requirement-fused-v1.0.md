# 第一篇 系统总纲

## 1 产品定位与系统整体落地逻辑

### 1.1 产品定位

数据迁移生命周期任务管理平台（以下简称「本系统」）是数据迁移项目**标准化任务流转管控工具**，承载蒙商银行、云南农信、印尼等多家客户方的迁移实施管控诉求。

### 1.2 核心落地逻辑（务实定义）

系统以五层要素构成闭环：

- 以「**角色权限**」为控制底座；
- 以「**组件 + 人员**」为责任主体；
- 以「**活动 + 工序**」为作业标准；
- 以「**专题**」为业务流程聚合；
- 以「**任务下发 / 流转 / 反馈 / 审核**」为执行闭环。

系统严格区分两层管控颗粒度：**项目级**（全局统筹）、**组件级**（明细执行）。所有模块、任务、流转、统计、权限均按两层颗粒度隔离联动，无交叉冲突；所有流程**可配置、可溯源、可自动阻塞解锁**。

### 1.3 系统形态与交付形态

| 维度 | 现状 |
| --- | --- |
| 前端 | React 18 + Vite 5 + TypeScript 5 + Ant Design 5（已完成四批次交付） |
| 路由 | 全应用统一 `HashRouter`（原型常以 iframe 嵌入或非根路径代理访问） |
| 数据层 | MySQL 8 表结构契约 + 契约视图；原型阶段以 Mock 数据层承载，闸门逻辑已收敛至单一出口 |
| 后端承接 | 真实后端接入时以 Spring StateMachine + 自研 Guard / Action 承接，**页面与闸门零改动** |
| 验收体系 | 四层：L1 数据层闸门 / L2 渲染冒烟 / L3 端到端全流程 / 类型检查（详见 19.3） |

## 2 全模块逻辑自洽校验结论

经整体链路校验，当前所有模块逻辑**完全自洽、无冲突、无遗漏、闭环完整**，核心校验结果如下：

- 人员-组件-角色绑定关系唯一，为所有任务分配提供唯一数据源，无重复、无空配风险。
- 活动区分项目级 / 组件级，专题同步适配两级颗粒度，颗粒度体系完全对齐。
- 工序依赖基于「准出交付物 + 审核状态」校验，流转触发条件明确，无模糊规则。
- 任务下发单发 / 批量逻辑区分清晰，支持单任务多组件、批量组件范围筛选拆分工单。
- 流转优先级：**专题自定义流转 > 活动默认工序流转**，规则唯一不冲突。
- 组件级任务强制同组件前置依赖，项目级任务无组件依赖，层级逻辑正确。
- 进度反馈、交付物模板、审核打回、批量操作全部配套闭环，功能无缺失。已同步补齐**历史问题知识库、任务时效（SLA）管控、状态机异常分支（暂停 / 转交 / 超时 / 异常重启）**三类能力，并统一全局状态枚举口径，模块闭环完整、无遗漏。

## 3 全局状态枚举唯一基准（全系统唯一状态定义处）

> **本章是全系统唯一状态定义处。** 依据项目《铁律与开发纪律》要求：后端状态枚举与前端显示状态严格 1:1 对应，**禁止使用布尔字段（如「是否完成」「是否作废」「是否审核」）拆分表达状态**。
> 各业务章节与各模块仅**引用**本章，**不得重复定义**，任何模块不得自行扩展状态值；状态枚举值一经发布，前端展示文案同步锁定，禁止出现「同一枚举多种显示名称」或「同一显示名称对应多个枚举」的情况。

| ③ | 活动状态 | 3 态 | 活动管理、任务发布、数据看板 |

### 3.2 ① 工单整体状态（9 态）

| 后端枚举 | 前端显示 | 状态说明与终态标记 |
| --- | --- | --- |
| WAIT_PRE | 待前置 | 存在未闭环的前置工序，工单尚未启动；非终态 |
| WAIT_ACCEPT | 待接收 | 前置工序已全部闭环，等待当前执行人接收；非终态 |
| EXECUTING | 执行中 | 执行人正在作业；审核打回后的整改亦回到本状态；非终态 |
| SUSPENDED | 已暂停 | 管理员暂停工单，全部工序锁定、禁止提审；可恢复，非终态 |
| REVIEWING | 审核中 | 已提交审核，等待审核人判定；非终态 |
| REVIEW_REJECTED | 审核打回 | 审核未通过，退回执行中整改；过渡态，非终态 |
| CLOSED | 已闭环 | 全部工序闭环达标，等待归档；非终态 |
| ARCHIVED | 已归档 | 全工序闭环并完成归档，只读；终态 |
| CANCELLED | 已作废 | 管理员异常作废，仅历史可查；终态 |

> **派生优先级说明（打回场景唯一口径）**：审核打回后，**工序**回落 `EXECUTING`、**审核态**保持 `REJECTED`，而**工单主状态**必须取「审核打回」。即判定「是否处于打回整改期」以**审核态**为准，**不得因工序状态回落而让工单主状态一并回落为「执行中」**。

### 3.3 ② 工序节点状态（5 态）

| 后端枚举 | 前端显示 | 状态说明与终态标记 |
| --- | --- | --- |
| LOCKED | 未解锁 | 前置工序未全部闭环，工序锁止，禁止执行；非终态 |
| EXECUTING | 执行中 | 工序已解锁，执行人作业与填报中；非终态 |
| REVIEWING | 待审核 | 已完成填报并提交审核，等待审核人；非终态 |
| REJECTED | 审核打回 | 审核未通过，退回执行中整改；过渡态，非终态 |
| CLOSED | 已闭环 | 准出内容 + 交付物 + 审核（按需）全部达标，工序固化；终态 |

### 3.4 ③ 活动状态（3 态）

| 后端枚举 | 前端显示 | 状态说明与终态标记 |
| --- | --- | --- |
| ACTIVE | 启用 | 允许下发新任务、允许被专题聚合关联；非终态 |
| INACTIVE | 停用 | 禁止下发新任务、禁止被聚合关联，存量任务不受影响；非终态 |
| OBSOLETE | 作废 | 逻辑删除，仅历史数据可查，不可恢复；终态 |

### 3.5 ④ 问题状态（4 态）

| 后端枚举 | 前端显示 | 状态说明与终态标记 |
| --- | --- | --- |
| WAIT_RECTIFY | 待整改 | 问题已登记，整改责任人待处理；非终态 |
| RECTIFYING | 整改中 | 整改方案已落地、整改进度实时更新；非终态 |
| CLOSED | 已闭环 | 整改完成并核验通过，固化归档并沉淀知识条目；终态 |
| CANCELLED | 已作废 | 无效或重复问题作废，仅历史可查；终态 |

### 3.6 ⑤ 风险状态（6 态）

| 后端枚举 | 前端显示 | 状态说明与终态标记 |
| --- | --- | --- |
| WAIT_PREVENT | 待防控 | 风险已登记，前置防控策略尚未落地；非终态 |
| PREVENTING | 防控中 | 前置防控措施执行中，防控进度实时更新；非终态 |
| AVOIDED | 已规避 | 风险未实际发生即被前置防控消除；终态 |
| OCCURRED | 已发生 | 风险已实际发生，进入处置流程；非终态 |
| CLOSED | 已闭环 | 已发生风险处置完成并经核验通过；终态 |
| CANCELLED | 已作废 | 误报或无效风险作废，仅历史可查；终态 |

> **语义澄清（避免「已规避」与「已闭环」歧义）**：「已规避」＝风险未实际发生，通过前置防控即已消除；「已发生」＝风险已实际发生、进入处置流程；「已闭环」＝已发生的风险处置完成并核验通过。三者互斥，单条风险在任一时刻仅归属唯一状态，**禁止用布尔字段组合表达**。

### 3.7 ⑥ 审核状态（4 态，工序级）

| 后端枚举 | 前端显示 | 状态说明与终态标记 |
| --- | --- | --- |
| WAIT_REVIEW | 待审核 | 已提交审核，等待审核人处理；非终态 |
| PASSED | 审核通过 | 审核通过，驱动工序闭环与后置工序解锁；终态 |
| REJECTED | 审核打回 | 打回整改，工序退回执行中；非终态 |
| RECHECK | 整改复审 | 打回整改后重新提审，进入复审；非终态 |

### 3.8 ⑦ 时效标记（辅助标记，非状态枚举，不参与流转判定）

| 标记值 | 前端显示 | 判定规则 |
| --- | --- | --- |
| NORMAL | 正常 | 剩余时间 > 24 小时 |
| NEAR_OVERDUE | 即将超时 | 剩余时间 ≤ 24 小时 |
| OVERDUE | 已超时 | 已超过计划完成时间 |

> 时效标记独立于工单主状态，**不阻塞工序执行与流转**，仅用于超时预警通知与看板分桶统计，规则详见 18.3。

### 3.9 ⑧ 工序配置状态（辅助标记，非状态枚举，不参与流转判定）

| 标记值 | 前端显示 | 判定规则 |
| --- | --- | --- |
| DRAFT | 草稿 | 工序已录入但未满足「可发布」条件（准出三要素未齐备，或所在拓扑尚未通过发布校验）；不可被任务引用 |
| READY | 就绪 | 准出三要素齐备且所属拓扑已通过发布校验；可被任务快照引用并参与流转 |

> **性质说明**：与 ⑦ 时效标记同性质——由系统按规则计算，**无人工维护入口，不构成业务状态、不参与流转判定**。工序是否可执行由「所在工单状态 + 前置工序闭环」决定，与本标记无关。本标记为**活动配置期**的概念，任务下发后以快照固化，不再随活动配置变化而重算。

### 3.10 状态机主线与异常分支（速览）

- **主线链路**：待前置 → 待接收 → 执行中 →（按需）审核中 → 工序闭环 → 解锁后置工序 → 全工序完成 → 已闭环 → 已归档
- **打回回退**：审核打回自动退回「执行中」，支持多次整改重试
- **异常分支（4 类，仅管理员 / 责任人可触发）**：暂停（SUSPENDED）、转交（执行人变更，主状态不变）、超时（时效标记，不改主状态）、异常重启（按快照恢复至最近有效流转节点）
- **例外干预态**：已暂停、已作废为管理员例外干预态，常规流转不进入
- **派生铁律**：工单主状态是**派生值**。任何工序级状态变更（提审、审核通过、审核打回、工序闭环、解锁传播）之后，**必须调用工单主状态重算**，禁止只改工序状态而让工单主状态停留在旧值。

### 3.11 状态枚举可达性自检（强制）

> 本节声明「有定义」**不等于**「能被走到」。状态枚举是全部流转断言的地基，若某个枚举值在**种子数据与用例**中永不可达，则依赖它的断言要么恒真、要么从未执行，验收结论失真。

**① 硬约束** —— 每一个在本章登记的枚举值，必须同时满足三条：

| 序号 | 要求 | 说明 |
| --- | --- | --- |
| 1 | **定义处唯一** | 只在本章出现，模块章节仅引用 |
| 2 | **前端显示 1:1** | 有且仅有一条显示文案，无同值异名 / 异名同值 |
| 3 | **可达** | 满足三者之一即为可达：① 种子数据中存在 1 条实体处于该值；② 被用例显式构造出来；③ 存在**只追加的流转留痕**（如 `order_status_log.to_status`）证明该值曾被到达。三者皆无才是「死枚举」 |

**② 死枚举的判定与处置**

- 判定方法：对每个枚举类别，统计种子与用例中该值的实体数；计数为 0 且无用例构造 → 死枚举。
- 处置优先级：**补种子反例**（首选）> 补用例构造（其次）> 若该值在本期确不产生，须显式登记为「本期不可达」并说明原因，**禁止沉默**。
- 实证教训：`WAIT_PRE`（待前置）与 `CLOSED`（已闭环）曾因种子缺少「专题后置子活动」与「全工序闭环未归档」两类样本而不可达——这两个值恰好是「跨活动流转」与「闭环 → 归档」两条关键链路的必经状态，其不可达意味着**两条链路整体未被验证**。

**③ 可达性证据形态（重要）**

可达性的证据形态**不止「当前态实体」一种**，按优先级判定：**当前态实体 > 用例构造 > 流转留痕**。

> 实证：例外干预态 `SUSPENDED` 的唯一种子实体可能已被前序用例 resume 成其他状态，若只认「当前态实体」则可达性会误判为失败；实际上该工单的流转日志中**永久留存了 `to_status='SUSPENDED'` 的记录**——只追加的留痕是「曾到达该状态」的永久证明。

**④ 自检问题**

- 把本章枚举表逐行对照种子数据，**哪几个值一条实体都没有？**
- 若某值确实不产生，是「本期业务不产生」还是「我们忘了造数据」？二者必须区分清楚并写明。

## 4 系统级铁律（业务 8 条 + 工程 11 条，共 19 条）

> 本章铁律**随开发流程恒加载**，不得跳过。业务铁律（#1~#8）约束「业务规则怎么判」，工程铁律（#9~#19）约束「代码怎么装配、交付怎么算可用」。
> **业务逻辑全部正确但页面打不开，同样属于交付失败。** 违反任一条即不予验收。

### 4.1 业务铁律 #1 ~ #8

#### 【铁律 #1 双颗粒度体系】

- **项目级**：全局统筹，不绑定任何业务组件，无组件维度权责、无组件前置流转依赖。
- **组件级**：明细执行，依托组件维度，所有责任、流转、依赖、统计均按组件隔离。
- **强约束**：项目级专题 / 活动仅可聚合项目级普通活动；组件级专题 / 活动仅可聚合组件级普通活动；**禁止跨颗粒度聚合、跨颗粒度下发、跨颗粒度统计**。
- **落地校验**：组件勾选控件随所选活动 / 专题的颗粒度**物理启停**；前端置灰控制 + 后端接口双重校验，接口层对跨颗粒度组合直接拒绝并返回明确错误码；数据库层以 CHECK 约束兜底（`component_id` 与 `granularity` 的一致性）。

#### 【铁律 #2 状态建模】

- 后端采用**独立状态枚举字段**存储，前端展示状态与后端枚举 1:1 对应，**禁止用布尔字段拆分状态**。
- 严格区分**可编辑内容 / 流转必填内容 / 审核联动内容**。
- 全系统状态枚举以**第 3 章**为唯一定义处：工单 9 态 / 工序 5 态 / 活动 3 态 / 问题 4 态 / 风险 6 态 / 审核 4 态 + 时效标记 3 档 + 工序配置状态 2 态。
- 任何模块仅可引用，不得重复定义、不得自行扩展状态值；枚举值一经发布，前端展示文案同步锁定。
- 状态枚举值**禁止在业务表中以多布尔字段（`is_closed` / `is_voided` / `is_rejected` / `is_passed` 等）共存分拆表达**。
- 状态变更的唯一驱动因子为「**执行反馈达标 + 审核结果**」。

#### 【铁律 #3 快照机制】

- 任务下发瞬间**深拷贝**固化活动配置 JSON 至 `task.snapshot` 字段（深拷贝，不引用）。
- 后续活动 / 工序 / 拓扑 / 准出 / 校验 / 模板任何修改均**不影响存量任务**，配置变更仅对新任务生效。
- 快照与活动流程版本 **1:1 绑定**；工单流转无模块自定义特殊规则，所有解锁 / 阻塞 / 闭环判定仅以快照配置为唯一依据。
- 工单快照**禁止被任务快照回填覆盖**。

#### 【铁律 #4 准出规则双因子】

工序准出由两道布尔因子独立决定流转闭环：

- **因子 A**：`must_audit`（是否需审核）→ 决定是否走「执行 → 审核 → 闭环」链路；
- **因子 B**：`must_submit_deliverable`（是否需提交交付件）→ 决定是否校验交付物齐全。

四种准出现实场景（穷举）：

| 场景 | 因子组合 | 闭环条件 |
| --- | --- | --- |
| 1 | A0 ∩ B0 | 执行人完成 + 准出内容填报 → 自动闭环解锁后置 |
| 2 | A0 ∩ B1 | 交付物齐全 + 准出内容填报 → 自动闭环解锁后置 |
| 3 | A1 ∩ B0 | 审核通过 + 准出内容填报 → 闭环解锁后置 |
| 4 | A1 ∩ B1 | 审核通过 + 交付物齐全 + 准出内容填报 → 三项全满足方可闭环解锁后置 |

- 交付物标准模板为**可选项**，仅作作业参考，**不参与流转校验判定**。
- 两个因子的取值**必须取自 `task.snapshot`（工单固化快照），而非实时活动配置**——这是四象限判定的唯一前提。
- 详版判定器见 18.2。

#### 【铁律 #5 人员唯一数据源硬约束】

- 组件负责人、组件参与人 / 任务执行人、任务参与人 / 审核人，**仅允许从「已激活」状态的系统成员中选取**。
- 禁止手动输入非系统人员、禁止非激活成员参与任务绑定。
- 人员字段一律为**成员 ID 外键 + 冗余姓名快照**（用于历史留痕），**不得存字符串自由文本**。

#### 【铁律 #6 组件启用状态硬约束】

- 已停用组件**不参与新任务下发、不参与批量筛选、不被拓扑关联**。
- 已停用组件的**存量历史任务正常保留、可查、可流转**。

#### 【铁律 #7 颗粒度流转隔离硬约束】

- 组件级工单**仅依赖同组件自身前置工序**，不同组件工单互不阻塞、互不依赖、互不干扰。
- 项目级工单**无组件维度依赖**，仅遵循活动工序拓扑流转。
- 任意前置工序未达标（准出未填 / 交付物缺失 / 审核打回 / 未审核），系统**强制锁止后置工序**，无法执行、无法跳过、无法提前闭环。

#### 【铁律 #8 权限隔离】

| 角色 | 可视范围 |
| --- | --- |
| 普通执行人 | 仅可视本人负责 / 本人参与工单 / 问题 / 风险 |
| 审核人 | 仅可视本人待审 / 已审 / 打回工单 |
| 组件 / 项目负责人 | 可视管辖范围内全量数据 |
| 数据迁移管理员 | 全局可视，无权限隔离 |

**实现口径**：所有列表查询与看板统计，**统计前先做权限过滤**（数据范围 SQL 前置），杜绝「先统计后过滤」导致的数据泄露。

### 4.2 前端工程落地铁律 #9 ~ #19

> **#9~#13** 源自批次 1 实际缺陷归因（页面白屏）；**#14 / #15** 源自批次 2（活动管理）；**#16** 源自批次 2 验收实证（画布降级路径可验证性 + L2 假白屏）；**#17 / #18** 源自批次 3（任务发布 / 流转引擎 / 进度反馈）；**#19** 源自端到端测试后的人工验收反馈。**十九条约束力完全等同**，且随第 4 章恒加载。

#### 【铁律 #9 入口装配完整性】

- 全应用唯一的挂载入口（`index.html` → `main.tsx`）必须**一次性装配完毕**全部全局容器：路由容器 → 主题 / 国际化 Provider → 应用级 Provider（消息 / 弹层）→ 全局状态 Provider → 根组件。
- **禁止把 Router / Provider 下沉到子组件或页面内**：任何「某页面能打开、另一页面白屏」的现象，根因必在入口装配缺失。
- 装配顺序固定（由外到内）：路由容器 → ConfigProvider（主题 + locale）→ App（消息容器）→ 全局 Store → 业务根组件。
- **自检问题**：把所有路由逐个打开一遍，是否每一个都能渲染出内容？只要有一条路由 `#root` 为空，即判定入口装配不完整。

#### 【铁律 #10 路由容器选型与硬约束】

- 使用 react-router 的 `<Routes>` / `useRoutes` / `useNavigate` / `<Outlet>` 等 API 时，**祖先链上必须存在 Router 容器**，否则运行期抛 `useRoutes() may be used only in the context of a <Router> component` 并导致整树挂载失败。
- 本系统默认采用 **`HashRouter`**：原型与预览场景常以 iframe 嵌入或经非根路径代理访问，hash 路由不依赖 `history.pushState` 与服务端重写回退，稳定性优先。
- **禁止 `<Routes>` 裸用**；禁止在同一应用内混用多种 Router 类型。
- **自检问题**：入口文件里能否搜到 Router 容器包裹？搜不到即违规。

#### 【铁律 #11 闸门单一出口（集中实现）】

- 铁律 #1~#8 的判定逻辑（颗粒度隔离、状态枚举、快照、准出、人员数据源、组件启用、权限过滤）**只允许在唯一一处实现**。
- 页面 / 组件层**禁止二次判断业务铁律**（禁止在页面里写 `if (member.status === 'ACTIVE')` 之类的过滤），只允许消费已过滤结果。
- 选择器类数据（人员下拉、组件下拉、角色下拉）必须与异步 API **同源同闸门**，禁止两处各写一份过滤逻辑。
- 数据库侧用**契约视图**承载唯一出口（如 `v_member_option` / `v_component_available` / `v_role_option`），**视图定义即闸门定义**。
- 派生字段（`task_status` / `flow_progress` / `deadline_status` / `block_reason` / `close_progress`）**只许闸门重算**，禁止页面自行计算。
- **自检问题**：把闸门实现处整体替换为真实 HTTP 调用，页面是否需要改动？需要改动即说明闸门被分散了。

#### 【铁律 #12 契约错误码 1:1】

- 每个校验项对应**唯一专属错误码**，禁止多个校验项复用同一错误码。
- 错误码的语义必须与校验项名称一一对应。反例：把「必须且仅可绑定 1 名负责人」与「负责人必须为已激活成员」合并成一个 `OWNER_INACTIVE`，会让调用方无法区分是漏填还是填了停用成员。
- 校验顺序固定：**存在性 → 数量约束 → 状态约束**（先判「有没有」，再判「几个」，最后判「合法不合法」），保证同一非法入参每次返回同一错误码。
- 错误码常量**集中定义，前后端共用同一份命名**。

#### 【铁律 #13 交付可达性（构建通过 ≠ 运行期可用）】

- **`tsc --noEmit` 通过、`vite build` 成功，均不构成「可交付」的证据。** 本系统已实际发生「类型检查 0 错误 + 3050 模块构建成功 + 页面完全白屏」的案例。
- 任何模块交付前必须完成 **L1 + L2 双层验收**，任一层未通过不得声明完成：
  - **L1 数据层 / 闸门验收**：业务断言，验证铁律 #1~#8 的判定结果正确。
  - **L2 渲染冒烟验收**：拿**真实生产构建产物**在 DOM 环境（jsdom）中实际挂载，逐路由断言 `#root` 渲染出内容且运行期无未捕获异常。
- L2 的判定基准是**最终交付形态**（生产产物），不是开发态源码；在源码层做的任何 mock 都不算数。
- 一切「编译期无提示、仅运行期暴露」的缺陷（缺 Provider、缺 Router、循环依赖、未定义的运行时 API）**只能由 L2 捕获**，故 L2 不可省略、不可用「人工点一下」替代。
- **自检问题**：有没有一条断言，是在真正挂载组件树之后才成立的？若全部断言都停留在数据层，则验收不完整。

#### 【铁律 #14 可空参数语义显式化（「不校验」≠「校验空集」）】

- 判定器 / 校验函数的「名单类可选参数」，必须让调用方能够**显式表达「本次不做该校验」**。
- 反例：`validateGraph(ids, edges, limit, noPreIds: string[] = [])` 语义含混——传 `[]` 是「已开启校验且无人被标记」，会把所有独立节点判为「未标记」而整体拦截；调用方传 `undefined` 想「跳过校验」，却被默认值退化成 `[]`，结果静默触发拦截。
- 正确做法：默认值取 `null`（或独立布尔开关），**`null` = 跳过校验，`[]` = 校验且空集**，二者语义必须可区分；函数注释中写明差异，并补一条断言锁死该语义。
- **自检问题**：这个可选参数不传 / 传 `undefined` / 传空数组，三种写法的行为差异是否被明确设计并测试过？

#### 【铁律 #15 固化载荷自描述（快照 / 模板 / 版本化配置）】

- 任何被「冻结」后长期留存的载荷（任务快照、模板包、版本化配置），必须**自描述**：自带**版本号、归属主体标识、生成时间**。
- 反例：快照载荷只写业务字段，版本号仅存在于外层 `activity_snapshot` 记录；下游取数得到 `topology_version === undefined`，无法回答「本任务基于哪个版本冻结」，违背铁律 #3 的可追溯性。
- 约束：载荷内版本号与外层记录版本号必须**恒等（1:1）**，且在同一次发布事务中一并写入，**不允许事后补齐或反查**。
- **自检问题**：把这份载荷单独导出发给第三方，不查库能否回答「它是谁、什么版本、何时冻结」？

#### 【铁律 #16 降级路径可达性（「只在真机上验过」≠「验证过」）】

- 凡是为「主路径不可用」而设计的**降级 / 兜底 / 异常分支路径**（画布降级视图、加载失败兜底、状态机异常分支、超时与重启分支等），都必须在**自动化环境（无头 DOM / jsdom）中可被触发并断言**。
- 强制要求：
  - 降级路径必须是**能力探测驱动**（运行时探测依赖能力是否具备），且降级原因**回显到界面**，禁止静默吞掉异常；
  - 为每条降级 / 异常分支至少写一条**可在自动化环境触发**的断言，并在断言名中显式标注该分支；
  - 确属物理上无法自动化的指标（如拖拽帧率、真机触感）必须**单独登记为「人工验收项」**，且不得以该登记替代分支可达性断言。
- **自检问题**：把主路径打断（如让画布引擎加载失败），自动化测试能否跑到降级分支并断言它成立？若答案是否，则该降级路径未验证。

#### 【铁律 #17 条款可实施性（「声明了规则」≠「可实现」）】

本文件中凡出现下列五类**指向算法的表述**，条款必须同时给出可执行的落地定义，否则视为条款未完成、不得据此开工：

| 类型 | 表述特征 | 必须补足的内容 |
| --- | --- | --- |
| **优先级类** | 「A 优先于 B」「XX 优先执行」 | 优先级判定式、判定发生的**时机**、判定结果向下游的**传播 / 回写路径** |
| **自动类** | 「自动带出」「自动同步」「自动归集」「自动派生」 | 取值来源、计算式与**触发时机** |
| **派生所属类** | 同一实体多个源状态同时变化时的归一 | 显式指定**派生主状态的取值依据与优先级**，禁止让实现方从直觉推导 |
| **互斥派生标记类** | 「标记 A 与数据 B 互斥、A 应由 B 派生」 | 显式声明该标记是**派生值而非独立可编辑字段**，给出判定式、**计算时机**、派生值与显式校验的**先后顺序** |
| **判定器复用类** | 判定依赖某状态 | 必须写明「**该状态在本步之前已写入**」 |

**典型反例（4 项）**：① 「专题流转优先级高于活动原生工序流转」只声明优先级、未给跨活动解锁传播算法，导致后置子活动在前置未闭环时即被解锁；② 「前置全闭环后解锁」未**并列**声明「无前置 → 启动即解锁」与「其余保持 `LOCKED`」，实现方把两条合并为一个 OR 条件，导致全部工序启动即 `EXECUTING`、`LOCKED` 永不可达；③ 未声明「工序级事件之后必须重算工单主状态」，派生值被遗忘，提审 / 审核后主状态停在「执行中」；④ 未声明打回后主状态的派生优先级，主状态回落为「执行中」而非「审核打回」。

**典型反例（阻塞级）**：⑤ 只写「支持设置『无前置任务』」，未声明 `is_no_predecessor` 的权威来源；实现方按独立字段处理（新建工序默认 `true`），而保存拓扑时又按库内既有标记先校验冲突，导致**新建活动的任何连线在首次保存时必然报冲突、依赖永远配不上**，页面文案与实际行为自相矛盾。

- **双向断言强制**：凡声明了派生关系，验收断言必须**双向齐备**——「非法必拒」（派生值与显式校验冲突时必须拒绝）**加**「合法必通」（合法输入必须被接受且派生值被正确重算）。只验单向即视为验证不完整。
- **自检问题**：把本条条款单独交给一个不了解业务的实现者，他能否不追问、不猜测地写出代码？该标记的权威来源（派生 vs 独立字段）条款是否显式声明过？只要存在需要「揣摩」的措辞，该条款即不完整。

#### 【铁律 #18 验证有效性（「断言通过」≠「验证有效」）】

一条断言只有在**失败时能自证归因**、且**运行前其被判对象处于可分辨状态**时才有效。下列五类属**无效断言（假通过）**，一律不得计入验收证据：

| 类型 | 特征 |
| --- | --- |
| **恒真断言** | 被断言对象在运行前已处于目标态，操作与断言双双空转（异常重启的恢复点之后本无可重置工序，「重置」分支恒真通过） |
| **死枚举断言** | 被依赖的状态值从未有实体或被用例构造，断言永不失败（`WAIT_PRE` 与 `CLOSED` 在种子中均无实体，导致「跨活动流转」与「闭环 → 归档」两条关键链路整体未被验证） |
| **参数缺失断言** | 用例未按接口契约给全必填字段，断言因**自身抛错**而失败，无法区分「业务不符合预期」与「用例参数没给对」 |
| **口径不明断言** | 期望值由验收方自行理解得出，不可计算、不可复核（专题矩阵拆分误用组件范围并集做笛卡尔积，未与各活动 `component_scope` 取交集） |
| **单向断言** | 闸门规则只断言「非法必拒」，未配对「合法必通」——非法路径的错误码断言全绿，而合法路径被同一闸门误杀却无人发现。曾出现「无前置一致性冲突必拒」断言长期全绿，但「给无前置工序配置前置依赖必须被接受并派生标记」的正向断言缺失，导致依赖配置恒冲突的**阻塞级缺陷漏网** |

- 每条断言必须能回答四个问题：① 失败时是否唯一指向某个业务判定（可自证归因）？② 被判对象在操作前是否确实处于**非目标态**？③ 其依赖的枚举值 / 种子实体是否真实存在（可达）？④ 单独运行本用例与全量运行的结论是否一致（相互隔离）？
- **正向可达性断言族（强制）**：L1 中每条「非法必拒」断言，必须存在至少一条与之一一配对的「合法必通」断言（同一规则的合法输入必须被接受、派生值必须被正确落库），两者构成双向闭环；仅有负向断言的闸门规则视为**未完整验证**。
- **强制要求**：逐条核对第 3 章枚举表，确认本模块用到的每个状态值都有实体或已被用例构造；**种子生成脚本须在产出前对铁律不变式做全量自检并打印结果**。
- **自检问题**：把这条断言中「真正会发生变化」的那一步删掉，它还会失败吗？若不会失败，即为恒真断言，必须重写。

#### 【铁律 #19 入口可发现性（「功能可达」≠「入口可发现」）】

- 每个模块的**核心能力**（高频、主链路功能），除在详情页 / 二级页签中可达外，必须在其**列表级入口**提供**显式直达动作**（操作列直达按钮 / 可点击统计），并支持页签深链（`?tab=`）定位；**禁止让核心能力只藏在「列表 → 详情 → 第 N 个页签」三级路径里被动等待发现**。
- 反例：工序管理与依赖配置功能一直存在且端到端测试早已驱动其闸门 API 跑通全链路，但唯一入口是列表「详情」按钮 → 详情页第 2/3 个页签，列表页只有被动的「N/M 已完善」统计列——**用户人工验收时判定「未发现活动工序的管理以及活动工序依赖关系的功能」**。自动化全绿不能豁免本铁律：**自动化验证的是能力可达，用户验收看的是入口可发现**。
- 强制要求：
  - 新模块交付前，须列出「本模块核心能力清单」，并逐项回答「用户从列表页几步可达？」——超过两步的须补直达入口；
  - 直达入口须带**功能说明 Tooltip**（用户不需要先点进去才知道按钮是什么）；
  - L2 渲染冒烟须对每个直达入口加**锚点断言**，入口缺失时冒烟必须失败。
- **自检问题**：假设一个新用户只看到列表页，他能否在不读文档、不逐个点详情的情况下发现本模块的全部核心能力？逐项在 L2 中有锚点断言背书吗？

### 4.3 工程基线执行细则（#9~#19 的执行层细则，非新铁律但强制）

- **渲染期副作用禁令**：React 组件的渲染函数体内**禁止执行任何副作用**——异步取数 / 订阅 / 计时器 / 手动 DOM 操作一律放进 `useEffect`；`useMemo` 只允许做**纯派生计算**。
  - 反例：在 `useMemo` 回调里 `void refresh()` 触发异步取数，StrictMode 与 jsdom 重负载下形成渲染期状态循环，单路由渲染挂起直至超时。
  - **自检问题**：把组件函数体从头到尾扫一遍，是否存在「调用即改变外部世界」的语句跑在渲染路径上？
- **枚举 / 类型单一声明**：TypeScript 类型、枚举常量与标签映射（`*_LABEL` / `*_ORDER`）只允许在**唯一声明处**定义（本项目为 `src/types/index.ts`），其他文件只 import；新增模块段落时**先全文检索同名符号**再落笔。
  - 反例：某模块段重复声明 `DeadlineStatus` / `DEADLINE_STATUS_LABEL`，与流转段冲突，触发约 30 个编译错误。
  - **自检问题**：新段落的每个类型 / 常量，是否都确认过「别处没有同名声明」？
- **状态机式 UI 视图切换必须可回到初始态**：凡以内部模式状态驱动多视图的组件（画布 / 表格切换、展开 / 收起、主 / 降级视图切换），**任何一次视图切换后组件必须能回到初始装配态**——切回需重新装配的视图时，必须显式走「重置 + 重装」路径（如自增 reloadKey 触发重装配），禁止只 `setMode(...)` 而不触发装配副作用。
  - 反例：拓扑画布「切换画布视图」从表格切回时仅 `setMode('pending')`，无任何重装机制，页面**永久停留在「正在装配…」**。
  - **自检问题**：把本组件的每种视图切换路径各走一遍再切回，是否都能恢复到与首次进入一致的状态？

### 4.4 工程配置基线（配套约定，强制）

- 工程内脚本读取文件，一律以**进程工作目录**（`process.cwd()`）解析路径；**禁止用 `import.meta.url` 定位源码同级目录**——打包后它会指向产物位置，必然读不到文件。
- TypeScript 项目工程配置：避免 `references` + `composite` 与 `noEmit` 混用（触发 TS6310）；本系统统一为单 `tsconfig.json`，构建脚本用 `tsc --noEmit && vite build`。
- 枚举显示文案（状态字典）**统一定义在类型模块**（`src/types`），主题模块只承载视觉 token；禁止交叉导入。
- **演示数据与库侧种子必须同源生成**：Mock 种子（`src/mock/*.ts`）为唯一事实源，DB 种子 SQL 由脚本转换产出，**禁止两份数据各自手工维护**。
  - **升级口径**：凡存在**闸门重算的派生字段**（如 `task_status` / `close_progress` / `deadline_status` / `block_reason`），种子 SQL 的生成源不得只取纯数据模块，而应取**运行时闸门库装载后的状态**（装载时已 `recomputeAll` 统一重算）。否则 SQL 里存的是占位初值、页面上是重算值，形成「同源却不同口径」的隐性漂移，且此类漂移**不会被类型系统或 L1 断言捕获**。
  - **种子自检必须前置**：种子生成脚本在写出 SQL 前，须对全部铁律不变式做一次遍历自检（颗粒度互斥绑定、状态枚举合法、终态时间戳齐备、闭环门槛成立、外键闭合、反例可达），**自检不通过即中止并列出违规记录**。种子是「未来所有断言的地基」，地基脏了会让后续所有验收结论失真。
- **同一文件的多处改动必须逐条串行下发并即时复核（工具链纪律）**：并行下发对同一文件的多个编辑存在静默覆盖风险（实际发生过多次「报成功但内容未落盘」），故改动后须用检索命令回读关键锚点确认落盘。

## 9 模块 4 · 活动管理（需求 3.4 / 提示词原 §7）

### 9.1 模块定位

活动为系统**唯一任务标准模板来源**，所有任务下发必须基于已启用标准活动生成。系统统一将活动分为**普通基础活动**、**专题聚合活动**两类，通过「活动类型」标签做全局唯一区分；**专题本质为可聚合多活动、自定义跨活动流转的高阶特殊活动**，统一纳入本模块管控，无需独立模块维护。

严格区分**项目级活动 / 组件级活动**双颗粒度，两类活动共享基础属性、快照机制、任务流转规则，仅在**生命周期必填约束、聚合能力、流转优先级**存在差异化适配。本模块另提供活动模板导入 / 导出能力，支持跨项目标准作业模板快速复用。

**技术选型**：AntV X6 2.19.2 + @dagrejs/dagre 1.1.8（详见 7）。

### 9.2 功能实现（需求 ↔ 开发落点）

#### 9.2.1 活动基础管理（新增 / 编辑 / 启用 / 停用 / 查询）（需求 3.4.1）

**需求**

- 新增活动：支持自主创建两类标准活动，活动编码系统自动生成；必填项包含活动名称、活动类型（普通基础活动 / 专题聚合活动）、归属生命周期阶段、活动颗粒度、活动状态；其中**专题聚合活动的归属生命周期阶段为非必填项，普通基础活动该字段必填**。创建时间、更新时间默认取系统当前时间，无需手动录入。保存后生成对应类型的活动模板，初始状态默认为启用。
- 编辑维护：支持修改活动基础信息、工序内容、依赖关系、交付模板。
- 状态管控与下发约束：支持活动启用 / 停用切换，仅启用状态的普通活动、专题活动允许任务下发与聚合引用。
- 多维度组合查询：支持通过活动编码、活动名称、归属生命周期阶段、活动颗粒度、活动状态、创建时间区间精准检索筛选。
- 流程关联约束：所有后续任务发布、任务流转、工序执行管理，均严格沿用活动模块已配置的工序内容、工序流程、依赖规则执行。

**开发落点**

- 活动编码自动生成且规则可辨识：`ACT-PRJ-###` / `ACT-CMP-###` / `ACT-TPC-###`；**全局唯一、不可重复、不可修改**。
- 活动类型采用**可扩展枚举设计**：本期落地「普通基础活动（NORMAL）/ 专题聚合活动（TOPIC）」两类，后端枚举预留「审批类活动（APPROVAL）」「集成类活动（INTEGRATION）」扩展位——**本期前端不展示、不参与流转判定**，后续版本可直接启用，**无需重构活动模型与流转引擎**。
- 编辑维护的生效范围：活动、工序所有配置修改后**仅对未来新建任务生效**；已下发存量任务采用快照机制永久固化，不受后台配置变更影响。
- 状态管控：仅 `ACTIVE` 状态的普通活动、专题活动允许任务下发与聚合引用；`INACTIVE` / `OBSOLETE` 活动禁止新任务下发、禁止被专题聚合关联，**不影响历史存量任务**。
- **作废（OBSOLETE）为终态，须同时满足「三不准」**（对应缺陷 D-06）：**不可编辑、不可重新启用、不可重复作废**；对已作废活动执行任一写操作一律拒绝并返回同一语义错误码（`ACTIVITY_OBSOLETE_READONLY`），**不得静默重写、不得刷新其作废时间**。
- 颗粒度**不可变更**（创建后锁定）；组件级活动必须绑组件、项目级活动禁止绑组件。

#### 9.2.2 活动核心展示字段（列表 + 详情）（需求 3.4.2）

**需求**

- 基础字段：活动编码（系统自动生成、唯一不可修改）、活动名称、活动类型、归属迁移阶段（普通活动必填、专题活动非必填）、活动颗粒度（项目级 / 组件级）、活动状态（启用 / 停用 / 作废）、创建时间（系统自动赋值）、更新时间（系统自动赋值）。
- 业务字段：活动适用场景、活动执行目标、整体准入条件、整体准出说明、整体交付物清单。

**开发落点**：列表及详情统一展示上述字段，**无冗余自定义字段**。

#### 9.2.3 活动双颗粒度硬性定义与约束（需求 3.4.3）

**需求**

- **项目级活动**：不绑定任何业务组件，面向项目管理人员、项目统筹人员下发全局类作业任务，适用于全项目方案评审、整体环境准备、统一投产等项目统筹型工作，**无组件维度权责、无组件前置流转依赖**。
- **组件级活动**：基于组件最小颗粒度设计，绑定对应业务组件，作业权责、执行人、流转依赖、任务拆分**全部依托组件维度**；核心用于支撑组件维度精准作业、批量组件任务下发、组件级流程自动流转管控场景。
- **颗粒度绑定约束**：项目级专题 / 活动**仅可**聚合 / 关联项目级普通活动，组件级专题 / 活动**仅可**聚合 / 关联组件级普通活动，**禁止跨颗粒度关联绑定**。

**开发落点**：专题聚合设**四道闸门**（类型、颗粒度、状态、范围），候选范围必须与专题同颗粒度（铁律 #1）。

#### 9.2.4 工序拓扑依赖配置（需求 3.4.4）

**需求**

系统内置可视化工序拓扑画布，支持拖拽排序、节点配置、连线依赖，为单活动搭建完整工序流程。

- **拓扑节点定义**：单道工序为独立流程节点；节点展示固定字段：工序序号、工序名称、工序负责人角色、是否必选节点、当前配置状态；支持工序拖拽排序、自由布局、连线配置依赖关系。
- **单节点串行依赖**：当前工序仅配置单个前置工序，仅当前置工序完全闭环完成后系统自动解锁，适用于前后强依赖、串行执行的作业场景。
- **多节点聚合依赖**：当前工序可同时配置多个前置工序，需**所有前置工序全部闭环达标**方可解锁，适用于多前置条件汇聚、统一收尾的作业场景。
- **无前置并行节点配置**：准入环节支持设置「无前置任务」，该节点无任何前置依赖，活动启动后可直接执行；同一活动内支持配置多个无前置工序，实现多工序并行同步作业。
- **依赖校验判定依据**：后置工序解锁条件不做固定强制约束，完全沿用当前工序准出配置的两道自定义校验规则判定闭环（四种场景穷举见 18.2）。
- **交付物标准模板为可选项**，仅作作业参考，不参与流转校验判定。
- **拓扑展示形式**：横向标准流程图，清晰区分串行流程、并行汇聚流程；存在依赖关系的工序实线关联，独立无依赖节点单独展示；支持画布缩放、全屏预览、一键重置布局。
- **拓扑保存与快照规则**：拓扑新增、删除、排序调整、依赖关系修改后需手动保存生效；保存成功后生成对应活动流程快照；新下发任务基于最新拓扑流程执行，历史存量任务沿用原有快照。

**开发落点**

- ⚠️ **「无前置任务」标记的权威来源（阻塞级约束，对应缺陷 D-28）**

  `is_no_predecessor` 是**依赖连线的派生值，不是独立可编辑字段**：

  - **判定式**：`is_no_predecessor = 该工序在依赖表中无入边`（有入边 → `false`，无入边 → `true`）；
  - **计算时机**：`saveTopology` 保存时**必须先按连线重算标记并落库，再执行显式冲突校验**——顺序不可颠倒（先按库内既有标记校验，会使新建工序的默认标记与首次连线**恒冲突**，依赖永远配不上）；
  - **配对断言双向齐备**：非法（有入边仍标无前置）必拒（`TOPOLOGY_NOPRE_CONFLICT`）+ 合法（给原无前置工序配置前置依赖后标记自动派生为 `false`）必通。

- **拓扑合法性校验**：禁止自连、禁止重复依赖、禁止成环、禁止引用缺失节点、禁止超限（单活动 ≤ 30 节点），**非法连线即时提示并回滚**；校验顺序固定（铁律 #12）。
- **发布校验唯一出口**：严格校验统一由发布出口（`publishVersion → checkDraftGraph`）兜底，**同一规则不得在两处重复校验且语义不一致**（对应缺陷 D-07）。
- **画布降级兜底（能力探测驱动的设计内路径，铁律 #16）**：
  1. 画布渲染前必须执行**能力探测**，至少覆盖三类不可用场景——运行环境缺少 SVG 度量能力（如无头 / jsdom 环境下 `getBBox` 不可用）、渲染容器有效宽度或高度为 0、画布引擎自身加载或初始化失败；
  2. 探测不通过即以**表格化配置视图**降级承载（工序列表 + 前置节点多选 + 依赖连线编辑），保证配置能力不丢失；
  3. 降级**原因必须回显到界面**（如工具条提示「当前环境不支持图形画布，已切换为表格化配置」），并保留手动重试入口；**禁止静默吞掉异常**；
  4. 降级是**设计内路径**而非补丁：降级视图与画布视图**共享同一份校验与保存出口**，两条路径产出的数据必须完全等价（均过同一闸门）；
  5. 降级路径须有**可在自动化环境触发**的断言，不得仅做真机人工验证。
- **配置视图可深链**：活动配置工作台须支持页签级深链（如 `?tab=basic|process|topology|topic|version`），使每个页签（含降级视图所在页签）可被直接访问、分享与自动化验证；**深链参数非法时回退至默认页签而非白屏**。
- **拓扑保存必须生成快照版本**；快照载荷必须**自描述**（含 `topology_version` + 活动标识 + `frozen_at`），且与外层记录版本号 **1:1 恒等**，同一次发布事务中一并写入（铁律 #15，对应缺陷 D-04）。
- **视图切换回归**：画布视图 ↔ 表格视图任意方向切换后均可回到正常装配态；从表格切回画布必须**显式触发重装配**，禁止停留在永久 pending（对应缺陷 D-29b）。

#### 9.2.5 工序标准化配置（准入 / 准出 / 角色 / 模板）（需求 3.4.5）

**需求**

单工序支持精细化**双向配置（客户方 / 金科方）**，所有字段固化标准，作为任务执行、反馈、审核、流转的唯一依据：

- **准入配置**：前置输入条件、前置依赖说明、前置所需资料清单；支持设置「无前置任务」，该工序为独立直达执行节点，无需依赖任何前置工序闭环即可解锁执行，支持多工序并行作业。
- **执行配置**：执行角色、参与角色、标准执行步骤、作业指南、注意事项。
- **准出配置（核心可自定义校验规则）**：工序必须配置准出内容、准出交付物清单、合格判定规则；交付物标准模板为参考性可选项，仅用于作业指导参考，不强制绑定提交校验。系统支持自定义两道校验规则：① 是否需审核 ② 是否需提交交付件。支持灵活适配场景：无需审核、无需提交交付件的工序，执行人完成工序执行操作后，系统自动判定工序闭环，直接自动跳转解锁下一道工序。
- **工序约束**：所有准出内容、交付物为任务进度反馈必填项，缺项无法完成工序闭环、无法解锁后置节点。

**开发落点**

- **准出三要素必填**：准出内容、准出交付物清单、合格判定规则**三项齐备**方可发布；工序名称 / 序号唯一；角色引用走闸门（仅 `ACTIVE` 角色）；两道因子**独立可置位**。
- 「无前置任务」标记为**依赖连线的派生值（非独立字段）**，随拓扑保存自动重算（见 9.2.4）。
- 工序配置状态（`DRAFT` / `READY`）为**辅助标记，非业务状态、不参与流转判定**（见 3.9）。
- **活动至少保留 1 道工序**；删除工序后序号重排 `1..n` 连续。
- 无模板工序**允许保存发布**（模板为选填项）。

#### 9.2.6 活动模板导入 / 导出（跨项目复用能力）（需求 3.4.6）

**需求**

- **导出能力**：支持单活动 / 批量活动导出为标准化模板包（JSON 或 Excel），内容包含活动基础属性、工序配置、拓扑依赖关系、准出校验规则、交付物清单与模板；**导出内容不含项目、组件、人员等实例数据**，保证可跨项目复用。
- **导入能力**：支持上传模板包批量创建活动；系统自动执行**四类校验**——字段完整性、活动编码冲突、颗粒度一致性、工序依赖合法性（缺失节点引用、环路依赖）；校验通过后生成「停用」状态的活动草稿，人工复核确认后启用，避免脏模板直接进入生产。
- **冲突处理策略**：活动编码冲突自动重新生成新编码并提示；活动名称冲突提示人工确认是否覆盖；工序依赖引用缺失节点或形成环路时**直接拦截导入并输出异常明细**。
- **权限与留痕**：导入、导出权限**仅数据迁移管理员**拥有；所有导入导出行为记录操作人、操作时间、模板包摘要，全程可溯源。
- **适用场景**：跨项目标准作业模板复用、多项目并行投产时的活动快速搭建、历史项目经验沉淀为可复用模板。

**开发落点**

- **格式落地范围声明**：本期落地 **JSON 通路**（导出 / 导入双向可用）；**Excel（.xlsx）通路延后统一实现**——此处显式声明，避免被误判为遗漏。导入侧须按格式分流（**同一套四类校验逻辑复用于两种格式**）。
- ⚠️ **脱敏验收口径（必守）**：**不得以「导出结果中不含某字段名」作为脱敏通过依据**；必须以**库内当前实际存在的项目 / 组件 / 人员实例标识清单**逐项比对导出内容的序列化结果，**命中任一实例标识即判定脱敏失败并拒绝导出**（错误码 `EXPORT_INSTANCE_DATA_LEAK`）。模板内的角色、阶段等字典类引用以**编码**表达，不携带实例主键。
- 导入落库为 `INACTIVE` 草稿；组件范围待人工复核。

#### 9.2.7 模块全局约束条件（需求 3.4.7）

**需求**

- 活动编码全局唯一，不可重复、不可修改。
- 停用活动不允许新增工序、不允许被专题聚合关联、不允许下发新任务。
- 单活动工序依赖仅允许同活动内配置，跨活动依赖统一在专题聚合活动拓扑中配置，职责边界严格拆分。
- 组件级活动下发任务严格遵循组件前置依赖，项目级活动无组件依赖约束。
- 活动基础配置、工序配置、聚合拓扑配置修改后，仅对后续新下发任务生效；已下发存量任务全程快照固化。
- 所有工序必须配置准出内容与交付物合格规则；交付物标准模板为选填项，无模板工序允许保存发布。
- 专题聚合活动仅可聚合同颗粒度普通活动，禁止跨层级聚合。
- 专题聚合活动无生命周期阶段强制约束，可独立于迁移阶段配置跨阶段聚合流程。

**开发落点**：以上八条全部转为模块铁律（见 9.4），并在 L1 断言中逐条落地。

### 9.4 模块铁律

- 活动编码**全局唯一、不可修改**。
- 停用（INACTIVE）/ 作废（OBSOLETE）活动**不允许新增工序、不允许被专题聚合关联、不允许下发新任务**（铁律 #6 同理）。
- 单活动工序依赖**仅允许同活动内配置**；跨活动依赖一律在专题聚合拓扑中配置。
- 所有工序必须配置准出内容与交付物合格规则；交付物标准模板为选填。
- 专题聚合活动**仅可聚合同颗粒度普通活动，禁止跨颗粒度聚合**（铁律 #1）。
- 专题聚合活动无生命周期阶段强制约束。
- 拓扑保存**必须生成快照版本**；配置修改仅对新任务生效（铁律 #3）。
- 准出两道校验因子的表述必须统一为「是否需审核」「是否需提交交付件」，**禁止变体**（第 5 章）。
- 作废活动「三不准」：**不可编辑 / 不可重新启用 / 不可重复作废**。
- `is_no_predecessor` 为**派生值**，权威来源是依赖连线；保存顺序为「先派生落库 → 再显式校验」（铁律 #17）。

### 9.5 上下游接口契约

- **输入 ← 角色管理**：工序负责人角色、执行角色、参与角色下拉唯一数据源。
- **输出 → 任务发布**：活动列表（按颗粒度 / 类型 / 状态筛选）、活动拓扑与工序配置快照源、专题聚合关系、活动标准工期。
- **输出 → 任务流转引擎**：拓扑版本号 + 工序依赖 + 准出校验配置（写入 `task.snapshot`）。
- **输出 → 数据看板**：活动类型标签（区分普通 / 专题）、活动状态、归属生命周期阶段。

### 9.6 落地产物

- **DB**：`activity` / `activity_process` / `activity_topology` / `activity_snapshot` / `activity_template`（导入导出包元数据）等 9 张表 + 3 个契约视图。
- **API**：`/api/activity`、`/api/activity/{id}/topology`、`/api/activity/export`、`/api/activity/import`、`/api/activity/{id}/publish-status`。
- **页面**：活动列表、活动详情（配置工作台，支持 `?tab=` 深链）、工序拓扑画布、工序配置面板、模板导入导出页。
- **闸门实现**：`src/api/activity.ts`（活动域唯一闸门出口）+ `src/store/ActivityStore.tsx`（不承载业务判定）。
- **路由**：`/activity`（活动列表 = 系统唯一任务标准模板库）、`/activity/:activityId`（配置工作台）。

### 9.7 验收要点

- 拓扑画布绘制含环依赖时被拦截并回滚，提示明确。
- 30 节点画布拖拽流畅度 ≥ 50 FPS（真机指标，登记为人工验收项）；**画布不可用场景（无 SVG 度量能力 / 容器零宽 / 引擎加载失败）必须探测到并降级为表格化配置视图，且该分支有自动化断言**（铁律 #16）。
- 活动配置工作台各页签支持深链直达，非法深链参数**回退默认页签而非白屏**。
- 【**入口可发现性**·铁律 #19】工序配置与工序拓扑为本模块核心能力，必须在**活动列表操作列**提供「工序」「依赖」直达按钮（带功能说明 Tooltip，深链 `?tab=process` / `?tab=topology`），「N/M 已完善」统计列可点击直达；L2 对两个直达入口有**锚点断言**（缺入口即冒烟失败）。
- 【**视图切换回归**·执行细则】拓扑组件画布视图 ↔ 表格视图任意方向切换后均可回到正常装配态；从表格切回画布必须显式触发重装配，禁止停留在永久 pending。
- 【**双向断言**·铁律 #17 / #18】无前置标记派生语义双向断言齐备：有入边仍标无前置**必拒** + 合法连线**被接受且标记派生正确**。
- 作废活动「三不准」：不可编辑 / 不可重新启用 / 不可重复作废。
- 修改某活动工序配置后，已下发工单的流转逻辑不变；新建工单按新配置执行。

## 10 模块 5 · 任务发布（需求 3.5 / 提示词原 §8）

### 10.1 模块定位

本模块为系统**唯一正式任务工单下发入口**，支撑任务台账新增、编辑维护、多维度查询、单发 / 批量下发全流程能力。所有单次、批量生成的组件任务，严格遵循活动管理模块定义的工序拓扑依赖、准出校验规则、流转解锁机制执行，保证**批量任务与单条任务流转逻辑统一、标准统一、约束统一**。

### 10.2 功能实现（需求 ↔ 开发落点）

#### 10.2.1 模块基础能力（新增 / 维护 / 查询）（需求 3.5.1）

**需求**

- **任务新增下发**：支持两种正规任务来源——普通基础活动直接下发、专题聚合活动下发；严格区分项目级、组件级任务，遵循颗粒度匹配约束，**禁止跨颗粒度下发任务**。支持单任务指定多组件绑定、按组件范围批量生成任务；下发瞬间自动生成独立工单，固化任务快照。
- **任务台账维护**：仅数据迁移管理员拥有任务基础信息编辑、作废、补录权限；任务下发后工序流程、校验规则、拓扑依赖沿用快照固化内容，**不可回溯修改**；仅支持临时调整本次任务执行人、备注信息，不影响活动原生标准配置。**已完结、已归档任务禁止任何编辑操作**。
- **多维度组合查询**：支持通过任务来源（活动 / 专题）、关联专题名称、关联活动名称、任务颗粒度、所属项目、所属事业群、绑定组件、任务状态、创建时间区间、执行人进行精准筛选与检索；支持列表快速筛选、导出台账。

**开发落点**

- **下发白名单闸门**：仅 `ACTIVE` 活动可下发；停用、作废的标准模板禁止生成新任务。
- **任务作废口径**：未终态工单同步作废并留痕；已归档工单保留历史。
- 任务下发 / 台账维护权限**仅数据迁移管理员**（铁律 #8）；普通成员只读。
- 已闭环 / 已归档任务禁止任何编辑。

#### 10.2.2 任务列表与详情核心展示字段（需求 3.5.2）

**需求**

- **基础归属字段**：任务编号、任务名称、任务颗粒度（项目级 / 组件级）、活动类型（普通活动 / 专题活动）、活动名称、所属项目、所属事业群、绑定组件（组件级任务展示）。
- **责任人员字段**：默认执行人、当前执行人、任务参与人、创建人、创建时间。
- **状态流程字段**：任务整体状态、当前所处工序、已完成工序数 / 总工序数、闭环进度、审核状态。
- **规则溯源字段**：任务快照版本、下发依据（活动拓扑版本）、流转约束说明。

**开发落点**：以上为标准化字段，无冗余。

#### 10.2.3 单发任务实现逻辑（单任务多组件）（需求 3.5.3）

**需求**

- **颗粒度与组件勾选控件联动规则（强制约束）**：任务下发页面的「组件勾选」控件严格随所选活动 / 专题的颗粒度**动态启停**，禁止越界组合：
  1. **项目级活动 / 专题**：组件勾选控件整体**物理禁用**（置灰且不可点击），无需也无法绑定组件，下发后仅生成 **1 张项目级工单**；
  2. **组件级普通活动**：组件勾选控件**必填**，支持单选或多选（多选即「单任务多组件」），下发后按「组件」维度拆分为 N 张组件级工单；
  3. **组件级专题聚合活动**：组件勾选控件**必填**，可选组件范围由该专题所聚合普通活动的组件范围共同决定（默认取并集，允许人工裁剪），下发后按「**普通活动 × 组件**」二维矩阵拆分工单。
- **下发规则**：选择指定活动 / 专题后，手动勾选一个或多个组件完成任务绑定，系统按勾选组件维度自动拆分多张独立组件工单，各工单**数据隔离、权责隔离、流转隔离**。
- **人员匹配规则**：每张组件工单自动读取对应组件预设的负责人、参与人作为默认执行人；支持单次任务临时微调执行人，微调内容仅当前工单生效，不改动组件基础配置。
- **流转适配规则**：所有拆分后的组件工单，完全沿用所选活动的工序拓扑结构、依赖关系、准出自定义校验规则执行流转。

**开发落点**

- ⚠️ **矩阵拆分判定式（必须按此计算，口径可复核）**

  ```
  工单集合 = { (普通活动 A, 组件 C) | A ∈ 专题被聚合的普通活动集合，
                                    且 C ∈ A.component_scope ∩ 本次勾选的组件集合 }
  ```

  即**每个组件只参与「其自身范围包含该组件」的那些普通活动**，**不得**用「专题组件范围并集」去笛卡尔积全部普通活动——否则会为某活动生成它并不覆盖的组件工单。
  同时须满足：同一 `(活动, 组件)` 组合**只生成 1 张工单**；工单数 = **各活动与其组件范围的交集个数之和**。

- ⚠️ **后置子活动的初始态**：若某被聚合活动 A₂ 在专题跨活动拓扑中依赖 A₁，而 A₁ 在本组件下尚未下发生成（或尚未闭环），则 A₂ 对应的工单**初始态必须为「待前置」且其工序为「未解锁」**。该规则是「专题跨活动流转优先级高于活动原生工序流转」的落地体现（算法见 11.2.3）。
- **双重校验**：前端置灰控制 + 后端接口双重校验，**接口层对跨颗粒度组合直接拒绝并返回明确错误提示**，杜绝脏数据。
- **组件闸门**：所选组件须在该活动关联范围内，且组件为启用状态（铁律 #6）。

#### 10.2.4 批量任务下发核心实现逻辑（重点）（需求 3.5.4）

**需求**

- **批量筛选范围**：支持多维度批量圈选组件，包含按所属项目、所属事业群、组件分组、自定义批量勾选；批量筛选后统一基于同一活动 / 专题批量生成任务。
- **批量工单拆分机制**：系统严格按**单一组件单一工单**原则拆分，筛选 N 个组件即生成 N 张独立组件工单，每张工单独立管控、独立执行、独立审核、独立流转。
- **批量任务流转统一约束（核心强制规则）**：所有批量生成的组件工单，统一继承当前所选活动的全套流转规则：
  1. **拓扑节点规则**：统一识别活动内无前置并行节点、单节点串行依赖、多节点聚合依赖；
  2. **工序解锁判定规则**：完全沿用各工序准出配置的两道自定义校验规则（是否需审核、是否需提交交付件），系统按工序配置自动判定闭环、解锁后置工序；
  3. **组件隔离依赖**：批量生成的各组件工单**仅依赖自身组件前置工序闭环**，不同组件的任务、工序不存在跨组件阻塞与依赖；
  4. **快照固化**：批量下发瞬间，所有工单统一固化当前活动拓扑、工序配置、校验规则快照。
- **批量人员自动匹配**：批量生成工单时，系统自动批量读取各组件预设责任人员，精准匹配至对应工单；支持批量统一调整执行人或单条单独微调。

**开发落点**

- **批量任务无简化、无特例流转规则**——流转解锁、工序闭环、阻塞判定逻辑与单发完全一致。
- 数据隔离：批量拆分后的所有组件工单，数据、状态、进度、审核记录完全隔离，统计、查询、归档均独立展示。

#### 10.2.5 模块全局约束条件（需求 3.5.5）

**需求**

- **下发前置约束**：仅启用状态的活动允许下发任务；停用、作废的标准模板禁止生成新任务。
- **颗粒度强约束**：项目级活动 / 专题仅可下发项目级任务，无组件绑定、无组件流转依赖；组件级活动 / 专题仅可下发组件级任务，**必须绑定有效、未停用组件**。
- **流转统一约束**：无论单发、批量生成的组件任务，流转解锁、工序闭环、阻塞判定逻辑完全一致，均以活动管理配置为唯一标准。
- **数据隔离约束**：批量拆分后的所有组件工单，数据、状态、进度、审核记录完全隔离。
- **快照固化约束**：所有单发、批量任务下发后**永久固化快照**，活动工序、拓扑、校验规则后续修改不回溯、不改动存量任务流转逻辑。
- **人员数据源约束**：批量、单发任务执行人**仅可从系统已激活成员中选取**，禁止非系统成员绑定任务。
- **停用组件约束**：已停用组件不参与批量筛选、不支持下发新任务，规避无效工单生成。
- **计划完成时间约束**：任务下发时**必填**「计划完成时间」，默认按活动配置的**标准工期（小时）**自动带出，允许下发人按投产窗口人工调整。

**开发落点**

- **计划完成时间闸门**：不得早于当前时间；缺省由活动标准工期自动带出。
- 专题聚合下发的**快照必须自适应到「工单级」**（见 10.4 铁律）。

### 10.4 模块铁律

- **下发瞬间必须深拷贝生成快照**（铁律 #3），禁止引用活动配置对象。
- **颗粒度约束**：项目级任务 `component_id` 必须为空；组件级任务 `component_id` 必填且组件状态为启用（铁律 #1 / #6）。
- **批量拆分严格遵循「单一组件单一工单」**；批量任务不得有简化或特例流转规则。
- 执行人仅可从**已激活成员**中选取（铁律 #5）；临时调整执行人**不回写**组件基础配置。
- 已完结、已归档任务**禁止任何编辑操作**。
- 任务下发时「计划完成时间」必填，且默认值来自活动标准工期。
- ⚠️ **专题聚合下发的快照必须自适应到「工单级」**（对应缺陷 D-22）：专题矩阵拆出的每张工单，其 `snapshot_json` 必须取自**被展开的那一个普通活动**的快照（**而非专题活动自身**），并把 `topic_activity_ids` 与 `aggregate_edges` 挂入载荷；`sub_activity_id` 显式记录被展开的普通活动 ID。否则工单无法回答「我执行的是哪套工序」，跨活动解锁也无从判定（铁律 #15）。
- ⚠️ **下发即冻结，禁止回填**：工单快照一旦写入不得被任务快照或后续配置回写覆盖；**专题工单尤须防止「被错误覆盖为专题活动快照」**。

### 10.5 上下游接口契约

- **输入 ← 活动管理**：活动基础信息、工序拓扑、准出校验配置、专题聚合关系、活动标准工期。
- **输入 ← 组件管理**：组件范围筛选接口、默认责任人匹配接口（**仅启用组件**）。
- **输入 ← 成员管理**：人员下拉唯一数据源。
- **输出 → 任务流转引擎**：工单列表 + 快照 JSON + 快照版本号 + 计划完成时间（**工单承接唯一入口**）。
- **输出 → 数据看板**：任务颗粒度、活动类型、绑定组件、任务状态。

### 10.7 验收要点

- 选择项目级活动时，组件勾选控件置灰不可点；后端接口对携带 component 的项目级下发请求返回明确错误。
- 单发选 3 个组件 → 生成 3 张独立工单，各自绑定对应组件默认执行人。
- 批量筛选 50 个组件 → 生成 50 张工单，彼此前置依赖互不干扰。
- 任务下发后修改活动工序配置，**存量工单流转规则不变**。
- 停用组件不出现在批量筛选结果中。
- 【专题矩阵】按「普通活动 × 组件**交集**」拆分，生成工单数 = Σ(各被聚合活动与其组件范围的交集个数)，**不得出现某活动覆盖不到的组件工单**。
- 【专题矩阵】专题跨活动拓扑中受前置约束的被聚合活动，其工单初始态必须为「**待前置**」、工序为「**未解锁**」。
- 【专题矩阵】每张工单的快照取自被展开的普通活动（`sub_activity_id` 非空），且**任务快照与工单快照不得互相覆盖**。
- 【**工程可达性**·铁律 #13】本模块对应页面路由在真实生产构建产物中可正常渲染：`#root` 渲染出内容（非白屏）、运行期无未捕获异常 / React 致命报错。
- 【**双层验收**·铁律 #13】本模块交付须同时通过 L1 数据层断言与 L2 渲染冒烟断言；仅 L1 全绿不得声明完成。

## 11 模块 6 · 任务流转引擎（需求 3.6 / 提示词原 §9 + §18 + §19）

### 11.1 模块定位

本模块为系统**任务工序自动流转核心驱动引擎**，承接任务发布模块生成的所有工单，统一负责全量工单的台账维护、状态迭代、工序流转、条件校验、数据查询全流程管控。所有单发、批量生成的项目级、组件级工单，流转流程、解锁条件、状态变更规则**完全遵循任务下发时活动固化的拓扑依赖、工序准入准出配置、自定义校验规则，无独立特殊流转逻辑**。

模块同时提供**任务时效（SLA）预警管控**能力，保障工单在投产窗口期（通常 1~3 天）内闭环。

### 11.2 功能实现（需求 ↔ 开发落点）

#### 11.2.1 模块基础核心能力（承接 / 维护 / 流转 / 查询）（需求 3.6.1）

**需求**

- **工单新增承接**：被动承接任务发布模块生成的所有有效工单，支持项目级、组件级两类工单同步接入；工单生成瞬间自动绑定对应活动快照版本、拓扑流程、工序校验规则，完成流转参数初始化，**无需手动配置流转规则**。
- **工单台账维护**：仅数据迁移管理员拥有台账维护权限，支持工单备注修改、异常作废、异常重启流转操作；所有工单核心流转规则（工序顺序、依赖关系、校验条件）固化快照，**不可手动篡改**。正常流转中的工单、已闭环归档工单禁止人工干预流转状态，杜绝手动改状态、跳过工序的违规操作。
- **全自动工序流转驱动（核心能力）**：依托活动预设拓扑结构与准出校验规则，自动判定工序阻塞、解锁、闭环，驱动工单状态、工序节点自动迭代，支持串行、并行、多节点聚合汇聚等全场景流转模式，**全程无人工手动操作**。
- **多维度角色差异化查询（权限可视逻辑）**：基于登录用户角色实现数据权限隔离展示；不同角色登录后工单列表、详情仅展示权限范围内内容；同时支持多条件组合精准检索、溯源查询、台账导出：
  1. **普通执行人**：仅展示本人负责、本人参与的相关工单，仅可查看自身权责范围内的任务进度、工序记录、交付物、审核结果，无法查看他人、其他组件及全局工单数据；
  2. **审核人**：仅展示本人负责审核的待审核、已审核、打回整改工单，可查看对应工单完整流转与交付详情，无权限查看非本人审核权责的工单；
  3. **数据迁移管理员**：拥有全局查询权限，可查看系统所有工单，无数据权限隔离限制。
- **通用多重查询条件**：所有角色均支持按工单编号、活动类型、活动名称模糊搜索、任务颗粒度、所属项目 / 事业群、绑定组件、工单整体状态、当前工序、创建时间区间进行精准筛选检索；支持流转进度、工序闭环记录、审核记录溯源查询；支持台账导出。

**开发落点**

- **负向闸门**：工单状态**禁止人工直改**——唯一驱动因子为「执行反馈 + 审核结果」。
- 管理员仅可执行备注修改、异常作废、异常重启；**正常流转工单不可人工干预状态**。

#### 11.2.2 流转核心展示字段（列表 + 工序详情）（需求 3.6.2）

**需求**

- **工单基础字段**：工单编号、工单名称、任务颗粒度、活动类型（普通活动 / 专题活动）、活动名称、快照版本号、所属项目、所属事业群、绑定组件（仅组件级工单展示）。
- **责任与时间字段**：默认执行人、当前执行人、创建时间、流转启动时间、最新更新时间、工单闭环时间。
- **整体流转状态字段**：工单整体状态（待前置、待接收、执行中、已暂停、审核中、审核打回、已闭环、已归档、已作废，共 9 态）、时效标记（正常 / 即将超时 / 已超时，**独立标记不改变主状态**）、总工序数、已闭环工序数、流转进度占比；其中「已暂停」为可恢复状态，「已归档」「已作废」为终态。
- **单工序流转字段**：工序序号、工序名称、工序状态、前置依赖状态、准出完成状态、交付物提交状态、审核状态、工序解锁时间、工序闭环时间。
- **流转溯源字段**：当前工单遵循的拓扑规则版本、各工序校验配置（是否需审核、是否需提交交付件）、流转阻塞原因（**无阻塞 / 前置工序未闭环 / 交付物缺失 / 审核未通过**）。

#### 11.2.3 全流程流转实现逻辑（需求 3.6.3）

**需求**

所有工单流转逻辑 **100% 继承任务下发时活动固化的配置内容**，包含拓扑节点规则、前置依赖、准出自定义校验规则；新老工单均遵循快照机制，互不干扰。

- **流转模式自适应规则**：
  1. **普通活动工单**：严格遵循活动内部工序拓扑依赖流转，无跨活动流转逻辑；
  2. **专题聚合工单**：优先遵循专题自定义跨活动流转规则，**专题流转优先级高于活动原生工序流转**，完全匹配专题配置的串行、并行、聚合依赖逻辑。
- **三大拓扑场景流转实现**：
  1. **无前置并行工序**：活动配置为「无前置任务」的工序，工单启动后直接解锁可执行，同一工单支持多道无前置工序同步并行作业；
  2. **单节点串行依赖**：仅前置单道工序完全闭环达标后，系统自动解锁当前工序，严格按前后顺序串行流转；
  3. **多节点聚合依赖**：配置多个前置工序的节点，必须所有前置工序全部闭环达标，系统方可解锁当前工序，实现多分支流程汇聚流转。
- **工序闭环 & 解锁判定实现（完全对齐活动准出配置）**：系统根据每道工序预设的两道自定义校验规则，自动判定工序是否闭环、是否解锁后置工序，无固定强制校验，四种场景全覆盖（详版见 18.2）。
- **组件级工单隔离流转机制**：所有组件级工单**仅校验当前组件自身的前置工序**，不同组件的工单、工序互不阻塞、互不依赖、互不干扰，完全实现单组件独立流转。项目级工单无组件维度依赖，仅遵循活动工序拓扑流转。
- **状态全自动迭代链路**：工单严格遵循「待前置 → 待接收 → 执行中 →（按需审核）→ 审核中 → 工序闭环 → 解锁后置工序 → 全工序完成 → 已闭环 → 已归档」全链路自动流转，审核打回自动退回「执行中」状态，支持多次整改重试，全程系统自动驱动，**禁止人工手动篡改状态**；其中「已暂停」「已作废」为管理员例外干预态，常规流转不进入。
- **状态机异常分支规则（四类）**：暂停、转交、超时、异常重启（详见 18.4）。

**开发落点**

- ⚠️ **跨活动解锁传播算法（「优先级高于」必须落到可实现算法，对应缺陷 D-21）**

  「专题流转优先级高于活动原生工序流转」若只声明优先级而无算法，专题拓扑形同虚设。实现要点四步：

  1. **建图**：自工单快照的 `aggregate_edges` 构建「被聚合活动 → 被聚合活动」的跨活动前置映射（`topicPreMap`），**键为活动而非工序**；
  2. **归集**：按同一工单所属的 `topic_activity_ids` 确定本工单涉及的全部子活动，**未下发生成的子活动视为「未闭环」**；
  3. **总闸门**：某工序可解锁 ⇔ **其活动内前置全部闭环** 且 **其所属活动的跨活动前置全部闭环**（两个条件必须**同时成立**，顺序为「先跨活动闸门、后活动内闸门」）；
  4. **传播时机**：跨活动前置闭环后必须**主动向下游传播解锁**（`propagateTopicUnlocks`），且传播必须放在「**工单主状态重算之后**」执行，否则会出现「上一步状态未落定、下一步按旧状态判定」的时序错位。

  说明：跨活动前置未闭环时，对应工单初始态为「待前置」、工序为「未解锁」，**不允许「先解锁、后锁回」**。

- ⚠️ **两条并列解锁规则，缺一不可**（对应缺陷 D-09）
  - 无前置工序（`is_no_predecessor == true` 或快照中无入边）→ **工单流转启动即解锁**；
  - 有前置工序 → **全部前置闭环才解锁**；
  - **其余情形一律保持 `LOCKED`**，禁止「启动即全部解锁」。

  历史缺陷根因：两条规则被合并为一个 `OR` 条件，导致全部工序启动即 `EXECUTING`、`LOCKED` 永不可达。

- ⚠️ **工序级事件必须回写工单主状态**（对应缺陷 D-13）：工单主状态是**派生值**，任何工序级状态变更（提审、审核通过、审核打回、工序闭环、解锁传播）之后，必须调用工单主状态重算。典型后果：提审后工单仍显示「执行中」而非「审核中」。
- ⚠️ **打回后工单主状态取「审核打回」而非「执行中」**（对应缺陷 D-11）：判定「是否处于打回整改期」以**审核态**为准；工序状态回落 `EXECUTING` 不改变该判定（见 3.2 派生优先级说明）。

#### 11.2.4 模块全局约束条件（需求 3.6.4）

**需求**

- **规则固化约束**：工单下发瞬间固化活动拓扑、工序依赖、准出校验规则快照，后续活动配置修改、拓扑调整、规则变更，**不影响已下发存量工单的流转逻辑**，仅对新工单生效。
- **规则唯一约束**：工单流转**无模块自定义特殊规则**，所有解锁、阻塞、闭环判定，仅以活动下发快照中的配置为唯一依据。
- **颗粒度隔离约束**：项目级工单不产生任何组件维度依赖，组件级工单严格执行同组件前置依赖隔离规则，禁止跨组件、跨颗粒度流转联动。
- **流转锁止约束**：任意前置工序未达标（准出未填、交付物缺失、审核打回 / 未审核），系统**强制锁止后置工序**，无法执行、无法跳过、无法提前闭环。
- **权限操作约束**：普通执行人、审核人仅可执行作业反馈、审核操作，无权限修改流转状态、跳过工序、解除阻塞；仅管理员可处理异常工单重启、作废操作，正常流转工单全程自动管控。
- **闭环归档约束**：工单所有工序全部闭环、无未完成节点，系统才可自动归档；存在打回未整改、未闭环工序的工单，**禁止归档**。
- **数据溯源与权限展示约束**：所有流转状态变更、工序闭环、审核操作、阻塞记录全部留痕，关联快照版本，可全程溯源复盘；系统严格按登录角色隔离工单展示数据，执行人、审核人仅可见自身权责工单，管理员全量可见。

#### 11.2.5 任务时效与 SLA 管控（需求 3.6.5）

**需求**

迁移项目投产窗口通常为 1~3 天，为保障工单在窗口期内闭环，系统增加全链路时效管控能力。**时效管控仅做预警与统计，不改变任务流转主逻辑**。

- **计划完成时间录入**：任务下发时必填「计划完成时间」，默认按活动配置的标准工期（小时）自动带出，允许下发人按投产窗口人工调整；工序级可选配置「标准工期（小时）」，用于计算工序级时效。
- **时效三档分档**：系统按「计划完成时间 − 当前时间」自动判定为 **正常 / 即将超时（剩余 ≤ 24 小时）/ 已超时（已超过计划完成时间）**，全部由系统计算，**无人工维护入口**。
- **时效标记**：工单详情展示时效标记，该标记为**独立维度**，不改变工单主状态、不阻塞工序执行与流转，仅用于预警与统计。
- **超时预警通知**：进入「即将超时」时通知当前执行人；进入「已超时」时同步通知当前执行人、组件负责人、项目负责人；通知走系统消息中心，通知记录留痕可查。
- **看板时效分桶**：数据看板按「正常 / 即将超时 / 已超时」三档分桶统计超时分布，统计口径与工单进度状态统计保持一致。
- **延期与豁免**：管理员可对单张工单执行「调整计划完成时间」或「时效豁免」，必须填写原因并留痕；豁免后的工单不再参与超时预警与超时率统计。
- **时效指标**：统计工单按时闭环率、平均闭环时长、超时工单占比，作为项目复盘与活动标准工期优化的依据。

**开发落点**：判定规则、独立维度硬约束、通知分档、SLA 特殊规则等详见 **18.3 时效与 SLA 判定器**。

| exit_filled | bool | ✓ | 准出完成状态 |
| deliverable_submitted | bool | ✓ | 交付物提交状态 |
| audit_status | enum(4 态) | ✓ | 审核状态，见 3.7 |
| must_audit / must_submit_deliverable | bool | ✓ | 因子 A / 因子 B：**取自工单固化快照，非实时活动配置**——这是四象限判定的唯一前提，活动侧改配置不得回写存量工序实例（铁律 #4） |
| reject_count | int | ✓ | 打回次数，支持多轮整改留痕 |

### 11.4 模块铁律

- 工单流转**只以快照为唯一依据**，禁止任何模块自定义特殊规则（铁律 #3）。
- 组件级工单禁止跨组件流转联动；项目级工单禁止产生组件维度依赖（铁律 #7）。
- 前置工序未达标**强制锁止后置工序**，禁止跳过、禁止提前闭环。
- 常规流转**禁止人工改状态**；仅「已暂停」「已作废」「异常重启」为管理员例外操作。
- 闭环归档前置条件：全部工序闭环、无未完成节点、无打回未整改。
- 时效标记为**独立维度**，任何情况下**不得因超时改变工单主状态或阻塞工序流转**。
- 状态变更**唯一驱动因子**为「执行反馈达标 + 审核结果」。
- ⚠️ **工序级事件必须回写工单主状态**（对应缺陷 D-13）。
- ⚠️ **打回后工单主状态取「审核打回」而非「执行中」**（对应缺陷 D-11）。
- ⚠️ **终态工单必须携带闭环时间**（对应缺陷 D-20）：`order_status ∈ {CLOSED, ARCHIVED}` ⇒ `closed_at` 非空，且语义为**最后一道闭环工序的闭环时间**；DDL 以 `ck_order_closed_at` 兜底，种子自检与 L1 断言各锁一条。
- ⚠️ **未解锁工序不得持有解锁时间**：`process_status = LOCKED` ⇒ `unlocked_at` 为空，防止「锁止但仍记录解锁」造成的溯源矛盾。
- **项目归属与组件绑定必须互斥绑定**（项目级无组件 / 组件级必有组件），DDL 层以 CHECK 兜底。

### 11.5 上下游接口契约

- **输入 ← 任务发布**：工单承接接口（工单列表 + 快照 JSON + 快照版本 + 计划完成时间）。
- **输入 ← 任务审核**：审核结果驱动解锁接口（`{order_id, process_seq, audit_result, audit_status}`）。
- **输入 ← 问题管理 / 风险管理**：状态变更推送（用于流转阻塞原因留痕）。
- **输出 → 任务进度反馈**：工序解锁状态推送（`{order_id, process_seq, process_status}`）。
- **输出 → 问题管理 / 风险管理 / 任务审核**：可执行工序上下文（工单 + 工序 + 执行人 + 快照版本）。
- **输出 → 数据看板**：工单状态、时效标记、颗粒度、进度占比（实时统计源）。

### 11.6 落地产物

- **DB**：`work_order`、`order_process_instance`、`order_status_log`、`order_transfer_log`、`order_suspend_log`、`order_sla_log`、`order_restart_log`、`notification`。
- **API**：`/api/order`、`/api/order/{id}`、`/api/order/{id}/processes`、`/api/order/{id}/suspend`、`/api/order/{id}/resume`、`/api/order/{id}/transfer`、`/api/order/{id}/restart`、`/api/order/{id}/sla-adjust`。
- **页面**：工单列表、工单详情、工序流转面板、时效预警面板。
- **闸门实现**：`src/api/order.ts`（流转域唯一闸门出口，含四象限判出器 + 时效判定器 + 四类异常分支 + 工单主状态与进度派生重算 + 跨活动解锁传播）。
- **路由**：`/flow`、`/flow/:orderId`。

### 11.7 验收要点

- 前置工序未闭环时，后置工序状态恒为「未解锁」且无执行入口。
- 组件 A 的工序未闭环，**不影响组件 B 工单的任何工序解锁**。
- 工单超过计划完成时间后，**主状态不变**，时效标记变为「已超时」，并触发通知。
- 暂停期间 SLA 计时停止；恢复后回到暂停前状态。
- 审核打回后，工单退回「执行中」（**注意：工单主状态为「审核打回」，工序状态为「执行中」**），执行人编辑权限自动解锁。
- 存在打回未整改工序的工单，**无法归档**。
- 【专题跨活动流转】后置子活动工单在前置子活动闭环前恒为「**待前置**」且工序「**未解锁**」；前置闭环后自动解锁并传播到其后续节点。
- 【互斥绑定】组件级工单的项目归属与组件绑定必须互斥绑定，DDL 层以 CHECK 兜底。
- 【终态时间戳】终态工单（已闭环 / 已归档）必须携带闭环时间；未解锁工序不得携带解锁时间。
- 【主状态派生】提审后工单主状态**即时**派生为「审核中」；打回后为「审核打回」（**不得回落为「执行中」**）。
- 【**工程可达性**·铁律 #13】本模块对应页面路由在真实生产构建产物中可正常渲染：`#root` 渲染出内容（非白屏）、运行期无未捕获异常 / React 致命报错。
- 【**双层验收**·铁律 #13】本模块交付须同时通过 L1 数据层断言与 L2 渲染冒烟断言；仅 L1 全绿不得声明完成。

**L1 断言方向**：本模块 7 条 + 与三个专项判定器共用 18 条（含负向闸门「工单状态禁止人工直改」、跨组件流转隔离、项目级无组件依赖、闭环归档约束、归档只读终态、流转溯源留痕、专题跨活动流转、9 态 / 5 态 / 4 态 / 3 档枚举与文案 1:1 全覆盖）。

### 11.8 交付状态

**状态：已完成（批次 3，本模块为批次内第 2 个模块，系统核心驱动）**

- 验收证据：L1（本模块 7 条 + 共用 18 条）PASS；L2 渲染冒烟新增 3 条路由（`/flow`、`/flow/WO-0001`、`/flow/WO-0002`），其中 **`/flow/WO-0002`（已暂停）用例是「异常分支可达性」（铁律 #16）的关键落地**——锚点「已暂停」，锁死「暂停态工单页面可渲染且回退依据可见」，**异常分支不再只存在于文档**。
- 种子数据：工单 18 张覆盖 **9 态全部可达**、工序实例 85 条覆盖 5 态。
- **遗留项**：① 「暂停 / 转交 / 异常重启 / SLA 调整」四类分支的**真机交互**（弹窗流程、二次确认）未自动化，已登记为人工验收项；② 流转引擎的**服务端承接**：闸门逻辑已收敛于单一出口，真实后端接入时以 **Spring StateMachine + 自研 Guard / Action** 承接，页面零改动；③ 时效分桶的**看板展示**待数据看板模块消费本模块 `deadline_status` / `v_order_deadline_live`。

## 12 模块 7 · 任务进度反馈（需求 3.7 / 提示词原 §10 + §17）

### 12.1 模块定位

本模块为任务流转引擎的**核心执行中间环节**，承接任务流转解锁后的工序执行工作，是**工序闭环、审核提报、后置节点解锁的唯一执行依据**。所有进度填写、内容修改、交付物上传、进度更新均由执行人完成；系统严格区分**可编辑内容、流转必填内容、审核联动内容**，所有反馈结果直接参与工序闭环判定与自动流转，完全遵循任务下发时活动快照固化的工序准入准出规则、自定义校验配置，**无独立流转逻辑**。

**流转环节定位**：处于「工序解锁 → 执行反馈 → 提交自审 → 审核判定 → 工序闭环 → 解锁后置工序」核心中间节点，**无进度反馈完成则无法进入审核与下一阶段流转**。

### 12.2 功能实现（需求 ↔ 开发落点）

#### 12.2.1 模块基础定位与能力（权限约束）（需求 3.7.1）

**需求**

- 操作权限约束：仅工单对应**执行人、参与人**拥有进度编辑、内容填报、交付物上传权限；管理员、审核人仅可查看不可修改执行反馈内容，保证**作业权责唯一**。

**开发落点**

- ⚠️ **闸门校验顺序（必须按固定四段顺序判定，对应缺陷 D-10 / D-12）**

  写操作进入闸门后必须按固定四段顺序判定，保证同一非法入参每次返回同一错误码（铁律 #12）：

  | 顺序 | 校验段 | 说明 |
  | --- | --- | --- |
  | ① | **工单只读态** | `CANCELLED` / `ARCHIVED` / `SUSPENDED` → 直接拒绝 |
  | ② | **契约类前置** | 如「本工序配置为无需审核，无审核入口」→ 拒绝 |
  | ③ | **工序锁态** | 未解锁 / 已闭环 / 已被打回锁定 |
  | ④ | **身份权限** | 是否本人或参与人 |

  **设计意图**：**契约类校验先于状态类校验**——「打了不该打的接口」与「此刻不能写」是**两类问题**，前者必须返回契约错误，**不能被状态错误吞掉**。若把 ③ 置于 ② 之前，无需审核的工序提审将返回「已锁定」而非「无审核环节」，调用方无从定位根因。

- ⚠️ **管理员不得代填执行反馈**（对应缺陷 D-10）：管理员仅拥有台账维护与异常干预权，**作业内容的权责主体只能是执行人 / 参与人**。可写主体收敛为 `current_executor_id` / `participant_ids`。
- ⚠️ **只读态判定先于一切**：工单处于 `CANCELLED` / `ARCHIVED` / `SUSPENDED` 时，**任何反馈写操作**（保存、提审、上报、日志）一律拒绝并返回只读原因；不得因后续分支判定而放行。
- ⚠️ **提审入口的存在性由快照因子决定**：`must_audit = false` 的工序**不得存在审核入口**，接口层须显式拒绝并返回契约错误；**重复提审同样拒绝**。

#### 12.2.2 执行人可自主修改 / 填报的具体内容（需求 3.7.2）

**需求**

执行人在工序执行阶段，可针对当前工序自主编辑、完善、修改以下内容；所有修改全程留痕，更新后实时同步至工单详情与审核面板：

- **工序进度信息**：实时填报、修改当前工序执行进度、作业完成情况、实施进展描述，支持多次更新迭代进度内容。
- **执行日志、问题上报与风险上报**：支持执行人在工序执行阶段新增、编辑常规作业日志，同步区分**问题专项上报**与**风险专项上报**两类独立台账，互不冲突、分别归档。
  - **问题上报**：针对已发生的工序卡点、异常故障、流程阻塞、资源缺失等**已发生**问题登记；
  - **风险上报**：针对**未发生、预判可能发生**的进度延迟、资源不足、合规偏差、环境异常、协同风险、投产风险等潜在隐患进行提前预判上报；**单次工序支持多条风险记录上报**，每条风险独立留存风险标题、风险等级、风险描述、发生概率、影响范围、佐证附件、上报时间、整改预备措施；全程操作留痕、可溯源、不可随意清空。
- **准出标准内容填报**：按照工序预设准出要求，完整填写、修正准出结果、执行结论、合规判定、落地说明等标准化准出内容。
- **交付物上传与替换**：按需上传、删除、替换当前工序所需交付文件、核对报表、落地截图、备案资料等附件内容。
- **作业补充备注**：自主补充作业说明、特殊场景备注、差异化落地说明、需审核人重点关注事项等辅助内容。

**开发落点**：上传的字段必填要求为——问题上报三项必填（标题 / 描述 / 发生场景），风险上报五项必填（标题 / 等级 / 描述 / 概率 / 影响范围）；上报记录**不可清空或删除，仅可补充更新**。

#### 12.2.3 流转过程强制必填项（闭环前置硬约束）（需求 3.7.3）

**需求**

系统根据当前工序准出自定义配置动态校验；以下内容为工序闭环、提交审核、解锁后置工序的强制必填项，**缺项无法完成进度提报、无法进入下一流转环节**，所有必填规则完全匹配活动工序快照配置：

- **基础进度必填**：所有工序必须完整填报工序执行进度、准出标准对应落地内容，**空白内容禁止提交保存与提报审核**。
- **交付物动态必填**：工序准出配置为「需提交交付件」的场景，对应必选交付物必须完整上传、合规命名、齐全无误，**缺失则锁止流转**；配置为「无需提交交付件」的工序，无需上传附件。交付物参考模板仅作作业指导，**不强制匹配模板格式**。
- **审核前置必填**：工序准出配置为「需审核」的场景，必须完成全部进度填报与交付物上传后，方可发起审核提报；无审核配置的工序，完成必填内容后系统自动闭环流转。

**开发落点**：必填校验严格跟随工序快照中的两道因子，**禁止越权强制或放宽**（铁律 #4）。

#### 12.2.4 进度反馈联动流转与审核内容（需求 3.7.4）

**需求**

所有进度反馈结果将作为审核判定、工序闭环、流转解锁的**唯一依据**，直接联动任务流转引擎与审核模块：

- **审核展示内容**：审核人审核页面自动加载执行人填报的进度详情、执行日志、问题卡点、准出结论、全部交付物附件、作业备注，作为审核判定依据。
- **审核联动流转逻辑**：四场景穷举（详见 18.2）：
  1. 无需审核、无需交付件：执行人完成全部必填内容填报 → 系统自动判定工序闭环 → 直接解锁后置工序；
  2. 需交付件、无需审核：必填交付物齐全 + 准出内容完整 → 系统自动闭环流转；
  3. 需审核、无需交付件：准出内容完整 → 提交审核 → 审核通过后方可闭环解锁；
  4. 需审核 + 需交付件：内容填报完整 + 交付物齐全 → 提交审核 → 审核通过完成闭环流转。

#### 12.2.5 全流程留痕与流转约束（需求 3.7.5）

**需求**

- **全程操作留痕与问题台账溯源**：所有进度修改、内容更新、交付物上传 / 替换、日志新增、提报审核、问题上报操作，均记录操作人、操作时间、变更内容，支持全程溯源复盘。系统自动生成工单问题台账，绑定对应工序与工单，作为项目问题管控、复盘、运维优化的依据。
- **管理员全局问题、风险管控与策略能力**：数据迁移管理员拥有全局查看权限，可通过工单详情、独立问题与风险台账页面，查看系统所有工单、所有工序的上报问题记录与风险记录。针对上报问题，管理员可录入、编辑官方整改建议、解决方案、处置意见；针对上报风险，管理员可维护、录入标准化风险应对策略、规避方案、预案措施、降级手段、前置防控要求，明确风险处置优先级、处置时限与落地要求。所有风险应对策略永久绑定对应风险记录归档，可供执行人实时参考落实风险防控，同时沉淀为系统风险库，用于后续项目同类风险提前规避与复用。
- **阶段锁定约束**：工序审核通过、工序闭环后，执行人**禁止再次修改当前工序进度与交付内容**；已上报问题记录与管理员整改建议固化归档、**不可删除**，保证流转结果与问题台账完整可追溯。
- **打回重新编辑、问题整改与风险闭环联动机制**：审核打回的工序，工单退回「执行中」状态，执行人可结合管理员给出的整改建议、风险应对策略，重新编辑进度内容、补充交付物、整改现存问题、落实风险防控措施，更新问题整改结果与风险处置进度，整改与防控完成后再次提报审核，**支持多轮迭代闭环**。系统同步记录风险处置状态，形成「上报 - 策略指导 - 落地防控 - 闭环归档」的完整风险管控链路。
- **快照规则约束**：所有进度反馈、问题上报、整改记录、必填校验逻辑，完全遵循任务下发瞬间固化的活动工序快照，后续后台活动配置修改**不影响存量工单执行与问题台账数据**。

**开发落点**：工序闭环后执行内容锁定（`is_locked = true`），禁止再编辑。

### 12.4 模块铁律

- 仅执行人、参与人可编辑反馈内容；**管理员、审核人只读且不得代填**（铁律 #8）。
- 必填校验严格跟随工序快照中的两道因子（是否需审核 / 是否需提交交付件），禁止越权强制或放宽（铁律 #4）。
- 工序闭环后执行内容锁定，**禁止再编辑**（阶段锁定约束）。
- 问题上报与风险上报为**两类独立台账**，禁止混用同一表或同一状态机（铁律 #2：状态独立枚举）。
- 上报内容**不可随意清空**；所有修改留痕。
- 所有反馈校验逻辑遵循快照，后台活动配置变更不影响存量工单（铁律 #3）。
- ⚠️ **只读态判定先于一切**：工单处于 `CANCELLED` / `ARCHIVED` / `SUSPENDED` 时，任何反馈写操作（保存、提审、上报、日志）一律拒绝。
- ⚠️ **校验顺序固定**：只读态 → 契约类前置 → 工序锁态 → 身份权限，**四段各自唯一错误码、禁止复用**。
- ⚠️ **提审入口的存在性由快照因子决定**：`must_audit = false` 的工序不得存在审核入口，重复提审同样拒绝。

### 12.5 上下游接口契约

- **输入 ← 任务流转引擎**：工序解锁状态推送（工单 + 工序上下文）。
- **输入 ← 活动管理（经快照）**：工序准入准出配置、必填项规则。
- **输出 → 任务流转引擎**：闭环判定入参（`{order_id, process_seq, exit_filled, deliverable_submitted}`）。
- **输出 → 问题管理**：问题上报被动同步接口（问题描述、附件、上报人、工单、工序、组件）。
- **输出 → 风险管理**：风险上报被动同步接口（风险全字段）。
- **输出 → 任务审核**：提审接口（解锁审核入口）+ 审核展示数据包。
- **输出 → 数据看板**：问题 / 风险来源数据。

- **API**：`/api/feedback/{orderId}/{processSeq}`、`/api/feedback/save`、`/api/feedback/submit-audit`、`/api/feedback/issue-report`、`/api/feedback/risk-report`。
- **页面**：工序执行页（进度填报 + 准出填报 + 附件上传）、问题上报弹窗、风险上报弹窗（支持多条）。

### 12.7 验收要点

- 工序配置为「无需审核、无需提交交付件」时，填写准出内容后工序**自动闭环，无审核入口**。
- 工序配置为「需提交交付件」时，未上传必选交付物**无法提交**。
- 工序闭环后，执行人再次进入页面**无编辑入口**。
- 一次风险上报可录入**多条**风险记录，各自独立留痕。
- 上报的问题 / 风险**实时**出现在对应台账中，且**双向可跳转**。
- 【权限】管理员登录后进入执行反馈页，只能查看，**无任何可编辑控件**；代填请求被闸门拒绝。
- 【契约优先】对 `must_audit = false` 的工序调用提审接口，返回「**无审核环节**」契约错误（**而非锁态错误**）；重复提审被拒绝。
- 【只读态】工单处于已暂停 / 已作废 / 已归档时，任何反馈写操作（含工作日志、问题 / 风险上报）**一律被拒**。
- 【**工程可达性**·铁律 #13】本模块对应页面路由在真实生产构建产物中可正常渲染：`#root` 渲染出内容（非白屏）、运行期无未捕获异常 / React 致命报错。
- 【**双层验收**·铁律 #13】本模块交付须同时通过 L1 数据层断言与 L2 渲染冒烟断言；仅 L1 全绿不得声明完成。

**L1 断言方向（12 条）**：编辑权限（仅执行人 / 参与人）；基础进度必填；阶段锁定；作业日志追加式留痕；问题上报三项必填与独立台账；风险上报五项必填与多条留痕；两类独立台账字段语义互不混用；上报记录不可清空仅可补充；管理员整改建议 / 风险策略仅管理员可录入并固化归档；提审前置（无需审核工序无审核入口、重复提审被拒）；反馈遵循快照（必填校验与实时活动配置解耦）；工单暂停期间禁止任何反馈写操作。

## 13 模块 8 · 问题管理（需求 3.8 / 提示词原 §11）

### 13.1 模块定位

本模块为系统**全量问题统一归集、台账维护、整改管控、闭环复盘核心模块**，汇聚系统所有作业问题数据，支持**双渠道问题来源录入**（后台手动新增 / 批量导入 + 任务进度反馈模块自动同步上报问题），实现工单作业问题与独立问题台账统一管理、全程留痕、整改闭环、可溯源统计。

模块完整支撑问题新增、批量导入、日常维护、多维度角色差异化查询、整改闭环管理能力；所有问题数据联动关联工单、工序、责任人，贴合系统权限体系与颗粒度规则。**本模块同时沉淀历史问题知识库，实现问题经验的结构化归档、智能匹配与复用。**

### 13.2 功能实现（需求 ↔ 开发落点）

#### 13.2.1 模块基础核心能力（新增 / 批量导入 / 维护 / 查询）（需求 3.8.1）

**需求**

- **双渠道问题新增能力**（数据统一归集，台账无重复归集）：
  1. **主动新增**：管理员、项目负责人可后台手动单条新增问题，自主填报问题全量信息；
  2. **被动同步**：执行人在任务进度反馈模块上报的工序问题，系统实时自动同步至本模块问题台账，自动绑定对应工单、工序、组件、责任人，无需人工二次录入。
- **问题批量导入能力（专属强化功能）**：支持 Excel 模板批量导入问题数据；系统提供标准导入模板，适配线下问题批量补录、批量归档场景；导入时自动数据校验、自动去重、字段合规性校验，异常数据批量提示、单独罗列，合规数据一键入库，同步归属对应项目 / 事业群 / 组件维度。
- **问题台账维护**：仅数据迁移管理员、项目负责人拥有台账编辑、状态修改、作废归档权限；支持修改问题基础信息、整改方案、处置状态、备注信息；同步保留所有修改记录、操作人、操作时间，全程留痕。普通执行人仅可查看本人关联问题、提交整改进度，无全局维护权限。
- **角色差异化多维度查询**（适配分层管控）：
  1. **普通执行人**：仅查看本人上报、本人负责整改的问题数据；
  2. **组件 / 项目负责人**：查看对应管辖范围内组件 / 项目的全量问题台账；
  3. **管理员**：全局查看系统所有问题数据，无权限隔离，支持全量统计复盘。
- **通用筛选条件**：支持按问题编号、关联工单 / 工序、所属项目 / 事业群 / 组件、问题来源（手动新增 / 批量导入 / 工单同步）、问题状态、上报时间、责任人多维度检索；支持台账批量导出。

**开发落点**

- ⚠️ **数据同源实现（单一事实源 + 字段级权威划分）**：问题域采用**对账式同步**（`reconcile`，幂等）：
  - **归属类字段**（项目 / 事业群 / 组件 / 关联工单 / 关联工序 / 上报人）**权威在上报单**，台账侧为只读镜像；
  - **整改 / 处置类字段**（整改建议 / 解决方案 / 整改进度 / 状态）**权威在台账**，回写镜像到上报单。
  - 一方修改另一方自动同步更新，**保证数据一致性**，禁止出现两套数据各自演进。

#### 13.2.2 问题标准化展示字段（列表 + 详情）（需求 3.8.2）

**需求**

- **基础归属字段**：问题唯一编码、问题标题、问题来源、所属项目、所属事业群、绑定组件（组件级问题展示）、关联工单编号、关联工序名称。
- **责任与时间字段**：上报人、责任整改人、首次上报时间、最新更新时间、整改完成时间。
- **问题属性字段**：问题描述、问题发生场景、问题影响范围、原始卡点说明、佐证附件（截图 / 报表 / 日志）。
- **整改管控字段**：管理员整改建议、标准化解决方案、整改执行进度、整改过程记录、整改后佐证附件、问题状态（待整改、整改中、已闭环、已作废）。
- **溯源字段**：关联工单快照版本、数据同步来源、所有操作变更日志。

**开发落点**：问题状态必须使用 3.5 定义的 4 态枚举，**禁止布尔字段拆分**（铁律 #2）。

#### 13.2.3 核心功能实现方法（需求 3.8.3）

**需求**

- **工单问题自动同步实现**：执行人在任务进度反馈模块提交工序问题后，系统实时触发同步机制，自动抓取问题描述、附件、上报人、所属工单、工序、组件信息，一键同步至问题管理模块，生成独立问题台账条目；**双向关联、双向可跳转，修改数据实时双向同步**。
- **批量导入实现逻辑**：
  1. 系统提供固定标准导入模板，包含所有必填字段与选填字段，标注字段录入规则；
  2. 用户下载模板、线下批量填报后上传文件；
  3. 系统自动校验：字段完整性、数据格式、**重复编码**、非法内容校验；
  4. 合规数据批量入库，自动匹配项目 / 组件 / 责任人信息；
  5. **异常数据拦截**，弹窗展示异常条数、异常原因，支持下载异常明细修正后重传。
- **问题整改闭环实现**：责任人根据管理员录入的整改方案执行整改，实时更新整改进度、上传整改佐证、填写整改总结；管理员核验整改结果，核验通过后标记问题闭环，**数据永久固化归档**。

**开发落点**：批量导入必填项缺失、格式错误、编码重复数据**一律禁止入库**，杜绝无效脏数据。

#### 13.2.4 模块全局约束条件（需求 3.8.4）

**需求**

- **数据同源约束**：工单反馈问题与问题台账数据双向联动、实时同步，一方修改另一方自动同步更新，保证数据一致性。
- **导入校验约束**：批量导入必填项缺失、格式错误、编码重复数据禁止入库，杜绝无效脏数据。
- **权限隔离约束**：普通用户仅可整改、查看本人权责问题，无权限修改全局问题台账、作废问题；管理员拥有全量维护权限。
- **闭环固化约束**：问题标记已闭环后，禁止随意修改、删除，整改记录、方案记录永久留存溯源。
- **颗粒度对齐约束**：所有问题自动继承关联工单 / 组件的颗粒度属性，严格遵循项目级 / 组件级数据隔离规则。

**开发落点**：问题颗粒度自动继承关联工单 / 组件，**禁止跨颗粒度归于同一问题**（铁律 #1）。

#### 13.2.5 历史问题知识库（经验沉淀与复用）（需求 3.8.5）

**需求**

实现问题经验的结构化沉淀、智能匹配与跨项目复用，避免同类问题重复排查：

- **知识条目自动沉淀**：问题状态标记为「已闭环」后，系统自动将「问题描述 + 解决方案 + 整改过程记录 + 佐证附件」归档为知识条目；管理员亦可手动补录历史项目、外部经验类知识条目。
- **多级标签体系**：支持多级分类标签（业务域 / 组件 / 工序环节 / 问题类型 / 根因归类），提供标签云与多标签组合检索，标签由管理员统一维护。
- **三元组知识模型**：知识条目以「**问题 → 解决方案 → 复用次数**」三元组建模；每次被引用自动记录引用关系与采纳结果，形成解决方案采纳率指标。
- **相似问题智能匹配**：新建或批量导入问题时，系统按「问题标题 + 问题描述」执行关键词检索与向量相似度匹配，自动推荐 **Top5** 历史相似问题及对应解决方案，供录入人参考引用。
- **一键复用与回写**：问题整改环节支持一键引用历史解决方案；引用后自动生成引用记录，并**回写**对应知识条目的复用次数与采纳结果。
- **知识库统计**：提供 Top10 高频问题、解决方案采纳率、按组件 / 阶段的问题分布、问题复发率统计，支撑项目复盘与标准作业模板优化。
- **权限与约束**：全员可检索查看；知识条目的编辑、合并、下线**仅数据迁移管理员拥有**；**已归档知识条目禁止删除，仅可标注「已失效」**，保证知识资产完整可溯。

**开发落点**：知识条目状态枚举为 `ACTIVE` / `INVALID`（有效 / 已失效），**禁止物理删除**。

## 14 模块 9 · 风险管理（需求 3.9 / 提示词原 §12）

### 14.1 模块定位

本模块为系统**全流程风险预判、台账归集、策略管控、前置防控核心模块**，用于沉淀所有迁移作业潜在风险数据，支持**双渠道风险来源录入**（后台手动新增 + 任务进度反馈模块自动同步上报风险），实现工序作业风险全域归集、等级管控、策略匹配、闭环防控。

模块与任务流转、进度反馈、问题整改模块深度联动，形成「**风险上报 - 策略指导 - 前置防控 - 闭环归档**」完整链路。

### 14.2 功能实现（需求 ↔ 开发落点）

#### 14.2.1 模块基础核心能力（新增 / 维护 / 查询）（需求 3.9.1）

**需求**

- **双渠道风险新增能力**（数据统一归集、独立台账管理）：
  1. **主动新增**：管理员、项目负责人可后台手动新增潜在风险，提前预判录入全域业务风险；
  2. **被动同步**：执行人在任务进度反馈模块上报的工序风险，系统实时自动同步至本模块风险台账，自动绑定对应工单、工序、组件、预判责任人。
- **风险台账维护**：仅数据迁移管理员、项目负责人拥有风险编辑、策略录入、状态维护、作废权限；支持维护风险等级、发生概率、影响范围、前置防控策略、风险应对预案、降级处置方案；普通执行人仅可查看本人关联风险、更新防控进度，无全局编辑权限。
- **角色差异化多维度查询**：
  1. **普通执行人**：仅查看本人上报、本人负责防控的风险数据；

**开发落点**：与问题域共用同一套**对账式同步（`reconcile`）**协议与幂等约束；归属类字段权威在上报单、防控类字段权威在台账。

**需求**

- **风险属性字段**：风险等级（高 / 中 / 低）、发生概率（高 / 中 / 低）、影响范围、风险详细描述、潜在危害、预判场景、佐证附件。

- **闭环管控字段**：风险防控进度、落地执行记录、防控佐证附件、风险状态（待防控、防控中、已规避、已发生、已闭环、已作废）。

#### 14.2.3 核心功能实现方法（需求 3.9.3）

**需求**

- **工单风险自动同步实现**：执行人在任务进度反馈模块提交工序风险上报后，系统实时同步全量风险信息至风险管理模块，自动生成独立风险台账；**双向关联、数据互通**，进度模块风险更新后本模块自动同步刷新，保证风险数据实时一致。
- **风险策略配置与复用实现**：管理员针对各类风险录入专属应对策略与防控预案，系统自动沉淀为**全局风险知识库**；后续同类风险上报可智能匹配历史策略，**支持一键复用**，提升风险处置效率。
- **风险防控闭环实现**：防控责任人依据管理员配置的策略落地前置防控，实时更新防控进度、上传落地佐证、记录处置过程；管理员核验防控效果，完成风险规避或处置闭环，实现预判风险前置管控。

#### 14.2.4 模块全局约束条件（需求 3.9.4）

**需求**

- **数据同步约束**：进度反馈模块风险与风险管理台账双向实时同步，数据同源、统一更新，**无数据偏差、无重复数据**。
- **风险等级唯一约束**：每条风险仅可配置**单一风险等级、单一发生概率**，保证统计标准统一。
- **权限管控约束**：风险策略配置、状态作废、全局编辑仅管理员 / 项目负责人可操作；普通用户仅可查看与执行防控操作。

- **颗粒度对齐约束**：风险数据严格继承项目 / 组件颗粒度，数据隔离、权限可视范围与全系统规则统一。

**开发落点**：风险等级、发生概率**各仅可为单一值**，禁止多选或组合表达。

## 15 模块 10 · 任务审核管理（需求 3.10 / 提示词原 §13）

### 15.1 模块定位

本模块为系统**工序合规验收、流转闭环、质量卡点管控的最终核心模块**，承接进度反馈提审后的所有验收工作，是**工序闭环、后置工序解锁、工单最终归档的唯一审核依据**。

模块完整支持多条件筛选查询、单条精细审核、批量审核操作、打回整改闭环；所有审核流转规则严格遵循任务下发快照对应的活动工序准出配置，完全联动任务流转引擎自动驱动状态迭代。实现**审核过程规范化、结果可溯源、流转自动化、整改可闭环**。

### 15.2 功能实现（需求 ↔ 开发落点）

#### 15.2.1 模块基础能力与权限规则（需求 3.10.1）

**需求**

- **核心能力**：支持审核工单台账查询、待审任务校验、单条审核、批量审核、任务打回、整改复审、审核记录留痕、审核结果驱动流转闭环。

- **权责唯一约束**：单工序审核权限严格匹配活动工序预设审核角色，**禁止无权限用户提审、代审、私自修改审核结果**。

**开发落点**

- ⚠️ **权限刚性**：审核操作**仅审核角色（`ROLE_REVIEW`）可执行**；**管理员可查看全量台账但不得代审**——「谁审核、谁负责」，不可跨角色、跨权限代审。
- 审核留痕**写入流转域库，与工序状态迁移在同一次提交**（遵守 18.2 落库时序）。

#### 15.2.2 多维度查询筛选功能（角色差异化可视）（需求 3.10.2）

**需求**

系统基于登录角色做数据权限隔离，同时支持多条件组合精准筛选审核工单，适配批量审核、问题复盘、台账统计场景：

- **角色差异化查询范围**：
  1. **审核人**：仅展示本人待审核、本人已审核、本人打回整改的权责工单，无法查看其他审核人的审核台账；
  2. **执行人**：仅可查看本人提交审核的工单进度、审核结果、打回记录，无全局查询权限；
  3. **管理员**：支持查询系统全量审核工单数据，无权限隔离。
- **通用多重筛选条件**：支持按工单编号、关联活动 / 专题、任务颗粒度、所属项目 / 事业群、绑定组件、当前工序、审核状态（待审核、审核通过、审核打回、整改复审）、创建时间区间、提审时间区间、执行人多维度组合筛选。
- **台账导出能力**：支持筛选后审核台账批量导出，包含所有审核字段、整改记录、流转结果，用于项目复盘与合规归档。

#### 15.2.3 页面标准化展示字段（列表 + 审核详情）（需求 3.10.3）

**需求**

- **工单基础字段**：工单编号、工单名称、任务颗粒度、活动类型（普通活动 / 专题活动）、活动名称、所属项目、所属事业群、绑定组件、当前所处工序。
- **责任与执行字段**：任务执行人、参与人、提审时间、工序执行进度、准出内容填报状态、交付物提交状态。
- **审核状态字段**：工序审核状态、审核人、审核时间、审核结果、打回原因、整改要求、整改完成状态、复审次数。
- **流转溯源字段**：当前工序审核配置（需审核 / 无需审核）、工单快照版本、审核流转结论、后置工序解锁状态。

**开发落点**：字段标准化无冗余。

#### 15.2.4 审核核心操作字段（必填 / 选填标准化）（需求 3.10.4）

**需求**

审核人执行审核操作时，系统固定操作字段，区分必填、选填，所有操作内容**全程留痕归档，不可篡改**：

| 字段 | 必填规则 | 说明 |
| --- | --- | --- |
| **审核结果** | **必选** | 固定枚举「审核通过、审核打回」，为核心流转判定字段，**无默认值，必须手动选择** |
| **审核意见** | **必填** | 无论通过或打回均需填写；通过需填写合规验收结论，打回需明确问题定位、不合规点 |
| **打回整改要求** | **打回状态必填** | 选择审核打回时该字段**强制必填**，需明确整改内容、整改标准、补充资料要求、复审条件；缺项无法完成打回操作 |
| 审核佐证附件 | 选填 | 支持审核人上传校验截图、核对报表、问题截图等佐证资料 |
| 特殊备注 | 选填 | 记录专项审核说明、特殊场景豁免、差异化验收说明等辅助内容 |

**开发落点**：三者的必填规则**不可放宽**。

#### 15.2.5 审核通过 / 打回完整流转规则及实现方法（需求 3.10.5）

**需求**

所有审核流转逻辑完全遵循工单下发时活动工序快照配置，结合工序准出校验规则联动任务流转引擎自动执行，**无人工手动改状态操作**：

- **前置准入规则（进入审核的必要条件）**：仅当执行人完成当前工序必填准出内容填报 + 必选交付物齐全后，方可提交审核；**内容缺失、交付物不全禁止提审**，系统拦截审核入口。无需审核配置的工序，直接自动闭环、不进入审核流程。
- **审核通过流转实现**：
  1. **校验前置**：审核人确认工序执行内容合规、准出达标、交付物齐全；
  2. **操作动作**：选择「审核通过」、填写验收意见，提交审核；
  3. **系统自动逻辑**：标记工序审核通过、锁定工序执行内容、固化审核记录，判定当前工序完全闭环，**自动解锁所有后置依赖工序**，工单流转进度同步更新；
  4. **收尾规则**：单工单所有工序全部审核闭环后，系统自动判定工单整体完成，进入可归档状态。
- **审核打回流转与整改闭环实现**：
  1. **操作动作**：选择「审核打回」、必填打回原因与整改要求，提交完成打回；
  2. **状态回退**：工序状态自动从「审核中」退回「执行中」，已锁定的执行编辑权限自动解锁，执行人可重新修改进度、补充交付物、整改问题、更新风险防控措施；
  3. **迭代复审**：执行人整改完成后可再次提审，**支持多轮打回整改、多次复审**，系统记录每一轮审核记录、打回记录与整改记录；
  4. **流转锁止**：打回未整改、未重新提审的工序，**永久锁止后置工序**，无法继续流转。
- **批量审核实现逻辑**：
  - **批量通过**：支持批量勾选多条待审工单，批量执行「审核通过」操作，批量统一生成审核意见。
  - **批量打回**：支持批量操作（**单批次上限 50 条**，超出需分批执行），但必须满足**三项强制约束**，兼顾投产窗口期批量整改效率与误操作风险：
    1. ⚠️ **强制统一打回原因**：批量打回必须填写**唯一**打回原因与整改要求，系统按工单**逐条留存**（统一原因 + 各工单原始提审信息），支持单条独立复核与追溯；
    2. ⚠️ **强制二次确认**：提交前弹出二次确认弹窗，明确展示本次将打回的**工单数量与工单清单**（含工单编号、活动名称、当前工序），二次确认后方可提交；
    3. ⚠️ **撤销窗口**：批量打回提交后 **10 分钟内支持整批撤销**（仅限尚未被重新提审的工单），撤销操作留痕。

**开发落点**

- ⚠️ **闭环判定落库时序**（对应缺陷 D-14，与流转引擎共用同一份修订）：审核通过路径必须**先落 `audit_status = PASSED`，再判定工序是否闭环**；顺序颠倒会使判定读到旧值 `WAIT_REVIEW`，把「审核通过」误报为「前置未满足」，导致需审核场景整体不可闭环。
- 批量打回提交后，二次确认弹窗展示的工单数量与清单**必须与实际一致**；撤销需将工序还原为「待审」。

#### 15.2.6 模块全局约束条件（需求 3.10.6）

**需求**

- **规则快照约束**：工序是否需审核、审核流转判定规则，以**下发时活动快照配置**为准，后续后台工序配置修改**不影响存量工单审核逻辑**。
- **状态不可篡改约束**：审核完成、工序闭环后，审核结果、打回记录、整改记录**永久固化，禁止删除、修改、撤销**，全程可溯源。
- **无跳过审核约束**：配置为「需审核」的工序，**禁止跳过审核、禁止强制闭环**，未审核 / 打回未整改**永久锁止后置流转**。
- **权限刚性约束**：谁审核、谁负责，不可跨角色、跨权限代审；管理员无权限替普通审核人完成审核操作，仅可查看与复盘。
- **整改闭环约束**：打回工单必须完成整改复审并审核通过，方可完成工序闭环、解锁后置节点，**不允许打回工单直接归档**。
- **流程唯一性约束**：工序流转状态仅由「执行反馈达标 + 审核结果」双因子驱动，**无任何其他人工干预手段**。

### 15.4 模块铁律

- **打回工单不允许直接归档**（整改闭环约束）。
- **管理员不可替审核人执行审核**（权限刚性）。
- 批量打回必须**同时满足三项强制约束**（统一原因 / 二次确认 / 10 分钟撤销窗口），单批上限 50 条。
- 审核完成后记录**永久固化，禁止删除、修改、撤销**。

### 15.7 验收要点

- 未完成必填准出内容或交付物不齐时，**提审入口不可用**。
- 审核打回未填写「打回整改要求」时提交**被拦截**。
- 打回后工序状态退回「执行中」，执行人可再次编辑并提审，**复审次数 +1**。
- 批量打回超过 50 条时被拦截并提示分批。
- 批量打回提交后，**二次确认弹窗展示的工单数量与清单与实际一致**。
- 提交后 **10 分钟内可整批撤销**；已被重新提审的工单**不可撤销**。
- 管理员账号**无「审核通过 / 打回」操作按钮**。
- 【**工程可达性**·铁律 #13】本模块对应页面路由在真实生产构建产物中可正常渲染：`#root` 渲染出内容（非白屏）、运行期无未捕获异常 / React 致命报错。
- 【**双层验收**·铁律 #13】本模块交付须同时通过 L1 数据层断言与 L2 渲染冒烟断言；仅 L1 全绿不得声明完成。

**L1 断言方向（14 条）**：审核权限（仅审核角色可审、管理员不得代审）；必填规则三项；打回整改要求强制必填；前置准入（内容 / 交付物不全拦截提审）；无需审核工序不进审核流；审核通过驱动工序闭环与后置解锁；打回状态回退与编辑权限解锁；多轮复审与轮次记录；打回未整改永久锁止后置；打回工单不得直接归档；批量通过；批量打回三约束（上限 50 / 统一原因 / 二次确认一致）；10 分钟撤销窗口与还原工序为待审；审核记录固化不可篡改。

## 16 模块 11 · 数据看板（需求 3.11 / 提示词原 §14）

### 16.1 模块定位

本模块为系统**全域业务数据可视化汇总、进度统筹、风险问题大盘管控核心模块**，自动聚合系统全量专题、活动、工单、问题、风险数据，实现一站式可视化统计展示。支持多维度状态统计、分层权限可视、颗粒度筛选、实时数据联动，**无需人工汇总统计**，自动同步各业务模块最新数据，为项目统筹、进度管控、风险预警、问题复盘提供全局数据支撑。

**核心统计维度为六大维度**：① 全生命周期阶段-活动-工单层级统计；② 普通活动进展状态统计；③ 专题活动进度与运行状态统计；④ 工单进度状态统计；⑤ 问题状态分项统计；⑥ 风险状态分项统计。

### 16.2 功能实现（需求 ↔ 开发落点）

#### 16.2.1 模块基础核心能力（需求 3.11.1）

**需求**

- **全域数据自动聚合**：实时联动活动管理（含普通活动、专题聚合活动）、任务工单、问题管理、风险管理四大模块；通过**活动类型标签**区分普通活动数据与专题聚合数据；数据实时刷新、无需人工录入汇总。
- **六大核心维度统计（统一口径）**：覆盖项目整体进度、活动运行、专题落地、工单流转、问题卡点、风险预警六大核心管控场景。
- **角色差异化权限可视**：基于系统角色、数据权限、颗粒度隔离规则，实现分层看板展示，不同角色查看对应权责范围统计数据，**杜绝数据越权查看**。
- **多维度筛选联动**：支持按项目、事业群、组件、时间区间、颗粒度、状态多条件筛选；筛选后所有统计大盘实时联动刷新，精准定位局部业务数据。
- **统计数据溯源跳转**：所有统计卡片、状态数据支持点击下钻，一键跳转对应模块明细台账，实现「**大盘统计 - 明细溯源**」闭环，支持快速排查卡点数据。
- **看板数据导出**：支持整体看板统计报表、各维度明细统计数据批量导出，用于项目汇报、阶段复盘、归档留存。

#### 16.2.2 角色差异化可视规则（核心约束）（需求 3.11.2）

**需求**

- **普通执行人**：仅统计展示本人负责 / 上报的活动、工单、问题、风险数据，**无全局统计权限**，仅可视个人权责进度。
- **组件 / 项目负责人**：统计展示管辖范围内对应项目 / 组件的全量专题、活动、工单、问题、风险数据，支持局部业务统筹管控。
- **数据迁移管理员**：展示系统全量业务统计数据，无权限隔离，支持全局统筹、整体复盘、数据汇总分析。

**开发落点**：所有统计计算**前置权限过滤逻辑**——根据当前登录用户角色、权责范围、颗粒度权限自动过滤无权限数据，统计结果为用户可视范围内真实数据，**杜绝全局数据泄露**（铁律 #8 实现口径）。

#### 16.2.3 多维度统计口径与展示字段（需求 3.11.3）

##### 16.2.3.1 全生命周期阶段-活动-工单层级统计（核心维度）

**需求**

看板按**数据迁移全生命周期阶段**做一级分组（**仅统计普通活动**），每个阶段下展示归属该阶段的所有普通活动，逐层汇总统计「活动对应工单总量 + 各状态分项数量」；**专题聚合型活动不归属生命周期阶段，单独独立统计展示**，通过活动类型标签区分两类数据，实现生命周期常规作业、专题聚合作业双向穿透统计。

- **统计层级结构**：全生命周期总览 → 各迁移阶段分组 → 阶段下各活动明细 → 对应工单状态统计。
- **核心统计口径**：按生命周期维度自动归集，分别统计每个阶段、每个归属活动下的工单总数，以及各状态分项数量：待前置、待接收、执行中、已暂停、审核中、审核打回、已闭环、已归档、已作废工单（共 **9 态**，与 3.2 枚举表 **1:1 一致**）。
- **可视化展示**：支持阶段折叠 / 展开；顶层展示各阶段整体工单进度占比、闭环率；展开后展示单活动工单总量、各状态分项卡片、进度趋势。
- **数据口径**：完全同步任务流转引擎实时工单状态，严格继承活动归属的生命周期阶段属性，区分项目级 / 组件级双颗粒度统计，遵循快照机制。
- **下钻能力**：点击对应阶段、对应活动、对应工单状态，直接跳转工单台账并自动筛选维度，精准查看该阶段 / 该活动下的明细工单。

##### 16.2.3.2 普通活动进展状态统计

**需求**

自动统计系统所有普通标准活动的运行状态数据，区分双颗粒度，展示基础活动整体运维情况，**与专题聚合活动数据完全隔离**。

- **统计维度**：活动总数、启用活动数、停用活动数、作废活动数、已关联专题活动数、未关联专题活动数。
- **状态可视化展示**：以统计卡片 + 饼图 / 柱状图展示各状态占比与数量，区分项目级 / 组件级活动统计。
- **数据口径**：同步活动管理模块实时状态；停用、作废活动纳入统计区分，**不参与新任务下发统计**。
- **下钻能力**：点击对应状态卡片，跳转活动管理台账自动筛选对应状态活动明细。

##### 16.2.3.3 专题活动进度与运行状态精准统计

**需求**

针对系统所有已创建专题，**单点穿透**统计专题维度工单数据，精准展示单专题下总工单数、各工单状态分项数量、整体进展闭环情况，实现专题聚合任务进度精细化管控。同时补充统计专题自身的运行状态，解决「当前有多少专题启用 / 停用 / 未下发任务」的治理口径缺失问题。

- **专题进度统计维度**：专题总数；各专题独立统计，单专题下展示关联工单总数与 9 态分项数量。
- **专题运行状态统计维度**：专题总数、启用专题数、停用专题数、作废专题数、已下发任务专题数、未下发任务专题数，按专题状态逐项拆分计数，**与专题进度统计并列展示**。
- **专题运行状态下钻能力**：点击对应专题状态卡片，跳转专题聚合活动台账并自动筛选对应状态明细。
- **辅助进度指标**：单专题工单闭环率、在办占比、问题卡点占比，直观呈现专题整体落地进度。
- **筛选适配**：支持单独筛选指定专题，单独展示该专题专属工单进度统计数据，屏蔽其他专题数据干扰。
- **下钻能力**：点击专题及对应工单状态，跳转专题详情 + 关联工单明细列表，查看专题下所有活动、工单的流转进度与卡点明细。

##### 16.2.3.4 问题状态分项统计

**需求**

纯基于当前问题实时状态做标准化分项统计，聚焦问题整改闭环现状，**无多余衍生统计**。

- **核心状态分项统计（固定口径）**：问题总数、待整改、整改中、已闭环、已作废，按状态逐项拆分计数（与 3.5 一致）。
- **基础辅助能力**：支持按项目、事业群、组件、问题来源筛选统计，展示各维度问题分布占比。
- **数据口径**：同步问题管理模块全量实时数据，包含**手动新增、批量导入、工单进度反馈同步**三类来源，数据实时刷新。
- **下钻能力**：点击任意问题状态，跳转问题台账自动筛选对应状态明细，快速处理存量问题。

##### 16.2.3.5 风险状态分项统计

**需求**

纯基于当前风险实时状态做标准化分项统计，聚焦风险防控处置现状，**同步保留风险等级分层统计**。

- **核心状态分项统计（固定口径）**：风险总数、待防控、防控中、已规避、已发生、已闭环、已作废，按状态逐项拆分计数（与 3.6 一致）。
- **分级叠加统计**：在状态分项基础上，叠加高 / 中 / 低风险等级分层统计，精准定位高危风险存量与处置进度。
- **数据口径**：同步风险管理模块全量实时数据，包含手动新增、工单进度反馈同步两类来源，防控进度、状态变更实时联动更新。
- **下钻能力**：点击任意风险状态、风险等级，跳转风险台账筛选对应明细，查看风险防控策略与落地记录。

##### 16.2.3.6 工单进度状态统计

**需求**

核心进度统计维度，自动聚合全量工单流转闭环情况，直观展示整体作业进度。

- **统计维度**：总工单数、待前置工单、待接收工单、执行中工单、已暂停工单、审核中工单、审核打回工单、已闭环工单、已归档工单、已作废工单（共 **9 态**，与 3.2 一致）。
- **进度指标**：整体工单闭环率、流转正常率、打回整改率、归档完成率。
- **颗粒度拆分统计**：独立统计项目级工单、组件级工单各状态数量与进度占比。
- **数据口径**：完全同步任务流转引擎实时工单状态，以工单最新流转状态为**统计唯一依据**，遵循快照机制区分新老工单。
- **下钻能力**：点击对应工单状态，跳转工单台账自动筛选对应状态明细，快速定位卡点工单。

**开发落点**

- ⚠️ **时效分桶统计是叠加维度而非主分类**：按「正常 / 即将超时 / 已超时」三档分桶统计超时分布，口径与 18.3 一致；**仅「在办工单」（9 态 − `CLOSED` / `ARCHIVED` / `CANCELLED`）参与**。
- ⚠️ **看板必须直接消费流转域的实时时效视图，不得自行重算三档**（避免第二份实现）：看板逐单对账，**不一致即抛 `DASHBOARD_DEADLINE_VIEW_MISMATCH`**。
- **工单归属活动判定式**：NORMAL 任务工单走 `task.activity_id`；TOPIC 专题拆分工单走 `order.sub_activity_id`。

#### 16.2.4 模块全局约束条件（需求 3.11.4）

**需求**

- **实时数据联动与类型隔离机制**：看板依托**活动类型标签**严格区分普通活动、专题聚合活动两类数据；普通活动关联生命周期阶段统计，专题活动独立无阶段统计；实时联动活动、工单、问题、风险四大数据源，数据更新同步刷新，零延迟零偏差。
- **权限过滤统计实现**：所有统计计算**前置权限过滤逻辑**，根据当前登录用户角色、权责范围、颗粒度权限，自动过滤无权限数据，统计结果为用户可视范围内真实数据，杜绝全局数据泄露。
- **颗粒度拆分实现**：所有统计维度默认支持项目级、组件级双颗粒度拆分展示，可自由切换全局统计 / 分级统计视图，适配统筹管理与明细管控场景。
- **快照兼容实现**：存量历史工单、专题、活动按固化快照状态统计，新数据按最新配置统计，新老数据统计逻辑兼容，**无统计错乱、无数据遗漏**。
- **下钻溯源实现**：通过状态参数、维度参数、颗粒度参数透传，点击统计卡片自动联动对应业务台账筛选条件，精准展示对应明细数据，实现统计与业务闭环联动。
- **数据同源约束**：看板所有统计数据完全取自各业务模块**原生数据**，无自定义统计逻辑，保证统计口径与业务台账 **100% 一致**，无数据偏差。
- **权限严格隔离约束**：禁止低权限用户查看全局统计数据，所有统计结果严格跟随用户数据权限，保证数据安全。
- **状态唯一统计约束**：单条业务数据仅归属唯一状态统计，**不重复计数、不遗漏计数**，保证统计精准度。
- **颗粒度强制约束**：所有统计数据严格区分项目级、组件级，**不跨颗粒度混合统计**，贴合系统层级管控规则。
- **历史数据固化约束**：已归档、已作废的历史数据正常纳入统计，区分状态展示，**不自动清除**历史数据，保证全周期数据可复盘。
- **无手动修改约束**：看板所有统计数据为系统自动计算生成，**无手动编辑、手动修改入口**，保证数据客观真实、可溯源。

> 本篇是**跨模块共用逻辑的唯一定义处**。任何涉及两个以上模块的功能点，必须在本篇约束下开发，**禁止在单个模块内私自实现跨模块逻辑，也禁止任何模块另写一套判定器**。

## 17 跨模块联动（6 条链路）

> 对应需求 4「模块联动务实逻辑」。每条链路都给出**不可绕过的落地约束**。

### 链路 1：人员 → 组件

**规则**：组件负责人、参与人必须从系统成员选取，绑定后作为任务默认执行人。

**落地**：`component_member_rel.member_id` 外键约束指向 `member` 表且 `member_status = ACTIVE`；**禁止存自由文本**。人员字段一律为成员 ID 外键 + 冗余姓名快照。

### 链路 2：组件 → 活动 → 任务

**规则**：活动分为普通基础活动、专题聚合活动两类；组件级普通活动绑定组件范围，专题聚合活动通过聚合普通活动关联组件维度；下发任务均自动匹配组件责任人；项目级活动不绑定组件。

**落地**：任务下发时，组件级任务必须携带 `component_id`；项目级任务 `component_id` 必须为空。

### 链路 3：活动 → 工序 → 流转

**规则**：工序定义准入、准出、依赖、模板，是任务执行与流转解锁的**唯一标准**。

**落地**：流转引擎**不得内置任何业务硬编码规则**，一切以 `task.snapshot` 为准。

### 链路 4：专题聚合 → 活动 → 流转

**规则**：专题聚合活动可重写多活动流转顺序，**聚合流转优先级高于单活动原生工序流转**。

**落地**：流转引擎需**先判定 `activity_type`**；`TOPIC` 类型优先读取专题跨活动拓扑，`NORMAL` 类型读取单活动内部拓扑。算法四步（建图 / 归集 / 总闸门 / 传播时机）见 11.2.3。

### 链路 5：任务下发 → 工单拆分 → 看板聚合

**规则**：单发多选组件、批量范围组件，均按组件拆独立工单，责任、流转、数据完全隔离，最终统一由进度看板全域聚合统计。

**落地**：拆分后各工单持有独立 `order_id`，看板按 `order_status` 聚合并支持按 `component_id` 下钻。

### 链路 6：执行 → 反馈 → 审核 → 流转 → 问题 / 风险归集

**规则**：反馈达标 + 交付物齐全 + 审核通过 = 节点闭环 + 解锁后置任务；作业过程上报的问题、风险自动归集至独立台账模块，实现专项管控闭环。

**落地**：闭环判定**唯一函数**见 18.2；问题 / 风险同步为**单向实时推送 + 双向可跳转**（对账式同步 `reconcile` 幂等）。

### 18.1 双颗粒度配置矩阵（汇总速查）

### 18.2 准出校验四象限穷举判定器

> 本节为**工序闭环判定的唯一实现依据**，被活动管理、任务流转引擎、任务进度反馈、任务审核四个模块共同引用。**禁止任何模块另写一套判定逻辑。**

**前提**：每道工序准出配置两个布尔因子（取值**来自工单固化快照**，**非实时活动配置**）：
- **因子 A**：`must_audit`（是否需审核）
- **因子 B**：`must_submit_deliverable`（是否需提交交付件）

**输入**

```
{
  exit_content_filled: bool,      # 准出内容是否完整填报
  deliverable_submitted: bool,    # 必选交付物是否齐全
  audit_status: enum(WAIT_REVIEW, PASSED, REJECTED, RECHECK)
}
```

**判定规则（四象限，穷举无遗漏）**

| 场景 | 因子组合 | 前置条件 | 动作 | 闭环条件 | 打回分支 |
| --- | --- | --- | --- | --- | --- |
| 1 | **A0 ∩ B0**（无需审核、无需交付件） | `exit_content_filled == true` | 系统自动判定工序闭环 → 工序置 `CLOSED` → 自动解锁所有后置工序 | — | — |
| 2 | **A0 ∩ B1**（需交付件、无需审核） | `exit_content_filled == true` 且 `deliverable_submitted == true` | 系统自动闭环 → 工序置 `CLOSED` → 自动解锁后置工序 | — | — |
| 3 | **A1 ∩ B0**（需审核、无需交付件） | `exit_content_filled == true` | 工序置 `REVIEWING`（待审核）→ 等待审核 | `audit_status == PASSED` → 工序 `CLOSED` → 解锁后置工序 | `REJECTED` → 工序退回 `EXECUTING`，锁止后置 |
| 4 | **A1 ∩ B1**（需审核 + 需交付件） | `exit_content_filled == true` 且 `deliverable_submitted == true` | 工序置 `REVIEWING`（待审核）→ 等待审核 | `audit_status == PASSED` → 工序 `CLOSED` → 解锁后置工序 | `REJECTED` → 工序退回 `EXECUTING`，锁止后置 |

**⚠️ 落库时序（强制，对应缺陷 D-14）**

判定器是纯函数，**但调用它的出口必须遵守「先落库、后判定」的时序**：

1. 审核动作**先将** `audit_status` 置为 `PASSED` / `REJECTED` **并落库**；
2. **再调用**闭环判定 `isProcessClosed()`；
3. 判定通过**方置**工序 `CLOSED`，并触发后置工序解锁传播。

反例（历史实际缺陷）：先判定后落库 —— 在需审核场景下判定时 `audit_status` 仍是旧值（`WAIT_REVIEW`），`isProcessClosed` 取到「审核未通过」而拒绝闭环，**审核通过被误报为「前置未满足」，A1 象限整体不可闭环**。

**自检问题**：本次闭环判定读到的 `audit_status`，是本次审核动作写进去的那个值吗？

**通用后置工序解锁条件**

```
某一个后置工序可解锁 ⇔ 其全部前置工序的 process_status == CLOSED
（单前置即串行；多前置即聚合；无前置即启动即解锁）
```

**⚠️ 两条并列规则，缺一不可**（对应缺陷 D-09）：

- 无前置工序（`is_no_predecessor == true` 或快照中无入边）→ **工单流转启动即解锁**；
- 有前置工序 → **全部前置闭环才解锁**；
- **其余情形一律保持 `LOCKED`，禁止「启动即全部解锁」**。

历史缺陷根因：两条规则被合并为一个 `OR` 条件，导致全部工序启动即 `EXECUTING`、`LOCKED` 永不可达。

**⚠️ 跨活动闸门**：专题聚合工单还须满足「其所属活动的跨活动前置全部闭环」，即解锁条件是「**跨活动闸门 ∧ 活动内闸门**」的**合取**（算法见 11.2.3）。

**禁止事项**

- 禁止在任何场景下**跳过解锁条件直接置工序为 `CLOSED`**。
- 禁止将**交付物标准模板是否匹配**纳入判定（模板仅作参考）。
- 禁止用 `is_passed` / `is_closed` / `is_rejected` 等**布尔字段拼装替代 `process_status` 枚举**。

### 18.3 任务时效与 SLA 判定器

> **核心原则：时效管控仅做预警与统计，不改变任务流转主逻辑。**

**一、三档判定规则（全部系统计算，无人工维护入口）**

```
剩余时间 = plan_finish_time - now()

剩余时间 > 24 小时                 → NORMAL（正常）
0 < 剩余时间 ≤ 24 小时             → NEAR_OVERDUE（即将超时）
剩余时间 ≤ 0（已超计划完成时间）    → OVERDUE（已超时）
```

**二、独立维度约束（硬约束）**

- `deadline_status` 为**辅助标记，不是工单主状态**，不得参与任何 `order_status` 判定。
- 超时**不得阻塞工序执行、不得阻塞流转、不得改变工单主状态**。
- 单条工单在任一时刻**仅有一个** `deadline_status` 值。

**三、计划完成时间来源**

- 任务下发时必填；默认值 = 活动配置的**标准工期（hours）**计算所得；
- 允许下发人按投产窗口人工调整；
- 工序级可选配置「标准工期（小时）」，用于计算工序级时效。

**四、预警通知触发**

- 进入 `NEAR_OVERDUE` → 通知「当前执行人」；
- 进入 `OVERDUE` → 通知「当前执行人 + 组件负责人 + 项目负责人」；
- 通道：系统消息中心；通知记录留痕可查。

**五、SLA 特殊规则**

- **暂停期间**：SLA 计时暂停，暂停时长不计入 SLA。实现：恢复时 `plan_finish_time` 顺延（+ 暂停时长），并记录 `suspend_log`。
- **时效豁免**（`sla_exempt = true`）：该工单**不再参与超时预警与超时率统计**。

**六、看板分桶**

数据看板按 `NORMAL` / `NEAR_OVERDUE` / `OVERDUE` 三档分桶统计超时分布，统计口径与工单进度状态统计保持一致，作为**叠加维度而非主分类**。

**七、时效指标**

- 工单按时闭环率 = 按时闭环工单数 / 应闭环工单数
- 平均闭环时长 = `avg(closed_at - flow_start_at)`
- 超时工单占比 = 超时工单数 / 总工单数

（以上指标用于项目复盘与活动标准工期优化，**不参与流转判定**。）

**八、口径确认（逐条可断言，均为实战实证后固化）**

1. **谁参与预警**：**仅「在办工单」参与预警**——`order_status ∈ {CLOSED, ARCHIVED, CANCELLED}` 一律不预警。已闭环 / 已归档 / 已作废的工单即使 `plan_finish_time` 已过，也**不得产生预警通知**，否则消息中心会被历史数据淹没。
2. **豁免即静默**：`sla_exempt = true` 的工单时效标记**恒为 `NORMAL`**，不预警、不进超时率分母。
3. **暂停与三档的先后**：恢复时**先顺延** `plan_finish_time`（+ 暂停时长），**再**据此重算三档；顺序颠倒会把暂停期间算成超时。暂停期间不重算三档（工单未在流转）。
4. **通知接收人分档**：`NEAR_OVERDUE` → 仅当前执行人；`OVERDUE` → 当前执行人 + **组件负责人** + **项目负责人**。**组件级工单**的组件负责人取 `component.migration_owner_id`；**项目级工单**无组件，第三位改为项目负责人，实现时**不得对 `component_id = NULL` 直接取组件负责人**。
5. **通知幂等**：预警生成必须幂等——同一工单在同一档位内重复触达**不得产生多条同档通知**，避免刷新即刷屏。
6. **时效刷新时机**：时效为**读写前置钩子**（读取列表 / 详情与状态变更前刷新），**非定时任务强依赖**；刷新只写 `deadline_status` 与通知，**绝不触碰 `order_status`**。
7. **冗余字段与实时值必须一致**：`work_order.deadline_status` 为派生冗余字段，须与看板视图 `v_order_deadline_live` 的实时计算值一致；**二者不一致即说明闸门漏算，属缺陷而非「允许的延迟」**。

### 18.4 状态机异常分支判定器（4 类）

> 四类分支均为**管理员例外干预**，**常规流转不进入**。

#### 分支 1：暂停（`SUSPENDED`，工单主状态）

- **触发角色**：仅数据迁移管理员
- **前置条件**：工单处于流转中（非终态、非已归档）
- **动作**：
  - `order_status → SUSPENDED`
  - **全部工序锁定**（禁止执行、禁止提审）
  - SLA 计时暂停，记录 `suspend_at`
- **恢复**：
  - `order_status` 回到**暂停前状态**（需记录 `suspend_before_status`）
  - 保留**全部**历史记录
  - 记录 `resume_at`，`plan_finish_time` **顺延**暂停时长
- **约束**：暂停时长**不计入 SLA**

#### 分支 2：转交（执行人变更，工单主状态不变）

- **触发角色**：数据迁移管理员 **或** 组件负责人
- **动作**：
  - `current_executor_id → next_executor_id`
  - `order_status` **不变**（禁止因转交改变主状态）
  - **必须填写转交原因**，写 `order_transfer_log`（原执行人、新执行人、原因、操作人、时间）
- **权限变化**：转交后**原执行人仅可查看、不可编辑**

#### 分支 3：超时（时效预警，非状态变更）

- **动作**：
  - 仅更新 `deadline_status → OVERDUE`
  - `order_status` **保持不变**
  - 触发超时通知（见 18.3）
- **约束**：不阻塞工序流转、不改变工单主状态

#### 分支 4：异常重启（管理员对锁死异常工单）

- **触发角色**：仅数据迁移管理员
- **动作**：
  - 按快照恢复至**最近一次有效流转节点**
  - **恢复点之后的解锁 / 已闭环工序必须被重置**（回到 `LOCKED`、清空 `unlocked_at` / `closed_at`），否则会出现「已经闭环的工序又排在恢复点之后、却仍显示已闭环」的溯源矛盾
  - 强制留痕（`restart_log`：恢复点、原因、操作人、时间）
- **约束**：**禁止跳过工序**；重启后仍须按快照配置逐工序流转

#### 可断言后果清单（对应缺陷 D-19）

四类分支在实现后**必须各自产生可被自动化断言观测到的后果**，否则「分支已实现」无法证明：

| 分支 | 可断言后果 |
| --- | --- |
| **分支 1 暂停** | ① 全部工序 `process_status == LOCKED`；② 反馈写操作被拒（含提审）；③ `order_status == SUSPENDED` 且 `suspend_before_status` 非空；④ `suspend_at` 已写入 |
| **分支 1 恢复** | ① `order_status` 回到 `suspend_before_status`；② `plan_finish_time` 已按 `suspend_hours` 顺延；③ `resume_at` 已写入；④ 历史记录（暂停前的进度、日志）一条不少 |
| **分支 2 转交** | ① `current_executor_id` 变为目标人；② `order_status` 与转交前**完全一致**；③ 原执行人对该工单反馈**只读**（写操作被拒）；④ `order_transfer_log` 有且仅有一条对应记录且原因非空 |
| **分支 3 超时** | ① `deadline_status == OVERDUE`；② `order_status` **不变**；③ 工序可执行性不变；④ 预警通知已生成且接收人符合 18.3 八·4 的分档 |
| **分支 4 异常重启** | ① `restart_log` 已留痕且恢复点 ≤ 最近一次有效流转节点；② **恢复点之后的工序被重置**（若恢复点之后本存在已闭环工序，该工序必须变为未解锁）；③ 恢复点及其之前的已闭环工序不受影响 |

> **设计要点**：挑选恢复点 / 断言对象时，**必须确保「恢复点之后确实存在可被重置的对象」**——若恢复点就是最近一次闭环节点，则其后本无可重置工序，用例会**恒真通过**（历史缺陷正是如此）。

#### 例外干预态清单

| 状态 | 性质 |
| --- | --- |
| 已暂停（`SUSPENDED`） | 可恢复 |
| 已作废（`CANCELLED`） | 终态，仅历史可查 |
| 已归档（`ARCHIVED`） | 终态，只读 |

- **常规流转链路不进入上述三态**；「审核打回」为过渡态，自动退回「执行中」。
- **三态只读的落地口径**：上述三态下，一切**写操作**（反馈保存 / 提审 / 问题风险上报 / 工作日志 / 流转推进 / 再次暂停 / 再次作废）**一律拒绝并返回只读原因**；**只读态判定必须先于任何后续分支判定**（详见 12.2.1）。
- **打回的派生口径**：工单主状态为「审核打回」时，其**工序状态可能已回落为「执行中」**，此时「是否处于打回整改期」以**审核态 `REJECTED`** 为准，而非工序状态（详见 3.2）。

**必查自检项（均为实测缺陷的直接整改）**

| 自检项 | 要点 | 自检问题 |
| --- | --- | --- |
| **按契约完整传参** | 构造入参必须显式提供接口契约要求的**全部必填字段与嵌套配置**，不得依赖「缺省即通过」；断言自身因缺参抛错会被误读为业务失败，更严重的是**掩盖真实缺陷** | 这条断言失败时，我能一眼区分「业务不符合预期」和「我自己参数没给对」吗？ |

| **状态枚举可达性** | 逐条核对第 3 章枚举表，确认每个值都有实体或已被用例构造；「某状态无人造数据」会让依赖它的断言**恒真通过** | — |
| **断言对象必须真实存在** | 验证「重置 / 清空 / 回退」类分支时，必须确认被作用的对象在操作前**确实处于非初始态** | — |
| **种子自检前置** | 若本模块依赖种子数据，种子生成脚本须在产出前对铁律不变式做**全量自检并打印结果** | — |
| **验证有效性** | 断言失败能否自证归因？被判对象操作前是否处于**非目标态**？依赖的枚举值 / 种子实体是否存在？单独跑与全量跑结论是否一致？期望值是否可由条款**计算**得出？ | 把断言里「真正会变化」的那一步删掉，这条断言还会失败吗？ |
| **副作用初始化** | 组件挂载期的异步取数是否全部经 `useEffect` 触发？渲染路径上是否存在 `useMemo` / 函数体直接执行取数、订阅、计时器？ | 删掉这条取数调用，组件首次渲染是否仍为纯函数？ |

**第 8 步：入口装配检查 + 可达性验证（L2 渲染冒烟）**

本步**强制，不得省略、不得以「人工点开看一下」替代**。

1. **入口装配自检**：确认挂载入口已一次性装配 路由容器 → 主题 / locale Provider → 应用级 Provider → 全局 Store → 根组件；在入口文件中能搜到 Router 容器包裹（本项目为 `HashRouter`）；不存在 `<Routes>` 裸用。
2. **渲染冒烟**：以真实生产构建产物（`vite build` 输出）在 jsdom 中实际挂载，逐路由断言：
   - 模块加载无未捕获异常；
   - 渲染期无 React 致命 `console.error` / `unhandledRejection`；
   - `#root` 已渲染出内容（innerHTML 长度显著大于 0，**非白屏**）；
   - 关键区域已渲染（左侧目录导航、当前页面标志性文案）。
3. **自证有效**：测试必须能复现「移除 Router 容器即失败」，避免写成恒真断言。
4. **入口产物权威定位**（对应缺陷 D-08）：产物 code-split 后存在多个 `index-*.js`，**禁止按文件名通配取「第一个」作为入口**——第三方库子 chunk 可能在顶层访问浏览器专有对象（如 `Document.prototype`），一旦被误当作入口加载，会抛 `Document is not defined` 并让**全部路由同时报白屏**，产生假阴性、误判为业务回归。正确做法：从 `dist/index.html` 的 `<script type="module" src>` 解析真实入口；解析失败时回退取体积最大的 chunk 并打印 WARN。
   - 自检问题：本次冒烟的入口文件路径，是从 `index.html` 得来的，还是猜出来的？
5. **降级路径可达性**（铁律 #16）：逐项确认本模块的降级 / 兜底 / 异常分支路径（画布降级视图、加载失败兜底、状态机异常分支、超时与重启分支等），每一条是否都有**在 jsdom 中可触发并断言**的用例；确属物理上无法自动化的指标（如帧率）必须单独登记为「人工验收项」，且**不得以登记替代分支可达性断言**。
6. **锚点轮询等待**（对应缺陷 D-24）：L2 对异步页面的等待**禁止固定 sleep**（`400ms` / `800ms` 在路由增多、负载变重后必然临界 flaky——单跑全绿、全量跑偶红）。统一改为**锚点轮询**：以 `100ms` 间隔轮询页面锚点文本（该路由 expect 清单全部命中即通过），命中即退、以 `5s` 为兜底上限；命中后保留 ~`100ms` 稳定缓冲。
   - 自检问题：把本机负载放大十倍，这条路由的判定结果还会变吗？会，即说明仍在赌时序。
7. **入口锚点断言**（铁律 #19）：对本模块「核心能力清单」逐项确认——该能力在列表级入口是否有直达动作，且该直达入口在 L2 中有**锚点断言**（按钮 / 链接文案出现在列表路由 expect 清单中）。
   - 自检问题：只看列表路由的锚点断言清单，能否回答用户从列表页如何到达每个核心能力？
8. **视图切换回归自检**：本模块若存在多视图切换组件（画布 / 表格、展开 / 收起、主 / 降级），逐方向验证「切走再切回」可恢复初始装配态；切回需重装配的视图必须显式触发重装路径。
   - 自检问题：每个切换方向来回各走一遍，是否存在某个方向永久卡在中间态？

### 20.1 系统硬性业务约束（最终落地规则）

### 20.6 经验条目汇总（建议纳入后续批次通用验收基线）

| 编号 | 经验 |
| --- | --- |
| E-01 | `build` / `typecheck` 通过 ≠ 运行期可用；任何批次交付前必须跑真实渲染冒烟 |
| E-02 | React 组件树依赖的「容器型 Provider」（Router / ConfigProvider / 状态容器）必须在入口文件一次性齐备；缺任何一个都表现为白屏，且**编译期零提示** |
| E-03 | 验收断言必须覆盖「交付物的最终形态」——前端模块的最终形态是**能渲染的页面**，而不是能返回数据的函数 |
| E-04 | 判定器可选参数必须显式区分「不校验」与「校验且空集」；**只测非法不测合法，等于没测** |
| E-05 | 「冻结」类数据必须能自证身份：版本号 / 归属 / 冻结时间随载荷写入并 1:1 恒等 |
| E-06 | 同一业务规则只允许在一个出口生效；两处都校验时必须确认语义一致，否则先删一处 |
| E-07 | L2 验收自身要保证加载的是入口产物：必须从 `index.html` 解析，**禁止按文件名猜** |
| E-08 | 工具链类改动（新增依赖 / 动态 import / code-split）属验收基础设施变更，须与业务改动**同批**回归 L2 |
| E-09 | 「优先级高于」不是条款，是**待实现的算法**：必须给出判定方式、判定时机与传播路径 |
| E-10 | 纯函数判定器无时序，**调用它的出口有时序**；必须声明「判定所需状态在本步之前已写入」 |
| E-11 | 多段校验顺序体现语义优先级：只读态 → 契约前置 → 状态锁 → 身份权限；**契约错误不得被状态错误吞掉** |
| E-12 | 多处状态同时变化时，必须显式指定派生主状态的取值依据，**禁止让实现方从直觉推导** |
| E-13 | 枚举「有定义」≠「能走到」；**死枚举是「假通过」的隐蔽来源**，须逐值做可达性自检 |
| E-14 | 断言失败必须可自证归因；用例按契约完整传参且相互隔离，否则无法区分「业务错」与「用例错」 |
| E-15 | 验证「重置 / 回退 / 清空」分支前，先确认被作用对象操作前处于**非初始态**，否则是空转的假通过 |
| E-16 | **种子是所有断言的地基**；种子生成脚本必须在产出前做铁律不变式全量自检并打印结果 |
| E-17 | 渲染函数必须是纯函数：异步取数 / 订阅 / 计时器一律放 `useEffect` |
| E-18 | L2 等待异步页面一律**锚点轮询**（100ms 间隔 / 5s 兜底 / 命中即退），禁止固定 sleep |
| E-19 | 可达性的证据不止「当前态实体」：**只追加的流转留痕是「曾到达」的永久证明** |
| E-20 | 给种子补实体（对账明细 / 留痕 / 反例）可能撞 L1 用例的构造前提；长会话恢复后先检索核对关键符号再增量修改 |
| E-21 | **自动化验收全绿 ≠ 交付无缺陷**：L1 验证规则、L2 验证渲染、E2E 验证链路，三者各自有盲区 |
| E-22 | 每条「非法必拒」必须配对「**合法必通**」：单向断言会让闸门误杀合法输入而全绿如常 |
