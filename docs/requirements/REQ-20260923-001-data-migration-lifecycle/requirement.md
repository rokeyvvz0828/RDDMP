# 数据迁移生命周期任务管理平台

## 业务目标

在 RDDMP 技术栈（后端 Java 17 / Spring Boot 3.4.4 / MyBatis-Plus / MySQL 8.4 / Flyway；前端 Vue 3 / TypeScript / Element Plus / Vue Router / Pinia）上落地实施《数据迁移生命周期任务管理平台》，形成「角色权限 → 组件+人员 → 活动+工序 → 专题聚合 → 任务下发/流转/反馈/审核」的任务流转管控闭环。角色管理、组件管理、成员管理**直接复用系统现有能力，不重复开发**。

正式需求基线为同目录附件`data-migration-lifecycle-requirement-fused-v1.0.md`（基线文档原文副本）（以下简称「基线文档」）。基线文档第 3 章（全局状态枚举唯一基准）、第 4 章（19 条系统级铁律）、第 18 章（跨模块专项判定器）为本需求不可违反的红线。

## 范围

### 本次实施（对应基线文档模块 4~11）

- 活动管理：普通基础活动/专题聚合活动、工序拓扑、工序标准化配置（准入/准出/角色/模板）、模板导入导出。
- 任务发布：单发/批量下发、组件勾选随颗粒度联动、专题「普通活动×组件」矩阵拆分、快照固化。
- 任务流转引擎：工单承接、自动流转（串行/并行/聚合依赖）、四象限闭环判定、SLA 时效、暂停/转交/超时/异常重启。
- 任务进度反馈：进度填报、准出内容、交付物、执行日志、问题/风险上报、提审。
- 问题管理 + 历史问题知识库；风险管理 + 风险策略库。
- 任务审核管理：单条/批量审核、打回整改、10 分钟撤销窗口、多轮复审。
- 数据看板：六大维度统计、权限前置过滤、专题独立统计、下钻跳转。
- 平台能力接入：角色权限/成员/组件复用现有能力（RBAC 权限点、数据范围四档、`dm_component` 组件与负责人绑定），仅做接入与权限点注册；文件附件复用 `platform/attachment` 受控能力。

### 本次不实施

- 不重新开发角色管理、组件管理、成员管理。
- 不迁移原 React/AntD 原型代码，不引入 React、Ant Design、AntV X6、Spring StateMachine 等新依赖（除非单独决策）。
- 不改变既有数据迁移资产库 V3 的行为；组件模型不足以支撑时（启用状态/参与人），以独立决策与最小扩展任务处理。
- 不依赖已下线的输入项配置/业务表单元数据能力（`biz_form_*`）。
- 基线文档登记为迭代/候选的项（图形化专题画布、看板图形化图表等）不在默认范围，除非用户另行确认。
- 不连接或修改生产系统。

## 现状与规则

- 组件复用现状：现有 `dm_component` 已具备项目归属、负责人（`owner_id`）、软删除（`deleted`）；**缺少启用/停用状态与参与人绑定**，与基线文档铁律 #6 存在差距，需在建模阶段核查并决策最小适配方案。
- 状态建模：全系统状态枚举以基线文档第 3 章为唯一定义处（工单 9 态/工序 5 态/活动 3 态/问题 4 态/风险 6 态/审核 4 态 + 时效 3 档 + 工序配置 2 态），后端枚举与前端文案 1:1，禁止布尔字段拆分状态。
- 权限与数据范围：服务端 RBAC + 四档数据范围（普通执行人/审核人/组件与项目负责人/数据迁移管理员）；列表与统计先权限过滤后计算；写操作审计留痕。
- 快照与流转：任务下发瞬间深拷贝固化活动配置快照，流转仅以快照为依据；准出双因子（是否需审核/是否需提交交付件）四象限判定；工序级事件必须回写工单主状态重算。
- 前端规范：业务页面复用 `delivery-showcase` 与公共组件，遵循 `design-h5.md` 桌面/移动验收；前端显隐不替代后端校验。

## 接口与数据

- API：统一 `/api` 前缀与 `{ code, data, message }` 响应；每个校验项唯一错误码（铁律 #12）；前后端先固定字段、错误语义、权限与数据来源后再并行实现。
- 数据 Owner：归属于 `business/data-migration` 模块（默认方案，见决策 D1）；新表通过 Flyway 追加迁移（当前最新迁移 V155，新增从 V156 起）。
- 依赖复用：成员/角色来自 `platform/system`；附件来自 `platform/attachment`；组件读取 `dm_component`（同模块内）。
- 脱敏：演示数据虚构，禁止生产数据、真实个人信息、口令与密钥入库。

## 决策点（实施前确认，对应 .ai-control 基线 decisions）

- D1 模块边界：并入现有 `business/data-migration`（推荐，避免跨模块契约与注册开销）或新建独立业务模块。
- D2 组件模型适配：`dm_component` 缺启用状态/参与人；选择「`deleted=0` 视为可用 + 台账侧补充参与人」或「最小扩展组件模型」。
- D3 批次推进：按基线文档批次 1~4 顺序分阶段实施，每个批次独立受控执行、观测与验收。
- D4 分支命名：`datamigration-ljy` 不符合仓库 `feat|fix/REQ-YYYYMMDD-NNN-*` 规则，需重命名为 `feat/REQ-20260923-001-data-migration-lifecycle`（或另行治理决策豁免）。

## 验收标准

1. 基线文档第 3 章全部状态枚举在种子/用例中可达（铁律 #11/#18 可达性自检）。
2. 19 条铁律逐条有断言覆盖；每条「非法必拒」配对「合法必通」；错误码 1:1。
3. `mvn -pl :ccb-data-migration -am test`、`mvn test`、`npm --prefix web run build`、`node scripts/check-all-governance.mjs`、`node scripts/check-codex-scope.mjs` 全部通过。
4. 本地开发环境启动后，按角色（数据迁移管理员/组件负责人/审核人/普通执行人）真实浏览器验收核心链路；桌面与移动视口（375/390/430/1280）无遮挡、无横向溢出。
5. 按批次登记 `.ai-control` 执行/观测证据，收敛后才可声明完成。
