# 项目级角色权限工程设计

## 文档状态

- 修订：1
- 状态：已确认
- 用户确认依据：用户依次确认系统权限与项目权限边界、存量角色初始化规则、页面交互及接口鉴权设计。

## 目标与成功信号

将业务页面权限从系统角色配置迁移到项目角色配置。用户切换顶部项目后，导航、页面和操作权限立即切换为该用户在目标项目中所有角色权限的并集；系统设置权限继续由全局系统角色控制。系统设置新增权限维护入口，维护的业务权限可在项目角色中勾选。

成功信号：同一用户在两个项目拥有不同角色时，切换项目后可见菜单、可访问路由、按钮和后端写接口同步变化；伪造项目上下文不能越权；系统管理权限不受项目角色影响。

## 使用者与场景

- 系统管理员在“系统设置 / 权限维护”维护权限目录及启停状态。
- 项目负责人或拥有项目角色维护权限的成员，在项目设置中维护项目角色并配置该角色的业务权限。
- 项目成员从顶部项目切换器切换项目，系统按目标项目重新计算权限。

## 必须需求与验收条件

- R1：系统设置以“权限维护”替换原角色权限配置，支持权限查询、新增、编辑、启停和删除；权限编码创建后不可修改。
- R2：项目设置的项目角色支持在可全屏抽屉中按菜单分组勾选业务权限，并显示成员数和权限数。
- R3：项目角色权限按租户、项目和角色隔离；成员多角色权限取并集。
- R4：切换项目后重新加载用户权限和动态路由；当前路由无权访问时跳转工作台并提示。
- R5：系统管理权限保持全局系统角色控制，项目角色不能配置系统管理权限；不依赖当前项目的能力（例如创建项目）保持全局控制。
- R6：服务端按可信用户身份和请求项目上下文执行 RBAC、项目成员关系、实体归属和租户校验，并审计权限目录及项目角色权限写操作。
- R7：存量项目的 PM 角色获得全部项目业务权限，其他已有项目角色获得查看权限；新角色默认无权限；项目负责人始终拥有当前项目全部业务权限。

反例包括：只隐藏前端按钮但接口仍可写入、切换项目后沿用旧权限、项目角色可勾选 `system:*` 权限、跨项目角色 ID 可读取或写入权限、权限保存失败后界面显示成功。

## 不变量与约束

- 保持现有 Java 包名、模块边界、JWT 登录方式和顶部项目切换入口。
- `sys_menu` 与 `sys_menu_permission` 继续是全平台菜单和权限目录的唯一事实源。
- `sys_role*` 继续承载平台级系统管理权限，不删除系统角色模型。
- Flyway 只追加迁移，不修改 V1-V200；所有数据访问包含 `tenant_id` 和项目归属校验。
- 前端权限显隐不替代服务端授权；权限配置写操作必须审计。
- 不读取或提交 `.env`、口令、Token、生产数据或真实个人数据。

## 非目标

- 不重构 JWT 格式，不把完整权限列表写入 Token。
- 不引入字段元数据或动态表单能力。
- 不改变组织架构、项目成员管理和业务数据本身。
- 不允许项目角色授予系统设置权限。

## 方案比较与选择

选择“请求携带当前项目上下文，服务端实时计算全局权限与项目权限并集”。前端统一携带 `X-Project-Id`，切换项目后重新获取个人信息和路由。该方案多标签页兼容性好，权限撤销可即时生效，且服务端可独立阻止越权。

未选择“切换项目时重新签发 Token”，因为会引入 Token 轮换、并发标签页和缓存失配；未选择“仅前端合并项目权限”，因为不能保护后端接口。

## 架构边界与组件职责

- 权限目录：System 模块负责 `sys_menu_permission` 的查询与维护，校验编码唯一、菜单归属、使用关系和状态，写操作进入审计。
- 项目角色授权：System 项目服务负责项目角色与权限关系，验证维护者、项目、角色和权限适用范围。
- 有效权限：Security 模块读取系统角色的系统权限，并按请求项目读取项目成员角色权限；项目负责人执行项目权限兜底。
- 项目上下文：前端 project-context store 保存当前项目；HTTP 层附加上下文；auth store 在切换后刷新个人权限和动态路由。
- 页面：权限维护页复用现有权限树语义；项目设置角色区复用权限树和可全屏抽屉能力。

系统权限目录属于平台公共能力。本需求需要 System、Security、Infrastructure 和前端公共鉴权协同修改，必须由对应 Owner 复核服务端授权、动态路由和前端操作权限。

## 接口、数据和状态流

新增 `pm_project_role_permission`，至少包含 `tenant_id`、`project_id`、`role_id`、`permission_id`、创建时间，并对 `(tenant_id, project_id, role_id, permission_id)` 建唯一约束和查询索引。权限 ID 引用 `sys_menu_permission`；写入时再次验证权限启用且不属于系统菜单树。

权限目录接口：

- `GET /api/system/permissions`：按菜单、关键字和状态查询权限。
- `POST /api/system/permissions`：新增权限。
- `PUT /api/system/permissions/{id}`：编辑名称、菜单、动作和状态，编码不可修改。
- `PUT /api/system/permissions/{id}/status`：启停权限。
- `DELETE /api/system/permissions/{id}`：仅未被系统角色或项目角色引用时允许删除。

项目角色权限接口：

- `GET /api/projects/{projectId}/roles/{roleId}/permissions`：返回可选业务权限目录及已选 ID。
- `PUT /api/projects/{projectId}/roles/{roleId}/permissions`：事务性替换该角色权限集合。

鉴权接口和状态流：

1. HTTP 客户端从项目上下文读取当前项目，向项目业务请求附加 `X-Project-Id`。
2. 后端校验请求路径/实体项目与请求头一致，验证租户、项目和成员或负责人关系。
3. `/api/auth/me` 与动态路由查询接受同一项目上下文，返回“系统角色的系统权限 + 当前项目角色的业务权限”并集。
4. 项目切换器进入提交中状态，刷新资料和路由；成功后发布项目变化，业务页面重新查询数据。
5. 目标项目无当前路由权限时跳转工作台并显示一次明确提示；刷新页面按持久化项目重新加载。

业务权限适用范围按菜单树判断：系统设置菜单树及不依赖项目上下文的全局操作不进入项目角色候选目录。动态路由保留父级目录，只要后代菜单存在一个有效权限即可展示。

## 错误、降级与恢复

- 缺少、非法或伪造项目上下文：项目业务接口返回 403，不回退到其他项目或全局业务权限。
- 用户不是项目成员且不是负责人：返回 403，前端提示无当前项目访问权并刷新可选项目。
- 跨项目 roleId 或 permissionId：返回 400/403，不产生部分写入。
- 权限目录编码重复、权限被引用、系统权限被配置到项目角色：拒绝并返回可理解错误。
- 切换项目加载失败：保留原项目和原权限，允许重试；不得先更新页面权限再报告失败。
- 保存失败：保留抽屉和本地勾选，解除提交中状态并允许重试。
- 权限在使用中被停用：后续请求立即不再授予；界面提示影响范围，历史关系保留以便恢复。

## 安全、性能、兼容性与运维

- 权限查询按用户、项目、角色和权限索引；单请求查询结果可做短生命周期请求级缓存，不跨项目共享。
- 系统管理员权限与项目权限分开读取和合并，禁止将系统权限通过项目角色提升。
- 迁移幂等初始化存量项目角色；PM 全量、非 PM 查看、新角色空权限，项目负责人兜底。
- 原系统角色中的业务权限关系迁移后不再参与项目业务授权，但系统角色及系统权限关系保留以支持回退。
- 审计记录操作者、项目、角色、权限集合变化和结果，不记录 Token 或敏感字段。

## 验证策略

- 后端单元/集成：权限目录 CRUD 与引用保护、权限并集、PM/负责人兜底、非 PM 初始化、跨租户和跨项目拒绝、停用即时生效。
- 前端构建与组件交互：权限搜索、分组全选、保存失败恢复、重复提交保护、项目切换刷新和无权路由跳转。
- API 验收：同一用户在项目 A/B 具有不同角色，使用相同账号和不同 `X-Project-Id` 获得不同权限；伪造项目 ID 返回 403。
- 浏览器验收：管理员维护权限，项目负责人授权角色，普通成员切换项目后菜单/按钮/接口同步变化；刷新保持；桌面和 390px 手机视口无溢出，抽屉可全屏。
- 回归：系统用户、组织、菜单、参数、登录、动态路由、项目成员与项目角色现有功能。

## 假设、未知项与决策记录

- 已确认 D1：系统管理权限保持全局系统角色控制，项目角色只配置项目业务权限。
- 已确认 D2：存量 PM 全权限、其他角色查看权限、新角色无权限，项目负责人全权限兜底。
- 已确认 D3：采用请求项目上下文实时鉴权，不重新签发 Token。
- 已确认 D4：权限维护使用系统设置页面，项目角色使用可全屏抽屉配置权限。
- 工程环境门禁：`node scripts/check-development-entry.mjs --require-plugin` 当前因 Codex 插件列表返回 `unknown error` 而失败；实施前必须恢复门禁或由仓库维护者确认该检查器误报并修复开发环境。

## 风险与回退原则

- 最大风险是项目上下文缺失或旧调用方未携带请求头。实施计划必须先盘点项目业务 API，并为系统级、项目级请求建立明确分类和兼容测试。
- 动态路由和接口权限来源必须同步切换，避免菜单可见但接口 403 或相反状态。
- 回退时恢复系统角色业务权限读取和原角色权限配置入口；新增关系表保留但停止读取，避免丢失已配置数据。Flyway 不回退版本，必要时使用追加补偿迁移。
