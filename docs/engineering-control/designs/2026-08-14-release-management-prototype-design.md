## 1. 目标与成功信号

修订现有配置管理 Mock 原型，使其准确表达以下核心关系：审批完成只代表制品准出；投产管理人员在窗口投产基线中维护实际结果；只有投产成功才更新跨窗口生产版本。

成功信号：

1. 使用者能从投产窗口、版本申请、投产基线、生产版本和统计分析五个视图理解完整业务链。
2. 常规、紧急、应急和追加申请的字段、窗口、冲突与流程编码互不混淆。
3. 同一份 Mock 事实能一致驱动申请详情、准出候选、投产结果、当前生产版本和报表。
4. 审批链接在桌面和 H5 共用路由与动作模型，核心路径可实际操作。
5. 正常用户界面不出现原型调试工具；开发人员仍可进入独立调试状态。

## 4. 不变量与约束

### 4.1 业务不变量

- 当前顶级项目上下文决定所有窗口、申请、基线和统计的数据范围。
- 一张申请只属于一个项目、一个物理子系统，且包含至少一个交付单元。
- 一个交付单元只有一种制品类型：镜像或二进制；平台不接收实际制品文件。
- 非应急申请至少关联一个需求；应急申请需求编号不展示且不必填。
- 版本号必填且不允许空格，首期不比较语义版本大小。
- 版本类型为常规、紧急、应急；申请特征为普通、追加。
- 申请审批结论是整单通过或整单不通过，退回后修改并重新提交必须形成新流程轮次。
- 审批完成只产生制品准出；只有投产成功产生当前生产版本。
- 窗口内同一交付单元的候选以审批完成时间决定最新，历史候选不可丢失。
- 生产版本由有效投产成功历史派生，不允许前端独立覆盖。

### 4.2 工程约束

- 当前交付为 Vue 3、TypeScript、Element Plus、ECharts 的前端 Mock 原型。
- 不新增 npm 依赖，不修改 Java、Flyway、真实菜单数据和平台私有实现。
- 物理子系统、交付单元、当前项目、需求编号、工作流、附件均使用虚构数据或占位适配器。
- 正式服务端必须执行认证、RBAC、项目数据范围、实体授权、幂等和审计；前端禁用状态不构成授权。
- 页面在 `375x812`、`390x844`、`430x932`、`1280x800` 及以上视口可用。

## 5. 非目标

- 正式配置管理后端、表结构、Flyway、菜单迁移和生产数据。
- 需求管理、测试缺陷、项目管理和研发管理的真实集成。
- 镜像仓库、二进制仓库、制品上传、制品校验和语义版本比较。
- 独立移动端产品或独立 H5 路由。
- 外部 CA、密码二次校验或法律数字签章。
- 自动判断实际投产成功、组会工作台或批量审批。

## 6. 方案比较与选择

### 6.1 已选：统一领域 Mock + 两级基线投影 + 响应式统一审批路由

模块保存窗口、申请、审批轮次、投产明细和投产历史五类事实数据，生产版本和统计只做派生。投产基线与生产版本分开呈现；审批 Web/H5 共用业务路由和动作契约。

优点是业务含义清晰，正式后端可按同一边界落地，且能用单一数据源验证跨页面一致性。代价是修订范围覆盖现有大部分 release 原型组件，但仍局限在当前前端模块。

### 6.2 未选：在旧“基线管理”页面增加几个状态字段

改动较小，但继续混淆准出候选、窗口投产结果和当前生产版本，无法正确处理投产失败及历史回算。

### 6.3 未选：分别创建 Web 与 H5 审批页面

可独立优化布局，但会复制权限、动作和状态逻辑，后续容易出现两端审批规则不一致。

## 7. 信息架构与用户流程

模块内导航固定为：

1. **投产窗口**：维护窗口四个时间、状态、常规申请开关和规模信息。
2. **版本申请**：列表、新建、编辑、冲突处理、详情、流程进度和审批链接。
3. **投产基线**：选择窗口，维护该窗口最新准出候选的实际投产结果。
4. **生产版本**：查询每个物理子系统、交付单元最近一次投产成功版本。
5. **统计分析**：窗口、系统、交付单元、需求、版本类型、准出与投产结果分析。

正常页面不再显示“当前项目 / Mock 原型 / 正常状态”工具条。当前项目由平台顶级切换区表达；原型阶段使用 Provider 返回固定 Mock 项目。加载、空、失败、无权限和重置功能仅在开发环境 `?debug=1` 时通过调试入口显示。

### 7.1 非应急申请

1. 用户选择“是否应急版本 = 否”。
2. 页面列出当前项目可用窗口；默认选中最匹配窗口，只允许选择有效项。
3. 根据业务日期与所选窗口判定常规或紧急版本，字段只读。
4. 用户选择一个物理子系统和至少一个交付单元，登记类型和版本。
5. 页面逐项显示最近生产版本，并检查同窗口历史申请。
6. 用户关联至少一个需求，选填说明和附件。
7. 冲突框按历史状态给出允许动作；确认后保存或提交。
8. 系统根据版本类型和追加特征映射流程编码。

日期判定：业务日期位于申报周期内为常规版本；申报截止后且投产开始前为紧急版本；达到投产开始后，该窗口不再接受非应急申请。界面名称改为“紧急版本”，既有 `overdue` 流程编码保持兼容。

### 7.2 应急申请

1. 用户选择“是否应急版本 = 是”。
2. 隐藏投产窗口、只读版本类型和需求编号。
3. 用户填写物理子系统、交付单元、版本、应急情况说明，并至少上传一份测试报告。
4. 提交前校验项目是否存在当前投产窗口或未来窗口；不存在时只允许保存草稿。
5. 审批完成时按完成时间归入当时投产中的窗口，否则归入最近未来窗口；归窗后固定。

### 7.3 重复申请

冲突范围是当前项目、同一投产窗口、同一物理子系统和交付单元。弹框展示申请单号、申请状态、申请人、部门、窗口、物理子系统、全部交付单元及版本、需求、说明、版本类型、申请特征、流程进度和创建/更新时间，不展示附件。

| 历史状态 | 允许动作 |
|---|---|
| 草稿、已退回、已撤回 | 取消旧申请、修改旧申请、创建新申请 |
| 审批中 | 创建新申请；旧申请必须先撤回，之后才可取消或编辑 |
| 制品准出 | 只能创建新申请，新单自动标记追加申请 |

用户自行决策，不因历史记录直接阻断创建新单；所有取消都必须填写原因。相同交付单元和相同版本也继续提示，但不自动替用户选择。

## 8. 数据与状态模型

### 8.1 核心实体

| 实体 | 关键字段 | 说明 |
|---|---|---|
| ReleaseWindow | projectId、code、declarationStart/End、productionStart/End、regularEnabled、status | 四个时间精确到分钟 |
| ReleaseApplication | code、projectId、windowId?、subsystemId、versionType、characteristic、status、workflowCode、approvedAt? | 应急草稿和审批中允许 windowId 为空 |
| DeliveryUnitVersion | applicationId、subsystemId、deliveryUnitId、artifactType、version | 单元版本登记事实 |
| ApprovalRound | applicationId、round、taskId、nodes、result、submittedAt、completedAt | 退回重提产生新轮次 |
| WindowProductionEntry | windowId、subsystemId、deliveryUnitId、candidateApplicationId、candidateApprovedAt、result | 窗口内最新候选及投产结果 |
| ProductionHistory | windowId、subsystemId、deliveryUnitId、version、versionType、productionAt、result、audit | 投产结果历史 |
| CurrentProductionVersion | projectId、subsystemId、deliveryUnitId、version、versionType、productionAt、sourceWindowId | 由有效成功历史派生 |
| ReleaseAttachment | businessId、category、name、size、status | 应急至少一份 TEST_REPORT |

### 8.2 状态流

申请状态：

```text
草稿 -> 审批中 -> 制品准出
          |  '--> 已退回 -> 草稿 -> 审批中
          '--> 已撤回 -> 草稿
草稿 / 已退回 / 已撤回 -> 已取消
```

投产结果独立于申请状态：

```text
制品准出 -> 投产成功
         -> 投产失败
         -> 未投产
```

允许在三种投产结果间更正，也允许从结果恢复为制品准出；每次更正必须记录原因、前值、后值、操作人和时间。更正后重新派生当前生产版本。

### 8.3 候选与生产版本算法

1. 审批完成时，为每个交付单元写入准出事实。
2. 相同窗口、物理子系统、交付单元按 `approvedAt` 取最新准出申请作为当前候选。
3. 投产基线列表展示当前候选，历史候选保留在版本轨迹中。
4. 候选被标记投产成功时写入成功历史；当前生产版本取该项目、物理子系统、交付单元最新有效成功记录。
5. 成功记录改为失败、未投产或准出时，按生产时间回算上一条有效成功记录；不存在则显示“暂无生产版本”。

## 9. 架构边界与组件职责

### 9.1 当前原型

```text
ReleaseManagementPrototype
  |-- ReleasePrototypeRepository (session Mock)
  |-- ProjectContextProvider (fixed Mock)
  |-- Window / Application / ProductionLedger views
  |-- CurrentProduction / Analytics views
  '-- WorkflowReviewPage (responsive Mock task)
```

- `types.ts` 定义受控联合类型和实体。
- `mock.ts` 只保存初始事实与纯派生函数，不保存互相矛盾的重复指标。
- 模块容器拥有会话状态和跨视图动作。
- 普通业务页面不承担调试状态切换。
- 审批页通过 `taskId` 与 `businessId` 读取同一申请详情。

### 9.2 正式实现边界

- 配置管理业务模块拥有申请、交付单元版本、窗口投产明细和生产版本投影。
- 工作流平台按流程编码启动，发布至少一次的生命周期事件；业务模块按 `eventId + applicationCode + workflowRound` 幂等消费。
- 附件平台拥有上传、绑定、预览、下载、删除和清理；业务模块只保存业务绑定语义。
- 项目管理提供当前项目和成员权限，研发管理提供物理子系统及交付单元；本期均以 Provider/Adapter Mock。
- 业务模块不得写工作流、附件或其他业务模块的私有表，平台也不得反向依赖配置管理。

## 10. 正式接口候选契约

原型不调用以下真实接口，但前端 Repository 按此形状组织：

| 接口组 | 主要行为 |
|---|---|
| WindowQuery | 查询窗口及 `selectable`、`disabledReason`、四个时间和状态 |
| ApplicationCommand | 保存草稿、提交、撤回、取消、重提；写操作接收幂等键和数据版本 |
| ConflictQuery | 按草稿交付单元返回历史申请完整业务快照及允许动作 |
| WorkflowGateway | 按流程编码启动、查询进度，消费 APPROVED/RETURNED/REJECTED/TERMINATED |
| ProductionLedgerCommand | 查询窗口候选、更新投产结果并记录审计 |
| CurrentProductionQuery | 查询交付单元最近成功版本和来源窗口 |
| AnalyticsQuery | 按窗口、系统、单元、版本类型、需求和投产结果聚合与下钻 |

关键命令字段：

- 保存/提交申请：`projectId`、`emergency`、`windowId?`、`subsystemId`、`deliveryUnits[]`、`requirementIds[]`、说明、附件绑定 ID、`requestId`、`dataVersion`。
- 更新投产结果：`windowId`、`subsystemId`、`deliveryUnitId`、`candidateApplicationId`、目标结果、原因、`requestId`、`dataVersion`。
- 工作流事件：`eventId`、`businessKey`、`businessRound`、`eventType`、`result`、`operatorId`、`occurredAt`。

## 11. 审批链接与响应式布局

统一路由为：

```text
/workflow/review/:taskId?businessType=release&businessId=<applicationId>
```

- 只有当前登录人拥有有效待办时显示同意、拒绝、退回和确认签署。
- 服务端以认证主体判定任务归属，不接受客户端传入签署人。
- 电子签名由工作流节点配置决定，签名使用当前登录身份点击确认。
- Web 使用完整摘要、交付单元、附件、流程进度和右侧/底部操作区。
- H5 使用业务卡片、纵向流程、局部滚动附件和固定底部操作栏；低频危险操作进入更多菜单。
- 已处理任务转只读；链接无效或过期显示明确结果，不回退到可操作状态。

## 12. 错误、降级与恢复

| 条件 | 页面行为 | 恢复 |
|---|---|---|
| 字段校验失败 | 字段附近显示错误并保留全部录入 | 修改后重新保存或提交 |
| 无可承接应急窗口 | 草稿可保存，提交按钮阻断并说明原因 | 维护窗口后重试 |
| 重复申请 | 打开业务快照弹框并仅展示允许动作 | 用户选择处理方式 |
| 并发版本不一致 `409` | 不覆盖服务器结果，展示差异并保留本地草稿 | 刷新对象后重新确认 |
| 业务规则不满足 `422` | 使用规则编码定位字段或交付单元 | 修正后重试 |
| 无权限 `403` | 显示无权限状态，隐藏写操作 | 重新取得授权或返回列表 |
| 待办已处理/链接过期 `410` | 转为只读并显示当前处理结果 | 返回待办或详情 |
| 重复点击 | 提交中禁用，同一幂等键不产生重复记录 | 使用服务端返回的最终状态 |
| Mock 失败态 | 只替换内容区，不破坏导航和已录入表单 | 调试入口恢复正常状态 |

## 13. 安全、性能、兼容性与运维

- **安全**：原型仅用虚构数据；正式写操作必须认证、RBAC、项目数据范围、实体授权和审计。审批与签名身份只取服务端会话。
- **性能**：窗口基线和生产版本正式实现应服务端分页；交付单元最近版本支持批量查询，避免逐行请求；图表实例卸载时释放。
- **兼容性**：保留既有流程编码，旧 `overdue` 编码映射新名称“紧急版本”；不新增 H5 专属接口或路由。
- **可访问性**：状态保留文字，图标按钮有可访问名称；页面无整体横向滚动，表格和流程仅在明确容器内滚动。
- **运维**：正式实现需监控工作流事件重试、死信、应急归窗失败、投产结果更正和生产版本回算异常。

## 15. 假设、未知项与决策记录

### 15.1 已确认假设

- 当前项目 Provider、物理子系统和交付单元可先用 Mock，未来替换接口不改变页面业务语义。
- 平台工作流最终能按稳定流程编码启动并提供生命周期事件、待办已办和内部电子签名。
- 正式附件能力沿用单文件 20MB、单业务最多 10 个附件。

### 15.2 未知项

当前无阻断设计或原型实施的产品未知项。具体审批节点、角色和加签规则由平台流程配置决定，不写死在配置管理模块中。

### 15.3 关键决策

- D1：选择两级基线模型，分为投产基线和生产版本。
- D2：审批完成仅为制品准出，投产结果独立维护。
- D3：紧急版本替代旧界面名“超期常规版本”，保留流程编码兼容。
- D4：追加是系统申请特征，不是版本类型。
- D5：应急申请不选窗口，审批完成后自动归窗且固定。
- D6：重复申请由用户决策，不因历史记录直接阻断新建。
- D7：Web/H5 使用同一审批路由和服务端动作契约。
- D8：正常页面移除 Mock 调试工具，仅开发入口保留。

## 16. 风险与回退原则

| 风险 | 影响 | 缓解 |
|---|---|---|
| 旧 Mock 同时保存基线批次和申请状态 | 跨视图产生矛盾 | 修订为事实数据 + 派生投影，禁止重复硬编码指标 |
| 应急归窗依赖审批完成时间 | 窗口变化导致归属歧义 | 提交前检查可承接窗口，审批完成时服务端原子归窗并固定 |
| 重复申请弹框信息量大 | 移动端操作拥挤 | Web 使用分区详情，H5 使用摘要卡片和展开区，附件始终排除 |
| 响应式审批动作重复实现 | 两端规则漂移 | 共用路由、状态模型和动作函数，只改变布局 |
| 旧修订已标记收敛 | 容易误判新需求已完成 | 明确修订 1 证据失效范围，为修订 2 重新计划和验收 |

回退只撤销修订 2 的 release 模块、路由和样式变更，恢复修订 1 原型；不涉及数据库和后端。任何正式后端候选契约都只是后续实现边界，本次不得借原型任务写入平台代码。
