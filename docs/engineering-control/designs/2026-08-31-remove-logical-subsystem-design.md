# 移除逻辑子系统模型工程设计

## 文档状态

- 修订：1
- 状态：已确认
- 用户确认依据：用户在 2026-08-31 选择“按 B 来做”，并回复“可以”确认落盘方案 B 设计。

## 目标与成功信号

本次目标是把架构模块的主数据根对象从“逻辑子系统 + 物理子系统父子模型”收敛为“物理子系统单一主模型”。成功信号是逻辑子系统不再有可调用接口、菜单、页面、选项或新工单入口；物理子系统支持人工编号、可选逻辑文本和业务组件编号字典字段；下游能力继续通过物理子系统运行。

## 使用者与场景

架构信息维护者发起物理子系统新增或变更工单时，直接填写物理编号、系统名称、可选逻辑子系统文本、业务组件编号、负责团队和技术分类。架构信息查看者在物理子系统列表、详情和下游选择器中只看到物理主数据，不再跳转到逻辑子系统详情。

## 必须需求与验收条件

| ID | 必须需求 | 验收条件 |
| --- | --- | --- |
| R1 | 系统必须退役独立逻辑子系统模型和入口。 | 后端无逻辑 CRUD/选项可调用入口；前端无逻辑菜单/页面/申请入口；路由访问逻辑页面不可达。 |
| R2 | 系统必须通过追加迁移删除逻辑表及仅服务逻辑父级模型的结构。 | 空库和已有库迁移通过；`arch_logical_subsystem`、逻辑草稿表和逻辑编号分配结构不再存在；物理表不再有逻辑外键。 |
| R3 | 物理子系统必须保留一个可选逻辑子系统文本字段。 | 迁移从旧逻辑父级回填文本；新增/更新可为空；列表、详情、工单和 Mock 均使用该字段。 |
| R4 | 物理子系统必须新增业务组件编号字段并由系统字典管理选项。 | `ARCH_BUSINESS_COMPONENT` 分类可由平台字典管理；物理接口只接受启用项或空值；页面用下拉选择并显示标签。 |
| R5 | 物理子系统编号必须由申请人自行填写。 | 物理 CREATE/REPLACE 草稿要求 `code`；服务端转大写、格式校验、永久唯一；不再生成 `W+逻辑序号+槽位`。 |
| R6 | 下游能力必须继续以物理子系统为引用根。 | 部署单元、资源申请、环境实例、网络访问和搭建计划的物理选项、列表和详情测试通过，且不访问逻辑字段。 |
| R7 | 权限、租户、审计和表单边界必须保持。 | 服务端 RBAC、当前租户过滤、行版本、审计、无动态表单依赖和无生产数据访问检查通过。 |
| R8 | 前端必须保持桌面和移动端可用。 | 物理列表、详情、工单表单在 1280 桌面和 375/390/430 手机视口无页面级横向滚动，状态可见。 |

## 不变量与约束

- 只追加 Flyway 迁移，不修改已发布迁移。
- 不连接生产系统，不读取或写入生产数据。
- 业务代码仍在 `business/architecture`，平台只提供字典读取能力。
- 物理子系统、部署单元、资源申请、环境实例、网络访问和搭建计划的租户隔离不能放松。
- 变更工单仍是物理主记录写入入口，直接物理 CRUD 不恢复。
- 不引入动态表单元数据、`biz_form_*`、form schema 或 `PublishedFormSchemaQuery`。
- 破坏性删除表上线前必须有数据库备份和人工复核。

## 非目标

- 不把逻辑子系统迁为字典、标签主数据或另一个轻量表。
- 不从需求管理系统清单同步业务组件。
- 不重建下游业务数据，不删除部署单元、资源申请、实例、网络访问或搭建计划记录。
- 不调整工作流平台、附件平台、系统字典管理页面或公共 UI 组件。

## 方案比较与选择

### 已选：方案 B，硬删除逻辑表和所有逻辑接口

该方案完全消除旧的父子主数据模型，避免用户继续在逻辑子系统页面和物理页面之间重复维护。代价是迁移和兼容风险最高，必须同步编号策略、工单草稿、发布事务、选项 API、前端路由和下游引用。

### 未选：方案 A，兼容退役

保留逻辑表只隐藏入口，迁移风险较低，但旧模型仍存在，后续容易被接口或历史逻辑重新使用，不符合用户对方案 B 的选择。

### 未选：方案 C，仅把逻辑关联改成可选

实现成本最低，但仍保留逻辑页面、逻辑工单和逻辑选项，不能满足“移除逻辑子系统模型”。

## 架构边界与组件职责

- `server/src/modules/architecture`：删除逻辑 CRUD 和逻辑选项服务路径，改造物理模型、工单草稿、发布事务、引用检查和下游查询。
- `server/src/platform/infrastructure/.../db/migration/V147__remove_logical_subsystem_model.sql`：执行字段新增、数据回填、约束删除、逻辑结构删除和字典种子。
- `web/src/modules/architecture`：删除逻辑页面入口，改造物理页面、物理工单卡片、类型、API 和下游展示。
- `mock/mock-data.json` 与 Mock 初始化测试：去除逻辑主数据，补充物理逻辑文本和业务组件编号。
- `docs/integration/architecture-module-contract.md`：冻结新的物理主模型和被删除接口清单。

## 接口、数据和状态流

物理新增工单输入 `code + shortName + name + logicalSubsystemName? + businessComponentCode? + responsibleTeamOrgId + ...`。服务端先校验编号和字典，再保留名称/编号值，提交审批后从草稿原子发布到 `arch_physical_subsystem`。列表和详情从物理表读取可选逻辑文本与业务组件编号，业务组件标签通过 `ARCH_BUSINESS_COMPONENT` 字典选项投影。

迁移状态流为：新增物理字段 -> 从旧逻辑表回填文本 -> 删除物理逻辑外键和逻辑相关索引/唯一键 -> 删除逻辑草稿、逻辑编号分配和逻辑主表 -> 种子业务组件字典 -> 更新 Mock 和契约。

## 错误、降级与恢复

- 物理编号为空、格式错误或重复返回 400/409，并保留前端草稿输入。
- 业务组件编号不存在、停用或跨租户不可见返回 400。
- 已退役的逻辑接口返回 404 或不再注册路由；不得用空列表伪装兼容。
- 迁移前发现下游表仍有强逻辑外键依赖时停止执行，回到建模阶段补齐删除顺序。
- 执行破坏性迁移后，回退依赖数据库备份或补偿迁移，不把简单代码回退描述为可恢复数据。

## 安全、性能、兼容性与运维

安全上继续使用服务端认证、RBAC、租户过滤和操作审计。性能上保留物理子系统分页、筛选和下游按物理 ID 查询索引，新增业务组件编号索引。兼容性上，公开契约明确逻辑 API 被删除，旧客户端必须迁移到物理接口。运维上，删除表迁移必须在发布说明中标注备份、验证 SQL 和补偿路径。

## 假设、未知项与决策记录

- 假设：业务组件编号只保存字典 code，显示名称由字典 label 投影。证伪条件：用户要求同时保存业务组件名称快照。
- 假设：逻辑子系统降为物理侧可选自由文本字段，不由字典维护。证伪条件：用户要求逻辑子系统字段也受控。
- 假设：历史逻辑目标工单可保留历史行，但不能再创建、编辑、提交或发布。证伪条件：用户要求清空历史工单。
- 决策 D1：用户选择方案 B，硬删除逻辑表和所有逻辑接口。
- 决策 D2：物理子系统编号改为人工填写，替代自动槽位生成。
- 决策 D3：业务组件编号由系统字典 `ARCH_BUSINESS_COMPONENT` 管理。

## 风险与回退原则

最大风险是破坏性迁移删除逻辑表后无法靠应用回滚恢复历史逻辑结构；缓解方式是上线前备份、在预发环境验证迁移后记录表级差异，并准备补偿迁移。第二风险是遗漏下游逻辑字段依赖；缓解方式是全仓 `rg` 负向扫描、聚焦回归和真实浏览器路径验收。第三风险是编号策略切换导致旧编号保留表残留；缓解方式是删除不再使用的编号分配代码和表，并用测试证明物理新增必须使用人工编号。
