# 重复申请确认交互修复工程设计

## 文档状态

- 修订：1
- 状态：已确认
- 用户确认依据：用户指出按钮层级和重复弹窗问题，确认采用“底部主操作 + 当前冲突令牌一次性放行 + 令牌变化才重新提示”的推荐方案，并明确要求开发。

## 目标与成功信号

修复版本申请重复冲突确认流程，使“仍创建新申请”成为整个冲突集合的确认动作，而不是某一条历史申请的卡片操作。点击后弹窗立即关闭并继续提交；同一冲突事实不重复确认。

## 必须需求与验收条件

- R1：主操作位于弹窗底部“暂不处理”右侧，使用 Element Plus 主按钮样式。
- R2：确认后立即关闭弹窗并携带当前 `conflictToken` 提交，提交期间禁止重复点击。
- R3：只有重新查询得到的新令牌与已确认令牌不同时才重新打开弹窗；相同令牌下的其他 `409` 展示真实错误。
- R4：取消旧申请、修改旧申请和暂不处理保持现有行为。

## 方案比较与选择

选择前端临时保存已确认令牌并直接调用提交接口。提交接口本身已经校验令牌，因而无需先调用只返回相同冲突报告的 `CREATE_NEW` 处理接口。该方案改动面最小且保持后端契约不变。

备选方案是在后端持久化“冲突已确认”状态，但需要字段、迁移和生命周期规则，不符合本次缺陷修复的范围。仅关闭弹窗而不区分后续 `409` 也会继续误弹，因此不采用。

## 组件与状态流

- `ReleaseConflictDialog.vue`：卡片中只保留针对具体历史申请的取消/修改；底部输出“暂不处理”和“仍创建新申请”。
- `ReleaseManagementPrototype.vue`：`pendingSubmission` 保存可选的 `confirmedConflictToken`。确认创建时先关闭弹窗，再以该令牌提交。
- 保存或再次提交时，如果服务端冲突令牌仍等于已确认令牌，直接提交；令牌变化时清除确认并重新提示。
- 提交返回 `409` 时重新查询冲突。无令牌或令牌变化才重开弹窗；令牌相同则保留弹窗关闭状态并展示原始错误。

## 约束、错误与兼容性

- 不修改 `web/src/api/release.ts`、后端、权限、审计、附件、数据库或工作流。
- 确认只在当前前端会话和当前申请内有效，页面刷新后允许重新确认。
- 提交成功清除待提交状态；切换申请或项目时不复用旧确认。
- 移动端适配按此前决定暂不扩展，本次不新增固定尺寸或影响现有响应式规则。

## 验证策略与回退

运行前端生产构建和 `git diff --check`。在桌面浏览器使用真实重复申请验证按钮位置、点击立即关闭、提交成功不重弹；通过可控错误验证相同令牌不重弹、变化令牌会重弹；检查控制台无新增错误。回退仅恢复两个 Vue 文件。
