# 追加申请相关历史申请参考工程设计

## 文档状态

- 修订：1
- 状态：已确认
- 用户确认依据：用户选择“直接相关历史申请”，并确认展示与接口设计。

## 目标与成功信号

在追加申请详情中展示与本次交付内容直接相关的历史申请及其当前状态，使审批人能够在当前工单内核对追加来源和版本变化。普通申请不增加无关信息，历史关系不得动态混入同窗口内后创建或无关的申请。

## 使用者与场景

审批人或具有版本申请查看权限的用户打开追加申请详情时，需要参考被追加申请的状态、申请背景和交付版本变化，再决定是否审批。

## 必须需求与验收条件

- R1：仅追加申请详情显示“相关历史申请”区块，数据来源必须是当前申请已持久化的 `ADDITIONAL` 关系，而不是动态冲突列表。
- R2：历史申请按申请单聚合并显示申请单号、当前状态、版本类型、申请人/部门、申请时间、准出时间、需求编号和申请说明。
- R3：每张历史申请显示与当前申请直接相关的交付单元或文件介质变化；变化使用当前有效交付内容重新计算，不能展示已移除修订的旧关系快照。
- R4：历史申请按最近准出时间倒序，申请单号可以站内跳转到对应详情；不在当前区块重复加载历史附件。
- R5：查询必须受租户和 `release:application:view` 权限约束；普通申请或关系为空时不得返回其他窗口申请作为补偿。
- R6：追加申请关系异常为空时显示明确空状态，不影响当前申请、审批进展和审批操作加载。

## 不变量与约束

- `rel_application_relation` 继续作为追加血缘事实源，不修改表结构。
- 历史申请状态读取当前业务状态；关系身份固定，状态值可随历史申请变化。
- 不复用 `conflicts` 字段，因为动态冲突查询没有“创建时间早于当前申请”的保证。
- 不修改审批动作、流程定义、冲突门禁、附件权限或申请保存行为。
- 沿用现有 Spring JDBC、服务、控制器、Vue 3、Element Plus 和页面样式约定。

## 非目标

- 不展示同窗口同子系统的全部早期申请。
- 不在参考区直接审批、撤销、编辑或取消历史申请。
- 不复制历史附件内容，不新增附件聚合接口。
- 不新增通用申请血缘图或跨窗口追溯页面。
- 不修订已有追加关系历史数据。

## 方案比较与选择

选择“持久关系聚合 + 独立只读接口”。`rel_application_relation` 精确标识本次追加所依据的历史申请，独立接口避免把历史数据递归嵌入通用申请 DTO，也不会扩大列表和冲突响应。

- 复用动态冲突列表改动较小，但可能包含后创建申请，语义不符合“之前申请”。
- 查询同窗口同子系统全部早期申请信息更全，但噪声大且无法说明哪些记录直接导致追加判定。

## 架构边界与组件职责

- `ReleaseApplicationStore`：按租户、当前申请和 `ADDITIONAL` 类型读取直接关联的历史申请 ID；关系项必须仍匹配当前申请的活动交付项。
- `ReleaseApplicationService`：验证当前申请、限制追加特征、加载历史申请并基于双方当前活动交付项重算变化，排序并输出扁平参考 DTO。
- `ReleaseApplicationController`：新增当前申请相关历史的只读端点，沿用查看权限。
- `web/src/api/release.ts`：声明历史参考 DTO 和请求函数。
- `ReleaseApplicationDetailPage.vue`：与详情并行加载参考信息，仅追加申请渲染参考区块和站内详情链接。
- `release-prototype.css`：提供紧凑、可扫描且响应式的历史申请列表样式。

## 接口、数据和状态流

新增 `GET /api/release/applications/{code}/related-history`。返回 `List<RelatedHistoryView>`；每项包含历史申请基本字段和 `versionChanges`，不包含附件、冲突动作或递归 `conflicts`。

数据流：当前申请单号 → 校验租户内申请 → 非追加返回空列表 → 按持久关系查询历史 ID → 加载历史申请当前状态和活动交付项 → 以当前申请活动交付项重算变化 → 过滤无当前关联变化的陈旧关系 → 按 `approvedAt`、`createdAt`、申请单号稳定倒序 → 前端展示。

## 错误、降级与恢复

- 当前申请不存在或跨租户时沿用现有不存在/无权访问行为。
- 单条关系指向已删除或不可见历史申请时跳过该记录，并保留其他有效参考。
- 参考接口失败时，详情主体和审批面板仍可使用；参考区显示局部错误和重试入口。
- 追加申请无有效关系时显示“暂无相关历史申请”，不回退到动态冲突或全窗口查询。

## 安全、性能、兼容性与运维

端点沿用查看权限和租户过滤，不暴露附件或跨租户数据。一次追加申请通常只关联少量历史申请，使用关系索引和批量 ID 查询避免逐行全窗口扫描。接口为新增只读能力，对现有客户端兼容；无迁移和配置变化。

## 验证策略

- Store 测试验证仅返回当前申请、当前租户、`ADDITIONAL` 且仍匹配活动交付项的关联 ID。
- Service 测试覆盖普通申请空列表、多个关系按申请聚合、实时状态、版本变化重算、陈旧关系过滤和排序。
- Controller 安全契约测试确认端点要求 `release:application:view` 或管理员权限。
- 前端构建验证 DTO 和模板类型；浏览器检查追加/普通/关系为空/局部失败四种状态，申请详情链接可达。
- 运行 Release 模块测试、前端生产构建和 `git diff --check`。

## 假设、未知项与决策记录

- 假设：已持久化追加关系能覆盖新建和更新后的有效追加来源；活动项过滤可以排除旧修订残留关系。
- 未知项：历史申请逻辑删除后是否需要保留不可跳转的审计快照，当前不阻塞，按现有可见业务记录处理。
- D1：只展示直接相关历史申请，不展示同窗口全部申请。
- D2：新增独立只读接口，不扩展递归通用 `Response`。
- D3：状态取实时值，版本变化基于当前有效内容重算。
- D4：历史附件通过详情链接查看，不在参考区重复加载。

## 风险与回退原则

主要风险是旧关系数据包含已移除交付项，或一个历史申请存在多条关系导致重复展示。通过当前活动项过滤、服务层按历史申请 ID 聚合和变化重算控制。回退可独立移除新端点、前端请求和参考区块，不影响已有关系表及申请流程。
