# 需求与架构管理操作列样式统一工程设计

## 文档状态
- 修订：1
- 状态：已批准
- 用户确认依据：用户于 2026-08-21 确认采用方案一，并再次明确只调整样式与操作入口排布，不修改业务逻辑。

## 目标与成功信号
统一需求管理和架构管理列表的桌面操作列，使列宽与实际操作数量匹配，并采用交付示范中心已经验证的“主操作、高频操作、更多操作”层级。

成功信号：
- 已评审差异只有少量操作时，不再出现当前 `380px` 操作列造成的大面积空白。
- 操作按钮图标、间距、语义颜色和更多菜单与现有交付示范列表一致。
- 固定右侧操作列在横向滚动、行悬停、浅色和深色主题下保持不透明、可读。
- 权限、状态判断、确认弹框和实际业务动作保持不变。

## 使用者与场景
- 需求人员在差异清单中查看修改/审批记录、提交评审或维护未评审差异。
- 需求人员在存量需求中推进阶段、查看记录或维护需求。
- 系统清单维护人员编辑或删除系统主数据。
- 架构人员在逻辑子系统和物理子系统列表中查看详情、编辑或删除记录。

## 必须需求与验收条件

### R1 需求差异操作列
差异清单必须保留记录查看和当前状态允许的评审动作，并把低频维护动作收进更多菜单。

验收条件：
- “修改记录”始终可见，“审批记录”仅在存在流程实例时可见。
- 待评审或已退回时，“提交评审”作为高频语义操作直接可见。
- “编辑”和“删除”继续遵循现有 `canEditDiff` 判断，并进入“更多”菜单。
- 操作列固定在右侧，宽度从 `380px` 收敛到不超过 `280px`。

### R2 存量需求与系统清单操作列
存量需求和系统清单必须按操作频率分层，不平铺全部低频或危险操作。

验收条件：
- 存量需求直接展示“阶段推进”和“修改记录”，阶段记录、编辑、删除进入“更多”。
- 系统清单直接展示“编辑”，删除进入“更多”。
- 所有原有处理函数、确认提示和错误反馈继续使用，不改变业务语义。

### R3 架构管理操作列
逻辑子系统和物理子系统必须统一采用“详情 / 编辑 / 更多”结构，并补齐公共图标和稳定间距。

验收条件：
- “详情”始终可见并使用查看图标。
- “编辑”仅在 `canUpdate` 时可见并使用编辑图标。
- “更多”仅在存在删除权限时可见，删除继续位于下拉菜单并保留确认流程。
- 两个页面的桌面与移动操作文案、图标语义一致。

### R4 视觉与响应式一致性
操作列必须复用 `UiDataTable`、Element Plus link button、语义主题变量和模块既有移动卡片，不引入新的公共组件。

验收条件：
- 按钮容器不换行，按钮间距稳定，Element Plus 默认相邻按钮外边距被局部消除。
- 固定列背景、阴影和 hover 继续由 `UiDataTable` 公共样式负责。
- `1280x800` 桌面视口无文字遮挡或无意义超宽操作列。
- `375x812`、`390x844`、`430x932` 移动视口无页面级横向溢出；架构移动卡片不平铺超过三个操作。

## 不变量与约束
- 不修改后端、API、数据库、权限编码或审计逻辑。
- 不改变任何操作的可见条件、状态条件、确认提示和服务调用。
- 不新增或修改业务处理函数；下拉菜单只复用现有处理函数作为点击入口。
- 不修改 `web/src/components/ui` 或 `web/src/styles.css` 公共能力；只在需求页面和架构模块局部样式中复用现有规范。
- 使用 Element Plus 已安装图标，不新增依赖。
- 保留 `UiDataTable` 固定列背景与阴影规则，不复制固定列底层样式。

## 非目标
- 不重构需求管理整个页面或表单。
- 不为需求管理新增完整移动卡片列表；本次只保证现有表格的局部滚动边界和操作可达。
- 不改造其他业务模块的操作列。
- 不新增或修改公共 `UiTableActions` 组件。
- 不改变删除、提交评审、阶段推进等业务流程。

## 方案比较与选择
选择“业务模块局部采用主操作 + 高频操作 + 更多菜单”。该方案直接复用交付示范中心模式，能够解决超宽空白和操作平铺问题，同时不扩大公共组件回归范围。

未选择：
- 仅缩小列宽：多操作状态下仍会拥挤或换行，不能解决操作层级问题。
- 新增公共 `UiTableActions`：长期复用价值更高，但需要修改公共前端能力并回归全部业务列表，超过本次两个模块的范围。

## 架构边界与组件职责
- `RequirementsView.vue`：调整三个列表的操作层级、图标、更多菜单和局部容器样式。
- `LogicalSubsystemPage.vue`：为桌面和移动操作补齐图标及统一容器结构。
- `PhysicalSubsystemPage.vue`：与逻辑子系统保持同构操作结构。
- `architecture.css`：提供架构模块局部操作容器的间距、禁止换行和按钮 margin 归零规则。
- `UiDataTable`：继续提供表格、固定列背景、阴影、边框和 hover；本次只读，不修改。

## 接口、数据和状态流
本次没有接口或数据结构变化。页面继续根据现有记录状态和权限计算按钮可见性；将原按钮移入下拉菜单只改变入口位置，不改变事件处理函数和服务调用。

用户点击直接操作或更多菜单项后，仍进入原有处理函数、确认弹框、API 请求、成功刷新和错误提示流程。

## 错误、降级与恢复
- 更多菜单项调用失败时，继续由原有处理函数展示错误，不关闭或伪造成功状态。
- 权限不足时，相应按钮或菜单不渲染，不提供无效占位。
- 当一行只有一个操作时，操作列保持紧凑左对齐，不拉伸按钮。
- 菜单弹层由 Element Plus 管理，不在表格容器中裁剪。

## 安全、性能、兼容性与运维
- 安全：仅调整前端入口位置，后端权限仍是最终授权边界。
- 性能：不新增请求、状态监听或依赖，渲染成本不变。
- 兼容性：现有路由、类型、API、测试数据和操作处理函数保持兼容。
- 运维：纯前端变更，无数据库迁移和配置变化；回退对应前端文件即可恢复原布局。

## 验证策略
- 静态检查：`git diff --check`，确认修改仅涉及授权前端与任务文档。
- 前端构建：`npm --prefix web run build`。
- 桌面浏览器：在需求差异、存量需求、系统清单、逻辑子系统、物理子系统页面检查操作列宽度、固定列、菜单与点击路径。
- 移动浏览器：在 `375x812`、`390x844`、`430x932` 检查页面级横向溢出、架构移动卡片操作和更多菜单可达性。
- 主题检查：浅色和深色主题下检查固定列背景、文字和危险操作语义。

## 假设、未知项与决策记录
- 假设：截图中的目标是操作列视觉与层级优化，不要求本次把需求管理全部列表重构为移动卡片。依据是用户明确指向操作框样式。
- 未知项：暂无阻塞未知项。
- D1：采用业务模块局部方案，不新增公共组件。
- D2：低频和危险操作进入更多菜单，高频操作直接展示。
- D3：本次不改变后端、权限和业务流程。

## 风险与回退原则
- 风险：状态组合可能导致直接操作数量变化。通过逐状态检查待评审、已退回、审批中和已评审行覆盖。
- 风险：下拉菜单触发事件参数错误会导致原处理函数未执行。通过真实点击编辑、删除和记录入口验证。
- 风险：固定列宽过窄导致中文按钮截断。使用稳定容器和桌面截图验证后再确定最终宽度。
- 回退：回退四个业务页面/样式文件即可恢复原操作列，不涉及数据回滚。
