# 部署单元名称、类型与关联模型工程设计

## 文档状态

- 修订：1
- 状态：已确认
- 用户确认依据：用户于 2026-09-01 逐项确认单输入框、名称格式、早期数据无需兼容、租户内跨物理子系统搜索、多选、双向关系、规范化模型和完整设计，并于 2026-09-02 回复“批准”确认落盘修订 1。

## 目标与成功信号

本次目标是把部署单元从“简称、名称、自由文本关联、登记类型、业务类型”多事实源模型收敛为“完整名称、业务类型、结构化双向关联”模型。成功信号是维护者只需在一个醒目的输入框内处理 `SMSLJ_AP` 一类完整名称，标准后缀与应用/数据库/Web 类型稳定联动，自定义后缀可显式选择类型；关联部署单元能够搜索、多选并在双方详情一致显示。

## 使用者与场景

架构信息维护者在架构管理的部署单元页面创建或发布新版本。用户先选择所属物理子系统，在醒目的名称输入框中输入完整名称或主名称，再选择应用、数据库或 Web 类型；最后从当前租户 ACTIVE 部署单元中搜索并多选关联项。架构信息查看者在列表、详情、版本历史、资源申请和其他下游页面看到统一完整名称，不再辨别简称、登记类型或自由文本关联。

## 必须需求与验收条件

| ID | 必须需求 | 验收条件 |
| --- | --- | --- |
| R1 | 模型必须删除部署单元简称和重复事实源。 | 主记录、版本、DTO、前端类型、Mock 和契约不再包含 `shortName`、`relatedDeploymentUnitName`、`deploymentUnitType`。 |
| R2 | 名称必须使用一个输入框并以 `_` 识别主名称和后缀。 | 输入自动大写；主名称与后缀格式通过服务端校验；完整名称租户内唯一；页面不出现第二个后缀输入框。 |
| R3 | 类型必须收敛为应用、数据库、Web，并与标准后缀双向联动。 | `_AP/_DB/_WB` 分别映射 `APPLICATION/DATABASE/WEB`；标准后缀切换可替换；自定义后缀保持并要求显式类型。 |
| R4 | 关联部署单元必须可搜索、多选且为双向关系。 | 可搜索租户内 ACTIVE 记录；排除自身；支持跨物理子系统；A-B 只存一条且双方可见、任一端解除即解除。 |
| R5 | 服务端必须保护名称与关系一致性。 | 拒绝非法名称、标准后缀错配、自关联、跨租户、无效状态、重复关系和并发半边关系；409 保留前端输入。 |
| R6 | 版本、审计和下游契约必须同步。 | 编辑发起方发布新版本；关系变更写独立历史和审计；资源申请按 `kind` 映射 AP/DB/WB；实例、网络和计划回归通过。 |
| R7 | 权限、租户和模块边界必须保持。 | 继续使用现有 view/manage 权限、认证租户、实体校验、行版本和操作审计；不修改平台公共实现。 |
| R8 | 前端必须覆盖全状态和桌面/移动体验。 | 加载、无结果、失败、无权限、提交中、重复提交和脏表单状态可见；四个视口与明暗主题无页面级横向滚动。 |

## 不变量与约束

- 只追加 Flyway 迁移，不修改 V1—V123 等已发布迁移。
- 保持部署单元 `code` 自动编号、所属物理子系统不可变、生命周期、网络分区、描述、备注和乐观锁行为。
- 服务端认证、RBAC、租户隔离、实体校验和操作审计不能由前端显隐替代。
- 业务代码和关系数据归 `business/architecture`；不得直接写平台或其他业务模块表。
- 固定强类型页面，不恢复 `biz_form_*` 或动态表单元数据。
- 不连接生产系统，不使用真实个人数据、密钥、附件或日志。
- 候选迁移为 V124，实施前必须重新扫描迁移版本；冲突时重新分配并同步 scope。

## 非目标

- 不保留 MQ、PL、旧登记类型或旧 DTO 的兼容入口。
- 不新增类型字典或类型维护页面。
- 不改变部署单元权限码、菜单、编号规则和生命周期。
- 不重构架构模块目录、Java 包名或公共 UI 组件。
- 不设计生产数据灰度双写；早期开发环境允许清理和重建虚构数据。

## 方案比较与选择

### 已选：规范化完整名称、业务类型与关系表

主表只保存最终 `name` 和 `kind`，后缀从名称解析，业务语义由 `kind` 决定；双向关联使用独立规范化关系表和关系历史。该方案只有一套名称和类型事实源，最符合单输入框和早期开发阶段的约束。

### 未选：主名称和后缀分列存储

分列便于数据库查询，但接口需要反复拼接，页面与模型不再是“只保留一个部署单元名称”，还会引入名称与后缀组合的一致性逻辑。

### 未选：保留旧字段但前端隐藏

改动较小，但 `shortName`、`name`、`deploymentUnitType`、`kind` 和自由文本关联仍可互相冲突。用户已确认现有开发数据可删除，没有保留兼容负担的必要。

## 架构边界与组件职责

- 部署单元领域模型与服务：负责名称规范化、类型/后缀校验、租户唯一性、关系替换、版本发布、生命周期和审计编排。
- 部署单元持久化：读写主记录、版本、规范化关系和关系历史；关系端点按 ID 排序，唯一键保证一对端点只存在一条当前关系。
- 架构 HTTP 接口：创建/更新接收 `relatedDeploymentUnitIds[]`，详情返回结构化 `relatedDeploymentUnits[]`，选项接口提供服务端分页搜索。
- 架构前端：复用页面头、工具栏、数据表、状态标签和 Element Plus 可搜索多选；只新增部署单元表单内的名称联动逻辑和局部醒目样式。
- Flyway V124：删除冗余列和旧类型约束，建立关系/历史结构和必要索引；不修改历史脚本。
- 模块内下游：资源申请从 `kind` 映射 AP/DB/WB，初始化导入、实例、网络和搭建计划继续以 deploymentUnitId 与完整名称工作。

## 接口、数据和状态流

创建请求为 `physicalSubsystemId,name,kind,relatedDeploymentUnitIds,defaultNetworkZoneId,description,remark`；更新请求增加 `rowVersion` 且不允许改变物理子系统。服务端将名称转大写，按最后一个 `_` 分割，校验主名称和后缀；标准后缀必须匹配类型，自定义后缀只受格式约束。

关系替换流程为：加载并锁定当前部署单元 -> 校验请求行版本 -> 去重关联 ID -> 按 ID 顺序加载目标 -> 校验租户、ACTIVE 和非自身 -> 将每对端点规范为 `(minId,maxId)` -> 比较当前集合 -> 原子新增/解除关系 -> 写关系历史和操作审计 -> 发布发起方新版本。被关联端详情从同一关系表双向查询，不为被关联端自动制造版本。

前端名称状态流为：输入自动大写；输入标准后缀时自动选择类型；选择类型且名称无后缀时追加标准后缀；当前后缀是另一标准后缀时替换；当前后缀为自定义值时保留并只更新业务类型。最终提交值始终来自同一个名称输入框。

## 错误、降级与恢复

- 名称缺少 `_`、主名称为空、非法字符、后缀为空或超过 8 位：返回 400，字段附近显示具体规则。
- `_AP/_DB/_WB` 与类型不一致：返回 400；前端联动避免但不替代服务端校验。
- 租户内完整名称重复、行版本冲突、存在关联时作废：返回 409，保留表单和已选关联。
- 关联目标不存在、跨租户、停用、作废或为自身：返回 400；页面提示失效目标并允许重新搜索。
- 选项搜索失败：保留已选标签，显示可重试错误，不清空用户当前表单。
- 并发关系更新：按端点排序锁定并以唯一键兜底；事务失败不允许出现半边关系。
- 迁移版本冲突或发现未建模的外键依赖：停止实施，回到建模/计划阶段，不覆盖他人迁移。

## 安全、性能、兼容性与运维

安全上继续通过服务端认证、RBAC、租户过滤、实体状态、乐观锁和审计保护写操作，HTTP DTO 不暴露 `tenantId`。性能上选项接口必须分页，名称与编号使用已有索引或任务内新增的最小索引；关系表为两个端点分别建立租户查询索引，避免详情逐项查询。兼容性上旧字段删除属于已批准的破坏性开发契约调整，模块内消费者必须同批更新。运维上 V124 只追加，空库和既有开发库都要验证；早期环境可重建数据库和 Mock，但生产回退必须使用补偿迁移。

## 验证策略

- R1/R3：源码和契约负向扫描、模型/DTO/持久化测试，证明旧字段和 MQ/PL 不再可用。
- R2：名称解析、大小写、格式、唯一性、标准/自定义后缀和前端联动测试。
- R4/R5：MySQL 关系唯一键、自关联、跨租户、状态、双向增删、重复提交和并发测试。
- R6：版本、关系历史、审计、初始化导入、资源申请、实例、网络和计划聚焦回归。
- R7：Controller 权限、租户、实体与行版本测试，以及模块边界、governance 和 scope 检查。
- R8：前端构建，真实浏览器新建/编辑/搜索/多选/错误恢复，桌面和 375/390/430 视口、明暗主题、Network 与 Console 检查。

## 假设、未知项与决策记录

- 假设：完整名称的主名称部分不包含下划线，只允许大写字母和数字；最后一个 `_` 是唯一分隔符。依据是用户确认的格式规则。证伪条件是后续要求主名称本身允许下划线。
- 假设：双向关系是当前态业务关系，独立关系历史承担双方可追踪性；只有发起编辑的一端发布新版本。依据是避免一次关系变更为所有目标产生无意版本。证伪条件是用户要求双方版本号同步增长。
- 假设：停用保留关系，作废必须先解除关系。依据是既有生命周期对历史可读和引用限制的规则。证伪条件是用户要求作废自动解除。
- 决策 D1：使用一个完整名称输入框，通过 `_` 解析和拼接。
- 决策 D2：类型固定为应用、数据库、Web，标准后缀 `_AP/_DB/_WB`，允许自定义后缀后手工选类型。
- 决策 D3：不考虑 MQ/PL 或旧字段存量兼容，早期开发数据可清理重建。
- 决策 D4：候选范围为当前租户全部 ACTIVE 部署单元，可跨物理子系统搜索、多选并排除自身。
- 决策 D5：关联采用双向无向关系和规范化单条存储。
- 未知项：V124 在正式实施前是否被并行分支占用；影响迁移文件名，不改变业务设计，由实施计划阶段重新扫描。

## 风险与回退原则

最大风险是删除 `deploymentUnitType` 后资源申请仍有遗漏读取，导致 DB/AP/WB 字段分流错误；缓解方式是全仓扫描字段消费者并对资源申请三类路径做聚焦回归。第二风险是双向关系并发造成重复或丢失；缓解方式是规范化端点、唯一键、排序锁定、事务替换和并发测试。第三风险是破坏性删列后旧客户端不可用；该行为已被批准，只允许在同批更新模块内消费者后交付。迁移执行后不回写历史脚本，回退采用补偿迁移；早期开发环境可重建虚构数据，但不能把重建生产库作为回退方案。
