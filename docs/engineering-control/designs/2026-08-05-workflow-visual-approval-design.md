# 可视化审批工作流工程设计

## 文档状态

- 修订：1
- 状态：已确认设计，实施计划待确认
- 用户确认依据：用户确认采用“Vue Flow + 自研流程运行器”，第一阶段实现串行审批、多人审批、同意、拒绝、加签、抄送和审批人配置。

## 目标与成功信号

将当前基于 JSON 文本的工作流定义升级为可拖拽的流程图设计器，并让已发布流程能够稳定执行审批人解析、审批动作、加签和抄送。流程定义发布后固定版本，实例和任务可以按租户、审批人和动作追踪。

成功信号：管理员可以拖拽节点并配置审批人、保存并发布流程；发起人可以启动流程；审批人可以在待办中同意、拒绝、加签或抄送；多人审批遵循任一人/全部人规则；抄送人员能看到抄送记录但不能误操作审批；非法图、越权任务和重复提交会被后端拒绝。

## 使用者与场景

- 流程管理员：绘制流程、配置节点、发布流程。
- 业务发起人：选择已发布流程并提交业务单号。
- 审批人：处理待办，查看当前任务上下文，执行同意、拒绝、加签或抄送。
- 被抄送人：在待办中查看抄送记录，不拥有审批动作。

## 必须需求与验收条件

### R1 可视化流程定义

- 流程页面不再要求用户直接编辑 JSON。
- 设计器提供开始、审批、抄送、结束四类节点，节点可拖拽定位、连线、删除和配置。
- 第一阶段只允许串行有向流程：开始节点一个、结束节点一个；非结束节点最多一条出边；所有节点必须从开始节点可达。
- 保存时保留节点位置、节点配置和边信息；发布前由后端再次校验。

验收：创建一个“开始 -> 部门审批 -> 财务审批 -> 抄送 -> 结束”的流程，刷新页面后图形和配置一致，发布非法断链流程会收到中文错误提示。

### R2 审批人配置

- 审批节点可配置指定用户、指定角色或流程发起人。
- 指定用户和角色可以选择多个候选人。
- 多人模式支持“任一人同意”和“全部同意”。
- 审批任务只分配给当前租户内的有效用户；角色解析取当前租户有效角色关联用户的并集。

验收：用户选择两个审批人并设置任一人模式时，两个待办同时出现，其中一个同意后另一个待办自动取消；全部同意模式下，最后一个审批人同意后才进入下一节点。

### R3 审批动作

- 待办审批任务支持同意和拒绝，拒绝后实例结束为拒绝。
- 当前审批人可以加签一个指定用户；加签任务串行阻塞当前审批任务，加签人同意后原审批人继续处理，加签人拒绝则实例拒绝。
- 当前审批人可以抄送一个或多个指定用户；抄送不改变审批任务状态，接收人只看到抄送记录。
- 抄送节点在流程运行到达时自动生成抄送记录并继续流转。

验收：分别执行同意、拒绝、加签和抄送，实例状态、任务状态、待办列表和操作记录与动作一致；重复点击同一动作不会产生重复流转。

### R4 流程运行与版本

- 发起实例只使用发布时的流程版本，后续修改草稿不影响已运行实例。
- 流程启动、任务创建、动作处理和下一节点创建在同一事务内完成。
- 所有查询和写入校验 `tenant_id`；审批动作必须校验当前用户是任务实际审批人。
- 任务和动作返回中文节点名称、审批人名称、业务单号、创建时间和状态。

验收：发布流程后创建新草稿或修改定义不会改变已运行实例；跨租户或非审批人调用任务接口返回业务错误；并发重复审批只有一个请求成功。

### R5 接入规范

- 流程定义使用 `schemaVersion=1` 的节点/边 JSON 契约，前端设计器与后端校验器共同遵守。
- 后续业务模块只需要提供流程编码、业务单号和展示上下文，不直接操作工作流表。
- 动作使用可扩展字符串枚举，第一阶段实现 `APPROVE`、`REJECT`、`ADD_SIGN`、`CC`，任务类型实现 `APPROVAL`、`ADD_SIGN`、`CC`。

验收：以现有工作流页面作为接入方完成定义、发布、发起、待办和动作闭环，不新增业务模块对数据库的直接依赖。

## 不变量与约束

- 单租户模型不变，所有工作流数据必须带租户条件。
- 已发布版本不可原地修改；保存新定义时生成新的草稿版本。
- 开始和结束节点只能各有一个；图中不能有不可达节点、断开的边或环路。
- 只有 `PENDING` 的审批任务可执行审批动作；抄送记录不可执行审批动作。
- `ANY` 组一人完成后取消同组其他待办；`ALL` 组必须全部同意才能继续。
- 用户界面全部使用中文，时间接口统一 `yyyy-MM-dd HH:mm:ss`，页面列表显示 `yyyy-MM-dd`。
- 使用 Vue 3、TypeScript、Element Plus 和新增的 Vue Flow；后端保持 Spring Boot 3、JDK 17、JdbcTemplate/MySQL/Flyway。

## 非目标

- 第一阶段不实现 BPMN 全量规范、条件表达式、并行网关、会签比例、定时任务、转交、退回和催办。
- 不引入独立工作流引擎，不改变现有登录、组织、角色和权限体系。
- 不实现跨租户流程共享。

## 方案比较与选择

| 方案 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| Vue Flow + 自研运行器 | 适配现有 Vue/Element Plus，节点和数据契约可控，能逐步扩展 | 需要自行实现图校验和任务流转 | 采用 |
| BPMN 编辑器 + BPMN 引擎 | 标准能力强，条件和并行扩展完整 | 引擎接入、学习和迁移成本高，超出当前阶段 | 暂不采用 |
| 自定义纵向节点编辑器 | 依赖少、实现快 | 难以表达任意连线，后续分支扩展弱 | 不采用 |

## 架构边界与组件职责

- `WorkflowView.vue`：页面编排、定义列表/待办切换、发布和启动入口。
- `WorkflowDesigner.vue`：Vue Flow 画布、节点增删连线、节点位置和选中状态。
- `WorkflowNode.vue`：统一的中文节点外观和节点类型图标。
- `WorkflowNodeInspector.vue`：节点名称、审批人、审批模式和抄送人的配置表单。
- `workflow.ts`：工作流 API 类型和动作请求封装。
- `WorkflowDefinitionValidator`：解析并校验节点/边 JSON，不依赖 HTTP。
- `WorkflowService`：定义版本、实例、任务、动作和下一节点流转。
- `wf_task_action`：记录审批、加签和抄送动作，作为审计和排错依据。
- `wf_task` 扩展字段：记录节点、任务类型、任务组和父任务关系。

## 流程定义契约

```json
{
  "schemaVersion": 1,
  "nodes": [
    {"id":"start","type":"START","label":"发起","position":{"x":120,"y":80},"config":{}},
    {"id":"approve-1","type":"APPROVAL","label":"部门审批","position":{"x":120,"y":220},"config":{"assigneeType":"USER","assigneeIds":[2,3],"mode":"ANY"}},
    {"id":"cc-1","type":"CC","label":"抄送财务","position":{"x":120,"y":360},"config":{"userIds":[4]}},
    {"id":"end","type":"END","label":"结束","position":{"x":120,"y":500},"config":{}}
  ],
  "edges": [
    {"id":"e1","source":"start","target":"approve-1"},
    {"id":"e2","source":"approve-1","target":"cc-1"},
    {"id":"e3","source":"cc-1","target":"end"}
  ]
}
```

审批节点 `assigneeType` 取 `USER`、`ROLE`、`STARTER`；`USER` 使用 `assigneeIds`，`ROLE` 使用角色 ID，`STARTER` 不需要 ID。`mode` 取 `ANY` 或 `ALL`。前端保存时发送现有 `definitionJson` 字段，后端按上述契约校验并保存。

## 接口、数据与状态流

保留现有接口路径并扩展请求/响应：

- `GET /api/workflows/definitions`：返回定义列表。
- `POST /api/workflows/definitions`：接收 `code`、`name`、`definitionJson`。
- `POST /api/workflows/definitions/{id}/publish`：校验并发布最新草稿。
- `POST /api/workflows/instances`：接收 `definitionId`、`businessKey`，创建实例和首个审批任务。
- `GET /api/workflows/inbox`：返回审批待办和抄送记录，含 `task_type`、节点名称和审批人名称。
- `POST /api/workflows/tasks/{id}/decision`：接收 `action`、`comment`、可选 `targetUserId`、可选 `ccUserIds`。

状态流：

```text
草稿 -> 已发布 -> 运行中 -> 已通过
                         \-> 已拒绝
审批任务：PENDING -> APPROVED / REJECTED / CANCELLED
抄送记录：SENT
```

到达 CC 节点时生成 `CC` 任务并继续寻找下一个节点；到达 END 时实例标记为 `APPROVED`。加签任务以原任务为父任务，原任务保持 `PENDING`，加签任务完成后原任务继续可处理。

## 错误、降级与恢复

- JSON 不合法、节点不完整、审批人为空、边断开或图不满足串行约束时返回 400 和明确中文错误。
- 任务不存在、已完成、非当前审批人或跨租户访问时返回冲突/禁止错误，前端显示具体动作失败原因。
- 数据库事务失败时不写入半成品任务；Flyway 迁移失败时停止启动，不删除已有表。
- Vue Flow 加载失败时保留定义列表和错误提示，不把图形状态写回后端。
- 回滚优先停止新后端并恢复上一 JAR，再根据迁移窗口处理新增列和表；不直接删除已有工作流数据。

## 安全、性能、兼容性与运维

- 继续使用现有 `system:access` / `workflow:access` 权限，任务操作必须再做用户、租户和状态条件校验。
- 角色解析只查询当前租户有效用户和角色，避免把停用用户加入待办。
- 事务内只执行当前实例相关查询；任务列表按租户、审批人、状态建立索引。
- 接口时间统一后端序列化格式，前端使用统一日期工具展示年月日。
- 操作表记录原任务、动作、目标用户和请求参数摘要，禁止记录密码、令牌等敏感数据。

## 验证策略

- 后端单元测试：定义解析与图校验、审批人解析、ANY/ALL 状态、拒绝、加签、抄送和重复动作。
- 后端编译：`mvn -pl ccb-boot -am compile -DskipTests`。
- 前端构建：`npm run build`。
- 浏览器验收：绘图、节点配置、保存、发布、发起、多人待办、四类动作和错误提示。
- 数据库验收：Flyway 执行 V16，检查新列/新表、索引和旧数据兼容。

## 假设、未知项与决策记录

- 假设：现有用户和角色接口可提供有效的用户/角色 ID，工作流模块可直接读取系统表。
- 假设：第一阶段的加签采用串行阻塞语义，抄送只读不参与审批。
- 未知项：后续条件分支需要业务字段表达式和安全执行策略，本阶段明确不实现。
- D1：采用 Vue Flow，理由是满足真实拖拽连线并保留节点扩展能力。
- D2：采用自研轻量运行器，理由是当前只需要串行节点和明确动作，避免引入完整 BPMN 引擎。
- D3：保留 `definitionJson` 请求字段以兼容现有接口，内部契约升级为节点/边结构。

## 风险与回退原则

- 风险：Vue Flow 新依赖可能影响构建环境；先在前端任务中锁定版本并以构建作为门禁。
- 风险：旧 JSON 定义只有 `steps` 数组；发布时兼容读取旧定义，保存新定义后统一使用节点/边契约，避免历史数据无法启动。
- 风险：角色多人待办会增加并发竞争；通过任务组和条件更新保证只有一个成功流转。
- 回退：保留旧 API 路径和表结构兼容字段；前端切回旧列表页面时不影响已发布实例，后端恢复上一版本即可停止新动作。
