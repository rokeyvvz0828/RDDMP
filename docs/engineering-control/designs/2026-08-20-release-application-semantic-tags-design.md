# 版本申请三列语义标签工程设计

## 文档状态

- 修订：1
- 状态：已确认
- 用户确认依据：用户查看“版本类型、申请特征、状态”三列截图后选择方案一。

## 目标与成功信号

统一版本申请列表中“版本类型、申请特征、状态”三列的标签尺寸、对齐和语义色，使同一行的信息能够稳定扫描，不再出现“普通”以裸文本展示、相邻字段以标签展示的视觉断层。

## 使用者与场景

配置管理人员在版本申请列表中快速判断版本类别、是否为追加申请及当前流程状态。

## 必须需求与验收条件

- R1：三列均使用统一的紧凑标签组件，标签高度、字号、圆角和内边距一致，并在单元格内左对齐、垂直居中。
- R2：版本类型保持语义映射：常规版本为中性色，紧急版本为警示色，应急版本为危险色。
- R3：申请特征完整显示“普通申请”或“追加申请”；普通申请为中性色，追加申请为警示色。
- R4：状态保持现有语义映射：草稿及取消类为中性色，审批中为主色，制品准出为成功色，退回及撤回为警示色。
- R5：不改变 `versionType`、`characteristic`、`status` 数据值、筛选、接口、权限或后端行为。

## 不变量与约束

- 复用现有 `UiStatusTag` 和 Element Plus 标签色彩体系。
- 只调整版本申请列表三列的展示，不全局修改其他页面标签。
- 保持当前列宽和表格行为，标签内容不得造成横向溢出。
- 保护 `rokey` 工作区中其他未提交修改，不提交、不推送、不清理。

## 非目标

- 不重构全局状态标签组件的视觉体系。
- 不修改详情页、冲突弹窗、统计页或其他列表。
- 不增加图标、说明文字、筛选条件或新的状态类型。

## 方案比较与选择

选择方案一“统一语义标签”：三列全部使用相同尺寸的描边小标签，通过颜色表达类别和状态语义。该方案扫描一致性最好，沿用现有组件，改动面最小。

- 方案二“分层标签”会为申请特征引入单独的填充标签规范，层级更强但增加一套局部视觉规则。
- 方案三“弱化普通状态”仍保留文本与标签混排，无法彻底解决当前对齐和视觉断层。

## 架构边界与组件职责

- `ReleaseApplicationView.vue`：将申请特征列改用 `UiStatusTag`，并复用现有版本类型和状态映射。
- `UiStatusTag.vue`：继续提供统一的 `small`、`plain` 标签表现，本次不修改其公共契约。
- 服务端和 API 类型在范围外。

## 接口、数据和状态流

列表仍从 `ReleaseApplicationDto` 读取 `versionType`、`characteristic` 和 `status`。三个字段只经过现有或局部标签文案、色调映射后渲染，不产生新状态，也不修改请求或响应。

## 错误、降级与恢复

- 未知申请特征仍按非追加申请处理，与当前行为一致。
- 标签宽度受当前列宽约束，完整中文文案应保持单行显示。
- 如出现视觉回归，可只恢复申请特征列的模板修改。

## 安全、性能、兼容性与运维

无权限、安全、接口、数据库、配置或部署变化。仅替换局部渲染组件，不产生可感知性能开销。

## 验证策略

- 运行 `npm --prefix web run build` 和 `git diff --check`。
- 静态检查三列均通过 `UiStatusTag` 渲染，现有色调映射未变化。
- 在列表中检查“常规版本 / 普通申请 / 审批中”“常规版本 / 追加申请 / 草稿”等组合的高度、对齐和颜色。
- 检查表格无横向溢出，控制台无新增错误。

## 假设、未知项与决策记录

- 假设：用户要求优化的是列表三列整体视觉，不涉及其他页面同名字段。
- 未知项：无阻塞未知项。
- D1：采用方案一，三列统一使用描边小标签。
- D2：将“普通”补全为“普通申请”，与“追加申请”形成对称文案。
- D3：保持现有版本类型和状态色调映射，不引入新颜色。

## 风险与回退原则

主要风险是“普通申请”由两字变为四字后在 100px 列内空间变紧。现有 `small` 标签在当前列宽内可容纳该文案，构建后仍需浏览器核对。回退仅涉及 `ReleaseApplicationView.vue` 的申请特征单元格。
