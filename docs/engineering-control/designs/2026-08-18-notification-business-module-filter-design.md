# 通知业务板块展示与筛选工程设计

## 文档状态

- 修订：1
- 状态：已批准
- 用户确认依据：用户于 2026-08-18 选择新增独立业务板块字段的方案 1，确认同时保留消息来源，并逐段确认业务板块筛选、计数、数据传递和存量兼容规则；复核落盘设计后明确“确认开发”。

## 目标与成功信号

在统一通知中心中增加独立、稳定的业务板块维度，使用户能够区分配置管理及后续业务模块的消息，并在全部或未读消息中按板块服务端筛选。

成功信号：配置管理审批消息展示“配置管理 · 审批中心”；板块筛选、分页和当前板块未读数一致；全局铃铛角标不受筛选影响；存量通知和运行中流程无回归。

## 使用者与场景

- 审批人：从全局通知抽屉识别通知所属业务板块，筛选配置管理消息并进入业务单据审批。
- 申请人：区分不同业务模块的审批结果通知并跳转查看意见。
- 后续业务模块：通过统一通知与工作流契约显式声明所属板块，不维护独立通知中心。
- 平台运维与审计人员：依据稳定板块编码定位通知来源和统计范围。

## 必须需求与验收条件

### R1 独立业务板块语义

- 通知必须同时保存 `moduleCode`、`moduleName`、`sourceName`、`businessType` 和 `businessKey`。
- `moduleCode` 表示稳定业务板块，`moduleName` 表示用户可见板块名称，`sourceName` 表示审批中心等触发来源，`businessType` 表示版本申请等业务对象类型。
- 验收：配置管理审批通知可同时识别板块、来源和业务单号。
- 反例：仍只显示“审批中心”，或前端从 `/release` 路由推断板块。

### R2 显式工作流上下文传递

- 新发起的业务工作流必须在业务上下文中显式提供板块编码和名称。
- 工作流实例和生命周期事件保存并传递板块信息，通知桥只转发，不依赖具体业务模块实现。
- 验收：新增业务类型无需修改通知前端映射即可产生正确板块通知。
- 反例：工作流桥硬编码所有业务类型到板块的长期映射。

### R3 通知展示与筛选

- 通知顶部展示“业务板块 · 消息来源”，底部保留消息级别和业务主键。
- “全部 / 未读”标签下增加可搜索板块下拉框，默认“全部业务”。
- 切换板块或全部/未读时重置到第一页并重新查询后端。
- 验收：配置管理筛选只展示该板块消息，清除筛选恢复全部消息。
- 反例：只过滤前端已加载的当前页，导致分页和总数错误。

### R4 用户范围与计数一致性

- 板块选项只根据当前租户、当前用户实际拥有的通知聚合生成。
- 选项返回板块总数和未读数；未读标签显示当前筛选范围内的未读数。
- 铃铛角标始终显示当前用户全平台未读总数，不受板块筛选影响。
- 验收：标记单条或全部已读后，列表、板块未读数和全局角标按各自范围同步。
- 反例：筛选配置管理后铃铛角标变成配置管理未读数。

### R5 存量兼容

- 通过追加迁移为存量通知补齐板块字段；已发布迁移保持不变。
- `release_application` 补为 `release / 配置管理`，`delivery` 补为 `delivery / 交付示范中心`，`system` 补为 `system / 系统管理`，其他类型使用 `businessType / sourceName` 兜底。
- 存量运行中工作流缺少板块上下文时使用同一受控兼容映射；新流程不得依赖兜底。
- 验收：旧通知仍可查询、标记已读和跳转，旧流程仍可完成并产生可识别通知。
- 反例：迁移后存量通知不可见，或运行中实例因新字段缺失无法审批。

### R6 响应式与状态完整

- 桌面通知抽屉保持紧凑信息层级；移动端筛选器使用完整可用宽度，不产生页面或抽屉横向溢出。
- 板块选项加载失败时保留未筛选通知列表，明确展示筛选加载失败并允许重试。
- 加载、空、失败、长名称和长业务单号在桌面及三个规定手机视口中可读。
- 验收：`375x812`、`390x844`、`430x932` 和桌面视口均可完成筛选、查看和跳转。
- 反例：筛选器挤压全部/未读标签或导致通知正文被裁剪。

## 不变量与约束

- `platform/system` 继续拥有通知主表和用户已读状态，业务模块只能调用公开 Publisher。
- 查询始终按认证租户和用户隔离，客户端不能指定用户身份或扩大数据范围。
- 通知幂等键继续使用 `(tenantId, businessType, eventId)`，本次不改变历史幂等语义。
- `actionPath` 继续只允许站内绝对路由；已读、全部已读和跳转行为保持兼容。
- Flyway 迁移只追加，不修改 V26、V35 或其他已发布文件。
- 使用 Java 17、Spring Boot 3.4.4、MySQL 8.4、Vue 3、TypeScript 和 Element Plus 现有技术栈。
- 当前在 `rokey` 分支实施，保护工作区内其他未提交修改。

## 非目标

- 短信、邮件、企业微信、WebSocket 或浏览器推送。
- 通知模板、用户订阅偏好、运营群发、附件、删除和归档。
- 业务板块后台维护页面和按项目筛选。
- 将治理模块清单直接作为运行时通知板块目录。
- 改变业务审批规则、审批权限或业务详情路由。

## 方案比较与选择

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 通知增加独立板块字段 | 语义清晰，可服务端筛选和统计，支持后续模块 | 涉及公开契约、迁移和工作流上下文 | 选择 |
| 前端按 `businessType` 映射 | 初期改动小 | 公共前端耦合所有业务类型，分页筛选不可靠 | 不选 |
| 根据 `actionPath` 推断 | 无需新增字段 | 无路由、路由变更和多路由时失效 | 不选 |

筛选控件选择可搜索下拉框而非固定页签：板块数量会增长，下拉框可扩展且适合移动端；“全部 / 未读”继续承担消息状态维度。

## 架构边界与组件职责

- `SystemNotificationPublisher` / `NotificationPublishCommand`：公开发布契约，接收并校验板块、业务对象、来源、接收人和路由。
- `SystemNotificationService`：持久化板块字段，执行用户范围分页、板块聚合、计数、已读和审计。
- `WorkflowBusinessContext` 与工作流持久化：保存来源业务板块并贯穿实例及生命周期事件。
- `WorkflowSystemNotificationBridge`：将工作流上下文转换为通知命令；兼容存量上下文但不拥有业务规则。
- `ReleaseSubmissionService`：新建版本申请流程时声明 `release / 配置管理`。
- `UiNotificationCenter`：展示板块与来源，维护状态和板块两个正交筛选条件及局部分页状态。
- 追加 Flyway 迁移与本地 Mock：增加字段、索引和存量补齐，保证本地数据同步不回写缺失字段。
- 系统通知与工作流接入文档：作为后续业务模块唯一公开接入说明。

## 接口、数据和状态流

### 通知数据

`sys_notification` 新增非空 `module_code VARCHAR(64)`、`module_name VARCHAR(128)`，并增加 `(tenant_id, module_code, created_at, id)` 索引。发布命令和返回 DTO 增加 `moduleCode`、`moduleName`。

工作流实例和生命周期事件增加对应业务板块上下文字段。新业务接入必须显式填写；存量记录允许为空并在通知桥兼容处理，避免阻断运行中实例。

### 查询接口

- `GET /api/notifications?page=&size=&unreadOnly=&moduleCode=`：`moduleCode` 可空；未知编码返回空分页。
- `GET /api/notifications/modules`：返回当前用户拥有的板块 `moduleCode`、`moduleName`、`totalCount`、`unreadCount`，按最近通知时间倒序。
- `GET /api/notifications/unread-count`：保持全平台当前用户未读总数，不接受板块参数。
- 单条已读和全部已读接口保持原路径及语义；全部已读仍作用于当前用户全部通知，不受前端筛选影响。

### 页面状态流

```text
打开通知抽屉
  -> 并行加载全局未读数、板块选项、默认通知页
  -> 选择板块或全部/未读
  -> 清空当前记录并从第一页按服务端条件查询
  -> 点击通知标记已读
  -> 更新全局角标、当前板块未读数和当前列表
  -> 存在 actionPath 时进入业务详情
```

筛选保留在抽屉组件当前会话中；重新登录后恢复“全部业务 / 全部”。板块选项不从当前 20 条通知去重生成。

## 错误、降级与恢复

- 发布缺少或非法板块编码、名称：返回参数错误，不写通知或部分接收状态。
- 板块选项加载失败：通知列表继续按“全部业务”加载，筛选控件显示失败并提供重试。
- 未知 `moduleCode`：返回空列表和零计数，不回退到全部业务。
- 板块名称过长：通知发布被拒绝；历史长文本在前端省略并提供完整可访问文本。
- 存量工作流缺少板块：仅对已知历史业务类型使用迁移/兼容映射，其他使用业务类型和可用来源兜底并记录告警。
- 标记已读后刷新计数失败：已读写入结果保持，前端重新拉取未读数和板块选项恢复一致性。
- 迁移或 Mock 同步失败：应用启动失败并暴露 Flyway 错误，不手工跳过迁移。

## 安全、性能、兼容性与运维

- 板块列表、分页和计数查询都从 `sys_user_notification` 起始并带租户、用户条件，禁止先查询全租户板块再由前端过滤。
- `moduleCode` 只接受小写字母开头及小写字母、数字、下划线、连字符，最长 64；名称去首尾空白后最长 128。
- 板块聚合查询使用用户通知未读索引和通知板块索引；分页维持现有上限，避免一次加载全部消息。
- 返回 DTO 只增加字段，既有接口路径、已读行为和前端跳转兼容；发布 Java record 属于源码级公开契约变更，所有仓库调用点必须同批更新和测试。
- 板块名称在通知发布时固化，历史通知不因后续模块改名自动变化；同一编码的新通知应使用当前约定名称。
- 监控迁移后空板块字段数量、兼容兜底告警和板块聚合查询耗时。

## 验证策略

- 系统服务测试：字段校验、幂等、用户隔离、板块分页、未知板块、聚合总数/未读数和已读更新。
- 工作流测试：新上下文持久化与生命周期传播、任务和结果通知转发、存量上下文兼容。
- 配置管理测试：版本申请提交显式传入 `release / 配置管理`，流程和通知业务单号一致。
- 迁移测试：MySQL 8.4 执行追加迁移，验证映射、兜底、非空字段和索引；Mock 同步后不回退字段。
- 前端构建与组件测试：筛选重置分页、并发请求防陈旧覆盖、全局与板块计数、失败恢复和长文本。
- 浏览器验收：使用至少两个业务板块的真实后端通知，在桌面与三个手机视口验证展示、筛选、全部/未读、已读、跳转、刷新和控制台。
- 完整门禁：JDK 17 聚焦测试、`mvn test`、前端生产构建、治理检查、范围检查和 `git diff --check`。

## 假设、未知项与决策记录

- 假设：业务板块编码在发布通知和发起工作流前已由业务模块确定，不需要运行时管理页面。
- 假设：当前“全部已读”继续作用于当前用户所有板块，用户未要求改为仅处理筛选结果。
- 假设：业务板块名称变更不追溯改写历史通知。
- 未知项：无阻塞未知项；实施前需按当前合并基线确认追加迁移版本号是否仍为 V44。
- D1：采用独立业务板块字段，不使用前端或路由推断。
- D2：顶部同时展示“业务板块 · 消息来源”。
- D3：本次增加板块筛选，使用服务端查询和动态板块选项。
- D4：铃铛显示全局未读，未读标签显示当前板块未读。
- D5：新流程显式传递板块，存量流程使用受控兼容映射。

## 风险与回退原则

- 公共发布命令变更可能遗漏调用方：编译全仓库并搜索全部构造点，契约测试覆盖必填字段。
- 工作流上下文字段传播遗漏可能导致通知丢板块：从发起、实例、生命周期事件到通知建立链路测试。
- 存量映射错误可能误分类历史通知：迁移前后按业务类型统计并抽查配置管理、交付示范和系统通知。
- 全局和筛选计数可能短暂不一致：写后重新拉取权威计数，不以当前页长度推算总数。
- 并行 Flyway 变更可能占用 V44：实施前重新检查远程主线和当前分支，若冲突只调整本需求新增迁移编号，不修改已执行脚本。
- 回退应用代码时保留新增字段、索引和补齐数据；旧应用忽略新增列，后续恢复不需要再次补偿。
