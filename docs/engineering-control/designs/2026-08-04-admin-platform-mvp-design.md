# 管理平台一期基础能力工程设计

## 文档状态

- 设计修订：1
- 状态：已确认
- 用户确认依据：用户确认先实现一期基础平台，并确认单租户、Vue 3 + TypeScript + Vite + Element Plus + Pinia + Vue Router

## 目标与成功信号

从空仓库构建一个可启动、可验证的前后端分离管理平台基座，覆盖登录、账号、组织、角色权限、动态菜单、字典、系统配置和主题切换，并为后续工作流与 AI 能力保留稳定模块边界。

成功信号：后端能连接 MySQL 并启动，前端能独立启动并完成登录；管理员可维护基础数据；普通角色只能看到和访问授权资源；菜单配置能驱动前端动态路由；主题切换可持久化；关键操作可审计。

## 使用者与场景

- 系统管理员：初始化系统、维护组织用户、角色、菜单和字典。
- 普通业务用户：登录后访问被授权的菜单和页面。
- 后续业务模块开发者：按照统一响应、鉴权、动态菜单和配置约定接入新模块。

## 必须需求与验收条件

| ID | 必须行为 | 验收条件 | 反例 |
| --- | --- | --- | --- |
| R1 | 用户可以安全登录并保持会话 | 正确账号返回 Access Token/Refresh Token；错误密码失败；Access Token 过期可刷新；禁用账号不可登录 | 前端只隐藏菜单但后端接口仍可越权访问 |
| R2 | 系统支持单租户组织与账号体系 | 可维护组织树、用户、角色；用户可关联组织和角色；停用用户不能登录 | 组织只能保存平面列表或删除父组织破坏子组织 |
| R3 | 角色权限同时约束菜单、按钮和接口 | 角色授权后前端出现对应菜单；未授权接口返回 403；按钮权限可判断 | 仅靠前端路由守卫实现权限 |
| R4 | 菜单支持动态路由配置 | 菜单保存组件路径、路由名、权限标识和排序；登录后按返回菜单生成路由 | 路由写死且修改菜单无效 |
| R5 | 系统支持字典和系统配置维护 | 可维护字典类型、字典项和键值配置；接口可按编码查询 | 配置散落在前端源码中 |
| R6 | 页面支持主题切换 | 浅色、深色、跟随系统三种模式可切换并持久化 | 只修改局部页面颜色或刷新后丢失设置 |
| R7 | 关键行为可审计 | 登录成功/失败、用户/角色/菜单等写操作产生记录 | 发生异常时无法定位操作者和时间 |
| R8 | 工程具备后续扩展边界 | 模块、响应体、错误码、鉴权注解和接入文档明确 | 后续工作流或 AI 只能修改核心登录代码 |

## 不变量与约束

- 本期固定单租户；表结构统一预留 `tenant_id`，不实现租户切换和租户管理。
- 后端使用 Spring Boot 3.x、JDK 17、MyBatis-Plus、MySQL、Maven。
- 前端使用 Vue 3、TypeScript、Vite、Element Plus、Pinia、Vue Router。
- 密码只保存 BCrypt 哈希；Token 不在数据库保存明文。
- 后端鉴权是最终权限边界，前端权限仅用于导航和交互控制。
- 业务模块不得跨模块直接访问其他模块的 Mapper；通过服务接口或公共契约交互。
- 所有接口使用统一响应结构和统一错误码；分页接口使用统一分页参数。
- 不引入工作流引擎、AI 模型供应商调用、微服务注册中心和复杂多租户能力。

## 方案比较与选择

### 方案 A：模块化单体（选定）

后端按领域分模块、单进程部署；前后端分离；数据库按模块归属表。适合空仓库一期交付，部署简单、接口边界清晰，后续可按模块拆服务。

### 方案 B：一开始拆微服务

可以获得独立扩缩容，但会立即引入注册中心、配置中心、网关、分布式认证和部署复杂度，无法提高一期基础能力的验收价值，因此暂不采用。

### 方案 C：前后端一体化管理端模板

启动快，但削弱后端领域边界和后续 AI/工作流接入规范，不符合本项目作为框架型系统的长期目标。

## 架构边界与组件职责

### 后端模块

- `ccb-boot`：启动类、环境配置、OpenAPI、全局异常和组件装配。
- `ccb-common`：统一响应、错误码、分页、实体基类、工具和公共注解。
- `ccb-security`：登录、JWT、刷新 Token、密码编码、当前用户上下文、权限注解和过滤器。
- `ccb-system`：用户、角色、组织、菜单、字典、配置、登录日志和操作日志的领域服务、Controller、Mapper、实体及迁移脚本。
- `ccb-infrastructure`：MySQL 数据源、MyBatis-Plus 配置、事务、审计落库和缓存抽象。

### 前端模块

- `src/layouts`：应用壳、侧边菜单、顶部栏和内容区。
- `src/router`：静态登录路由、动态业务路由、路由守卫和权限过滤。
- `src/stores`：认证、用户、权限、主题状态。
- `src/api`：按领域封装 HTTP 客户端和接口类型。
- `src/views/system`：用户、角色、组织、菜单、字典和配置页面。
- `src/styles`：主题变量和 Element Plus 主题覆盖。

## 接口、数据与状态流

### 认证接口

- `POST /api/auth/login`：用户名、密码登录。
- `POST /api/auth/refresh`：刷新 Access Token。
- `POST /api/auth/logout`：注销当前会话。
- `GET /api/auth/me`：当前用户摘要、角色和权限。
- `GET /api/auth/routes`：当前用户可访问菜单树。

### 系统管理接口

- `/api/system/users`：用户分页、详情、新增、修改、启停用、重置密码。
- `/api/system/roles`：角色 CRUD 与菜单授权。
- `/api/system/orgs`：组织树 CRUD。
- `/api/system/menus`：菜单树 CRUD 与路由字段维护。
- `/api/system/dicts`：字典类型和字典项 CRUD。
- `/api/system/configs`：系统配置查询与维护。
- `/api/system/logs`：登录日志和操作日志查询。

统一成功响应为 `{ code, message, data, traceId }`，分页数据为 `{ records, total, page, size }`。认证失败返回 401，权限不足返回 403，参数校验失败返回 400，业务冲突返回可识别的业务错误码。

### 登录状态流

登录成功 -> 前端保存 Token -> 拉取当前用户和菜单 -> 生成动态路由 -> 进入首页。请求遇到 401 时仅尝试一次刷新；刷新失败清理本地会话并回登录页。权限变化后由用户重新登录或主动刷新权限缓存生效。

## 错误、降级与恢复

- MySQL 不可用：后端启动失败并输出明确连接错误，不使用静默内存数据替代。
- 登录失败：统一返回非敏感错误信息，记录失败原因分类和客户端信息。
- 动态菜单包含不存在组件：后端仍返回配置，前端记录错误并跳过该路由，不阻塞其他菜单加载。
- 删除组织、角色或菜单存在引用：拒绝操作并返回冲突错误，要求先处理引用关系。
- Token 刷新失败：清理前端认证状态，用户重新登录。

## 安全、性能、兼容性与运维

- BCrypt 密码哈希；JWT 密钥从环境变量读取，不提交仓库。
- CORS 只允许配置的前端来源；生产环境关闭宽松跨域。
- 所有写操作使用参数校验和事务；分页查询限制最大页大小。
- 列表接口默认分页，组织和菜单树限制递归深度并校验环路。
- 提供 `.env.example`、MySQL 初始化迁移、启动文档和健康检查接口。
- 关键日志包含 `traceId`，不记录密码、Token 和敏感认证信息。

## 验证策略

- 后端：公共组件单测、密码与 Token 单测、权限服务单测、Controller 集成测试、MySQL 迁移启动验证。
- 前端：路由权限单测、主题状态单测、生产构建验证、核心页面手工流程验证。
- 集成：启动 MySQL 后，执行登录、刷新、动态菜单、权限拒绝、用户/角色/组织维护和主题持久化流程。

## 假设、未知项与决策记录

- 假设：一期使用用户名登录，不接入短信、LDAP、OAuth2 或企业微信。
- 假设：系统管理员通过数据库初始化脚本获得首个账号。
- 未知项：后续 AI 模型供应商和工作流 DSL 尚未确定，本期只冻结接入边界，不实现供应商适配。
- D1：选用模块化单体，依据是一期验证速度和后续拆分能力的平衡。
- D2：采用 JWT Access/Refresh Token，依据是前后端分离和无状态接口需求。
- D3：采用 Vue 3 + TypeScript + Element Plus，依据是后台管理场景的成熟度和动态权限支持。

## 风险与回退原则

- 先完成认证和权限最小闭环，再扩展管理页面；任一权限链路不通过，不扩大到更多业务模块。
- 数据库迁移采用版本化脚本；迁移失败停止启动并保留原数据库，不自动删除或重建用户数据。
- 计划只覆盖一期基础平台；工作流、AI 和微服务化需求作为后续独立设计，不在实施中隐式加入。
