# 数据迁移整体看板实时指标与滚动下钻工程设计

## 文档状态

- 修订：1
- 状态：已确认
- 用户确认依据：2026-09-08 用户批准高保真排版、无前后台定时任务、13 项独立实时请求、独立 loading、按需滚动分页下钻，以及通用白名单指标端点与最多 4 路并发方案；并在修订 1 落盘后明确回复“实施”。

## 目标与成功信号

在数据迁移模块当前项目范围内，以已确认的响应式排版展示 13 个实时资产指标。指标分别请求并独立反馈，单项故障不阻塞其他卡片；点击指标后才加载滚动分页明细。看板不再依赖前端轮询、后端定时任务或快照数据。

成功信号：13 个指标和对应下钻结果口径一致；项目切换无旧数据残留；单项失败可恢复；桌面和三个手机视口无页面级横向溢出；查询满足确定的延迟门槛。

## 使用者与场景

- 数据迁移管理员：进入整体看板快速识别资料覆盖结构，点击指标检查具体资产。
- 普通数据迁移人员：在已有看板访问权限和项目数据范围内查看相同统计及明细，不获得额外写权限。
- 高频场景：进入页面、切换顶部全局项目、手动刷新全部指标、重试单项、滚动查看某项明细。

## 必须需求与验收条件

### R1 13 项项目级实时统计

必须展示以下指标：

| 指标码 | 展示名称 | 数据口径 |
| --- | --- | --- |
| `OVERALL_PLAN` | 迁移整体方案 | `dm_plan.granularity='PROJECT'` |
| `COMPONENT_PLAN` | 组件级迁移方案 | `dm_plan.granularity='SYSTEM'` |
| `PROJECT_TOPIC` | 项目级专题 | `dm_topic.granularity='PROJECT'` |
| `COMPONENT_TOPIC` | 组件级专题 | `dm_topic.granularity='SYSTEM'` |
| `REPORT` | 汇报资料 | `dm_report` |
| `MEETING` | 会议纪要 | `dm_meeting` |
| `ISSUE` | 问题清单 | `dm_issue` |
| `RELEASE_DRILL` | 投产及演练资料 | `dm_release_drill` |
| `MAPPING_DOC` | 迁移映射资料 | `dm_mapping_doc` |
| `RULE` | 迁移检核规则 | `dm_rule` |
| `PARAMETER` | 迁移参数 | `dm_parameter` |
| `DEPENDENCY` | 迁移过程依赖文件 | `dm_dependency` |
| `SCRIPT` | 迁移程序 | `dm_script` |

每项均限定认证租户、必填且可访问的当前项目与 `deleted=0`。验收时逐项将卡片数量与完整下钻分页结果交叉核对。

### R2 取消定时刷新与快照运行依赖

前端不得创建轮询计时器，后端不得运行 `DashboardSnapshotScheduler`，整体看板指标及下钻不得读取或写入 `dm_dashboard_snapshot`。本次保留空闲表，不增加破坏性删表迁移。

### R3 独立请求和独立状态

每个指标通过独立 HTTP 请求实时获取；前端请求队列最多同时执行 4 项。卡片分别维护 idle/loading/success/error 状态并提供失败重试。刷新全部指标时重新排队，不清除已经成功但尚未被新响应替换的跨指标数据；项目变化时则必须立即清空全部旧项目数据。

总量只有在 13 项全部成功后才显示。部分失败时显示未完成项数和重试入口，不显示误导性的部分总和。构成图与排行显示成功项，并明确标注部分数据未加载。

### R4 按需滚动下钻

点击指标才打开下钻抽屉并加载第一页；每页固定 20 条。滚动接近底部后串行加载下一页，不预取其他指标或未到达的下一页。首屏加载、空、首屏失败、后续页失败、无权限和全部加载完成均有稳定状态；后续页失败保留已有记录。

### R5 项目隔离与权限

服务端从认证主体读取租户，逐次执行看板 RBAC 与 `requireProject(projectId, user)`。未知指标码、缺少项目、不可访问项目均失败关闭。前端项目切换时取消请求或使用请求代次丢弃旧响应，并关闭下钻。

### R6 响应式视觉实现

桌面端按“总量锚点 + 四项方案/专题 + 九项内容资产 + 构成与排行”组织；平板将四项核心指标排为 2x2，总量卡与其对齐；手机端保留两列指标、精简辅助文字、图表下移，抽屉接近全宽且标题和关闭操作固定。使用语义主题变量，并覆盖明暗主题。

### R7 性能门槛

单指标查询 P95 不高于 500ms，13 项全部完成不高于 2s，下钻分页 P95 不高于 800ms。`EXPLAIN ANALYZE` 必须证明查询受租户和项目范围索引约束；超标时优先修正数据迁移模块内索引或查询，不自动引入缓存、快照或定时任务。

## 不变量与约束

- 全局项目切换器是唯一项目来源，页面不新增所属项目筛选或字段。
- 服务端租户、RBAC、项目可达性和实体数据范围不能由前端替代。
- 指标码由后端固定白名单解析，不能将外部字符串作为 SQL 表名或条件拼接。
- 指标计数与下钻明细必须共享同一指标定义，不能分别猜测口径。
- 不修改平台公共组件、全局 store、附件、审计和其他业务模块。
- `dm_dashboard_snapshot` 仅保留兼容，不参与运行；Flyway 历史脚本不修改。

## 非目标

- 不实现自动轮询、WebSocket、SSE、缓存预热或后台快照刷新。
- 不预取任何下钻明细，不将全部明细加载到浏览器后本地分页。
- 不改变各资产内容页的 CRUD、标准分页、字段或权限行为。
- 不删除 `dm_dashboard_snapshot` 表，不新增写操作审计。
- 不改造组件级看板。

## 方案比较与选择

### 选定：通用白名单端点 + 最多 4 路并发

接口按指标码复用统一 Controller/Service 入口，后端通过固定定义选择 SQL；前端仍为 13 个独立请求，并使用最多 4 路的队列限制瞬时数据库连接占用。该方案同时满足独立 loading、局部恢复、代码集中和性能可控。

### 未选方案

- 13 个专用接口：契约直观，但 Controller、权限声明和测试重复，新增指标维护成本高。
- 13 路无界并发：首批响应可能更快，但多用户同时进入时形成连接池和数据库突发压力。
- 单次批量汇总：网络开销最低，但不满足每项独立请求和独立 loading 的已确认要求。

## 架构边界与组件职责

- `DashboardMetricDefinition`：固定登记 13 个指标码、展示类别、计数条件和下钻投影，拒绝未知指标；是计数与明细的唯一口径源。
- `DashboardService`：执行项目校验、单指标计数和单指标分页下钻；不读取快照。
- `DashboardController`：承载整体/组件兼容接口以及新的单指标、下钻端点和 RBAC 声明。
- `OverallDashboardPage`：渲染已确认布局，管理 13 项独立状态、并发队列、派生总量/图表和下钻抽屉。
- `data-migration.ts`：提供有类型的指标与下钻请求，不暴露任意指标字符串。
- `DashboardSnapshotScheduler`：从 Spring 运行图中移除；若无其他引用则删除类和对应测试。

交付示范中心复用：沿用 `UiPageHeader`、语义面板、ECharts 主题重建、响应式图表和可访问标签模式。新增指标布局的例外原因是示范中心只覆盖少量同状态指标，无法表达 13 项独立 loading/error/retry；新样式严格限定在整体看板，不修改 `web/src/components/ui`。

## 接口、数据和状态流

### 单指标

```text
GET /api/data-migration/dashboard/overall/metrics/{metricCode}?projectId={id}
```

统一响应数据：

```json
{
  "metricCode": "OVERALL_PLAN",
  "count": 6,
  "calculatedAt": "2026-09-08T22:30:05+08:00"
}
```

### 下钻分页

```text
GET /api/data-migration/dashboard/overall/drilldowns/{metricCode}?projectId={id}&page=1&size=20
```

响应沿用模块分页信封，记录统一投影为 `id`、`businessCode`、`title`、`category`、`granularity`、`systemCode`、`systemName`、`updatedByName`、`updatedAt`；不适用字段返回空值。排序固定为 `updated_at DESC` 加稳定业务主键倒序，避免滚动分页同页顺序漂移。

### 状态流

1. 项目 ready 后建立 13 项任务并以最多 4 路执行。
2. 单项响应只更新对应指标；所有成功后计算总量和完整图表。
3. 手动刷新生成新请求代次；旧代次响应不得写入。
4. 点击卡片后重置该抽屉分页并请求第一页。
5. 滚动阈值触发下一页；在途、无下一页或失败待重试时不重复请求。
6. 项目变化立即递增代次、清空页面、关闭抽屉并重新排队。

## 错误、降级与恢复

- 指标请求失败：对应卡片显示错误和重试，其他指标继续完成。
- 下钻第一页失败：抽屉展示错误与重试，不伪装为空。
- 下钻后续页失败：保留现有记录，在底部显示继续重试。
- 空数据：指标显示 0，抽屉显示明确空状态。
- 无权限：页面级 403 显示无权限；单项异常权限响应不得泄露项目是否存在。
- 请求乱序：使用取消信号和请求代次双重保护；取消不展示为业务错误。
- 图表降级：部分指标失败时保留成功数据并显示不完整标记；全部失败时显示错误状态而非空画布。

## 安全、性能、兼容性与运维

- 安全：所有接口认证、RBAC、租户和项目校验；静态指标定义阻断 SQL 注入。
- 性能：每次请求只统计一个项目中的一个指标；并发上限 4；下钻固定 20 条并使用稳定索引排序。
- 兼容：保留当前 `/dashboard/overall` 和 `/dashboard/component(s)` 路由供兼容，整体页面切换到新接口；组件看板行为不变。
- 运维：无后台调度和快照一致性运维；通过接口耗时和慢查询观测性能。保留表的后续删除必须另立迁移需求。

## 验证策略

- 服务单元测试：13 个指标码、表/颗粒度映射、未知码拒绝、`deleted=0`、租户与项目参数。
- Controller 安全测试：权限、缺项目、跨项目、未知指标和响应字段白名单。
- MySQL 集成测试：指标数字与下钻全分页一致，`EXPLAIN ANALYZE` 和延迟门槛；验证会议、问题及方案/专题分层。
- 前端静态与构建：类型检查、构建、请求并发上限和请求代次逻辑测试。
- 浏览器：`1280x800`、`375x812`、`390x844`、`430x932`，覆盖逐卡 loading、部分失败、单项重试、全量刷新、项目切换、抽屉滚动、后续页失败、空状态、明暗主题和页面级横向溢出。
- 治理：`git diff --check`、当前需求范围检查、`node scripts/check-all-governance.mjs`、聚焦 Maven 测试和 `npm --prefix web run build`。

## 假设、未知项与决策记录

- 假设：13 张业务表均保留以 `tenant_id, project_id` 为前缀的可用索引；`EXPLAIN ANALYZE` 可推翻该假设并触发有界索引纠正。
- 假设：统一下钻投影足以完成看板快速核查；完整编辑与领域专属字段仍由原内容页承担。
- 未阻塞未知项：目标环境的真实单项目数据规模尚未提供，以性能门槛和查询计划作为上线前事实判断。
- D1：取消所有前后台定时刷新和运行时快照依赖。
- D2：采用通用白名单指标端点，每项独立请求，前端最多 4 路并发。
- D3：下钻使用页面内右侧抽屉和滚动分页，每页 20 条，点击后才加载。
- D4：保留但停用 `dm_dashboard_snapshot`，本次不做破坏性删表迁移。

## 风险与回退原则

- 风险：多用户同时进入产生数据库突发；以 4 路并发、项目索引和性能门槛控制。
- 风险：异构表字段导致下钻投影或计数条件漂移；以单一指标定义和计数/分页交叉测试控制。
- 风险：项目切换时旧响应污染；以取消信号和请求代次双重保护。
- 回退：恢复旧整体看板页面和兼容汇总接口即可；快照表未删除，数据库无需反向迁移。不得通过恢复后端定时任务掩盖新接口问题。
