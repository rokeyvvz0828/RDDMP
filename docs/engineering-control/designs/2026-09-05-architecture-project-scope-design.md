# 架构与环境能力按项目隔离工程设计

## 目标与成功信号

物理子系统、部署单元、环境管理、资源申请、环境部署实例和搭建计划接入顶部项目上下文。普通用户只能访问其有效成员项目中的架构数据，所有接口和关联均由服务端强制校验项目归属，不同项目允许使用相同编号和名称且不会发生数据串联。

成功信号包括：双项目同编号数据可同时存在；列表、详情、直接 ID、关联选项、写入、审批、通知和项目切换均无跨项目泄漏；工作流实例项目与业务项目一致；默认项目迁移和项目删除保护具有可重复验证证据。

## 使用者与场景

- 项目成员在顶部选择项目后进入架构管理，查看当前项目资产和执行记录。
- 具备对应架构动作权限的项目成员维护物理子系统、部署单元和环境，提交资源申请并执行搭建计划。
- 审批人在工作流待办或业务详情中处理当前项目审批。
- 超级管理员跨项目维护和排查，但每次请求仍具有明确项目上下文。

## 必须需求与验收条件

1. 六类主数据及关键子数据具有显式项目归属，查询和写入限定 `tenant_id + project_id`。
2. 页面自动跟随顶部当前项目，不提供业务页面内项目选择器。
3. 项目内保持永久唯一，跨项目允许相同编号和名称。
4. 所有关联、资源下发、实例生成和计划目标保持项目一致。
5. 项目成员资格与现有架构 RBAC 叠加授权，超级管理员保留全项目访问。
6. 搭建计划模板与版本租户级共享，生成的计划绑定当前项目。
7. 架构业务流程复用现有项目工作流能力并传递真实项目上下文。
8. 存量数据归入 `RDDMP-PLATFORM`，默认项目缺失时迁移失败。
9. 存在架构数据的项目不能删除。
10. 受影响的跨模块消费者按项目匹配物理子系统。
11. 原“具体环境”用户界面名称改为“环境管理”，内部稳定契约保持兼容。

完整可观察验收条件以需求文档第“验收标准”节为准。

## 不变量与约束

- `tenant_id` 和 `project_id` 均来自服务端可信上下文，业务写入 DTO 不接收两者。
- architecture 只能直接写自身 `arch_` 表，通过公开契约访问项目和工作流能力。
- system 不得反向依赖 architecture；项目删除保护使用 system 定义扩展点、architecture 提供实现。
- Flowable `ACT_*` 表、历史 Flyway 和现有 Java 包名不得修改。
- 搭建计划模板无项目归属；业务执行计划必须有项目归属。
- 只使用本地、测试和虚构数据，不访问生产系统。

## 非目标

- 多项目共享、跨项目复制或转移架构数据。
- 新增项目级架构角色。
- 将架构页面移入项目详情。
- 工作流平台再次项目化或新增流程范围类型。
- Java 包、数据库表和环境 API 路径重命名。

## 方案比较与选择

选择“全链路显式项目归属”：六类主表及需要独立访问、关联、审计和回调的关键子表保存 `project_id`。该方案修改面较大，但查询条件明确、数据库约束可表达、直接 ID 访问容易验证，最符合项目完全隔离目标。

未选择“根实体保存项目、子表 JOIN 推导”，因为直接访问子数据时容易遗漏隔离条件；未选择“项目绑定关系表”，因为它增加查询和唯一性复杂度，并与单项目独占模型不一致。

## 架构边界与组件职责

- 前端项目上下文：提供当前 `projectRef`，切换确认后整页刷新。
- architecture Controller：要求 `projectRef`，完成 HTTP 输入校验并调用项目解析。
- architecture Service/Store：只接收已解析的项目上下文，执行业务规则、项目一致性和持久化限定。
- `ProjectAccessService`：由 system 校验项目存在、租户和成员访问权，返回可信项目 ID、编号和名称。
- 项目删除检查扩展点：system 在删除项目前调用所有业务引用检查器；architecture 统计未删除架构数据并在存在引用时阻断。
- 工作流网关：沿用现有项目流程匹配、实例固化、成员/角色审批和待办隔离。
- 下游消费者：数据迁移、测试管理等查询物理子系统时同时匹配自身 `project_id` 与架构 `project_id`。

## 接口、数据和状态流

```text
顶部当前项目 projectRef
  -> 架构 API 必填 projectRef
  -> ProjectAccessService.requireAccessible
  -> ProjectAccess(projectId, projectRef, projectName)
  -> architecture Service
  -> tenantId + projectId 查询、写入、唯一性与关联检查
```

详情、更新和删除即使使用全局实体 ID，也必须附带当前 `projectRef`，Store 只按 `id + tenant_id + project_id` 命中。创建表单不显示所属项目，服务端从可信上下文写入项目主键。

工作流启动时，业务记录项目、`WorkflowBusinessContext.projectRef/projectName` 和最终 `wf_instance.project_id` 必须一致。生命周期消费者收到事件后先校验业务类型、主键、轮次、实例及项目，再更新业务状态。

迁移先增加可空项目列，按业务关联链回填默认项目并校验无空值、无跨项目关系，再改为非空并重建项目维度唯一索引和必要约束。计划模板表不参与项目列迁移。

## 错误、降级与恢复

- 未传项目：`400`，提示选择项目。
- 项目不存在或已删除：`400`，重新加载项目列表。
- 无项目访问权或缺少动作权限：`403`，页面进入无权限状态。
- 实体不属于项目：列表不可见，详情返回 `404`。
- 跨项目关联：`400` 并保留表单输入。
- 并发归属或版本冲突：`409`，刷新后重试。
- 工作流项目不一致：拒绝启动或事件消费，不改变业务事实。
- 默认项目缺失：迁移失败，不自动选择其他项目。
- 项目存在架构引用：删除返回 `409`，先处理业务数据。

## 安全、性能、兼容性与运维

- 安全：每个服务端入口重复校验认证、RBAC、项目访问和实体归属；前端显隐不作为授权依据。
- 性能：为常用列表、唯一性和关联条件建立 `tenant_id + project_id` 前缀索引，避免通过全表 JOIN 推导项目。
- 兼容：保留现有菜单路由、Java 包、表名和 API 根路径；新增必填 `projectRef` 属于受控接口变更。
- 运维：发布前扫描迁移版本并确认默认项目；迁移后抽样检查各层项目列、孤立引用和工作流项目一致性。

## 验证策略

- 双项目数据矩阵：同编号数据、单项目成员、双项目成员和超级管理员。
- API：列表、详情、创建、更新、删除、选项、直接 ID 和跨项目关联。
- 数据库：空库、既有库、默认项目缺失、非空列、索引、唯一性和关联一致性。
- 工作流：项目流程启动、审批人限制、跨项目待办拒绝和生命周期回调。
- 跨模块：数据迁移与测试管理的物理子系统解析、列表和统计。
- 前端：切换项目、六个页面全状态、桌面和三个手机视口、明暗主题及页面横向溢出检查。

## 假设、未知项与决策记录

- 假设 `RDDMP-PLATFORM` 在每个存在架构存量数据的租户中唯一且未删除；迁移前置检查会验证该假设。
- 假设现有 `ProjectAccessService` 的成员访问语义继续作为业务模块统一项目访问规则。
- 实施迁移版本尚未分配，进入计划和编码前必须重新扫描主干当前最高版本。
- 具体受影响子表和跨模块查询将在实施计划中以文件和表清单固定，不允许执行阶段临时扩大范围。

已确认决策：单项目独占；默认项目迁移；模板共享；保留架构菜单；项目内唯一；项目成员与 RBAC 叠加；全链路显式项目字段；复用现有项目工作流。

## 风险与回退原则

- 多表回填或约束顺序错误可能导致迁移中断；使用前置统计和分阶段 SQL 限制风险。
- 直接 ID 查询遗漏项目条件会导致越权；通过双项目负向测试和 Store SQL 扫描发现。
- 跨模块按编号关联未增加项目条件会串数据；将消费者清单纳入任务范围和回归测试。
- 项目删除扩展点属于公共能力变更，需要 system Owner 审批和项目管理回归。
- 应用回退不删除已执行列；结构回退使用后续补偿迁移，不修改历史脚本。
