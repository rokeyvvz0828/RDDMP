# 追加申请冲突取消终态工程设计

## 文档状态

- 修订：1
- 状态：已确认
- 用户确认依据：用户确认仅调整追加申请冲突弹框；弹框内撤销应直接形成“已取消”且永久只读，普通申请列表撤回保持“已撤回”并允许后续编辑、重新提交；复核落盘设计后要求开始实施。

## 目标与成功信号

追加申请被审批中的旧申请阻塞时，旧申请的创建人可从冲突弹框发起“取消申请”。系统必须先可靠终止旧申请的审批流程，再将旧申请最终置为 `CANCELLED（已取消）`；此后旧申请只能查看，不能编辑、保存草稿、修改附件或重新提交。申请列表中的普通“撤回”继续形成 `WITHDRAWN（已撤回）`，既有可编辑和重新提交能力不变。

## 使用者与场景

版本申请人在创建或保存追加申请时，发现同窗口、同交付内容存在自己创建且仍处于审批中的旧申请，需要在冲突弹框中终止旧审批并取消旧申请，之后继续当前申请。

## 必须需求与验收条件

- R1：冲突弹框仅对当前用户创建、状态为 `IN_REVIEW` 且用户具备 `release:application:withdraw` 权限的旧申请显示“取消申请”；其他状态、其他创建人的申请不得显示该操作。
- R2：冲突弹框取消使用独立后端命令，不得调用普通撤回接口；命令校验租户、所有者、权限、`IN_REVIEW` 状态、行版本、有效审批轮次和必填原因。
- R3：取消命令必须先将审批轮次从 `IN_REVIEW` 原子更新为 `CANCEL_REQUESTED`，再调用现有工作流终止网关；终止生命周期事件到达后，申请由 `IN_REVIEW` 变为 `CANCELLED`，轮次变为 `TERMINATED`。
- R4：普通撤回状态流保持 `IN_REVIEW -> WITHDRAW_REQUESTED -> WITHDRAWN`，列表按钮、接口、权限及可编辑、重新提交行为不得改变。
- R5：取消请求处理中，冲突弹框显示“取消处理中”，底部“继续申请”保持禁用；轮询确认旧申请不再为 `IN_REVIEW` 后才允许继续原保存或提交动作。
- R6：`CANCELLED` 申请详情必须只读；更新、保存草稿、提交、重新提交、附件新增或删除等写操作必须由后端拒绝，前端不得展示可用编辑入口。
- R7：工作流终止调用同步失败时，不得把申请提前写为 `CANCELLED`；接口返回明确错误，弹框保持阻塞并允许刷新后重试。

## 不变量与约束

- 业务申请处于 `CANCELLED` 时，不得存在仍可审批的活动工作流任务。
- 业务申请在工作流终止确认前保持 `IN_REVIEW`，避免业务终态与流程活动状态分裂。
- 普通撤回仍以 `WITHDRAWN` 为终态，既有恢复编辑能力不变。
- 复用现有工作流终止网关、生命周期事件、冲突轮询和申请只读判断；不新增数据库字段，轮次状态列继续存储字符串状态。
- 保持现有租户隔离、所有者校验、行版本并发控制和权限模型。
- 保护 `rokey` 工作区已有未提交修改，不清理、不回退、不切换分支。

## 非目标

- 不改变申请列表中的普通撤回、普通取消和重新提交流程。
- 不允许取消其他用户创建的审批中申请。
- 不改变冲突匹配、追加申请判定或保存/提交门禁范围。
- 不新增工作流引擎能力、数据库迁移或新的角色权限项。
- 不将已撤回历史申请批量转换为已取消。

## 方案比较与选择

选择“独立取消意图 + 生命周期终态映射”。冲突取消将轮次标记为 `CANCEL_REQUESTED`，终止事件根据轮次意图映射到 `CANCELLED`；普通撤回的 `WITHDRAW_REQUESTED -> WITHDRAWN` 不变。该方案能区分两类用户动作，并保证业务终态只在工作流确认终止后产生。

- “立即写入 `CANCELLED` 再终止工作流”响应更直接，但终止失败时会留下已取消申请和活动审批任务并存的不一致。
- “先普通撤回到 `WITHDRAWN` 再调用取消”可复用更多代码，但会产生短暂可编辑状态、额外行版本竞争和两段事件噪声。

## 架构边界与组件职责

- `ReleaseApplicationController`：新增冲突取消端点，沿用 `release:application:withdraw` 权限。
- `ReleaseSubmissionService`：校验冲突取消命令，记录 `CANCEL_REQUESTED` 意图并终止审批流程。
- `ReleaseWorkflowStore`：提供轮次 `IN_REVIEW -> CANCEL_REQUESTED` 和申请 `IN_REVIEW -> CANCELLED` 的并发安全更新。
- `ReleaseWorkflowLifecycleConsumer`：在 `TERMINATED` 事件中区分 `WITHDRAW_REQUESTED` 与 `CANCEL_REQUESTED`，分别形成 `WITHDRAWN` 与 `CANCELLED`。
- `web/src/api/release.ts`：提供独立冲突取消 API 函数，保留普通撤回 API。
- `ReleaseManagementPrototype.vue`：冲突弹框改调冲突取消命令并轮询最终状态。
- `ReleaseConflictDialog.vue`：使用“取消申请/取消处理中”文案和既有继续门禁。

## 接口、数据和状态流

新增 `POST /api/release/applications/{code}/conflict-cancel`，请求继续使用 `{ rowVersion, reason }`，响应沿用 `WorkflowActionResult`。端点要求 `release:application:withdraw` 或 `system:admin`，服务层继续强制所有者校验；管理员提升权限沿用现有行为。

状态流：

1. 前端对满足条件的阻塞申请发起冲突取消。
2. 后端锁定申请和最新审批轮次，校验申请与轮次均处于 `IN_REVIEW`。
3. 轮次原子更新为 `CANCEL_REQUESTED`，调用工作流终止网关，记录 `CANCEL_REQUESTED` 业务事件；申请暂时保持 `IN_REVIEW`。
4. 工作流发送 `TERMINATED` 生命周期事件。
5. 消费者将申请原子更新为 `CANCELLED`，轮次从 `CANCEL_REQUESTED` 更新为 `TERMINATED`，记录 `WORKFLOW_TERMINATED` 事件及取消来源。
6. 弹框轮询看到旧申请退出 `IN_REVIEW` 后，按原逻辑允许继续当前申请。

普通撤回继续使用 `POST /api/release/applications/{code}/withdraw`，状态流不变。

## 错误、降级与恢复

- 状态、行版本或轮次已变化：返回 409，保持继续禁用，刷新冲突信息后由用户重试。
- 原因缺失：返回 400，前端输入校验同时阻止请求。
- 工作流终止同步抛错：事务回滚 `CANCEL_REQUESTED` 和事件写入；申请、轮次仍保持原状态。
- 终止事件延迟：申请保持 `IN_REVIEW`，按钮显示处理中，轮询继续；不得提前允许继续申请。
- 重复终止事件：沿用生命周期事件幂等机制；已处理或状态不匹配事件不得重复转换。
- 详情只读前端判断遗漏：后端状态校验仍拒绝所有写操作。

## 安全、性能、兼容性与运维

安全上沿用认证、租户、所有者、权限和乐观锁校验。性能上不增加常驻任务，仍仅在冲突弹框开启时每 2 秒轮询。接口为新增命令，不破坏现有撤回客户端；轮次状态列可直接承载新字符串，无数据库迁移。事件和轮次状态可用于排查异步终止延迟。

## 验证策略

- 后端服务测试：冲突取消校验所有者、权限、状态、行版本和原因；成功时写入 `CANCEL_REQUESTED` 并调用终止网关。
- 生命周期测试：`CANCEL_REQUESTED + TERMINATED -> CANCELLED`；`WITHDRAW_REQUESTED + TERMINATED -> WITHDRAWN`；重复事件保持幂等。
- 写保护测试：`CANCELLED` 的更新、提交、重新提交和附件变更均被拒绝。
- 前端构建与组件/交互验证：弹框文案、显示条件、处理中禁用、2 秒轮询、完成后继续；普通列表撤回仍显示并形成已撤回。
- 浏览器端到端验证：创建审批中旧申请、从追加冲突弹框取消、确认审批任务终止、旧详情只读、当前申请可继续。
- 运行 release 模块测试、前端生产构建和 `git diff --check`。

## 假设、未知项与决策记录

- 假设：工作流终止网关在同步异常时抛出异常，使事务能够回滚；依据为现有普通撤回实现。
- 假设：生命周期事件包含可定位当前审批轮次的实例和业务上下文；依据为现有 `ReleaseWorkflowLifecycleConsumer`。
- D1：冲突弹框取消与普通撤回使用不同后端命令和轮次意图。
- D2：只有工作流终止事件才能把审批中申请转换为 `CANCELLED`。
- D3：冲突取消继续使用现有撤回权限，不新增权限数据迁移。
- D4：已取消为永久只读终态，普通已撤回仍可编辑和重新提交。
- 未知项：无阻塞未知项。

## 风险与回退原则

主要风险是工作流终止事件延迟或丢失，使申请长期停留在 `IN_REVIEW` 且轮次为 `CANCEL_REQUESTED`。通过明确处理中状态、轮询、事件日志和现有运维重放机制保持可观察性。回退时可独立移除冲突取消端点和 `CANCEL_REQUESTED` 分支，并让弹框恢复普通撤回；不得只回退生命周期映射而保留新命令，以免产生无法收敛的轮次。
