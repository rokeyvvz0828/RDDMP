# 业务详情内审批工程设计

## 文档状态

- 需求编号：`REQ-20260815-027`
- 上游需求：`REQ-20260814-022`、`REQ-20260814-026`
- 修订：1
- 状态：已确认
- 用户确认依据：用户指出通用工作流审批缺少版本申请详情，明确要求审批操作回到填写工单所在的业务模块；随后确认移除工作流待办/已办、选择独立业务详情路由方案，并确认用户流程、架构接口、页面状态和验收设计。

## 目标与成功信号

让审批人始终在完整版本申请上下文中完成判断和操作，同时收敛工作流、工作台与业务模块职责。

成功信号：

1. 工作流管理模块不再承载业务待办、已办和审批表单。
2. 首页及任务中心能够聚合任务，但所有查看与处理都进入业务详情。
3. 配置管理业务详情是版本申请查看、流程进展和审批操作的唯一页面。
4. 工作流平台仍统一控制任务权限、允许动作、签名和审计。
5. Web 与 H5 使用相同业务路由和状态规则。

## 使用者与场景

| 使用者 | 场景 |
|---|---|
| 审批人 | 从首页、任务中心或通知进入完整版本申请并完成审批 |
| 申请人 | 从版本申请列表查看工单、审批进展、退回意见和流转日志 |
| 已办人员 | 从已办记录回到原业务工单查看处理结果 |
| 工作流管理员 | 配置流程并在流程监控中观察实例与审计，不执行业务审批 |

## 必须需求与验收条件

| ID | 必须需求 | 验收条件 |
|---|---|---|
| R1 | 业务详情拥有审批界面 | 完整工单与当前任务操作在同一业务页面 |
| R2 | 单一稳定业务路由 | 列表、待办、已办、通知和 H5 使用 `/release/applications/:applicationCode` |
| R3 | 工作台仅聚合导航 | 首页和任务中心没有审批表单或快捷审批按钮 |
| R4 | 工作流管理职责收敛 | 菜单只保留流程定义与监控，页面无业务审批操作 |
| R5 | 单任务上下文可查询 | 服务端返回业务路由、节点、状态、动作、签名和处理资格 |
| R6 | 服务端权限与幂等 | 越权、已处理、失效和重复动作被服务端拒绝 |
| R7 | 审批后原地刷新 | 页面更新申请状态、流程进展和日志，不跳出业务模块 |
| R8 | 历史地址兼容 | 旧待办、已办和审核地址安全转向工作台或业务详情 |
| R9 | 菜单持久下线 | 新 Flyway 迁移移除菜单 202、204 及角色关系，API 保留 |
| R10 | 响应式业务审批 | 桌面和三个手机视口均可查看完整工单并完成允许动作 |

## 不变量与约束

- 配置管理拥有版本申请业务信息和展示规则。
- 工作流平台拥有任务、待办人、允许动作、签名、流程状态与审计。
- 工作台只聚合任务投影，不复制业务详情。
- 流程监控只用于管理和审计，不成为审批入口。
- `action_path` 是受控站内绝对业务路径，不包含外部地址。
- 前端显隐不能替代服务端租户、身份、任务状态和动作校验。
- 当前版本申请由 Mock Provider 提供，正式 API 接入时保持路由与工作流契约。
- 不修改已发布 Flyway，菜单下线使用 `V37` 前向迁移。

## 非目标

- 不实现正式配置管理持久化后端。
- 不把版本申请 DTO、附件和业务规则复制进工作流模块。
- 不删除待办、已办、决策、监控等工作流后端公共能力。
- 不建立第二套移动端审批规则或独立 H5 应用。
- 不允许任务中心执行快捷审批。

## 方案比较与选择

### 已选：独立业务详情路由

使用 `/release/applications/:applicationCode` 作为版本申请唯一详情和审批地址。业务详情按任务上下文决定是否显示审批区，工作台只导航。

选择原因：地址稳定、可刷新和分享，业务上下文完整，Web/H5 可复用，工作流与业务职责最清晰。

### 未选：查询参数打开详情抽屉

改动较小，但刷新、返回、深链接和移动端长内容体验较弱，详情和审批容易继续分散。

### 未选：工作流动态加载业务组件

能在通用页面展示业务内容，但工作流必须理解业务组件注册和生命周期，仍然承担业务展示职责。

```text

```

| 组件 | 职责 | 依赖 |
|---|---|---|
| `ReleaseApplicationDetailPage` | 完整业务详情、审批进展和条件审批区 | 业务 Provider、工作流 API、当前身份 |
| `ReleaseApprovalPanel` | 意见、签署、同意、退回、拒绝和提交状态 | 单任务上下文、任务决策接口 |

| `DashboardView` | 每类最多五条摘要及查看全部 | TaskCenter、action_path |
| `WorkflowView` | 流程定义和流程监控 | 工作流定义与监控 API |

| `V37` | 下线待办/已办动态菜单 | sys_menu、sys_role_menu |

## 接口、数据和状态流

### 业务路由

```text
/release/applications/:applicationCode
  ?taskId=<pending-task-id>
  ?instanceId=<done-instance-id>
```

`applicationCode` 等于工作流 `business_key`。工作流实例登记：

```text
business_type = release_application
business_key = <applicationCode>
action_path = /release/applications/<applicationCode>
```

### 单任务上下文

候选接口：`GET /api/workflows/tasks/{taskId}/context`

返回至少包含：`taskId`、`instanceId`、`businessType`、`businessKey`、`businessTitle`、`businessRound`、`actionPath`、`taskType`、`nodeId`、`nodeName`、`status`、`allowedActions`、`signatureRequired`、`actionable`。

- `actionable=true` 只在任务属于当前登录人、仍待处理且任务类型可操作时成立。
- 非当前待办人不能通过篡改 `taskId` 获得审批能力。
- 决策接口继续使用 `POST /api/workflows/tasks/{taskId}/decision`。

### 导航流

1. 首页或任务中心读取 inbox/done 投影。
2. 校验 `action_path` 为站内绝对路径。
3. 待办附加 `taskId`，已办附加 `instanceId`，进入业务详情。
4. 业务详情按 `applicationCode` 加载完整版本申请。
5. 存在 `taskId` 时加载指定任务上下文；不存在时按 `business_type=release_application`、申请单号和当前登录人解析本人待办。上下文有效才显示审批区。
6. 提交决策后重新解析当前任务，并刷新申请、进展和日志。

### 页面状态

| 状态 | 行为 |
|---|---|
| 可审批 | 展示意见、签署和允许动作 |
| 只读 | 展示业务详情和流程记录，不展示提交控件 |
| 无权限 | 业务详情按业务权限展示，审批区说明无处理权限 |
| 任务失效 | 提示任务已变化，刷新流程进展 |
| 提交中 | 锁定全部审批按钮，禁止重复提交 |
| 提交成功 | 保留当前页面，刷新业务状态和日志 |

## 错误、降级与恢复

| 条件 | 行为 | 恢复 |
|---|---|---|
| 业务单不存在 | 显示明确空结果，不显示审批区 | 返回版本申请或任务中心 |
| 任务不存在/已处理 | 详情保留，审批区切为只读 | 刷新进展或返回任务中心 |
| 任务越权 `403` | 不显示任何审批能力 | 使用有权账号或返回 |
| 状态冲突 `409` | 保留已填写意见，提示任务已变化 | 刷新上下文后重新判断 |
| 业务数据加载失败 | 不允许仅凭任务摘要审批 | 重试业务详情加载 |
| 决策失败 | 不本地伪造成功状态 | 保留意见并允许重试 |
| 历史 action_path | 路由兼容层转换旧地址 | 进入业务详情或工作台 |

## 安全、性能、兼容性与运维

### 安全

- 单任务上下文和决策都使用认证主体，不接受客户端指定审批人或签署人。
- 服务端校验租户、待办人、任务状态、任务类型和允许动作。
- `action_path` 继续执行站内绝对路径校验，拒绝协议、双斜线、反斜线和换行。
- 页面无法加载完整业务详情时禁止审批。

### 性能

- 首页每类最多五条；任务中心分页查询。
- 业务详情按单号加载，任务上下文按单任务加载，不扫描完整待办列表。
- 审批成功后仅刷新当前申请及流程数据。

### 兼容性

- inbox、done 和 decision API 保留。
- 旧工作流地址提供路由重定向。
- 旧实例 action_path 可通过兼容映射进入业务详情。
- 回退数据库菜单时只允许新增前向迁移。

### 运维

- 记录任务上下文查询失败、决策冲突、历史路由转换失败和业务页面加载失败。
- 工作流监控继续提供实例级排障与审计。

## 假设、未知项与决策记录

### 假设

- 当前 inbox/done 投影中的 `business_key` 和 `action_path` 足以定位版本申请。
- 正式配置管理 API 会沿用申请单号作为稳定业务键。
- 当前工作流决策和签名服务可以继续复用，无需改变动作语义。

### 非阻塞未知项

- 正式配置管理业务详情 API 尚未实现；当前继续使用 Mock Provider。
- 通知中心正式跳转接入可复用同一 `action_path`，不阻塞首页和任务中心实现。

### 决策

| ID | 决策 | 依据 |
|---|---|---|
| D1 | 采用独立业务详情路由 | 用户选择方案1 |
| D2 | 移除工作流待办与已办菜单 | 用户明确要求先移除 |
| D3 | 任务中心只聚合和跳转 | 防止出现第二套通用审批页面 |
| D4 | 工作流后端保留任务和决策能力 | 平台统一权限、签名和审计 |
| D5 | 当前版本申请继续 Mock | 项目与业务基础数据模块尚未正式接入 |

## 风险与回退原则

| 风险 | 影响 | 缓解 |
|---|---|---|
| 历史 action_path 指向旧页面 | 待办无法到达业务详情 | 旧路由兼容和安全转换 |
| Mock 跨路由状态重建 | 审批后返回列表可能恢复初始数据 | 原型使用共享会话仓储；正式实现由业务 API 持久化 |
| 单任务接口泄露他人任务 | 越权审批信息暴露 | 服务端以当前身份过滤并对决策强校验 |
| 菜单迁移影响既有收藏 | 旧入口失效 | 路由重定向到任务中心 |
| 平台和业务页面重复状态 | 显示不一致 | 任务状态只取工作流，业务状态只取业务 Provider |

回退时恢复前端旧入口和独立审批页；菜单只能用新的前向迁移恢复。工作流公共 API 不删除，因此业务页面和平台能力可以分别回退。
