# 配置管理审批流程场景绑定工程设计

## 文档状态

- 修订：1
- 状态：已确认
- 用户确认依据：用户确认在本地 `rokey` 分支实现按项目独立的“审批流程配置”，逐项确认页面位置、场景范围和生命周期规则，并于 2026-08-17 明确要求“开始实施”。

## 目标与成功信号

在配置管理模块增加“审批流程配置”，由配置管理员为当前项目的版本申请场景选择已发布流程，替代业务人员记忆和维护固定流程编码。版本申请提交时由后端根据场景解析绑定并启动流程，已启动申请继续固定使用提交时的流程定义及版本。

成功信号：配置人员可通过下拉框完成项目级绑定；未配置或失效场景在提交前给出明确错误；绑定变更只影响后续申请；已发布、已有实例或已绑定的流程不会被误删；活跃绑定阻止流程归档。

## 使用者与场景

- 配置管理员：在当前顶级项目上下文中维护五类版本申请场景的审批流程。
- 项目研发人员：提交版本申请时无需选择或填写流程编码。
- 工作流管理员：维护流程图和发布版本，并在归档前获知业务引用。
- 审计人员：查询绑定变更前后值、操作人、时间及原因。

## 必须需求与验收条件

### R1 项目级审批场景配置

- 配置管理顶部导航增加“审批流程配置”，与投产窗口、版本申请、投产基线等并列。
- 页面固定展示常规版本、常规追加版本、紧急版本、紧急追加版本、应急版本五个场景。
- 每个场景通过下拉框选择当前租户的已发布流程，不在该页面编辑流程图。
- 绑定按 `tenant_id + project_id + scene_code` 唯一，项目来自当前顶级项目上下文。
- 验收：切换项目后展示对应项目绑定；同一项目同一场景最多一个有效绑定；不同项目可选择不同流程。
- 反例：配置人员需要手输流程编码，或项目 A 的绑定覆盖项目 B。

### R2 允许部分配置并在命中时阻断

- 五个场景允许分批保存，未配置项明确显示“未配置”。
- 版本申请提交命中未配置场景时，后端在创建流程实例前阻断，并提示当前项目及场景尚未配置审批流程。
- 已绑定流程不再是已发布状态时，配置项显示“已失效”，提交时同样阻断。
- 验收：未启用的场景不影响其他已配置场景提交；错误提交不产生审批轮次、流程实例或申请状态变化。
- 反例：缺少应急绑定导致常规申请无法提交，或失败后留下 `STARTING` 审批轮次。

### R3 后端解析并固定流程版本

- 配置管理后端继续负责判定版本类型和追加特征，再以场景编码查询项目绑定。
- 绑定保存 `workflow_definition_id`，提交时校验定义为当前租户的 `PUBLISHED` 状态，并启动其当前已发布版本。
- 流程启动后，审批轮次保存实际定义 ID、定义版本和实例 ID；后续绑定变化不修改已有轮次和实例。
- 验收：绑定变更后新申请使用新流程，旧申请仍可在原流程版本中完成审批。
- 反例：前端传入流程定义 ID决定审批流程，或修改绑定导致审批中的申请跳转流程。

### R4 绑定审计与并发控制

- 新增、修改和解除绑定必须填写变更原因，并记录原流程、新流程、操作人和操作时间。
- 保存接口使用行版本或等价乐观锁；过期页面提交时返回明确冲突并要求刷新。
- 所有读取和写入按租户及项目隔离，服务端校验当前用户具有配置管理审批配置权限。
- 验收：可按场景查看完整变更记录；两个管理员并发修改时只允许一个基于相同版本成功。
- 反例：仅记录最终值而无法追溯前后变化，或依赖前端隐藏按钮实现授权。

### R5 工作流删除与归档保护

- 只有从未发布、不存在任何流程实例、没有有效业务场景绑定的纯草稿定义允许软删除。
- “从未发布”以不存在任何 `wf_version.status = 'PUBLISHED'` 的历史版本判断；“没有实例”以不存在任何 `wf_instance` 记录判断，不排除已终止或软删除实例。
- 已发布或曾发布流程不允许删除，只允许归档；有效绑定引用的流程归档前必须先改绑或解除绑定。
- 归档不影响已有实例、历史版本、审批记录、电子签名和审计日志。
- 验收：取消发布后的历史流程仍不能删除；归档被绑定流程时返回引用项目和场景；纯草稿可正常软删除。
- 反例：取消发布后通过 `DRAFT` 状态绕过删除保护，或归档后历史实例不可查询。

## 不变量与约束

- 版本申请的场景判定继续由后端完成，前端不决定流程定义。
- 已启动实例始终绑定原 `definition_id + version_no`，配置变化不得改写历史轮次。
- 项目上下文当前仍由前端 Mock 提供，接口使用稳定 `project_id/project_ref`，后续接入项目管理时不改变绑定语义。
- 工作流定义、版本、实例和业务绑定均按租户隔离。
- Flyway 迁移只追加，不修改已执行迁移。
- 保护 `rokey` 分支现有未提交修改，不进行无关重构或格式化。

## 非目标

- 不在本次建设平台级通用“业务场景中心”。
- 不允许在版本申请单中人工选择审批流程。
- 不在审批流程配置页面编辑流程图、审批节点或电子签名。
- 不自动为五个场景创建具体流程图或审批人。
- 不改变常规、紧急、应急及追加场景的既有判定规则。

## 方案比较与选择

| 方案 | 优点 | 代价与风险 | 结论 |
| --- | --- | --- | --- |
| 固定流程编码 | 实现简单，现有代码已具备 | 依赖人工记忆，错误发现晚，场景改绑需要改代码 | 不选 |
| 配置管理项目级绑定 | 贴近业务、操作直观、改动边界可控，可按项目差异化 | 需要新增数据、接口、页面和工作流引用保护 | 选择 |
| 平台级通用场景中心 | 可复用于所有业务模块 | 当前范围过大，需要定义跨模块场景治理模型 | 后续演进 |

## 架构边界与组件职责

- `ReleaseWorkflowBindingService`：维护项目级场景绑定、审计和乐观锁，提供提交期解析能力。
- `ReleaseWorkflowBindingStore`：读写绑定与绑定历史，不直接启动工作流。
- `ReleaseSubmissionService`：完成既有场景判定后调用绑定解析，再通过 `WorkflowBusinessGateway` 启动流程。
- `WorkflowDefinitionCatalog`：平台工作流提供的只读能力，列出已发布流程并校验定义状态和租户归属。
- `WorkflowService`：删除和归档前查询历史版本、实例及业务引用保护。
- `ReleaseWorkflowBindingReference`：配置管理向工作流平台暴露的引用查询接口，避免工作流直接查询 `rel_*` 表。
- `ReleaseApprovalWorkflowPage`：展示五个场景、流程选择、状态、变更原因和历史记录。
- `web/src/api/release.ts`：承载场景绑定列表、候选流程、保存及历史接口类型。

## 接口、数据和状态流

### 数据模型

新增 `rel_workflow_binding`：

- `id`, `tenant_id`, `project_id`, `project_name`
- `scene_code`: `REGULAR`, `REGULAR_ADDITIONAL`, `URGENT`, `URGENT_ADDITIONAL`, `EMERGENCY`
- `workflow_definition_id`
- `row_version`, `created_by`, `updated_by`, `created_at`, `updated_at`
- 唯一键：`tenant_id + project_id + scene_code`

新增 `rel_workflow_binding_history`：

- `id`, `tenant_id`, `binding_id`, `project_id`, `scene_code`
- `old_workflow_definition_id`, `new_workflow_definition_id`
- `operation`: `CREATED`, `UPDATED`, `UNBOUND`
- `reason`, `operator_id`, `operator_name`, `created_at`

解除绑定保留主记录并将 `workflow_definition_id` 置空，避免丢失行版本和场景历史；是否有效由流程定义当前状态联合计算，不冗余保存流程状态。

### HTTP 接口

- `GET /api/release/workflow-bindings?projectId=...`：返回五个固定场景、当前绑定流程摘要、有效性和行版本。
- `GET /api/release/workflow-bindings/candidates?projectId=...`：返回当前租户已发布流程候选项。
- `PUT /api/release/workflow-bindings/{sceneCode}`：新增、修改或解除当前项目场景绑定，请求包含 `projectId`、`projectName`、可空 `workflowDefinitionId`、`rowVersion`、必填 `reason`。
- `GET /api/release/workflow-bindings/{sceneCode}/history?projectId=...`：返回该项目场景的绑定变更记录。

### 提交状态流

```text
提交版本申请
  -> 后端判定 REGULAR / URGENT / EMERGENCY 与 ADDITIONAL
  -> 转换为五类 scene_code
  -> 查询 tenant + project + scene 绑定
  -> 校验绑定存在且流程为 PUBLISHED
  -> 创建审批轮次并按 definition_id 启动当前发布版本
  -> 固化实际 definition_id + version_no + instance_id
```

工作流完成后继续使用既有 `business_type = release_application` 生命周期事件回调，不增加前端回调或人工同步。

## 错误、降级与恢复

- 场景未配置：返回“当前项目尚未配置【场景名称】审批流程”，不写业务状态。
- 绑定流程已取消发布或归档：返回“当前审批流程已失效，请联系配置管理员重新绑定”。
- 候选流程加载失败：配置页保留当前绑定摘要并提供局部重试，不清空表单。
- 行版本冲突：拒绝覆盖，提示刷新后重试。
- 归档仍被引用流程：拒绝归档并返回有限数量的项目和场景引用摘要。
- 删除存在历史版本或实例的流程：返回不可删除原因，建议归档。
- 绑定保存失败：事务回滚，主记录和历史记录不得部分成功。

## 安全、性能、兼容性与运维

- 新增权限建议为 `release:workflow-config:view` 与 `release:workflow-config:update`；超级管理员迁移时自动授予。
- 候选流程接口仅返回必要字段，不返回完整流程 JSON。
- 绑定查询使用唯一索引；引用查询使用 `tenant_id + workflow_definition_id` 索引；历史按绑定和时间索引。
- 现有版本申请数据和流程实例无需迁移；现有硬编码流程编码不再用于新提交解析。
- 上线后未配置绑定的项目按显式未配置处理，不静默回退到固定编码，避免误走流程。
- 日志记录绑定解析失败、流程失效和归档引用冲突，不记录流程图或敏感审批内容。

## 验证策略

- 数据库迁移：表、唯一键、索引、权限和重复执行安全性。
- 后端单元测试：五种场景映射、部分配置、失效流程、跨项目/租户隔离、乐观锁和审计。
- 提交流程测试：新绑定生效、改绑只影响新申请、旧申请固定原版本、失败无部分数据。
- 工作流生命周期测试：纯草稿删除、曾发布草稿禁止删除、存在实例禁止删除、绑定引用阻止归档、改绑后可归档。
- 前端构建与交互：项目切换、五个场景状态、候选下拉、解除绑定、原因必填、历史查看和错误重试。
- 浏览器端到端：创建并发布测试流程、完成场景绑定、提交申请、在业务详情审批并验证申请状态回写。

## 假设、未知项与决策记录

- 假设：当前项目 Mock 提供稳定项目标识，后续项目管理接入继续使用该标识。
- 假设：流程定义 ID 在租户内稳定，发布新版本不更换定义 ID。
- 未知项：无阻塞未知项。
- 决策 D1：审批流程配置位于配置管理模块，不放入流程定义页面。
- 决策 D2：绑定按项目独立维护。
- 决策 D3：固定展示五个场景并允许部分配置，提交命中未配置场景时阻断。
- 决策 D4：绑定变更只影响后续新提交申请。
- 决策 D5：仅纯草稿可删除，活跃业务绑定阻止流程归档。

## 风险与回退原则

- 项目 Mock 标识变化可能导致绑定不可见：固定 Mock 标识并在真实项目接入时提供一次映射迁移。
- 配置与提交并发可能启动旧绑定：提交事务读取当时已提交的绑定并固化结果，改绑只对后续事务生效。
- 流程取消发布造成业务中断：配置页突出失效状态，提交前校验并记录告警。
- 跨模块引用形成直接表耦合：通过只读引用接口连接配置管理与工作流生命周期服务。
- 回退应用版本时保留新增绑定和历史表，不执行破坏性数据库回滚；旧版本不会读取新表。
