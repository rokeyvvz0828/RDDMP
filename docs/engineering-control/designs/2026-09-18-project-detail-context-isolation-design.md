# 项目详情上下文隔离修复设计

## 状态

- 修订：1
- 状态：已确认，待实施计划复核
- 用户确认：进入或编辑项目详情不切换顶部项目；后续菜单仍使用顶部项目选择器已选项目。

## 目标与范围

修复顶部全局项目与项目详情路由目标不一致时，项目详情编辑被拒绝的问题。`/projects/:projectId` 中的项目 ID 是该详情页面所有项目资源请求的唯一上下文来源。

范围包含项目基础信息、设置、计划、风险、成员、组织、角色、阶段、公告、投产日历、附件分类与文件操作。不改变路由、请求体、数据模型、数据库、成员授权、审计或乐观锁。

## 方案比较

1. **选用：项目 API 客户端显式传入路由项目上下文。** 每个 `/api/project/{projectId}` 请求都调用已有 `withProjectContext(projectId)`。影响限于项目详情接口，和后端路径校验契约完全一致。
2. 放宽后端路径和请求上下文一致性校验。拒绝：会削弱跨项目请求的防护，且不能保证权限按目标项目加载。
3. 在通用 HTTP 拦截器从 URL 推断项目 ID。拒绝：属于全局公共能力变更，影响所有调用方，也会隐藏非项目页面的上下文错误。

## 交互与状态

- 通过顶部选择器切换项目时，既有确认与刷新行为不变。
- 用户从工作台打开项目详情时，不调用 `projectContext.select`；顶部选择器保持原值。
- 详情内的读取、保存、删除、上传和下载请求显式携带详情项目 ID。全局选择器即使指向另一项目，也不会改变这些请求。
- 后端继续要求 `X-Project-Id` 等于 URL 中的项目 ID，并继续根据该 ID 计算权限。因此缺失、伪造或不匹配的上下文仍被拒绝。

## 实现边界

- 修改 `web/src/api/project.ts` 和 `web/src/api/attachments.ts`，复用 `withProjectContext`。
- `ProjectView.vue` 不修改全局选择器；仅继续将路由项目 ID 传给 API 客户端。
- 不修改 `http.ts`、项目上下文 Store、后端安全过滤器或业务服务。

## 验证与回退

- 静态检查全部项目详情 API 是否显式绑定 `withProjectContext(id)`。
- 在顶部选择器指向项目 A、详情路由打开项目 B 时，验证基础信息保存、计划维护和附件操作；确认顶部选择器仍为 A。
- 执行前端生产构建和差异检查。
- 回退仅撤销两个前端 API 客户端的上下文配置及对应任务文档；后端安全边界、数据和全局选择器状态不受影响。
