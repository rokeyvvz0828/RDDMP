# 需求管理平台方案（重构版）

> 依据 2026-08-16 会议纪要及补充说明重新设计，替代原 REQ-20260814-018 方案（旧实现已删除）。
> 本文为设计草案，待评审确认后形成正式 `requirement.md` 与 `codex-task-scope.yaml`。

## 1. 背景与目标

原需求管理实现按「需求台账 → 功能差异清单 → 系统清单 → 版本变更 → 测试覆盖」设计，与业务实际用法有偏差。本次按会议结论重构：

需求管理平台由三大功能模块组成：

1. **新建项目（0~1 项目）**：以《附件1：需求分析差异清单》为核心，各项目组针对自身系统做差异分析，支持在线填写与上传解析，差异走评审审批流，全部评审完成后形成基线。
2. **存量项目（常态化需求管理）**：以《蒙商常态化需求管理表-需求管理基线-业务组填写》sheet 为核心，按阶段（需求提出、需求对接、工作量评估、立项、软需、投产）管理，支持在线提交与上传解析，每个阶段有状态。
3. **配置管理**：本期不做，仅预留扩展位。

贯穿性要求：**每一条数据都必须有改动记录**（谁改的、什么时间改的、改了什么），列表行内提供「修改记录」入口，点击弹出小窗口展示历史记录。

### 已确认决策（2026-08-16）

1. 差异评审**单条提交**，审批人**按角色路由**（评审角色由流程配置，不指定具体人）。
2. 存量项目**不走审批流**，阶段推进采用状态确认。
3. 开发状态/测试状态**先做成差异上的状态字段**，本期不打通研发/测试模块。
4. 基线后**不做变更流程**，已评审/已基线差异锁定，如需修改另立需求。

## 2. 总体设计

### 2.1 模块划分

本期实现为单一业务模块 `business/requirement`（Maven artifact `ccb-requirement`，包名 `com.ccb.requirement`），内部按两个业务域组织，共用一套公共支撑：

| 域 | 说明 | 页面入口 |
| --- | --- | --- |
| 新建项目（new-project） | 项目主数据 + 需求差异清单 + 评审审批 + 基线 | `/requirements/new-project` |
| 存量项目（legacy） | 常态化需求基线 + 阶段管理 | `/requirements/legacy` |
| 公共支撑 | 系统清单、统一改动记录、附件、基线版本 | 服务端共享 |

配置管理后续作为独立需求扩展（参数实例化、菜单/岗位/角色/权限实例化内容等），本期不建表、不留入口。

### 2.2 复用平台能力

- 审批流：复用平台 workflow（按流程编码启动实例、业务生命周期事件），不复制流程实现。
- 附件：复用平台 file-preview / ccb-attachment 能力，业务代码不暴露底层存储路径。
- 权限：复用平台组织、用户、角色、菜单、参数与 RBAC。
- 前端：复用 `web/src/components/ui` 与 `web/src/modules/delivery-showcase` 已验证的列表、表单、弹窗、审批、图表设计，按 `design-h5.md` 完成移动端适配。

### 2.3 数据 Owner 与迁移

- 表前缀 `req_`，全部含 `tenant_id`、软删除与审计字段。
- Flyway 迁移追加式新增（V35 起，旧 V36/V37 已删除），不修改历史脚本。
- 系统清单主数据（`req_system`）为两域共用，由模块内统一维护。

## 3. 模块一：新建项目（0~1 项目）

新建项目以「项目」为顶层容器，一个项目下有多个项目组、每个项目组负责一个或多个物理子系统，基于自己的系统做差异分析。

建议字段：项目编码、项目名称、项目类型（0~1 新建）、启动时间、状态、说明。

- 所属项目、所属系统（从需求编号解析或显式选择）
- 差异状态：`待评审` / `评审中` / `已评审` / `已退回`
- 评审信息：评审人、评审时间、审批实例 ID、评审意见
- 开发状态：`未开始` / `开发中` / `已完成` / `已上线`
- 测试状态：`未开始` / `测试中` / `已通过`
- 是否基线：所属基线版本

### 3.3 差异状态机与评审

```text
待评审 ──提交评审（发起审批流）──> 评审中
   ^                                |
   └────────审批退回───────────────┤
                                   v
                              已评审（锁定）
```

规则：

1. 差异录入后状态为「待评审」，项目组成员可修改、删除。
2. 提交评审为**单条提交**，走平台审批流（流程编码 `requirement.diff.review`），审批人**按角色路由**；评审中不可修改。
3. 审批通过 → 状态「已评审」，项目组成员不可再修改；审批退回 → 回到「待评审」并记录退回意见。
4. 同一项目下全部差异均为「已评审」时，可执行「形成基线」，生成基线版本快照并整体锁定。
5. 已评审/已基线差异锁定，本期不做变更流程，如需修改另立需求。

差异上的**开发状态**（未开始/开发中/已完成/已上线）与**测试状态**（未开始/测试中/已通过）本期作为状态字段随差异维护，不打通研发/测试模块。

### 3.4 录入方式

**在线填写**：页面表单逐条新增/编辑，枚举字段用选择器（受控组件），不自由输入。

**上传文件自动解析**：

- 提供《附件1》标准模板下载。
- 上传 Excel 后逐行解析校验：必填项、枚举值、需求编号格式、涉及系统存在性。
- 返回校验报告（总行数、成功行数、错误行数与错误原因），确认后事务化导入。
- 导入成功的数据状态为「待评审」，来源标记为 `IMPORT`。

### 3.5 权限

- 项目组成员：维护本项目差异（仅「待评审/已退回」状态），发起评审。
- 评审人：审批流节点配置的审批人，可评审。
- 管理员/统筹：项目管理、系统清单维护、形成基线。
- 服务端校验认证、RBAC、数据范围与实体授权；前端仅做体验层显隐。

### 3.6 改动记录

差异条目的每一次新增、编辑、提交评审、评审通过/退回、基线纳入均写入统一改动记录（见 6.1）。列表行操作「修改记录」弹窗展示：时间、操作人、操作类型、字段、旧值、新值。

## 4. 模块二：存量项目（常态化需求管理）

### 4.1 数据模型（对应《需求管理基线-业务组填写》sheet）

按表格的 8 个阶段列组设计字段：

**需求提出阶段**

业需文档名称、需求编号（来自蒙商维普系统）、需求名称、需求内容简述、需求提出部门、需求提出人及电话、蒙商 BA、蒙商架构、业务期望上线时间、外部监管单位、监管文件名称+文号、监管文件内容描述、监管要求上线时间、业需入手日、需求类型（监管/业务/技术）、监管分类（国家级/地方级/处罚整改）、业务组、分组、金科对接人及电话、是否需要金科架构决策、金科架构人员、是否纳入蒙商统一管理。

**需求对接阶段**

业需评审完成日。

**工作量评估阶段**

工作量评估完成日。

**立项阶段**

财务立项完成日（任务书）。

**软需阶段**

软需文档名称、主责事业群、主责物理子系统编号+名称、主责项目组联系人及电话、是否涉及金科引入组件协同、协同事业群、协同系统名称、软需提交日、软需评审完成日。

**投产阶段**

计划上线时间、实际上线时间、上线形式（常规版本/紧急版本）。

**需求状态及备注**

需求状态（需求分析/业需修订/业需评审通过/立项中/软需编制/软需评审通过/已投产/需求终止）、备注。

**需求变更信息**

是否涉及需求变更、需求变更信息（谁发起变更/变更内容/发起变更阶段）、变更评审结论（评审通过/评审不通过）、变更结论及状态（审核通过/评估工作量/蒙商立项完成）、需求变更备注、未立项已开发。

### 4.2 阶段与状态

- 每个需求一条记录，按阶段推进；阶段枚举：需求提出 → 需求对接 → 工作量评估 → 立项 → 软需 → 投产。
- **每个阶段有状态**：`未开始` / `进行中` / `已完成`（阶段关键字段填写完成且确认后置为已完成）。
- 阶段推进留痕：记录推进人、推进时间、前后阶段。
- 阶段完成校验：例如软需阶段完成需软需文档名称与软需评审完成日非空。
- 阶段状态变更同样写入统一改动记录。
- **阶段推进不走审批流**（已确认），采用状态确认方式。

### 4.3 录入方式

- 在线提交：表单维护需求全部阶段字段，支持草稿保存与提交。
- 上传解析：支持上传《需求管理基线-业务组填写》格式 Excel，逐行解析校验（必填、枚举、日期格式、需求编号唯一性），输出校验报告后确认导入。
- 主责/协同信息按表格字段保留（主责事业群、主责系统、协同事业群、协同系统名称）。

### 4.4 权限

- 业务组填写人：维护本业务组需求（按数据范围）。
- PMO/统筹：整体视图、阶段确认、状态调整。
- 管理员：系统清单与字典维护。

### 4.5 改动记录

同 3.6：需求各阶段字段的每次变更写入统一改动记录，「修改记录」弹窗查看。

## 6. 公共设计

### 6.1 统一改动记录（req_change_log）

```text
req_change_log
- id, tenant_id
- biz_type     业务类型: NEW_PROJECT_DIFF / LEGACY_REQUIREMENT / SYSTEM / BASELINE
- biz_id       业务主键
- field_name   字段名（英文名，前端映射中文）
- old_value    旧值
- new_value    新值
- change_type  操作类型: CREATE / UPDATE / SUBMIT_REVIEW / REVIEW_PASS / REVIEW_RETURN / BASELINE / STAGE_TRANSITION / IMPORT
- operator_id, operator_name
- source       来源: ONLINE / IMPORT
- created_at
```

- 新增/修改/状态流转等全部写操作在同一事务内写入改动记录，操作人取当前登录身份。
- 不记录敏感字段（密码、Token 等，业务侧无此类字段）。
- 列表行操作「修改记录」→ 弹窗展示该业务主键的历史记录（时间倒序、操作人、操作类型、字段、旧值、新值），支持按操作类型筛选。

### 6.2 审批流接入

- 新建项目差异评审通过平台 workflow 按流程编码启动：`requirement.diff.review`。
- 业务侧保存审批实例 ID、审批人、评审结论与时间；审批状态变化通过业务生命周期事件回写差异状态（幂等）。
- 评审期间差异锁定（服务端校验不可编辑/删除）。

### 6.3 系统清单主数据（req_system）

参考《参考资料-输出系统清单》：系统编号、英文简称、系统名称、事业群、状态、所属逻辑子系统编号/名称、归属业务组件/名称、业务领域、产品视图、投产点、系统介绍、灾备等级、类别、引入系统/保留系统。两个模块共用，供涉及系统/主责系统/协同系统选择与校验。

### 6.4 附件

- 差异清单 Excel、业需/软需文档等通过平台附件能力上传、预览、下载，业务代码不接触底层存储。
- 导入文件按模板类型记录导入批次（文件名、总行数、成功/失败数、错误明细）。

### 6.6 页面与交互

复用交付示范中心已验证的列表、检索、表单抽屉、状态标签、分步流程、弹窗与图表设计：

- 新建项目：项目列表 → 项目详情（差异清单、状态统计）→ 新增/导入差异 → 提交评审（审批进度）→ 形成基线 → 差异详情（开发/测试状态、修改记录弹窗）。

- 移动端按 `design-h5.md` 适配列表卡片、弹窗高度与操作层级。

## 9. 实施决策记录（2026-08-16 代码交付）

本文档随 REQ-20260816-001 代码交付同步更新，补充以下实施期决策（与需求评审口径一致）：
