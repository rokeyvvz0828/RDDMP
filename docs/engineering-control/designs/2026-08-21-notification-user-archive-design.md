# 通知用户级归档工程设计

## 文档状态
- 修订：1
- 状态：已确认
- 用户确认依据：用户于 2026-08-21 复核落盘设计并明确要求开始实施。

## 目标与成功信号
让用户能够收纳已经阅读和处理的通知，使默认通知列表保持可用，同时完整保留通知正文、接收关系和业务审计证据。

成功信号：
- 已读通知可被当前用户单条归档，并立即从“全部”列表消失。
- 当前用户可批量归档全部未归档的已读通知。
- “已归档”页签可查看归档通知并单条恢复。
- 归档不影响其他接收人，不删除共享通知记录，不改变业务事件或审计日志。
- 未读角标、业务板块计数和默认列表均只统计未归档通知。

## 使用者与场景
- 用户读完审批、配置管理或其他业务通知后，将其归档以清理默认列表。
- 用户误归档通知后，在“已归档”页签中找到并恢复。
- 用户积累大量已读通知后，一次归档全部已读通知。
- 运维和审计仍可通过持久化通知与用户接收关系追溯历史事件。

## 必须需求与验收条件

### R1 用户级归档
仅已读且未归档的通知允许被当前用户归档。归档只更新当前租户、当前用户的接收关系，不删除 `sys_notification`，也不影响同一通知的其他接收人。

验收条件：
- 归档后该通知从当前用户“全部”和“未读”列表消失。
- 另一接收人的通知状态不变。
- 对未读通知发起归档返回明确的业务冲突。
- 重复归档不产生错误或额外副作用。

### R2 已归档查看与恢复
通知中心增加“已归档”页签，展示当前用户的归档通知；恢复后通知重新进入“全部”列表并保持已读。

验收条件：
- 已归档列表支持现有分页和业务板块筛选。
- 恢复只作用于当前用户。
- 重复恢复保持幂等。
- 恢复不会重新增加未读角标。

### R3 批量归档已读
通知中心提供“归档全部已读”操作，二次确认后归档当前用户全部未归档的已读通知。

验收条件：
- 未读通知不受影响。
- 返回实际变更数量并刷新列表、业务板块和角标。
- 没有可归档通知时操作禁用或返回零变更，不报错。

### R4 计数一致性
未读角标、业务板块汇总、“全部”和“未读”列表只统计未归档通知；“已归档”页签统计归档通知。

验收条件：
- 单条归档、批量归档和恢复后，页签、板块数量和分页总数一致。
- 仅含归档通知的业务板块仍能在“已归档”页签中作为筛选项使用。
- 一秒未读轮询继续只请求轻量未读计数，不轮询完整归档列表。

### R5 权限与审计边界
所有归档接口从认证主体读取租户和用户，不接受客户端传入身份；通知发布契约和既有业务事件审计不改变。

验收条件：
- 用户不能归档或恢复其他租户、其他用户的通知。
- 归档不删除通知正文、发布审计或用户接收关系。
- 现有发布、已读和全部已读接口保持兼容。

## 不变量与约束
- `sys_notification` 继续作为共享、幂等的通知正文与事件记录，不进行物理删除。
- 归档状态属于 `sys_user_notification`，与接收人的已读状态处于同一用户边界。
- 归档通知必须已经是已读状态；恢复后仍是已读状态。
- 所有查询和更新必须包含认证租户与认证用户条件。
- 使用现有 Java 17、Spring Boot、MySQL 8.4、Vue 3、TypeScript 和 Element Plus 技术栈。
- 保持现有一秒前台未读轮询、失败退避和业务板块筛选行为。

## 非目标
- 不提供通知正文的物理删除。
- 不提供管理员删除用户通知或批量恢复。
- 不增加消息保留期限、自动归档策略或定时清理任务。
- 不改变通知发布者、工作流通知内容、站内路由或外部消息渠道。
- 不把“全部已读”改为自动归档。

## 方案比较与选择

选择“用户级软归档并支持恢复”。它把收纳状态放在用户接收关系上，既解决列表长期堆积，也保留审批和业务审计能力。

未选择：
- “仅在前端隐藏已读”：状态无法跨设备同步，用户不能可靠恢复，分页和计数仍不一致。
- “物理删除通知”：共享通知可能属于多个接收人，并承担业务追溯作用，删除会破坏审计完整性。

## 架构边界与组件职责
- Flyway 迁移：在 `sys_user_notification` 增加可空 `archived_at`，并补充用户、归档状态、时间顺序组合索引。
- `SystemNotificationService`：拥有活动/未读/已归档查询、单条归档、单条恢复、批量归档已读及租户用户隔离。
- `NotificationController`：暴露认证用户范围内的归档与恢复接口。
- 通知 DTO 和前端 API：传递归档时间、列表视图和变更数量。
- `UiNotificationCenter`：提供三页签、单条归档/恢复和批量归档交互，并保持现有轮询生命周期。

## 接口、数据和状态流

### 数据模型
`sys_user_notification.archived_at TIMESTAMP NULL`：
- `NULL`：活动通知，可进入“全部”或“未读”。
- 非空：已归档通知，只进入“已归档”。

不增加 `is_archived`，避免布尔值与归档时间出现双状态不一致。

### HTTP 接口
- `GET /api/notifications?view=ALL|UNREAD|ARCHIVED&moduleCode=...`：新增 `view`，默认 `ALL`。为兼容旧客户端，保留 `unreadOnly`，未显式传 `view` 时继续生效。
- `PATCH /api/notifications/{id}/archive`：仅归档当前用户已读通知。
- `PATCH /api/notifications/{id}/restore`：恢复当前用户归档通知。
- `PATCH /api/notifications/archive-read`：归档当前用户全部未归档已读通知，返回实际变更数量。
- `GET /api/notifications/modules?view=ALL|UNREAD|ARCHIVED`：按当前视图返回可筛选业务板块及一致计数。

### 状态流
`UNREAD_ACTIVE -> READ_ACTIVE -> ARCHIVED_READ -> READ_ACTIVE`

- 打开通知继续执行现有“标记已读并跳转”行为。
- 单条归档只允许 `READ_ACTIVE -> ARCHIVED_READ`。
- 批量归档只更新 `READ_ACTIVE`。
- 恢复只执行 `ARCHIVED_READ -> READ_ACTIVE`。

## 错误、降级与恢复
- 未读通知归档：返回 409，并提示“请先阅读消息后再归档”。
- 通知不存在或不属于当前用户：保持幂等且不泄露记录存在性；更新零行后返回成功或统一不可见结果。
- 列表、归档或恢复失败：保留当前界面状态，显示一次明确错误，可重试。
- 批量归档前弹出确认；失败时不提前清空前端列表。
- 路由跳转失败仍按现有方式提示，不回滚已读或归档状态。

## 安全、性能、兼容性与运维
- 安全：所有 SQL 以 `tenant_id`、`user_id` 为边界；客户端不能指定目标用户。
- 性能：活动未读查询继续命中用户状态索引；已归档分页按归档状态和通知时间排序，不增加一秒轮询负载。
- 兼容性：现有 `unreadOnly` 参数、发布接口、已读接口和通知 DTO 字段继续有效；新增字段对旧客户端可忽略。
- 运维：迁移只新增可空列和索引，历史数据默认未归档，不需回填；回退产品代码后该列可保留且无行为影响。

## 验证策略
- 服务单元测试：租户/用户隔离、未读禁止归档、归档与恢复幂等、批量仅处理已读、查询过滤及计数一致性。
- 控制器/API 测试：参数兼容、状态码、返回变更数量和认证主体绑定。
- Flyway 与完整后端测试：迁移成功，现有通知和工作流集成无回归。
- 前端构建与组件交互验证：三页签、按钮可见性、事件冒泡、批量确认、错误状态、桌面与移动布局。
- 浏览器真实数据验证：创建通知、阅读、归档、筛选、恢复，并验证角标与各计数同步。

## 假设、未知项与决策记录
- 假设：当前通知保留策略要求审计记录长期存在。依据是现有持久化发布日志和审批通知用途；若后续引入法定保留期限，应作为独立需求处理。
- 未知项：暂无阻塞未知项。
- D1：采用用户级软归档，不进行物理删除。
- D2：提供“已归档”页签和单条恢复。
- D3：仅已读消息可归档，并提供批量归档全部已读。
- D4：恢复后保持已读，避免重新触发未读角标。

## 风险与回退原则
- 风险：活动和归档视图的业务板块汇总若共用旧查询，可能出现筛选项与列表不一致。通过显式视图参数和服务测试约束。
- 风险：通知项整体可点击，新增图标按钮可能触发跳转。前端必须停止事件冒泡并设置可访问名称。
- 风险：历史数据量较大时新增索引耗时。实施前检查本地/目标环境表规模，并使用兼容 MySQL 8.4 的迁移语法。
- 回退：产品代码可回退到归档前行为；新增可空列和索引保留，不做破坏性逆向迁移。
