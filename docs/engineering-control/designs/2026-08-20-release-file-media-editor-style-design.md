# 文件介质编辑区样式整理工程设计

## 文档状态

- 修订：1
- 状态：已确认
- 用户确认依据：用户查看当前页面截图后选择方案 1，并在落盘设计后明确回复“确认”。

## 目标与成功信号

统一版本申请中“文件介质”区域的视觉层级，使其与物理子系统、交付内容和交付单元字段保持一致。桌面和移动端均应清楚表达字段标题、添加操作、路径输入和删除操作，不再出现标题过大、按钮悬空、行号与控件尺寸失衡的问题。

## 使用者与场景

版本申请人在“制品登记”步骤选择文件介质后，填写一条或多条文件路径，并按需添加或删除路径。

## 必须需求与验收条件

- R1：文件介质标题使用标准表单字段层级，不再表现为独立章节标题；“添加路径”与标题位于同一操作行，并使用紧凑的图标文字按钮。
- R2：每条路径使用稳定的“序号、输入框、删除按钮”三列布局；输入框和操作按钮垂直居中，序号不抢占视觉焦点。
- R3：多条路径保持一致间距；长路径不撑破抽屉；`375x812`、`390x844`、`430x932` 及桌面视口无页面级横向溢出。
- R4：保留现有文件介质启用、默认新增首行、添加、删除、路径长度和提交校验逻辑，不改变请求数据结构或后端行为。

## 不变量与约束

- 仅修改 `ReleaseApplicationDrawer.vue` 中的文件介质局部结构和 `release-prototype.css` 对应样式。
- 沿用 Vue 3、Element Plus、现有设计变量和 `Plus`、`Delete` 图标。
- 不覆盖 `rokey` 工作区内其他需求的未提交改动。
- 控件尺寸稳定，不随内容、悬停或视口变化引起布局跳动。

## 非目标

- 不调整制品登记的字段顺序和业务文案。
- 不修改交付单元、附件、审批或后端逻辑。
- 不重构整个申请抽屉或全局 Element Plus 主题。
- 不新增卡片、帮助文案或路径浏览功能。

## 方案比较与选择

选择方案 1“标准表单行”：保留轻量无外框列表，将“文件介质”和“添加路径”收敛到同一字段标题行，路径明细按三列紧凑排列。它与当前表单最一致，修改范围最小，也不会再引入一层面板。

- 方案 2“分组面板”能增强边界，但会使制品登记区域偏重，并形成不必要的嵌套容器。
- 方案 3“逐条表单项”校验表达直接，但占用纵向空间过多，多路径场景效率较低。

## 架构边界与组件职责

- `ReleaseApplicationDrawer.vue`：提供语义清晰的标题操作行和路径列表结构，保留所有事件与状态绑定。
- `release-prototype.css`：统一标题字号、按钮形态、行间距、三列尺寸和移动端约束。
- 其他页面、API、状态模型和服务端均在边界外。

## 接口、数据和状态流

用户勾选文件介质后，现有 `toggleContentTypes` 继续创建首条空路径；标题行的添加按钮调用现有 `addFileMedia`；每行删除按钮调用现有 `removeFileMedia`；输入仍双向绑定 `file.filePath`。本次不增加状态、不改变 payload。

## 错误、降级与恢复

- 空路径、重复路径和非法字符继续由现有前端及后端校验处理。
- 小屏空间不足时三列缩窄，但删除按钮保持可点击，输入框可收缩，页面不横向滚动。
- 若局部样式产生回归，可仅恢复两个限定文件中的本次修改。

## 安全、性能、兼容性与运维

无数据、安全、接口、数据库或运行配置变化。新增样式为静态局部规则，不产生可感知性能开销。现有草稿和已保存申请保持兼容。

## 验证策略

- 运行 `npm --prefix web run build` 和 `git diff --check`。
- 在桌面视口检查标题、添加按钮、单条和多条路径的对齐及间距。
- 在 `375x812`、`390x844`、`430x932` 检查无横向溢出、输入框和删除按钮可达。
- 实际点击添加和删除，确认行数与数据绑定仍正确；检查浏览器控制台无错误。

## 假设、未知项与决策记录

- 假设：截图中的主要问题是局部视觉层级与间距不一致，而不是要求改变业务交互。
- 未知项：无阻塞未知项。
- D1：采用方案 1，不增加外框面板。
- D2：添加入口保留图标和文字，但降为紧凑操作，不使用当前的大型朴素按钮。
- D3：删除继续使用圆形危险图标按钮，尺寸与路径行统一。

## 风险与回退原则

主要风险是 Element Plus 顶部标签样式与自定义操作行互相影响，以及移动端三列空间不足。通过局部类名、稳定列宽和指定视口浏览器测量控制。回退仅涉及文件介质局部模板和 CSS，不触碰业务数据。
