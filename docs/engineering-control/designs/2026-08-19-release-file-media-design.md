# 版本申请文件介质工程设计

## 文档状态

- 修订：1
- 状态：已确认
- 需求：REQ-20260819-039
- 用户确认依据：用户选择同一申请可同时包含交付单元和文件介质，确认文件介质可添加多条且每条只填写一个路径，逐段确认页面、数据、业务规则、兼容与验证设计，并在落盘后明确要求开始实施。

## 目标与成功信号

在现有版本申请、审批、冲突确认、投产基线和生产版本链路中增加文件介质交付内容。文件介质归属申请所选物理子系统，使用固定交付单元 `FILE`，以文件路径作为业务身份，不要求制品类型选择和版本号。

成功信号：

1. 一张申请可只含普通交付单元、只含文件介质或同时包含两者。
2. 文件介质可添加多条，每条只填写一个路径；后端持久化真实路径并生成稳定项键。
3. 相同窗口、相同路径触发现有重复申请确认流程，不同路径互不冲突。
4. 每条路径可独立进入投产基线、维护投产结果，并在投产成功后进入生产版本。
5. 存量申请和普通交付单元行为、权限、审批状态及投产数据不发生语义变化。

## 使用者与场景

- 版本申请人：在同一张申请中登记镜像/二进制交付单元和一个或多个文件路径。
- 审批人：在完整申请详情中查看普通交付单元和文件介质后执行审批。
- 投产管理人员：按窗口逐条维护普通制品和文件路径的投产结果。
- 查询人员：在生产版本和统计分析中识别当前成功投产的文件介质及其来源申请。

## 必须需求与验收条件

### R1 交付内容类型

版本申请必须提供“交付单元”和“文件介质”两个可同时选择的交付内容类型，至少选择一种。新建申请默认选择“交付单元”；编辑申请根据持久化数据恢复选中状态。

验收：分别创建仅交付单元、仅文件介质和混合申请，保存与重新打开后内容类型及数据一致。

### R2 多文件路径

选择文件介质后必须支持添加和删除多条文件路径。每条记录只包含一个路径，不展示或提交版本号和制品类型选择。

验收：同一申请可保存两条不同路径；空路径、超长路径、控制字符和同申请重复路径被前后端拒绝。

### R3 固定交付单元

文件介质由后端固定映射为交付单元 ID/编码 `FILE`、名称“文件介质”和制品类型 `FILE`，版本号为空。客户端不得通过伪造固定字段改变该映射。

验收：请求只提交路径，响应和数据库记录包含服务端生成的固定字段；传入伪造字段不影响持久化事实。

### R4 物理子系统归属

一张申请继续只选择一个物理子系统，申请中的普通交付单元和文件介质全部归属该物理子系统。

验收：文件介质详情、投产基线和生产版本均展示申请的物理子系统快照。

### R5 路径业务身份

文件路径去除首尾空格后作为业务身份，正文、大小写和斜杠保持不变。后端基于规范化路径生成稳定 `item_key`，不得把路径写入版本号或拼接进交付单元编码。

验收：首尾空格不产生两个身份；大小写或正文不同的路径保持独立；长路径不参与数据库长索引。

### R6 冲突与追加

非应急申请按“同一投产窗口 + 相同规范化文件路径”检索历史申请。冲突提示沿用现有三种处理动作并展示原申请业务信息及文件路径，附件除外。相同路径已有制品准出记录后再次申请时识别为追加申请。

验收：同窗口相同路径触发冲突，不同路径不触发；用户确认继续创建后可再次提交；历史准出路径使新申请具备追加特征。

### R7 投产基线

审批准出的每条文件路径必须作为独立投产项进入承接窗口基线，可分别维护投产成功、投产失败或未投产，并保留现有变更原因、操作人和时间审计。

验收：一张申请的两条路径在基线中显示为两行，修改其中一条不影响另一条。

### R8 生产版本

文件介质投产成功后，生产版本按“物理子系统 + 规范化文件路径”展示最近一次成功记录、路径、投产时间和来源申请；版本号位置显示“无版本号”。结果回改后沿用现有历史成功记录回算。

验收：同一路径多次成功投产仅展示最近记录；最近记录改为非成功后回算上一条成功记录。

### R9 详情与统计

申请详情、冲突弹窗、投产基线、生产版本和统计分析必须区分 `DELIVERY_UNIT` 与 `FILE_MEDIA`。文件介质不参与普通交付单元的最新版本查询，统计制品类型增加 `FILE`。

验收：所有关联页面使用路径表达文件介质，不出现空版本代码、伪造版本号或错误的普通交付单元生产版本提示。

### R10 兼容、权限与响应式

沿用现有版本申请和投产管理权限，不新增菜单或动作权限。存量普通交付单元回填后行为不变。版本申请抽屉在桌面和规定手机视口内无页面级横向溢出，新增、删除和提交操作可达。

验收：存量申请可查询和编辑；无权限用户仍被后端拒绝；`375x812`、`390x844`、`430x932` 和桌面视口通过浏览器检查。

## 不变量与约束

- 一张申请仍只属于一个项目和一个物理子系统。
- 审批继续整单处理，不支持按文件路径部分审批。
- 文件介质没有版本号，任何界面和接口不得要求或派生文件版本。
- 文件介质固定交付单元为 `FILE`，但冲突、唯一性和投产身份必须按路径区分。
- 应急申请沿用现有无窗口提交和准出后归入承接窗口规则。
- 项目、物理子系统和普通交付单元选择源继续使用当前前端 Mock，本需求不建设主数据服务。
- Flyway 只追加新迁移，不修改 V38、V39 或其他已执行迁移。
- 后端权限、数据范围、乐观锁、修订历史、状态事件和投产审计继续作为事实源。

## 非目标

- 不上传、复制、校验或预览文件路径指向的实际文件。
- 不校验路径在操作系统、共享存储或目标服务器上真实存在。
- 不为文件介质增加版本号、校验和、文件大小、主机、环境或目录浏览能力。
- 不改变审批流程配置、版本类型判定、窗口规则或菜单权限。
- 不重构整个交付明细、投产基线或统计模块。

## 方案比较与选择

### 方案 1：扩展现有交付明细模型，已选择

申请交付明细和投产明细增加项类型、文件路径和稳定项键。普通交付单元和文件介质共享审批、冲突、基线、投产结果和统计链路，文件项用路径区分。

选择原因：文件介质仍是一次投产申请中的交付内容，共享同一业务状态机。该方案改动集中，能够复用现有事务、权限和审计，同时避免维护两套投产事实。

### 方案 2：文件介质申请与投产完全分表

数据库语义独立，但申请详情、冲突、基线、生产版本和统计都需要双表聚合和两套状态操作，增加一致性风险，未选择。

### 方案 3：文件介质分表并统一投影

写模型边界清晰，但需要额外投影层和更多跨表事务、回算及集成测试，当前范围收益不足，未选择。

## 接口、数据和状态流

### 写入接口

现有版本申请创建和更新请求保留：

```json
{
  "deliveries": [
    {
      "deliveryUnitId": "UNIT-1",
      "deliveryUnitCode": "PAYMENT-API",
      "deliveryUnitName": "支付接口",
      "artifactType": "IMAGE",
      "artifactVersion": "v1.2.0"
    }
  ],
  "fileMedia": [
    { "filePath": "/opt/app/config/application.yml" }
  ]
}
```

服务端将两组输入转换为统一内部交付项。文件介质固定字段由服务端生成，版本号为 `null`。

### 读取接口

- 申请响应保留普通 `deliveries`，新增 `fileMedia`。
- 冲突响应的历史申请同时返回普通交付单元和文件介质。
- 投产基线和生产版本行增加 `itemType`、`filePath`；普通项的 `filePath` 为空。
- 统计聚合的 `artifactType` 增加 `FILE`，下钻行可识别项类型。

### 数据模型

申请交付明细新增：

- `item_type VARCHAR(24) NOT NULL`
- `file_path VARCHAR(1024) NULL`
- `item_key VARCHAR(128) NOT NULL`
- `artifact_version` 调整为可空，仅允许文件项为空

普通项键为 `UNIT:<delivery_unit_code>`。文件项键为 `FILE:<SHA-256(normalized_path)>`。存量记录回填为 `DELIVERY_UNIT` 和普通项键。唯一约束调整为 `tenant_id + application_id + item_key + application_revision`，冲突索引使用 `tenant_id + item_key + active + application_id`。

投产明细同步保存 `item_type`、`file_path`、`item_key`，来源唯一约束和当前生产查询使用项键，避免多个文件路径因固定 `FILE` 编码互相覆盖。

### 状态流

1. 用户选择交付内容类型并填写普通交付单元和/或文件路径。
2. 前端提交普通 `deliveries` 与 `fileMedia`。
3. 后端重新校验、规范化路径、生成固定字段和项键，保存申请修订。
4. 非应急提交按窗口和项键查询冲突；相同文件路径已有准出记录时形成追加特征。
5. 审批整单准出后，生产服务按每个统一交付项创建或刷新窗口基线候选。
6. 投产管理人员逐项维护结果；文件项成功后进入生产版本查询。

## 错误、降级与恢复

| 条件 | 外部行为 | 恢复方式 |
| --- | --- | --- |
| 两种交付内容均为空 | 返回业务校验错误，不保存或提交 | 补充交付单元或文件路径 |
| 路径为空、超长或含控制字符 | 字段附近提示并由后端返回明确错误 | 修改路径后重试 |
| 同申请路径重复 | 指出重复路径，不生成重复项 | 删除或修正重复行 |
| 同窗口路径存在历史申请 | 返回完整冲突报告，不启动新审批 | 选择取消旧申请、修改旧申请或继续创建 |
| 冲突确认后事实变化 | 冲突令牌失效，阻止提交 | 刷新最新冲突信息后重新决定 |
| 数据迁移失败 | 后端停止启动，不跳过 Flyway | 修复迁移并从备份恢复本地数据后重试 |
| 关联页面无法识别项类型 | 显示明确加载错误，不伪造版本号 | 修复契约后重新加载 |

## 安全、性能、兼容性与运维

### 安全

- 文件路径按内部业务数据处理，不作为服务器文件访问参数执行。
- 后端不读取路径、不探测文件系统、不调用外部存储。
- 所有创建、编辑、提交和投产维护继续执行既有 RBAC、实体授权和审计。
- 路径输出由 Vue 默认转义，禁止使用为路径渲染的原始 HTML。

### 性能

- 使用固定长度路径摘要作为 `item_key`，避免对 `VARCHAR(1024)` 建长索引。
- 冲突和生产版本查询继续走窗口、租户、项键和状态索引。
- 路径摘要在服务端单次计算，不引入外部调用。

### 兼容性

- `deliveries` 请求与响应保持现有语义，旧客户端可继续只提交普通交付单元。
- 存量明细通过迁移回填，普通交付单元唯一性和查询结果保持不变。
- `artifactVersion` 仅对文件项允许为空，普通项继续强制非空且不含空格。

### 运维

- 应用启动时 Flyway 执行 V46 并校验回填数量和唯一约束。
- 启动后保持 Mock 数据同步关闭，避免当前人工测试数据被覆盖。
- 发布前备份数据库；Flyway 不降版本，结构问题使用后续补偿迁移处理。

## 验证策略

1. 迁移契约测试：字段、回填值、唯一约束和索引符合设计。
2. 应用服务测试：仅普通、仅文件、混合、空内容、多路径、重复路径、非法路径和存量兼容。
3. 冲突测试：同窗口同路径、不同路径、历史准出追加、冲突令牌失效及应急申请。
4. 投产测试：多路径独立基线、批量维护兼容、成功/失败/未投产、结果回改和生产版本回算。
5. 权限测试：只读、创建、编辑、提交、基线维护和无权限访问。
6. 前端构建与组件行为：动态行、类型清空确认、错误状态、提交中和长路径。
7. 真实接口流程：创建混合申请、提交、审批、进入基线、维护成功、查询生产版本。
8. 浏览器验收：桌面、`375x812`、`390x844`、`430x932`，检查抽屉操作可达、文字换行和页面级溢出。
9. 回归：发布模块测试、全量 Maven 测试、前端生产构建、治理和任务范围检查。

## 假设、未知项与决策记录

### 假设

- 路径是用户维护的业务标识，不需要在当前平台解析为真实操作系统路径。
- 路径大小写和斜杠差异可能代表不同目标，因此仅去除首尾空格。
- 固定交付单元 `FILE` 是业务映射，不依赖当前前端 Mock 主数据中存在同名选项。

### 未知项

无阻塞未知项。未来若需要主机、环境、校验和或实际文件访问，应建立独立需求，不扩展本次路径字段语义。

### 决策记录

- D1：同一申请允许同时选择交付单元和文件介质。
- D2：文件介质允许多条，每条只填写一个路径，没有版本号。
- D3：文件介质归属申请所选物理子系统，固定交付单元为 `FILE`。
- D4：冲突和基线按路径独立处理，投产成功后进入生产版本。
- D5：采用扩展现有交付明细模型的方案，不建立第二套投产状态机。

## 风险与回退原则

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 多条 `FILE` 破坏按交付单元编码唯一的旧假设 | 保存冲突、基线覆盖或生产版本串行 | 引入稳定项键并回归所有编码比较位置 |
| 空版本号被旧页面或查询当作异常 | 页面显示空白、排序或统计错误 | 所有关联 DTO 返回项类型，文件项显式显示“无版本号” |
| 路径规范化与用户预期不一致 | 重复判断错误 | 仅去首尾空格，保留正文、大小写和斜杠，并为边界写测试 |
| 迁移调整唯一键失败 | 应用无法启动 | 上线前备份、隔离库重复启动验证、失败即停止，不手工跳迁移 |
| 混合申请详情信息密度增加 | 手机端操作遮挡或横向溢出 | 动态区块纵向重排、长路径换行和规定视口浏览器验收 |

代码可按本需求文件范围回退。数据库迁移不得编辑或降版本；已执行 V46 的环境需要通过后续补偿迁移恢复约束。回退前必须确认没有已保存的文件介质记录，存在记录时不得回退到无法读取该数据的应用版本。
