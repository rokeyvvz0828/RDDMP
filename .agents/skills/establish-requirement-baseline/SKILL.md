# 建立需求基准

把自然语言意图定标为后续阶段不能擅自移动的设定值。目标不是扩写需求，而是减少误解自由度。

## 进入条件

- 已获得用户原始请求和可用上下文。
- 当前阶段为 `baseline`，或后续阶段因真实冲突回退到本阶段。
- 主 Agent 明确哪些陈述来自用户，哪些来自现有工程事实。

若请求只是局部、无歧义的 Light 修改，可建立精简基准，但仍需至少一个验收条件。

## 输入契约

收集以下输入；缺失项标记为未知，不得补成事实：

- 用户原话、后续修正和优先级；
- 已导入账本中的 `predevelopment.handoff.design`、设计修订与审批证据（如有）；
- 仓库级指令、技术限制、交付形式和时间边界；
- 已知现状及用户明确要求保留的行为；
- 术语定义、示例、反例和禁止范围；
- 需要用户授权的不可逆或高影响决策。

## 执行步骤

### 0. 复核开发前交接（如有）

若账本由 `import-handoff` 创建，逐项核对设计主题、修订、用户确认、必须需求、验收、反例和阻塞未知项。已确认且无冲突的内容不重复询问用户；发现当前请求与设计不一致时，停止并回到 `$brainstorming` 产生新修订。不得在基线阶段自行改写交接中的产品决策。

### 1. 提炼单一目标

用一句话描述要改变的外部可见结果，包含对象、变化和价值。若一句话中存在互相独立的多个结果，分成多个需求，不把它们塞进模糊目标。

### 2. 建立需求条目

为每个必须结果分配稳定 ID：`R1`、`R2`。每项必须包含：

- `statement`：系统必须做什么，不写实现方案；
- `acceptance`：什么观察能区分满足与不满足；
- `priority`：默认 `must`，可选需求不能冒充必须需求；
- `source`：用户陈述、工程约束或已批准决策；
- `counterexample`：至少一个明确失败例，适用时记录。

避免“优化、完善、支持、智能、尽量”等不可判别措辞。必须把它们转换为输入、输出、状态、边界或阈值。

### 3. 分离边界信息

- 不变量：修改期间必须始终成立的行为或数据性质；
- 约束：技术、权限、兼容、性能、时间和工具限制；
- 非目标：本轮明确不做的结果；
- 假设：暂时采用但可被事实推翻的判断；
- 未知项：尚无事实或授权支持的问题；
- 决策点：不同答案会实质改变实现或验收的用户选择。

假设不能悄悄变成需求，非目标不能被任务 Agent 顺手实现。

### 4. 建立需求到测量的意图

为每个 `must` 需求定义至少一种候选测量：测试、编译、日志、运行探针、截图、数据校验、性能测量或人工检查。此处只定义“需要观察什么”；传感器是否真实可用由建模阶段验证。

### 5. 消解冲突

按以下顺序处理冲突：用户最新明确指令 > 用户已批准基准 > 仓库指令 > 推断。若两个高优先级陈述无法同时成立，停止大范围实现并请求决策，不自行选择更方便的解释。

## 输出契约

生成结构化 JSON 前，完整读取 [references/requirement-baseline-contract.md](references/requirement-baseline-contract.md)；下列字段列表只是概要。

向主 Agent 返回一个 `RequirementBaseline`：

```text
objective: 单一控制目标
requirements: [{id, statement, acceptance[], priority, source, counterexample[]}]
invariants: []
constraints: []
non_goals: []
assumptions: [{text, falsifier}]
unknowns: [{question, impact, owner}]
decisions: [{question, options, blocking}]
measurement_intents: [{requirement_id, observable, candidate_sensor}]
baseline_status: ready | blocked
```

只返回基准和阻塞项，不给出架构、文件清单或实现任务。

## 退出门禁

进入 `modeling` 前必须同时满足：

- 目标唯一且没有隐含解决方案；
- 每个 `must` 需求具有稳定 ID 和可判别验收条件；
- 不变量、约束和非目标已分开记录；
- 所有会改变实现方向的冲突已解决或显式阻塞；
- 每个 `must` 需求至少有一个测量意图；
- 假设带有可证伪条件，未知项没有伪装成事实。

门禁失败时保留在 `baseline`。门禁通过后，将完整 `RequirementBaseline` 保存为 JSON，并执行 `record-artifact --phase baseline --input <json>` 写入共享账本；命令成功后才能请求主 Agent 转移到 `modeling`。

## 升级与回退

- 用户新增、删除或改变必须需求：创建新的基准修订，不覆盖历史。
- 只是发现新的代码事实：交给建模阶段更新模型，不重写需求。
- 需求在当前权限或现实约束下不可实现：向用户给出证据和最小决策，不擅自降级需求。
- 后续实现偏离基准：交给观测和纠偏阶段，不以“重新理解需求”掩盖偏差。
