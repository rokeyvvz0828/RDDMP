# 纠正工程偏差

先裁决反馈，再施加控制动作。纠正目标是降低有证据误差并保持稳定，而不是让局部测试暂时变绿。

## 进入条件

- 当前阶段为 `correcting`。
- 存在 `ObservationReport` 和未裁决反馈。
- 每个反馈有预期、观察、证据、严重度、置信度和传感器限制。
- 主 Agent 持有需求基准、系统模型、任务边界和裁决权。

## 输入契约

- 当前及历史反馈；
- 需求基准和不变量；
- 系统模型中的因果链、传感器、执行器、扰动和时延；
- 实际 diff、任务执行报告和连续误差样本；
- 可用权限、回滚点和最大允许影响面。

## 执行步骤

### 1. 裁决每个反馈

必须选择并记录一种处置：

- `accept`：证据证明输出偏离基准；
- `reject`：证据错误、重复、越界或已被事实否定；
- `defer`：保留非关键偏差，明确影响和交付披露；
- `escalate`：需求冲突、不可控或缺少授权，停止改变相关表面。

`P0/P1` 不得延期。拒绝必须给出可证伪理由，不能只写“不同意”。

### 2. 诊断误差动态

对已接受反馈检查：

- 局部偏差：单一因果来源、可稳定复现；
- 系统性偏差：同类错误跨任务重复，说明上游基准、模型、架构或测试有缺陷；
- 振荡：相反修复交替出现；
- 超调：局部修复产生更大回归面；
- 停滞：连续采样严重误差不降；
- 时延误判：动作尚未传播，过早触发反向纠正；
- 传感器故障：测量对象或断言本身错误。

先验证因果假设，再选择动作。无法定位时降低控制增益并增加观测，不盲目扩大修改。

### 3. 选择非数值控制律

- 比例作用：局部、可复现、高置信偏差，执行小范围直接修复；
- 积分作用：同类偏差反复出现，修改上游任务包、架构约束或测试体系；
- 微分作用：误差数量或严重度快速上升，暂停并行、缩小任务、提高采样；
- 死区：不影响需求和风险的偏好噪声，保持零动作；
- 抗饱和：反馈、上下文或权限积压时先清理状态，不继续叠加修改；
- 增益调度：确定局部故障高增益，集成偏差中增益，含糊架构意见低增益，越界意见零增益。

### 4. 形成纠正任务包

每个纠正动作必须绑定一个已接受反馈，说明因果假设、允许写入面、最大影响半径、不变量、回滚点和复验检查。能在原任务边界内完成时返回执行阶段；需要新消费者、共享契约或权限时返回规划/建模阶段。

### 5. 复验并关闭

执行后必须由观察阶段运行原失败检查和必要回归传感器。只有观察证据证明预期恢复且未产生阻塞性回归，才能用账本 `resolve` 关闭反馈。代码已改或执行者自述不能作为关闭依据。

## 输出契约

裁决反馈和生成结构化 JSON 前，完整读取 [references/correction-decision-contract.md](references/correction-decision-contract.md)；下列字段列表只是概要。

向主 Agent 返回 `CorrectionDecision`：

```text
feedback_id: 标识
decision: accept | reject | defer | escalate
decision_reason: 可证伪理由
dynamic_pattern: local | systemic | oscillation | overshoot | stagnation | delay | sensor-fault
causal_assessment: {hypothesis, supporting_evidence, falsifier}
control_action: {
  gain, target, write_scope[], invariants[], impact_limit,
  rollback, correction_check[], route
}
resolution: open | verified | deferred | escalated
residual_risk: []
```

对全部反馈形成裁决表，不只处理最容易的一项。

## 退出门禁

离开 `correcting` 前必须满足：

- 所有新反馈已裁决并写入账本 `decide`；
- 每个 `CorrectionDecision` 已用 `record-artifact --phase correcting --input <json>` 写入共享账本；
- 每个已接受反馈都有有界纠正动作或明确阻塞；
- 纠正动作触及已证实或可证伪的因果来源；
- 已定义原失败检查和回归检查；
- 振荡、超调或停滞已触发降增益、冻结、重规划或重建模；
- 没有把需求变化伪装成缺陷修复。

需要动作时转回 `executing`，动作完成后必须回到 `observing`。模型失效转到 `modeling`，任务边界失效转到 `planning`，缺少授权则升级用户。全部已接受反馈复验关闭后才可进入 `verifying`。

## 严重度规则

- `P0`：数据丢失、安全漏洞、不可逆破坏或系统不可用；
- `P1`：必须行为、公共契约或关键流程失败；
- `P2`：重要健壮性、维护性、性能或体验问题；
- `P3`：轻微质量问题，不影响必须需求。

置信度影响调查顺序，不降低已证实偏差的严重度。
