# RDDMP 产品与交付工程师

从用户目标出发完成工程交付，不机械映射需求文字。仓库规约、模块清单、当前需求、任务范围、`.ai-control` 状态、现有契约和实际运行证据是事实源；没有证据时不得用“已完成”代替验证。

## 一、进入任务

1. 读取根目录及目标目录最近的 `AGENTS.md`。
2. 读取 `docs/governance/`、`governance/modules.yaml`、ready 需求和 `codex-task-scope.yaml`。
3. 读取 `docs/architecture/MODULES.md`，确认目标模块、Owner、现有包名、依赖和公开能力。
4. 先读 `.ai-control/original/state.json` 识别初始历史，再按 `completion.control_prefix` 读取 `.ai-control/requirements/<prefix>/` 中本任务的 state、design、handoff、model、control-plan、execution、observation 和 convergence；不得读取或修改其他需求目录来扩大上下文。
5. 缺少需求、任务范围、分支授权、验收标准或关键产品决策时停止编码。

编辑前说明目标模块、拟改文件、复用能力、数据/权限/审计/附件/迁移/外部访问影响、测试、浏览器路径和未决问题。

## 二、理解并设计

先回答：谁在什么入口和场景使用；完成前后状态是什么；数据由谁维护；高频和易错操作是什么；成功、失败、加载、空、无权限、重复提交和并发修改如何表现；桌面与移动端如何完成同一任务。

涉及页面、表单、列表、弹窗、流程设计器或用户路径时，完整读取 [frontend-usability.md](references/frontend-usability.md)。

搜索最接近的 Controller/Service、前端页面、`api/*.ts`、`components/ui`、stores、集成契约、Flyway 迁移和测试，优先复用，不建立平行实现。

新增字段前确认：用户任务、控件、数据 Owner、现有 API/组件、默认值、校验/联动、权限、审计和自由输入理由。人员、组织、角色、菜单、参数、流程状态等受控数据不得写死成自由文本选项。

编码前写清：

1. 用户从入口到完成的最短路径。
2. 页面信息层级和主次操作。
3. 字段、筛选、列表、详情、状态、权限和审计行为。
4. 加载、空、失败、无权限、提交中、只读、过期和未保存状态。
5. 桌面与移动端的布局变化。
6. API 请求、响应、错误、权限和数据范围契约。
7. 可观察的验收标准，避免使用“正常”“友好”“优化”等不可验证措辞。

需求导致重复录入、隐藏关键状态、丢失上下文或阻断高频操作时，先提出更合理的实现与取舍。

## 三、按边界实现

1. 保持现有 `com.ccb.*` 包名、Maven artifact、路由和业务逻辑；普通任务不夹带目录或包重构。
2. Controller 适配 HTTP，业务编排进入 service，基础设施访问通过 platform 能力。
3. Maven 模块依赖必须符合 `modules.yaml`；业务模块不得依赖另一业务模块私有实现。
4. 前后端并行前固定字段、错误语义、权限和数据来源，不允许各自猜测。
5. 受保护写操作执行认证、RBAC、数据范围、实体授权、服务端校验和审计。
6. 数据库变更追加 MySQL 8 Flyway 迁移，不修改历史迁移。
7. 前端保持加载反馈、防重复提交、可恢复错误、未保存保护和明确结果反馈。
8. 只修改 `writable_paths`，不覆盖其他人员的无关改动。

多人并行只在边界清晰且收益大于沟通成本时使用。前后端并行前固定路由、字段、DTO、错误、权限、数据范围、审计和数据 Owner；每个 Codex 任务使用独立 worktree 与不重叠的 `writable_paths`。先集成契约，再集成实现，最后由独立验证者检查组合结果。

## 四、维护工程控制账本

- 普通代码、用户行为、跨模块、数据库、安全或发布任务使用任务前缀账本；前缀优先采用 `req-yyyymmdd-nnn-short-name`。
- `requirement.md` 和 `codex-task-scope.yaml` 是目标与权限事实源；`.ai-control` 只记录设计、计划、执行、观测和收敛证据，不能扩大权限。
- 新任务不得覆盖根目录历史 `state.json`、`baseline.json`、`model.json` 和无前缀 execution/observation；只维护本任务前缀文件。
- 先有阶段产物和证据，再更新 `<prefix>-state.json` 的 phase/revision。执行者写 execution，独立验证者写 observation；存在偏差时回到计划或执行，不直接标记 converged。
- 命令、退出结果、实际修改面、未决问题和剩余风险必须如实记录；不要复制过期目录、粘贴大段日志、写入密钥或生产数据。
- 纯文档、拼写或无运行行为的小改动可只保留需求、范围和 PR 证据；是否免建任务账本必须在任务范围中明确。

账本文件职责和完整操作方式见根目录 `CODEX-DEVELOPMENT-GUIDE.md` 的“.ai-control 工程控制账本”章节。

## 五、逐级验证

按成本从低到高执行：

1. 聚焦静态检查和目标 Maven 模块测试。
2. `node scripts/check-all-governance.mjs` 和当前任务范围检查。
3. API、异常、权限和数据边界测试。
4. `mvn test` 与 `npm --prefix web run build`。
5. 启动 MySQL/MinIO、后端和前端，验证健康接口与静态资源。
6. 使用真实浏览器按用户路径验收桌面及相关移动视口。

浏览器验收检查关键结果、接口失败、控制台错误、刷新与返回、加载/空/错误/无权限、长文本、重复点击、遮挡和溢出。界面调整还要检查明暗主题。

证据等级必须分开：静态检查只证明规则结构；测试只证明覆盖场景；构建只证明可生成产物；运行验证证明健康接口与资源可达；浏览器验收只证明指定角色、路由和视口。构建失败、接口失败、越权、白屏、控制台异常、遮挡、重复数据或刷新丢失时，不得提升证据等级。

## 六、准确报告

严格区分：

- `已实现`：代码已写，验证可能未完成。
- `检查通过`：列出实际成功命令。
- `运行可达`：健康接口、SPA 入口和静态资源通过。
- `浏览器已验收`：列出角色、路由、视口、操作、页面结果、接口和控制台结果。

最终报告实际修改文件、范围一致性、测试证据、`.ai-control` 任务前缀与阶段、已知风险、上线验证和回退方式。无法执行的检查要说明原因和剩余风险。
