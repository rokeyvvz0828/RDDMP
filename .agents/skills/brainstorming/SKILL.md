# 把想法澄清为工程设计

通过自然的协作对话，把用户想法转成完整设计和规格。先了解项目现状，每次只问一个关键问题；理解目标后比较方案、分段呈现设计并取得用户批准。

<HARD-GATE>
在呈现设计并取得用户明确批准之前，不得调用任何实现 Skill、编写产品代码、搭建项目、修改依赖或执行其他实施动作。无论任务看起来多简单，这个门禁都适用。
</HARD-GATE>

## “太简单，不需要设计”是反模式

待办列表、单函数工具和配置变更也包含未经检验的假设。简单任务的设计可以只有几句话，但仍必须说明目标、边界、行为和验证方式，并得到批准。

## 检查清单

必须为下列项目创建任务并依次完成：

1. 勘察项目上下文：文件、文档、接口、测试和最近提交。
2. 在真正需要视觉表达时即时提供可视化伴侣，不要在开场时一律询问。
3. 每次只提出一个澄清问题，理解目的、约束和成功标准。
4. 提出 2-3 个真实可行的方案，说明取舍和推荐理由。
5. 按复杂度分段呈现设计，每段都取得用户确认。
6. 写入设计文档：`docs/engineering-control/designs/YYYY-MM-DD-<topic>-design.md`。
7. 写入机器可读设计：`.ai-control/<topic>-design.json`。
8. 自检占位符、矛盾、歧义、范围和需求可验收性。
9. 请用户复核落盘设计；确认后只调用 `$writing-plans`。

## 流程

```text
勘察项目
  -> 逐项澄清
  -> 比较 2-3 个方案
  -> 分段呈现设计
  -> 用户批准？ --否--> 修订设计
  -> 写入人可读与机器可读文档
  -> 自检
  -> 用户复核落盘文档？ --要求修改--> 修订并复检
  -> $writing-plans
```

本 Skill 的终态是调用 `$writing-plans`。不得从这里直接调用前端实现、脚手架、闭环执行或其他实现 Skill。

## 执行过程

### 理解想法

- 先检查当前项目状态，再提出详细问题。
- 若请求包含多个可独立交付的子系统，立即指出范围过大，先给出拆分、依赖和优先顺序，只对用户选定的第一个子项目继续完整设计。
- 对适当范围的项目，每次只问一个会改变目标、边界、行为、方案或验收方式的问题。
- 能从工程事实得到的答案不要再问用户；无法由事实推出的产品决策不得自行补全。
- 优先提供 2-3 个互斥选项、推荐项和影响，也允许开放回答。
- 重点澄清使用者、目的、必须行为、反例、不变量、约束、非目标、失败行为和可观察成功标准。

### 比较方案

- 提出 2-3 个真正可行的方案，不要用一个正常方案搭配明显不可用的陪衬。
- 先给出推荐方案，并说明推荐依据。
- 比较需求覆盖、复杂度、影响面、回滚、可观察性、兼容性和关键风险。

### 呈现设计

- 确信理解目标后再呈现设计。
- 让篇幅匹配复杂度：简单部分几句话，复杂部分可到 200-300 字。
- 每个实质部分后询问是否准确；若不准确，回退澄清并修订。
- 至少覆盖：目标与范围、用户流程、架构与组件、接口、数据与状态流、错误处理、质量属性、验证策略和主要风险。

### 设计清晰边界

- 将系统拆成单一职责、接口清楚、可独立理解和验证的单元。
- 对每个单元说明职责、使用方式和依赖。
- 消费者需要阅读实现细节才能使用，或修改内部必然破坏消费者，说明边界仍需调整。
- 文件过大常意味着职责混杂；只设计服务当前目标的最小拆分。

### 现有代码库

- 提案前先理解现有结构和约定，并优先沿用。
- 现有问题确实阻碍本次目标时，可以设计有界改进。
- 不提出与当前目标无关的重构。

## 设计产物

写入经用户口头批准的设计：

```text
docs/engineering-control/designs/YYYY-MM-DD-<topic>-design.md
.ai-control/<topic>-design.json
```

用户或项目已有文档位置规范时服从其规范，并在 JSON 的 `human_document` 中记录真实路径。完整字段、审批证据和需求规则以 [references/design-contract.md](references/design-contract.md) 为准。

如果当前目录是 Git 仓库且项目指令允许提交文档，提交设计文档和机器可读设计；不是 Git 仓库时如实记录，不将提交作为设计有效性的必要条件。

## 设计自检

写完后用新的视角检查：

1. 占位符：是否仍有 `TBD`、`TODO`、未完成章节或空泛要求？
2. 内部一致性：架构、行为、验收和约束是否互相矛盾？
3. 范围：能否由一份实施计划完成，还是需要拆成子项目？
4. 歧义：是否存在两种合理解释，可能导致实现错误？
5. 追踪：每条 `must` 需求是否有稳定 ID、验收条件、来源和反例？
6. 事实与假设：候选路径、接口和未知项是否被误写成已证实事实？

表达问题直接修正；涉及产品选择时回到一次一个问题。多 Agent 可用且项目允许时，可以用 [spec-document-reviewer-prompt.md](spec-document-reviewer-prompt.md) 做独立复核，但它不能替代用户批准。

## 用户复核门禁

自检通过后，给出设计文件路径并要求用户复核，例如：

> 设计已写入 `<path>`。请复核落盘内容；如果需要调整，我会先修订设计，再编写实施计划。

等待用户答复。用户要求修改时，修改并重新自检。只有用户批准当前落盘修订后，才能把 `design_status` 和 `approval.status` 设为 `approved`，然后调用 `$writing-plans`。

## 可视化伴侣

可视化伴侣用于在浏览器中展示线框、架构图和并排方案，它是按问题使用的工具，不是整个会话模式。

不要预先询问。第一次遇到“看图比读文字更容易判断”的问题时，单独发送邀请；该消息只能包含邀请，等待用户同意。用户同意后，完整读取 [visual-companion.md](visual-companion.md) 并按其方式启动。概念、范围、技术决策和文字取舍仍在对话中完成。

## 核心原则

- 一次只问一个问题。
- 可选时优先给互斥选项。
- 严格执行 YAGNI，移除未要求功能。
- 总是比较替代方案。
- 逐段验证，不以 Agent 共识替代用户批准。
- 发现理解错误时主动回退。
